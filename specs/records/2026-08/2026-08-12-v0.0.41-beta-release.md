## Analysis and impact

- Observable state: reviewed database-backed source is published to `main`, but production still serves the legacy static topology and the product version remains `0.0.40-beta`.
- Direct trigger: the user explicitly requested the next beta branch and Release after database convergence.
- Data/control flow: one version synchronization commit becomes the common source for `main`, the requested branch, and the annotated tag. The tag runs `.github/workflows/build.yml`; only after all native artifacts are published does that workflow dispatch the release version, tag, and peeled source SHA. `.github/workflows/deploy-opencorvus-com.yml` validates the tag-to-commit binding before building and pins every checkout/artifact to that SHA, then signs and activates the database-backed site.
- Root cause of the deployment prerequisite: the installed legacy activator validates a root static tree and can only switch static symlinks. It cannot create the locked web identity, release-external SQLite/blob state, root-pinned deploy key, backup timer, systemd service, or dynamic Caddy routes. The signed routine artifact deliberately cannot grant itself this root authority.
- Why the prior path is insufficient: pushing a tag before bootstrap would let the Release succeed while its required website dispatch fails, or invite an unsafe attempt to make a non-root deployment self-bootstrap. Keeping deployment disabled does not protect repository dispatch because that event intentionally enters the production job.
- Affected definitions and consumers: the synchronized release metadata files, beta branch/tag refs, native build workflow, immutable Release-to-website dispatch payload and checkout contract, its focused workflow test, desktop update channel, website download manifest, production bootstrap assets, Registry database publication, Release and website records/indexes.
- Explicit exclusions: no product behavior, Market copy, visual layout, signing-key rotation, updater-key rotation, public submission, database schema change, or actual VPS reboot belongs to this release-only round. Bootstrap proves enablement through systemd state and service/readiness checks. A real reboot requires a separate explicit authorization, stated interruption window and rollback channel, followed by the complete production acceptance suite.
- Risks: parallel worktree contamination, remote movement, branch/tag divergence, stale build caches, incomplete root inventory, unavailable root channel, Windows runner failure, missing signed assets, failed website dispatch, and public cache lag. Every risk has an exact precondition or terminal verification below; none is handled by a fallback path.
