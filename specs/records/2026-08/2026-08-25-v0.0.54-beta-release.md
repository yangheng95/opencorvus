## Impact and release-chain analysis

- Observable state: public binaries, beta updater, website manifest, and canonical source still identify `0.0.53-beta`; one shared LLM stream-recovery fix and one website download-selection repair are reviewed but unpublished.
- Direct trigger: bring the reviewed website repair onto the clean maintenance line, synchronize all canonical version projections, update the changelog and release record, validate the exact source, then publish its immutable tag.
- Runtime data/control flow: the ordinary assistant processor already uses the shared streaming LLM activity policy, but first-turn title generation runs synchronously after an execution occurrence starts and before the processor, while Project Memory organization and VCS commit-message generation also open Provider streams directly. Because the stream wrapper disables its soft timeout when those callers pass `timeoutMs: false`, those three paths can park indefinitely. The repair adds one shared text-stream activity collector over the existing activity runner, passes the occurrence abort into title generation, and moves all three direct text helpers behind the same first-byte, semantic-idle, total-deadline, error-classification, and abort contract. Replay-safe title and memory calls use the default retry policy; VCS's externally visible delta callback uses a no-retry projection so a failed attempt cannot duplicate visible text. Queue ownership, wake delivery, durable occurrence state, terminal settlement, project isolation, and parallel scheduling remain unchanged.
- Website data/control flow: published GitHub Release assets -> generated `downloads/latest.json` -> Astro landing links -> browser platform/architecture selection. The pending repair binds Windows' single x64 row to the manifest-ordered EXE and exposes format, version, and exact filename; ambiguous multi-architecture platforms remain explicit.
- Why old paths were insufficient: the first recovery change bounded the main Session processor but did not structurally cover direct text-only Provider consumers; title generation could therefore block an already-started occurrence before normal processing, while memory and VCS helpers could stall their owners. Separately, the landing action required high-entropy architecture hints and otherwise presented a Release link as a direct download. The release-blocking repair extends the existing activity primitive instead of adding a parallel timeout mechanism, and the website change keeps one manifest authority without fallback protocols or duplicate version sources.
- Release flow: canonical source commit -> immutable tag -> five-platform desktop and command-line build matrices -> staged assets/checksums/updater metadata -> GitHub prerelease -> repository dispatch -> immutable website build/sign/activation -> public readiness and download probes -> exact-source merge to `main`.
- Risks: partial matrices, version drift, wrong tag target, stale or mismatched website manifest, selecting MSI instead of EXE, concurrent remote divergence, accidental video/benchmark inclusion, signing/deployment failure, or merging a source different from the published tag. Each is checked at the authoritative source, build, Release, deploy, public endpoint, or Git boundary.
