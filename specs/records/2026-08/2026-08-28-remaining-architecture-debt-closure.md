## Managed startup lifecycle residuals — current-source root cause and implementation plan

- **Observable phenomenon and direct trigger:** the managed backend currently receives only `--parent-pid`. `serve` then calls `observedProcessOccurrence(parentPid)` after the child has started. If the Overlay host exits and its process number is reused before this observation, the backend binds the replacement process as its host. If the fingerprint cannot be read, `serve` deliberately falls back to `{ pid }`; `ParentWatchdog` then uses process-number liveness. Even after a fingerprint was established, the watchdog treats `unknown_live` as permission to keep serving. A reused inaccessible process can therefore retain an orphan backend, listener, runtime and database writer.
- **Shared data/control-flow root:** exact ownership is minted at the wrong side of the launch boundary. The Tauri launcher owns the parent occurrence before spawn but publishes only its reusable numeric identifier; the child reconstructs identity later and admits an identity-free fallback. `ManagedServerLifecycle` and `ParentWatchdog` encode the same optional fingerprint, so CLI validation alone cannot make the invariant structural.
- **Why the earlier ARC-023 repair did not close it:** the repair replaced periodic PID-only checks when a fingerprint exists and correctly detects a readable same-PID replacement. It did not close the launch-to-observation window, did not require a fingerprint in the lifecycle type, and preserved both acquisition-time PID fallback and observation-time `unknown_live` continuation. The remediation record explicitly retained those boundaries.
- **Production-entry and terminal-path audit:** the Overlay/Tauri sidecar spawn is the only production publisher of `--parent-pid`. Initial start and restart-handoff both consume the same parsed `managed` value in `serve`; graceful shutdown releases one watchdog, while parent exit/reuse/unobservability requests the existing shared shutdown path. No Task, Mission or Session occurrence owns this host lifecycle, but an orphan backend can continue all three scheduling surfaces and block a successor, so the invariant is shared infrastructure rather than an Overlay-only symptom. Test fixtures that instantiate `ManagedServerLifecycle` must supply a real observed occurrence too; there is no second managed lifecycle owner.
- **Single-owner repair:** Tauri computes its own operating-system process-instance fingerprint before spawning the backend and passes the pair as `--parent-pid` plus `--parent-process-instance-id`. The CLI accepts either no managed-parent fields or the complete validated pair; it never observes or invents the parent identity. `ManagedServerLifecycle.StartInput` and `ParentWatchdog.start` require that exact pair. Only `exact_live` keeps the backend alive; `dead_or_reused` and `unknown_live` both converge on the existing one-shot shutdown callback. This removes the PID-only and fail-open paths rather than adding a compatibility protocol.
- **Positive verification plan:** Rust unit evidence must prove the launcher generates a non-empty platform-shaped fingerprint and exact argument pair. CLI/lifecycle evidence must accept the complete pair, keep an exact-live parent serving, and fire one orphan callback for both same-PID reuse and lost observability. Typecheck, focused serve/watchdog tests, Overlay Rust checks, architecture/docs checks and a real child-process lifecycle contract are required before review.
- **SDK residual:** the atomic framed startup receipt is already the sole readiness fact. `StartupOutputObserver.appendStdout` still decodes UTF-8, retains a partial line and returns lines, but its only caller ignores that result and uses only the bounded diagnostic bytes. The unused line protocol is therefore dead historical state, not a second active readiness source. Replace the observer with the existing byte-bounded `BoundedDiagnosticTail` directly for both streams; preserve startup failure diagnostics, UTF-8 tail bounds, post-readiness draining and exact process/receipt settlement tests.
- **Windows supervisor checker exclusion:** direct `bun test` is not acceptance for long process-owning files because Bun's default five-second elapsed timeout terminates their helpers. The exact invalid signature reproduced here (`killed dangling process`, helper exit 1, complete or published ready marker, missing settlement marker) disappeared under `bun script/run-with-inactivity.ts --inactivity-ms 120000 -- bun test --timeout=0 ...`, where the complete Session MEMORY file passed 11/11. No production supervisor change follows from invalid runner termination.

## Cross-process Session prompt owner — current-source root cause and implementation plan

- **Observable phenomenon and direct trigger:** `executePublicSessionExecution` joins only the process-local `publicSessionExecutionOperations` map. Two backends that receive the same caller-minted input can both miss that map; the winner persists the user Message, the loser catches `MessageOccurrenceClaimConflictError`, reads the same Message and calls `convergePromptTurn`. When the winner's assistant is still open, both enter `SessionPrompt.loop`. Each process has an empty `SessionPromptState`, so each calls `start`; the peer then runs `terminalizeRecoveredIncompleteAssistant` and can mark the live winner's assistant and Tool Parts interrupted before starting another physical Provider turn.
- **Shared data/control-flow root:** the durable identity and accepted-input relation added by ARC-027/ARC-041 converge completed replay, but the physical prompt owner, callback list, execution status and pending-delivery decision remain process-local. `SessionStatus.beginExecutionOccurrence` is an in-memory projection, not admission. The cross-process control-lease table contains no prompt owner. A distinct input arriving through backend B while backend A streams is also stamped `pendingDelivery` only when B has a local attached callback, so the durable queue fact differs by request routing.
- **Why a route-only lock is insufficient:** prompt, command and init share the route wrapper, but Mission wake, Task recovery, Orchestrator continuation, shell-to-prompt resume, Agent and internal Session execution call the same loop without that wrapper. A per-input route lock would also let two distinct inputs start two Session loops. The authority must be keyed by exact Project/Session and live for the whole prompt-owner lifetime, including standby, while accepted input identities remain Message-owned.
- **Why an expiring timer lease is not the chosen authority:** a prompt can be inside a long streaming Provider or Tool effect. Allowing takeover solely because an event-loop pause crosses a deadline would require every Provider effect and every Message/Part write to carry a transaction-time lease fence; otherwise the old process can resume after a peer has started a second turn. The repository already has an exact operating-system process-occurrence observer. Prompt ownership therefore records a random generation plus the exact runtime process occurrence and permits takeover only after `dead_or_reused`; `exact_live` and `unknown_live` refuse takeover. This makes process death, not clock delay, the physical-effect boundary.
- **Single-owner design:** one `session_prompt_owner` SQLite fact is keyed by Session and records Project, canonical directory, random generation, process ID, process-instance identity and runtime occurrence identity. `SessionPromptState.start` acquires it in an immediate transaction before constructing local ownership; cleanup releases only the exact generation. A peer with a live/unknown owner never creates local state and never terminalizes incomplete Messages. It waits on durable assistant settlement for an exact reply target, or retries admission after the recorded owner is released/proved dead. A dead owner is replaced atomically and only that takeover may invoke existing incomplete-assistant terminalization.
- **Input ordering:** write-time `pendingDelivery` consults the same durable owner instead of local callbacks. The first-owner race remains possible before either process has acquired ownership, so loop assembly also derives the complete contiguous set of durable user inputs not yet accepted by an assistant and binds that ordered set to the first assistant. This is the current accepted-input contract generalized to simultaneous first admission; no Message is synthesized, hidden or sliced from model context.
- **Horizontal scope:** ordinary prompt, command and init; Conversation and permitted Task/Mission public Sessions; Mission/Task recovery and wake; Orchestrator/Agent/delegate internal prompts; shell completion resume; normal standby, abort, Provider error, retry, compaction, restart, Project disposal, serial/parallel Sessions and multi-Project isolation. Shell's own command execution remains fenced by `session_shell`, but its temporary Session prompt state must join/refuse the same Session prompt owner so shell cannot overlap a peer model turn.
- **Positive verification plan:** retain the same-process single-owner/batch contracts and add two real backend processes over one isolated runtime root. A controlled streaming OpenAI-compatible fixture holds backend A after one physical request begins; backend B submits the same identity and then a distinct identity. While A is live, B must publish no second Provider request and no interruption terminal. A settles one first reply and one next-boundary accepted batch as applicable, both callers converge on their exact durable assistant, and the owner row names one generation. A killed owner with an open assistant is then proved `dead_or_reused`; B takes one new generation, terminalizes only the abandoned assistant, and performs at most one recovery turn. Focused prompt/command/init, Mission public-Session, wake/recovery, Session deletion and process-occurrence neighbors plus typecheck/checkers and independent review are required.

## Cross-process Session prompt owner — implemented evidence

- `session_prompt_owner` is the sole durable physical-loop coordinate. Its Session primary key, Project/Session cascade, canonical directory, random generation and exact PID/process-instance/occurrence identity are admitted under `BEGIN IMMEDIATE`. A peer refuses `exact_live` and `unknown_live`; only `dead_or_reused` is atomically replaced. The table is added to existing databases before strict drift validation, and the control-state checker classifies every field as identity, causal input or lease data.
- `SessionPromptState` acquires the durable coordinate before local worktree/status resources and releases only its exact generation. Local acquisition failures preserve both the primary error and cleanup error. Standby intentionally retains the row. A peer route polls the durable accepted-input reply and never creates local state while the recorded owner is live. Write-time `pendingDelivery` uses the same durable owner, and the first-owner race derives the complete durable unaccepted user batch in timeline order.
- Real two-process verification uses one SQLite runtime and production Hono Session routes with a streaming OpenAI-compatible Provider. Duplicate and queued peer inputs produce exactly two main Session Provider Turns, duplicate callers receive the same assistant, the next input receives the next assistant, and the standby row still names the first exact-live process. After that process exits, the row is observed `dead_or_reused`. In the takeover case, the abandoned assistant becomes a truthful error, one new generation performs one replacement main Turn, and the recovered reply succeeds.
- The real-process test exposed a separate shared bootstrap defect: `ProjectMemoryOrganizer.init` used a deferred read transaction and then published a durable Bus occurrence, so concurrent backends could receive `SQLITE_BUSY` and return 500 before prompt admission. All three Project Memory read-then-publish entry points now reserve the writer with `BEGIN IMMEDIATE`; no retry or fallback was added.

### Independent-review repair requirements

- Standby must treat durable user Messages, actionable Session controls and runtime wake facts as the cross-process source of truth. Process-local subscriptions may accelerate observation, but the owner must continue reading durable facts until wake, cancellation or a scheduled wake time settles the wait.
- Every peer-attached result mode needs an exact durable completion coordinate. Public summarize uses the real source user Message ID and returns only the valid compaction summary for that source, regardless of which backend owns the physical loop.
- Exact-generation durable-owner release is part of physical loop settlement. A transient delete failure must keep the process-local owner in terminating state and retry the same generation; only a successful delete or an explicit `superseded` result may permit local state removal and peer admission.
- Positive acceptance adds the missed production order: backend A finishes a reply and is observed in standby, then backend B commits the next input (and separately a summarize control). A must wake from durable facts, remain the only Provider/effect owner and settle B's exact result. A release failure injected while the process remains live must retain the local owner until retry succeeds, after which a peer can acquire one new generation.

### Re-review findings and closure

- The first repair re-review confirmed the continuous durable standby observation and exact-generation release retry, but found that summary joining still used only a source Message ID. That could return an older summary before the new control ran, or lose a failed control terminal and let the peer acquire an empty standby owner. It also found that fixed sleeps did not prove the peer submitted after the real standby boundary.
- `SessionCompaction.create` now returns the exact `SessionControl.Record`. The public summarize route carries both its control ID and source Message ID into the loop. Summary callbacks are keyed by that control ID. `SessionCompaction.process` returns the exact summary Message ID it just published; the executor writes that ID as amended `result_summary_message_id` and writes the consumed terminal in one `BEGIN IMMEDIATE` transaction. It never re-derives a newly generated result by source/time. An idempotent no-new-material control explicitly binds the already selected existing summary; a first control with neither compactable material nor a reusable summary writes `SessionCompactionMaterialUnavailableError` as a failed terminal instead of consuming without a receipt. Local callback and peer join read only the exact receipt. A failed control raises `SessionPromptSummaryControlError` from its persisted error payload.
- The real-process fixture installs a test observer at the production `beginStandby` boundary after the durable wait is installed and idle status is published. Peer input and summarize requests wait for that marker; no fixed delay is accepted as standby evidence.
- Focused evidence after the receipt-writer repair: the full real-process owner suite passed 5/5 with 41 assertions. One source generated a first summary, repeated manual and automatic no-material controls bound that exact ID, a subsequent real post-summary compaction bound a distinct second ID returned directly by its publisher, and only those two summary Messages existed. A first summarize with no compactable material made no Provider request and persisted one exact `SessionCompactionMaterialUnavailableError` failed terminal. The injected non-retryable Provider failure still persisted its exact failed terminal. Same-process idempotency passed 13/13, exact owner termination passed 9/9, migration passed 1/1, the two affected Session MEMORY integration cases passed independently, and full typecheck passed. The complete Session MEMORY file reached 10/11; its unrelated remaining case was blocked before test setup by the separately queued Windows native supervisor ready-marker race and left a complete `ready.json.<pid>.tmp` beside the missing final marker. Control-state redundancy, API docs, architecture index and diff checks passed. The final uninvolved read-only review returned PASS with no unresolved P0-P3.
