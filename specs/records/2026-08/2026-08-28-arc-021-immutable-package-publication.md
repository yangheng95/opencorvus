# ARC-021 Immutable Shared-Package Publication

## Recall

| Item | Evidence and decision |
| --- | --- |
| User requirement | Continue repairing every architecture-audit finding on `v0.0.55beta`; run the real Mission end to end only after the remaining ledger is closed. |
| Current-state correction | The public `Config.needsInstall()` already joins the same process-local and cross-process directory owner as `installDependencies()`, and per-config readiness already requires `PackageInstallReceipt`. Those historical halves are closed and are not rewritten. |
| Observable phenomenon | `BunProc.install()` runs `bun add --cwd Global.Path.cache`, so installation, upgrade, and retry rewrite the shared final `package.json`, lockfile, and `node_modules` tree in place. A completed Plugin or Provider path and the next installer therefore name the same mutable bytes. |
| Direct trigger and root | An install or `latest` refresh starts while another backend still imports the prior package, or the installer dies after Bun has partially changed the flat tree. The cross-process lock serializes writers but not readers; the completeness receipt prevents a new reader from accepting an unfinished tree but cannot make an already returned path immutable. |
| Why earlier repair is insufficient | The receipt answers whether one resolved revision completed. It does not isolate preparation from the public path, make publication atomic, or preserve the prior returned revision. Retrying an unsettled occurrence in the same flat root repairs eventual readiness but leaves the shared mutation and read/write race intact. |
| Definitions and callers searched | Saturation audit ARC-021; staged remediation record; `bun/{index,install-receipt,registry}.ts`; global cache versioning; Plugin and Provider installers/loaders; config dependency owner/readiness implementation; all `BunProc.install`, `PackageInstallReceipt`, and `Global.Path.cache/node_modules` callers and tests; current Config architecture. |
| Corrective contract | One package-scoped cross-process owner prepares a fresh same-filesystem staging tree. The complete resolved dependency closure is verified there, then the whole generation is atomically renamed to a unique package/resolved-version/generation revision path. Only after the final tree verifies and its durable receipt commits may the immutable module path be returned. Later versions and same-version recovery publish beside prior generations. An unreceipted or corrupt final generation is never returned, overwritten, or deleted by another installer. The old flat cache is not read as a fallback. |
| Acceptance | Positive focused tests prove one completed revision is reused, a second resolved version receives a different path while the first bytes remain unchanged, and failed post-rename publication plus committed-tree corruption are recovered by publishing a fresh generation. Exact, range and scoped selectors, a real dynamic Provider import, recursive dependency identity, normal failure settlement, killed-owner recovery and compromised-lock overlap are covered. Existing receipt/config contracts, package and root typechecks, docs/architecture checks, formatting and `git diff --check` must pass. No User Interface automation is added, modified, or run. |
| Delivery and risk | Plugin and dynamic Provider imports receive a new opaque cache path but their API remains a module-directory string. Cache version stays at 21: changing it would recursively delete live immutable revisions while readers may still hold them. Legacy flat package bytes are excluded by the new path and have no reader. Registry access and lifecycle-script behavior remain Bun-owned; this repair changes publication ownership, not package semantics. Unreceipted generations are retained as unreachable crash evidence until a separately designed safe garbage-collection owner exists. |
| Independent-agent feedback | None before implementation. After first green verification, an uninvolved read-only agent must review the complete scoped diff and evidence; all valid findings are repaired and review repeated until no unresolved P0-P3 remains. |

## Implementation record

- `BunProc.install` now derives one package publication root from the canonical package name, joins a retrying process-local and cross-process owner, and resolves the requested selector before enumerating committed generations for that resolved version. Reuse requires the generation's exact receipt and a fresh recursive verification of its root manifest, version and complete dependency closure.
- Bun writes only a fresh same-filesystem staging root with its own private manifest. `PackageInstallReceipt.verifyTree` recursively follows Node-style nested/ancestor resolution, requires every manifest to carry the requested package identity and a version, and validates the complete staged closure before publication. The owner atomically renames that whole tree into its UUID generation, verifies it again in final position, commits resolved-version and selector occurrences, and only then returns the module directory.
- Every owner has its own staging and final generation. A normal failure removes only that owner's unpublished staging directory; after rename, an unreceipted generation is retained and bypassed. A later same-version attempt publishes beside it. Therefore even a compromised cross-process lock cannot let one still-running owner overwrite or delete another owner's committed return path; the lock prevents duplicate work rather than carrying byte-safety authority.
- The preparation occurrence is durable before the staging directory is created or Bun writes any package bytes. Its intent records the exact staging path and runtime process occurrence. Admission requires that path to be the direct `staging/<generation UUID>` child and binds the UUID to the final revision generation basename. Recovery groups only the normalized exact bound path, then reclaims it only after every referencing journal is terminal or the operating system proves every open owner occurrence dead; a compromised lock does not authorize deleting a still-live peer's staging generation. Registry-resolution change begins the new occurrence before terminalizing the old one, so the shared preparation never has an ownerless transition window.
- Recursive resolution now treats the first existing dependency directory as authoritative. A missing directory continues through Node-style ancestor lookup; an unreadable or identity-mismatched manifest fails the closure instead of falling through to a hoisted package. Each queue edge retains its dependency key and declared spec. A validated `npm:` alias uses the key for its physical path and the alias target for manifest identity, including scoped targets; ordinary spec forms retain the dependency key identity.
- The initial selector occurrence and the resolved-version occurrence both terminalize on normal publication failure. An interrupted process may leave an open occurrence, but no receipt, and its final generation remains unreachable. Cache layout version remains 21, avoiding a startup-wide recursive deletion of live immutable generations. The old flat cache has no reader or fallback.
- The first repeat review was **NOT PASS** and found four valid boundaries: an existing corrupt private candidate could fall through to a good hoisted package; valid npm aliases were compared to their alias key instead of target identity; staging was created before its durable intent; and the tests did not exercise those paths. All four are corrected above. The same review confirmed the no-cache-bump, immutable-generation, compromised-lock, reuse revalidation and normal-failure terminalization repairs.
- Current focused acceptance after those corrections is **25 pass / 0 fail / 31 assertions** across immutable publication, receipt completeness, and per-config readiness. It includes real killed-child recovery before and after rename, live-owner staging preservation (including an older terminal occurrence sharing the same preparation), strict rejection of an unbound nested preparation path, terminal staging reclamation, real lock-directory compromise with overlapping backends, exact/range/scoped selector mapping, scoped and unscoped npm-alias identity, an npm-alias-backed dynamic Provider import, committed dependency corruption, corrupt-private-versus-hoisted resolution, recursive transitive closure and caught resolved-occurrence failure. Root typecheck is **8 / 8**; docs are **337 operations / 25 groups**; architecture index is **26**; package topology is **10**; focused Prettier and `git diff --check` pass. Final repeat independent review remains pending. No User Interface automation was added, modified, or run.

The reviewer independently reproduced the full focused **25 / 0 / 31** suite and the isolated immutable-publication **8 / 0 / 11** suite, confirmed cache-version stability, immutable generation ownership, pre-write durable preparation identity, exact process-liveness recovery, strict staging/final UUID binding, first-candidate resolution semantics, scoped/unscoped npm alias identity, recursive reuse verification and selector/resolved terminal convergence. It modified no files and delegated no work.
