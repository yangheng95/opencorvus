## Problem depth and impact analysis

- Observable state: source metadata and the last successful Windows artifacts identify `0.0.38-beta`, while the requested delivery family is `0.0.39-beta`.
- Direct trigger: the user explicitly requested a release-family increment followed by a fresh package build.
- Data/control-flow root cause: no product defect is asserted. The only required source mutation is advancement of the canonical version authority; all derived metadata must follow the existing synchronization path before native build scripts capture version constants and installer names.
- Why renaming old artifacts is invalid: the version is compiled into the command-line interface, Overlay server, Tauri executable, Cargo packages, and installer metadata. Reusing or renaming `0.0.38-beta` outputs would leave contradictory runtime and package identities.
- Definitions/callers/contracts: `packages/opencorvus/package.json` remains canonical; eight workspace packages, `bun.lock`, two Cargo packages and locks, and `tauri.conf.json` are synchronized consumers. MSI uses the numeric projection `0.0.39.0` while public filenames retain `0.0.39-beta`.
- Tests/docs/delivery: focused positive validation is `version:check`, `docs:check`, the real local GUI packaging path, the real host CLI matrix including runtime smoke and archive verification, artifact hash inspection, and independent read-only review. UI automation is excluded because this task changes metadata and produces native artifacts without a UI behavior change.
- Risks: stale build caches can preserve the previous version; Bun baseline target download can be incomplete; an already-running Overlay binary can lock the developer copy; signing credentials are unavailable in the ordinary local environment. The current packaging owners mitigate these through clean host builds, an explicit verified Bun runtime directory when needed, `--skip-dist-copy` inside local packaging, and a strict unsigned-local versus signed-release boundary.
- Build blockers found and rooted during the real path: `expert-squads/builtin/equity-research/report.md` was a generated research result committed at the package root, outside the package contract's sole allowed definition surface, so payload validation correctly rejected it. Deleting that result is required rather than weakening the contract or adding a compatibility path. Separately, `packages/opencorvus/package.json` already declared `open-websearch@2.1.11`, but the committed Bun lock omitted it and its dependency closure; `bun install` repaired the single dependency source, after which the compiled imports resolved. One Windows snapshot rename returned a transient `EPERM`; an isolated rerun of the same generator passed without source changes and the full packaging path then reused the validated immutable snapshot.

## Implementation plan

1. Synchronize the release family with `bun run version:bump -- 0.0.39beta`, then verify `0.0.39-beta` and MSI `0.0.39.0` across every declared target.
2. Run `bun run version:check`, `bun run docs:check`, and patch-hygiene checks.
3. Run `bun run package:local --skip-linux` for the host-bound Windows Overlay executable plus unsigned MSI/NSIS installers.
4. Run the Windows x64 CLI matrix with the verified Bun 1.3.14 regular and baseline runtimes if Bun's implicit target download is unreliable; require both runtime bundles, smoke checks, tar archives, and archive verification to pass.
5. Record artifact paths, sizes, SHA-256 values, exact source boundary, commands, and limitations in this ledger.
6. Commission an independent read-only Agent to inspect the full diff and all current artifacts. Resolve every valid finding and repeat review until clean.
7. Commit only the synchronized version metadata, repaired lock dependency closure, invalid generated report deletion, and this record/index update. Before automatic push, inspect the complete upstream-to-HEAD commit set and stop if it contains unauthorized or unreviewed commits.
