## Problem depth and impact

- Observable state: `main` fast-forwarded from `197a74f3` to remote `0805c43a`; the release family is aligned at `0.0.42-beta`; neither remote branch/tag nor GitHub Release exists for `0.0.43-beta`.
- Direct trigger: the requested release requires a new canonical version projection and an immutable source identity. A branch name alone does not change package, native, installer, updater, or download-manifest identities.
- Data and control flow root: `sync-version.ts` projects the canonical package version into every release consumer. The tag-driven `build.yml` independently synchronizes that same version on each runner, packages native artifacts, validates/stages the release asset contract, publishes one prerelease, promotes `latest.json`, and dispatches `deploy-opencorvus-com.yml` with the exact tag commit. The website build derives `downloads/latest.json` from complete published Releases and rejects incomplete asset families.
- Why old paths are insufficient: the `v0.0.42-beta` record says publication was pending, and the remote has no corresponding tag or Release. Reusing it would not identify the current source or fulfill the requested version. Manual local packaging cannot replace the native operating-system matrix, updater signatures, GitHub Release, or production website signing and activation.
- Website risk: the most recent manual production deployment built and signed successfully but failed on server activation because passwordless `sudo` was unavailable. Current `main` has since changed; the new release workflow must be observed from build through activation and public probes. A repeated infrastructure failure is an explicit website blocker, not a successful deployment.
- Current source-gate failures: remote `test` runs for both `0805c43a` and the later `1447c5af` are terminal failures while version synchronization and critical builds pass. The later run fails Channel Runtime STT expectations, an Overlay source-order assertion, macOS Project cleanup isolation, and a Windows active-operator case whose compact-ID prefix error is followed by the isolated runner's 120-second inactivity timeout. These are release blockers and must be resolved at their shared production/test-host roots before tagging.
- Local hang evidence: two local website `check` invocations remained in `generate-public-market.ts` for more than ten minutes with no generated-file timestamp change and only intermittent CPU. After user confirmation that the build tasks were hung, only the exact task-owned process trees were stopped. The website production path will be re-exercised after the source gate is healthy; the hung state is not validation evidence.
- Scope exclusions: no application feature behavior, public page layout, database schema, Registry content contract, or release workflow topology change is requested. No User Interface automation or visual redesign is applicable.
