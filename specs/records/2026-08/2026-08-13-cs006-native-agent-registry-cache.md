# CS-006 — Native Agent registry cache authority

## Recall

- Acceptance target: Host, Helper, and Primary native-Agent registries use one runtime-neutral configuration revision and one scoped-materialization cache lifecycle; semantically identical validated configuration reuses the exact materialized state, distinct canonical configuration never aliases through a digest collision, runtime capabilities do not enter a lossy serialized identity, and reset returns an explicit cache-settlement receipt.
- Hard constraints: no `Bun.hash`, `JSON.stringify` identity, fallback serializer, legacy cache, parallel key implementation, public HTTP or generated Software Development Kit (SDK) change, User Interface (UI) automation, or edits to the concurrently dirty Build/Workspace files. SHA-256 is only an index; canonical bytes remain equality authority.
- Sources read: repository `AGENTS.md`; continuous audit `CS-006`; prior `CS-031` canonical-digest and exact-cache remediation; all Host/Helper/Primary registry definitions and callers; native Agent materializer, permissions, lifecycle invalidation callers, Config schema, project instance-state lifecycle, Provider/Config/Auth refresh reset owners, current architecture records, and existing native-Agent integration tests.

Their explicit-snapshot maps are process-global while their default state is project-keyed through `createInstanceState`; every invalidation caller already converges through `NativeAgentRegistryLifecycle`. No external caller reads their cache keys or reset return values.
- Independent-agent feedback before implementation: the first plan review rejected a short-circuit capability classifier, an unspecified explicit/default scope boundary, and receipt semantics that did not define detachment generations or exact collision-entry counts. The corrected plan requires a complete invalid-wins classifier, project-scoped defaults plus process-global explicit snapshots, and exact per-registry/aggregate detachment receipts. The completed CS-031 review established the reusable strict canonical-byte/SHA-256 contract.

## Root cause and impact

Native Agent definition materialization is centralized, but each registry copied the configuration-key, Promise map, default instance state, failed-Promise lifecycle, and reset logic. The copied key is a Bun-only 64-bit hash of insertion-order-sensitive and lossy JSON serialization, and a hash hit is treated as equality. Equivalent configurations can split cache state; unsupported values can disappear; a collision can return the wrong materialized Agent permissions/model/prompt; and lifecycle fixes must be repeated in three files.

The registry-specific definitions and build functions are legitimate independent domain inputs. Configuration revision, cache equality, failure eviction, project-default state, and reset settlement are not. They require one reusable owner.

## Design

1. Add one `NativeAgentRegistryCache<State>` primitive under `src/agent`. Its constructor owns the registry label and build function. It alone creates the project-keyed default `createInstanceState`, the explicit canonical snapshot cache, failed-Promise eviction, configuration validation, revision calculation, and reset receipts.
2. Every explicit input is parsed once through `Config.Info`; that exact snapshot is both revision input and build input. `canonicalDigestSource("opencorvus.native-agent-config.v1", snapshot)` supplies deterministic UTF-8 canonical bytes and SHA-256. The existing exact-byte cache treats SHA-256 only as a bucket index.
3. One complete, non-short-circuiting classifier walks the entire parsed snapshot and produces exactly `declarative` or `recognized_runtime_capability`; any invalid value wins over either result and throws `CanonicalDigestContractError`. The only recognized runtime capability is currently a function in a schema-declared open runtime field (`agent.*.options`, Provider option bags, or MCP initialization payloads). Functions in closed fields and every `undefined`, symbol, bigint, non-finite number, sparse array, cycle, `Date`, `Map`, class instance, or other non-plain object are invalid even when a supported function appears earlier in the same graph. A capability-bearing valid snapshot is built without cross-call caching, and the exact function reference reaches materialized `options`; functions are never omitted, stringified, named, or treated as equal. There is no catch/fallback.
4. A cached construction Promise is inserted before awaiting so concurrent equivalent requests coalesce. Rejection removes only that exact source/value pair, allowing a later request to retry. Distinct canonical bytes remain distinct even if a test injects the same digest bucket.
5. Default lookups remain keyed by `currentProjectDirectory`: two project Instances materialize two independent default states, and current-project `reset` detaches only the current one. Explicit validated snapshots are deliberately process-global because the build function receives the entire config and reads no implicit Project state. `reset`/`resetAll` detach all explicit exact-byte entries plus respectively the current or all default project states. The typed per-registry receipt is `{registry, explicit_entries_detached, default_project_states_detached}`; the aggregate adds exact totals and the three per-registry receipts. Counts are exact entries, not SHA buckets; collision siblings count separately, and uncached runtime-capability calls do not count.
6. Reset establishes a new cache generation before it returns. All old entries are unreachable from the authority at return, but already-started callers may finish on their detached Promise. A late rejection or completion from the old generation cannot delete, decrement, or replace a same-source entry created after reset. Default `State` has the same detach semantics. The receipt proves detachment, not cancellation of caller-owned work.
7. Host, Helper, and Primary files retain only their definitions, ID validation, build logic, and public lookup/list helpers. Delete all three local maps, state-key functions, and copied reset implementations. Existing invalidation callers may ignore the richer receipt, preserving behavior without a compatibility path.
8. Document the runtime-neutral native-Agent materialization cache in the extensions architecture. No persistence, migration, HTTP schema, SDK generation, or UI surface is involved.

## Positive verification

- A focused non-UI test uses real `Config.Info` snapshots with reversed key insertion order and calls all three production registries. For each registry, equivalent snapshots return the same exact materialized Agent object; a semantically changed override returns a distinct object with the changed projection.
- Concurrent equivalent calls coalesce to the same state. Two real `Instance.provide` projects each establish default states for all three registries; current-project `reset` reports and replaces only one project's three states, while the other remains object-identical, and `resetAll` then detaches the other three. The aggregate receipts assert exact per-registry and total fields.
- The shared primitive exposes a fixed canonical revision fixture, proving runtime-independent 64-hex SHA-256. A constructor-only test source seam creates two distinct canonical byte entries in one injected digest bucket, proves both values remain distinct and the receipt counts two entries, and tests an in-flight old-generation rejection followed by reset/new same-source lookup without cross-generation deletion.
- A runtime-capability configuration containing an Agent option function succeeds twice through the real registry build, preserves that exact function reference in materialized `options`, and returns distinct materialized objects. Mixed `{supportedFunction, invalidSibling}`, `Date`, `Map`, and class-instance cases all produce typed `CanonicalDigestContractError`; invalid wins regardless of insertion order.
