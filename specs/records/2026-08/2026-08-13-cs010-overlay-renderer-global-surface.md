## Root cause and current failure mode

The renderer treated its global object as a test harness and dependency container. The bridge exposes mutable Solid stores by reference, so any renderer script can read the connection password or invoke state-changing workflows without using the typed host/business boundaries. The worst structural symptom is `applyDirectory()`: even though it already imports `saveSettings()`, it asks `window` for `persistOverlaySettings` and silently skips persistence when the bridge is unavailable. This makes a hidden test hook an optional production authority.

Deleting only the password property or gating `installGlobalBridges()` behind `import.meta.env.DEV` would not cure the root cause. A development renderer runs the same privileged context and would still expose live references/mutators; it would also preserve a second ABI whose behavior can drift. Likewise, a source-text assertion against the old names could miss minified/generated writes and would violate the repository's positive-checker rule.

## Target authority

- In `applyDirectory()`, call imported `saveSettings()` directly whenever `options.persist !== false`. ### 3. One release public-global checker

Add a non-UI build checker, for example `packages/overlay/script/check-renderer-public-surface.ts`, and invoke it after `build:vite` in the canonical Overlay build/check path. It parses both emitted entry HTML files (all inline classic/module scripts and external module references), walks the Vite manifest's complete static and dynamic JavaScript graph, and follows every executable asset edge emitted from those modules: Vite `?worker`, `?worker&url`, `?sharedworker`, executable `?url`, and statically resolvable `new URL(..., import.meta.url)` references. Those assets become explicit worker entry roots; their static/dynamic imports are traversed recursively and cannot be treated as opaque files. The checker then parses every reachable renderer and worker output with the repository's installed HTML/TypeScript parsers and emits a strict versioned receipt:

```ts
type RendererPublicSurfaceReceiptV1 = {
  schema_version: 1
  build_id: string
  entry_html: readonly string[]
  reachable_sources: readonly string[]
  execution_roots: readonly {
    root_id: string
    kind: "renderer_html" | "vite_worker" | "vite_shared_worker" | "raw_executable_url"
    source_module: string
    source_digest_sha256: string
    bundle_chain: readonly string[]
    entry_reference_digest_sha256: string
    emitted_outputs: readonly { path: string; digest_sha256: string }[]
  }[]
  observation_bindings: readonly {
    occurrence_id: string
    root_id: string
    bundle_chain: readonly string[]
    write_identity: string
    source_module: string
    realm: "renderer_window" | "worker_global"
    emitted_outputs: readonly string[]
  }[]
  global_writes: readonly {
    write_identity: string
    source_anchor: { ast_preorder_ordinal: number; normalized_expression_sha256: string }
    source_module: string
    global: "window" | "globalThis" | "self"
    realm: "renderer_window" | "worker_global"
    property: string
    operation: "assign" | "define_property" | "delete"
    classification: "application" | "internal_handoff" | "dependency"
    package_name: string | null
    package_version: string | null
  }[]
  approved_global_manifest: readonly {
    write_identity: string
    source_anchor: { ast_preorder_ordinal: number; normalized_expression_sha256: string }
    source_module: string
    global: "window" | "globalThis" | "self"
    realm: "renderer_window" | "worker_global"
    property: string
    operation: "assign" | "define_property" | "delete"
    classification: "internal_handoff" | "dependency"
    package_name: string | null
    package_version: string | null
    justification: string
  }[]
}
```

The checker is one build-scoped authority with fresh Vite/Rollup recorder instances, a raw executable-URL recorder branch and one post-build verifier, not independent scanners. Vite 6 runs each bundled worker in a separate Rollup build, so the main plugin alone is not authoritative for worker provenance: the Overlay Vite config installs the main recorder in `plugins` and a factory in `worker.plugins` that creates a fresh worker-recorder instance for every worker build. Every recorder publishes into one build-scoped typed collector identified by a unique build ID; recorder instances never retain or reuse state across builds. A worker receipt contains its build ID, exact entry-root identity, worker kind, ordered bundle/import chain, canonical source-module observations, chunk-module membership, emitted-code digest and the Rollup worker reference/placeholder needed to bind it to the parent output. The main recorder consumes those receipts when Vite re-emits worker output as assets without module metadata, resolves the placeholder/reference to the final asset, and only the main authority may finalize the single receipt. Missing recorder installation, missing/orphan/duplicate receipt, mismatched build ID, stale receipt from an earlier build, duplicate final-asset adoption, unbound worker output or concurrent collector reuse returns a stable typed checker failure. Two worker roots may legitimately include the same source module: the checked-in approval remains the exact write-identity multiset, so cross-root reuse references one manifest row while two distinct writes in that source require two rows. Only current-build bindings may map that one approved source write to multiple emitted assets. Bindings are keyed by an observation occurrence `(build_id, entry_root, bundle_chain, source_module, realm, write_identity)`; every occurrence and asset must still be accounted for exactly once.

Plain executable `?url` imports are a second Vite production path, not a worker-recorder fallback. When the main module graph imports a JavaScript or ECMAScript Module asset through `?url`, the main recorder follows the exact returned Vite reference and `originalFileName`, but classifies it as a `raw_executable_url` root only when that URL value reaches a statically proved `Worker`/`SharedWorker` construction sink. A JavaScript URL used as data/download/text is not executed and remains an ordinary asset outside the worker-global receipt. For a proved executable sink, the recorder reads the exact original asset while its source identity is known, resolves its package/version, hashes the original bytes, parses its static/dynamic import graph recursively, records its global writes under `worker_global`, and binds the Vite placeholder/reference to the final emitted asset and digest in the same collector. The source digest must match the emitted digest whenever Vite copies the raw asset byte-for-byte; if Vite transforms it, the collector records both source and output digests and the post-build verifier reconciles the parsed output. Missing or ambiguous Worker sink, source/original file, import, reference, final output or digest produces a typed failure. Same-content assets from different sources remain distinct roots by canonical source identity.

The existing PDF.js path is one explicitly bounded cross-module sink proof, not a property-name heuristic. The checker follows the one imported Vite URL binding from `FilePreviewArtifact.tsx` into the exact `pdfjs.GlobalWorkerOptions.workerSrc` setter; proves that setter accepts one string source and writes it unchanged to its single private static field; follows the exact getter chain from that field through `PDFWorker.workerSrc` into the initializer local/destructure; and proves that the only terminal alternatives are `new Worker(originalUrl, ...)` or PDF.js's exact same-origin wrapper whose generated module performs `await import(originalUrl)` and whose blob URL is passed to `new Worker`. The wrapper therefore changes the transport URL but retains the admitted worker asset as its sole executable import. The analysis rejects a second assignment/source, setter or getter transformation, unknown accessor, callback/escape, unresolved conditional alternative, fallback URL or wrapper containing any other executable import with a stable `renderer_raw_worker_sink_unresolved` error. A same-named `workerSrc` property without the proven sink is not executable authority. This branch is the canonical path for `pdf.worker.min.mjs?url`; it does not demand a `worker.plugins` receipt and it does not infer provenance from post-build content.

During each recorder's `transform`/`renderChunk`/`generateBundle`, while that Rollup build still exposes exact module IDs, asset references and chunk membership, it parses every renderer/worker module and inline entry script for direct property assignments/deletes, element access with a static string, `Object.defineProperty`, `Object.defineProperties` and `Object.assign` whose target is `window`, `globalThis` or `self`. Realm comes only from the explicit execution entry graph, never from the spelling of the identifier: `index.html` and `native-menu.html` roots are `renderer_window`; discovered worker/shared-worker roots are `worker_global`. `self` in a renderer entry is the Window alias, `self` in a worker entry is WorkerGlobalScope, and `globalThis` inherits the entry realm. If one shared source module is reachable from both graphs, it produces two separately bound realm observations. A guard such as `self instanceof DedicatedWorkerGlobalScope` does not relabel a renderer entry; a branch proven unreachable for that entry is recorded as an unreachable source observation but not approved as an emitted write, while a post-build surviving write still has to reconcile to its actual entry realm. A bare Node `global` binding is not an approved target; if it survives or can reach a renderer/worker bundle, it is observed as an unsupported global alias and fails typed validation. It records every write with its exact normalized source-module ID before minification, resolves a dependency module to its nearest package manifest and the exact locked package version, and binds renderer observations through the main chunk graph and worker observations through their worker-recorder receipt to the final emitted chunk/asset. The post-build verifier parses the final emitted HTML, chunks and worker assets, proves that every recorded observation occurrence remains represented in its exact reachable output set and that no additional emitted write is unaccounted for. Unknown, ambiguous or missing provenance, or provenance with an unaccounted extra occurrence, is a typed checker failure; a property name is never sufficient evidence of dependency ownership.

Global-object aliases are fail-closed rather than an escape hatch. The transform phase performs bounded lexical/data-flow binding analysis for aliases derived from `window`, `globalThis` or `self` (for example `const root = globalThis; root.x = ...`) and attributes the write to the original target. It also supports the one evidenced constructor-field shape needed by MapLibre: an exact worker entry passes its proven WorkerGlobalScope argument into a constructor, the constructor assigns that unchanged parameter once to a private/instance field, and writes through that field are attributed to the same worker-global target. The analysis rejects parameter reassignment, more than one source, escaping/callback transport, mutation before binding or any other field origin. Reassignment, unproved interprocedural/dynamic aliasing, destructured mutation targets or any alias whose global origin cannot be proved produces a stable `renderer_global_alias_unresolved` checker error. The post-build pass applies the corresponding bounded rules to minifier-introduced aliases and must reconcile them to the transform observation; it may not silently omit a write because the direct identifier changed.

The checker canonicalizes and sorts observations and validates their stable authority against one versioned exact manifest owned by the checker. Approved-manifest equality is an exact multiset keyed by `write_identity`; each row also carries the canonical source module, source anchor, execution realm, global object, property, operation, classification, package and version. This keeps two same-module/same-property writes distinct and makes add/remove/reorder drift reviewable, while comment/whitespace-only formatting leaves the canonical source anchor unchanged. A canonical source module is a repository-relative POSIX path for application code or a package-relative POSIX path rooted at the exact package name/version for dependency code; it is never an absolute machine path. Serialized source/root/bundle module identities use that same repository-relative or `package@version`-relative POSIX form. A Vite/internal entry reference is never serialized raw: `entry_reference_digest_sha256` is a domain-separated digest used only to correlate the in-memory reference with this receipt, preventing absolute temp/workspace path disclosure. Emitted output paths are distribution-root-relative POSIX paths. `execution_roots.emitted_outputs` is the complete asset inventory and digest set for that execution root; write-to-output ownership lives only on `observation_bindings`, while `global_writes` never carries an emitted path.

`build_id`, `execution_roots`, `observation_bindings`, entry-reference digests, bundle chains and output digests are current-build projections rather than stable manifest fields. They are nevertheless mandatory serialized receipt fields: an external verifier can round-trip the receipt, recompute its canonical ordering and prove the exact occurrence set that the collector accepted. `execution_roots` includes one `renderer_html` row for each entry HTML as well as every worker/raw-URL root. A renderer root's canonical source and digest are the exact HTML document; its entry-reference digest covers the normalized Vite HTML entry reference and its bundle chain starts at that HTML. Worker kinds use their exact recorder/asset reference. Every binding `root_id` must reference exactly one root row. Thus one renderer module reached by both `index.html` and `native-menu.html` has two distinct occurrences even when Vite deduplicates it into one shared chunk.

Module source identities and bundle-chain module identities are repository-relative or `package@version`-relative POSIX paths. `entry_html` is a repository-relative POSIX source path. Both `execution_roots.emitted_outputs` and every binding `emitted_outputs` path are relative to the Vite distribution root. A root inventory is complete, nonempty and digest-bearing; every binding output set is a nonempty exact subset of the referenced root inventory, with each path resolving to the same root digest. `global_writes` contains no emitted path: exact write-to-output ownership belongs solely to root-specific bindings, so one write identity can map to different assets without duplicating the authoritative write row. These categories are never interchanged in sorting or digest inputs.

The four identity/reference digests use one canonical tuple encoder: UTF-8; a fixed ASCII domain label; a u32 big-endian field count; for each field a one-byte type tag followed by u32 byte length and bytes; enums use their UTF-8 literal; null has its own tag and zero length; arrays encode a count followed by each independently length-delimited element; objects use their schema-declared field order. No delimiter concatenation is permitted. Exact domains are `opencorvus/renderer-write/v1`, `opencorvus/renderer-root/v1`, `opencorvus/renderer-observation/v1`, and `opencorvus/renderer-entry-reference/v1`. The reference digest encodes `(build_id, root_kind, canonical source, normalized in-memory reference)`. `write_identity` encodes `(canonical source module, realm, global, property, operation, ast_preorder_ordinal, normalized_expression_sha256)`; `root_id` encodes `(build_id, root kind, canonical root source, source_digest_sha256, ordered canonical bundle chain, entry_reference_digest_sha256)`; `occurrence_id` encodes `(root_id, write_identity, ordered canonical bundle chain)`. Boundary-collision vectors such as `['a','bc']` versus `['ab','c']` must differ across every array-bearing identity.

`source_digest_sha256` and emitted-output digests are ordinary SHA-256 over the exact source/output bytes, so a byte-for-byte raw asset has equal digests. `normalized_expression_sha256` is SHA-256 over the deterministic `opencorvus/renderer-expression-ast/v1` encoding: the pinned parser's semantic AST node kind; schema-declared semantic child-field names in fixed order; arrays in source order; identifiers and decoded string literals as length-prefixed UTF-8; booleans/null by fixed tags; numbers as their parsed finite IEEE-754 binary64 bits with `-0` preserved; object property order as authored; and operators by exact enum literal. Source positions, raw literal spelling, parentheses erased by parsing, comments, whitespace and parser-internal metadata are excluded. Unsupported/parser-version-new node kinds fail typed validation. The implementation pins the parser version and ships golden vectors for every supported global-write shape.

`build_id` is a fresh cryptographically random build nonce held only by this build-scoped collector, so stale/concurrent recorder state cannot alias. The source anchor's ordinal is the zero-based pre-order index among global-write expressions in the canonical source AST, and its expression digest uses the fixed encoding above. Formatting therefore preserves identity; inserting/reordering a write or moving the module changes the manifest authority and requires review. An external module's canonical source identity is its canonical module path. An inline HTML script's canonical source identity is the tuple `(canonical repository-relative HTML path, classic|module, zero-based DOM script ordinal among all script elements)` rendered through the same typed tuple encoding; its write ordinal is local to that script AST. Moving/inserting/retyping an inline script therefore produces manifest drift, and two identical inline scripts remain distinct. `global_writes.write_identity` is the authoritative observed-write row key and must equal the corresponding approved manifest row. Every `observation_bindings.write_identity` is a foreign key to exactly one row, and every reachable root occurrence of that write has exactly one binding whose output set is nonempty; no orphan write or binding is valid. Two semantically identical same-property writes in one module remain distinct by ordinal. Renderer observations bind to their exact current chunk; worker observations bind through the build/entry-root occurrence identity and may have an exact one-to-many emitted-asset set when the same approved source is bundled under multiple roots. The post-build verifier proves the matching final write in every bound output. Missing, ambiguous or additional occurrence-to-emitted bindings fail, while a different content hash with the same exact stable source authority and exact current occurrence set is valid.

The application-owned approved set remains empty: an application module that writes `window.__THREE__` or `globalThis.pdfjsLib` is classified by its source module as application and fails even though a dependency is approved to write the same property. The currently observed dependency side effects are represented explicitly rather than hidden or inferred from their property names: `pdfjs-dist@5.4.394` owns renderer `_pdfjsTestingUtils`/`pdfjsLib` and worker-asset `globalThis.pdfjsWorker`; `three@0.183.2` owns renderer `__THREE__` even though it reaches the bundle through `@google/model-viewer@4.3.1`; the exact vendored source module inside `vis-timeline@8.5.2` owns its renderer-reachable `filterCSS`/`filterXSS`/guarded `self.filterXSS` statements under the renderer realm; and the exact `maplibre-gl` worker modules own worker `self.worker` plus the proven constructor-field writes `registerWorkerSource`, `addProtocol`, `removeProtocol`, `registerRTLTextPlugin` and `makeRequest`. Implementation must resolve and record the actual normalized module IDs and versions from the installed dependency graph. If the renderer-only guarded vis-timeline branch is eliminated from emitted code, it remains a transform observation but not an approved emitted row; if it survives, its target is renderer-realm `self`, not worker-realm. A dependency upgrade, module move, same-name application writer, second dependency writer or new property is manifest drift requiring review. Host-created read-only ingress such as `__TAURI__` and `__OPENCORVUS_STARTUP_THEME__` is not an application write; if any entry HTML or bundled module writes it, the checker observes and rejects it unless the same manifest explicitly owns it.

Remove the acceptance-only locale global path: `index.html` no longer writes `__OPENCORVUS_LOCALE__`, and `utils/i18n.ts` no longer reads it. Runtime locale comes through the canonical navigator/host locale owner; a query-only UI-test ingress is not retained as production ABI.

Replace the two independent module scripts and `window.__opencorvusStartupReady` with one external module entry, `src/startup.ts`, referenced by the sole bottom-of-body `<script type="module" src="/startup.ts">`. `startup.ts` is the only startup coordinator: it imports a typed `startup-readiness.ts` owner, initializes the static surface and Tauri listeners, resolves that owner's Promise for browser/no-Tauri or the exact native ready event, and only then executes `await import("./main.tsx")`. `main.tsx` exports/executes the application mount but never discovers readiness through `window`; it can accept the exact ready receipt as an argument or assert the imported owner is resolved, while the dynamic import ordering itself proves the application module cannot begin before startup readiness. There is no separate `/main.tsx` script tag and no inline module that races the entry. The early classic theme script remains a separately scanned pre-module surface until a later owner replaces it; it may read host ingress but may not publish application globals. If Vite cannot build this explicit single-entry topology, implementation must stop and revise this plan rather than retaining a global handoff.

This is a positive manifest contract: the checker must parse the actual two entry HTML documents, prove every external/static/dynamic chunk and every referenced executable worker/URL asset graph is included, return a versioned receipt, and show exact equality between observed and approved classified writes by source and execution realm. It is not a test that greps for old identifiers. The build fails on HTML/script parse failure, missing entry/worker/reachability coverage, unknown dynamic write, application-owned write, owner/version/realm mismatch or manifest drift. The receipt contains property names/locations and non-secret owner metadata only, never values or source snippets that could leak secrets.

If Vite transforms a write into an alias that the direct global parser cannot prove, the build checker must move to a Vite/Rollup instrumentation phase that observes module-level global-write expressions before aliasing; it may not downgrade to a source grep. There remains one checker and one manifest.
