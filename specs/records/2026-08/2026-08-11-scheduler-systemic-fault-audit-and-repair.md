## Observable failure family and root model

The common failure is an ownership handoff that publishes or releases one layer before the downstream layer has durably accepted responsibility. Five authorities must form one ordered chain:

1. runtime database ownership;
2. exact execution/prompt generation ownership;
3. physical resource and worktree-owner settlement;
4. durable lifecycle or typed infrastructure outcome;
5. exact root ingress delivery and retry ownership.

The current implementation has gaps where a predecessor disappears early, a successor is inferred from a proxy such as `promptOwner`, or an error is logged without durable authority. Those gaps explain deadlocks, duplicate execution, false terminal states, orphan resources, and unrecoverable accepted dispatches. Existing local fixes addressed individual handoffs but also introduced active/terminal retry divergence and a permanent retry ceiling.

### Event job occurrence and settlement design

The repair is deliberately bounded at the Bus publication and `EventService` acceptance boundary. `Bus.publish` allocates one source occurrence identity before dispatch; exact subscribers, wildcard subscribers, and the resulting `GlobalBus` envelope all observe that same identity. `EventService` never synthesizes a subscriber-local replacement. Its unique `(event_job_id, event_occurrence_id)` insert is idempotent, so repeated delivery of one envelope converges on one fire even across process owners sharing the project database. An event lost before publication remains outside this contract and is not disguised by payload hashing or a fallback replay reader. Once published to the subscriber, that fire is the only execution and recovery fact.

Each fire stores its exact Event Job, project, accepted event occurrence/type, parent fire, complete ordered `{ fireID, jobID }` causation ancestry, target Session identity, status, lease owner, attempt, result Message, and terminal error or disposition. A job already present in the parent ancestry is not executed: its fire is durably terminalized with the `causal_cycle` disposition. Concurrent occurrences that become inapplicable after an earlier fire consumes a one-shot job or advances its cooldown receive `job_disabled` or `cooldown`; they are never silently dropped. This is causal integrity validation, not an event-name exclusion or workflow gate, so safe chains across different jobs remain executable.

`pending -> running -> succeeded|disposition` and `running -> retry_wait -> running` are the only current fire transitions. Claim and completion compare the exact fire owner. A transient wake failure records its error and durable next-attempt time on the same fire, then uses bounded exponential delay; it is recoverable both in-process and after restart rather than being discarded as a terminal `failed` row. Recovery first reconciles an already persisted `scheduler.event` wake Message carrying the same fire ID; only a fire with no such effect may execute its wake. A generated target Session identity is persisted before Session creation so a `session.created` event can resolve its parent fire even while the original wake is still running. There is no second in-memory outcome source: process maps contain only live Promise/timer handles for the durable rows.

Event-service disposal closes subscription/admission, aborts the fire execution signals, clears recovery timers, and joins every physical fire Promise before Instance release. It never clears ownership evidence while work continues. An execution that observes disposal settles through its exact fire owner when possible; an abrupt process loss remains a `running` row reclaimed through the same lease and message reconciliation path after restart. If runtime settlement rolls back before Instance disposal, the exact-token admission-reopen callback rescans the same project's durable `pending|running|retry_wait` fires and rebuilds their physical owners; normal ownership release disposes the Instance listener first, so it cannot restart work after database ownership transfer.

### Automation due-occurrence and fencing design

The Automation occurrence source is the persisted `automation.next_run` value claimed as `scheduled_due`; wall-clock polling time and process owner are not identity inputs. Fire identity is a deterministic projection of `(automation_id, scheduled_due)`. Each target has one deterministic target key and therefore one run, target Session (except an explicitly bound Session target), user Message, and primary text Part. Repeated delivery, process restart, or lease transfer reuses those identities; random fallback identity is forbidden.

The Automation row remains the single due-occurrence cursor and lease authority. Target runs remain `running` across a process interruption; expiry permits a new owner to claim the same unchanged `next_run`, take ownership of the same deterministic runs, reconcile exact persisted Messages, and execute only missing target effects. Interrupted-run cleanup must not mark the occurrence terminal or move `next_run`, because either action would manufacture a new fire and lose resume authority.

Message persistence and lease validation share one SQLite transaction through `SessionWake`'s commit hook. The hook requires both the Automation lease and exact run owner to match before the deterministic Message/Part bundle can commit. A zero-row lease renewal or renewal error immediately aborts the physical owner. If ownership changes after Message commit, the old completion compare-and-set fails; the new owner finds that exact Message under the same run and is the only owner allowed to advance recurrence. Recurrence and every run result settle in one owner-fenced transaction, so one due occurrence advances once.

Every Event or Automation physical fire reserves runtime settlement ownership before execution. Persisting a wake Message synchronously reserves a separate `session_wake_loop` owner before launching the independent project loop; the runtime signal crosses project initialization, is checked before Prompt start, and cancellation joins both `SessionPrompt.loop` and `waitForFinish`. Server handoff closes and cancels all three kinds, waits for their physical settlement, and only then reaches Instance/database ownership release. Scheduler fire completion is therefore not a proxy for a detached Session loop.

The same migration that introduces Event fire authority normalizes historical checkpoint/auxiliary settlement Artifacts whose legacy terminal label was `failed`. The canonical Artifact writer identities are recomputed in the migration transaction, the prior version is archived by the existing trigger, and the current row becomes `pending` with expired owner fields removed, the prior `failures` carried as `last_failure`, and `attempt` incremented. The runtime scanner remains single-source on `pending|running|completed`; no compatibility scan for `failed` exists.

### Durable Bus publication outbox

`bus_publication_outbox` is the one publication occurrence authority for post-commit protocol events. `publishOwnedInTransaction` writes the stable occurrence identity, parsed payload, causation, project/directory ownership, and source mutation in the same SQLite transaction. A process crash after the source commit therefore leaves a successor-readable occurrence rather than an in-memory retry gap. Direct awaited publications retain their caller-visible completion receipt; synchronous and post-commit producers use the same outbox implementation rather than an Instance-local failure array.

`bus_publication_delivery` records acceptance per stable subscriber identity and phase. Exact, wildcard, and durable Global subscribers retry only their own unsettled delivery; a successful peer is never replayed because another subscriber failed. EventService registers the stable durable wildcard identity `scheduler.event-service`, and its unique `(event_job_id, event_occurrence_id)` fire remains the downstream execution fact. Transient Global user-interface and Server-Sent Events projections receive one observed attempt and do not become scheduling authorities. Bootstrap restores Event subscriptions before draining pending outbox rows, so partial Instance disposal cannot make a retry succeed against an empty captured subscription map. Logging is observability only, never settlement.

## Runtime execution-settlement and launch-handoff design

Process-local asynchronous work has one registry with typed owner kinds for scheduler Event fire, scheduler Automation fire, Session wake loop, Task Queue execution/control, Engine queue completion, Task cancellation convergence, protocol publication, and auxiliary cleanup. A producer reserves its owner synchronously before its first asynchronous boundary, attaches the exact physical Promise, and releases only after that Promise settles. Timer owners retain the same reservation while transitioning from scheduled timer to callback execution, so shutdown cannot observe a transient empty registry. Admission closure returns one typed infrastructure error; it does not create a fallback execution path.

Server handoff uses the registry in phases. It first closes every upstream Prompt producer—Event fire, Automation fire, Session wake loop, Task Queue—and Task cancellation admission, requests cancellation of the producer owners, then closes Prompt/global Scheduler/detached admission and terminates captured Prompt owners. Engine completion admission remains available until those upstream producers and cancellation convergence have physically stopped; it is then closed and every registered completion owner is joined. The caller then disposes the complete Instance lifecycle (or the exact current Instance for an in-Instance CLI callback), which joins per-Instance Scheduler/Event/TaskQueue timers and subscriptions before cancellation settlement. Only after that barrier does Server close and drain Project Git admission, then acquire the runtime mandatory-process barrier. Every gate remains held through database runtime ownership release. Releasing the exact gate token reopens admission and invokes registered durable-owner rescans only for owners not already consumed by successful Instance disposal; it does not create a parallel timer source.

Each Task Queue claim creates one execution authority before `execute` crosses its first await. The authority contains the exact queue occurrence, owning directory, typed cancellation origin, `AbortSignal`, and physical `settled` Promise. Inactivity, Task/session cancellation, project deletion, and runtime settlement all call that authority's single cancel operation. Prompt-owner capture is only a downstream cancellation target; it is no longer the execution-liveness fact. The executor checks the signal at every pre-Prompt boundary and immediately cancels an owner captured after cancellation. The durable row remains `running` until this exact physical Promise reaches its failure/completion writer.

A graceful process handoff is not a business failure. After its exact physical owner settles, the same Task Queue occurrence transitions `running -> queued`, clears only execution-attempt timestamps/error text, publishes the queued receipt, and returns a typed `RuntimeExecutionHandoffCancellation`. It does not publish Session or queue terminal failure. Instance disposal consumes the old process-local rescan owner; after successor ownership reopens admission, the same durable row and identity are claimable by the new Instance.

Queued Engine Task launch has a durable `task_loop_launch` occurrence created atomically with `queued -> active`. Before physical loop execution, that same launch is durably bound to the exact wake ID. The occurrence remains pending until the completion owner is synchronously attached, then receives its accepted/completion receipt. Startup uses the bound wake's `running|drained` state and exact assistant anchor to complete an interrupted launch or resume the same wake; it never invents a replacement wake after an assistant result already committed. Graceful abort writes `runtime_handoff_pending` or a positive completion handoff on the same launch identity.

Positive acceptance records full event/state order rather than asserting absence: queue claim, typed cancel request, physical settlement, row terminalization, sibling claim; upstream admission closure, Prompt/detached settlement, Engine completion, Git drain, mandatory drain, ownership release; and Task launch claim, injected attach failure, durable launch disposition, requeue, restart recovery, and exactly one accepted replacement launch.

The Instance process gate is acquired only after upstream owners, Engine completion, the message bridge, and admitted database effects have stabilized, immediately before Instance disposal. Public `provide`, `provideProjectIdentity`, `tryProvideActive`, `forEachActive`, and convergence entry points share the same typed admission contract and have no public boolean bypass. After Instance disposal, the bridge is stabilized again and one database settlement gate atomically closes both post-commit effects and all new `Client/use/transaction/immediateTransaction` access; only a previously registered active effect owner can finish. This places Protocol append rejection before its first insert and prevents a committed row with a rejected publication effect.

Successful `Server.stop` and in-process Command Line Interface completion commit the scheduler and runtime-execution settlement gates only after every fallible barrier has passed. `RuntimeServerOwnership` retains an occurrence-specific handoff barrier and awaits asynchronous post-release cleanup; no local or cross-process successor may produce work until that exact cleanup settles. Retry exhaustion after filesystem ownership release remains a typed pending handoff and cannot roll back already committed old-runtime gates. A failed pre-release settlement restores captured scheduler registrations and durable-owner scans while the same runtime still owns the database. Initial startup and restart restoration both recover started Tasks before binding or announcing a listener.

## State recovery closure design

The recovery implementation keeps the existing durable rows as the only state authorities; it does not create replacement occurrences or a second recovery protocol.

1. A `queued_operator_wake` left `running` by a prior host is returned to `pending` under the same Artifact identity whenever no current process-local root queue owns it. Cancellation remains the sole exception: its terminal transaction assigns `terminal_inapplicable` to the same ingress. Ordinary completed and failed Tasks then use the existing terminal-conversation resolver, which first reconstructs any already-persisted assistant result before executing delivery.
2. `task_checkpoint_settlement` and `task_auxiliary_settlement` have one terminal state: `completed`. Operation failure returns the same Artifact to `pending`, removes the expired owner lease, records typed last-failure/attempt evidence, and schedules the existing lease runner again. Startup claims that same Artifact after process replacement. The shutdown settlement gate clears process-local retry timers while quiescing; releasing that gate after rollback, released ownership, or same-process successor activation rescans durable `pending|running` receipts and rebuilds their runners. Operation registration precedes execution so a synchronously settling Promise cannot leave a ghost owner that suppresses this rescan.
3. Startup exact-delivery recovery enumerates the existing `delivery_failed` wake rows, not inferred task-infrastructure errors. The wake's parsed `source_kind`, lifecycle event ID or infrastructure fact ID, and embedded exact event are the complete retry authority. The per-runtime attempt identity bounds retries inside one runtime while allowing a successor runtime to revive the same Artifact.
4. Startup recovery isolates work by durable Artifact/dispatch identity. One malformed or temporarily failing item produces a typed failure result and remains durable for retry; it cannot short-circuit requeueing, other exact deliveries, or ordinary pending-wake draining. Aggregate observability is preserved without reporting the project initialized before unfinished work has an in-runtime retry owner.

Positive acceptance covers the same Artifact identity across every transition: terminal `running -> pending -> drained`; cancellation settlement `pending -> running -> pending -> running -> completed`; and exact delivery `delivery_failed(old runtime) -> pending(new runtime) -> drained`. A multi-item startup case must prove that one failing item does not prevent another valid wake from draining.
