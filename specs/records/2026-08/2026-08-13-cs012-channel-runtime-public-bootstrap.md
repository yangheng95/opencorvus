# CS-012 — One public Channel Runtime bootstrap

## Recall

- User requirement: finish the accepted code-smell remediation to zero, progress independent work in parallel where file ownership is disjoint, merge upstream before final push, and require focused positive evidence plus uninvolved review for every implementation.
- Accepted finding: the OpenCorvus Channel supervisor dynamically imports many sibling private `packages/channel-runtime/src/**` modules and assembles adapters, Speech-to-Text (STT), vision, credentials, start/rollback and receipts itself, while `channel-runtime/src/main.ts` independently performs a second assembly. OpenCorvus does not declare the workspace package dependency.
- Acceptance target: `@opencorvus-ai/channel-runtime` exports one pure `resolveConfiguredChannelRuntime` planner and one `startConfiguredChannelRuntime` consumer of that exact immutable plan; both the standalone process entry and the OpenCorvus in-process supervisor resolve once and start the same plan; OpenCorvus imports only the declared public package. Within one process, a secret-sensitive operational identity owns runtime reuse and rotation. Across processes, both hosts project the same explicitly non-secret public **topology** receipt for the same bounded Channel/profile/adapter/capability input. Host attachment receipts separately and honestly describe embedded versus external server mode, directory, paths and launch/client policy; neither public receipt claims equality of secret bytes or equality between inherently different host attachments.
- Hard constraints: one current composition root, no private-path imports, no standalone fallback assembly, no process-global environment mutation inside the reusable boundary, no ambient config/Auth fallback, no swallowed optional-capability configuration error, no injectable public adapter registry, no UI changes or UI automation, and no non-streaming model path.
- Sources read: root `AGENTS.md`; the `CS-012` register entry and remediation program; `packages/opencorvus/src/channel/supervisor.ts`; `packages/channel-runtime/src/{main,index,core,registry,runtime-config,bundled-env,dashscope,vision}.ts`; STT setup/providers; Channel config catalog; both package manifests/lockfile; existing Channel start, registry, bundled-environment, runtime-config and supervisor receipt tests; and current architecture references.
- Whole-repository findings:

  - standalone `main.ts` separately owns bundled-environment loading, permission-profile projection, canonical Auth/DashScope observation, server/directory/shared-mode inputs, adapter creation, STT/vision setup, logging and start;
  - the public index exports core/adapters/registry/format but no complete composition function, and omits Telegram plus configuration/capability receipt types;

The revision below incorporates every item; a second uninvolved review is required before implementation.

## Root cause and current failure mode

The package exposes ingredients but not the application boundary that gives those ingredients one meaning. Both hosts therefore decide which adapters exist, how environment/config/auth are resolved, which optional capabilities are installed, how readiness is interpreted, and how rollback is owned. The shared registry does not cure this because each host still supplies a handwritten full adapter factory map and surrounds it with different configuration sources. Publicly exporting more individual classes would make the private topology reachable without eliminating the second composition.

The direct failure is contract drift: changing an adapter, permission profile, credential source, bundled environment, STT/vision behavior or start receipt in one host can leave the other host compiling with different semantics. The package boundary is also false because OpenCorvus reaches the sibling source tree without a manifest dependency, bypassing workspace/package verification.

## Target authority

### 1. One pure immutable plan, resolved once

Add a public runtime-neutral input schema/type owned by channel-runtime and split the authority into two functions:

- `resolveConfiguredChannelRuntime(input): ConfiguredChannelRuntimePlan` is pure with respect to runtime resources. It validates and normalizes every input, computes credential fingerprints and the digest, and returns a deeply frozen plan. It creates no server, adapter, listener, timer, subprocess, STT provider or vision client.
- `startConfiguredChannelRuntime(plan, {signal}): Promise<ConfiguredChannelRuntimeOwner>` consumes that exact branded/frozen declarative plan plus one fresh lifecycle-owned cancellation capability. It never accepts the raw configuration input, recomputes it, rereads environment/Auth/config, or lets a host alter membership between comparison and start; all failures use the typed throws defined below.

The input is domain-separated rather than one ambiguous environment bag. A package-private symbol/WeakSet created in the planner module records every authentic plan object; deep freezing protects its declarative fields. `startConfiguredChannelRuntime` rejects any cast/deserialized/copied/forged object not present in that provenance set with `ChannelRuntimeConfigurationError{reason:"invalid_plan"}` before resource creation. A valid plan remains an in-process capability and is not serialized/reconstructed:

- `adapterEnvironment`: a frozen string map limited to Channel catalog and adapter option keys;
- `capabilityEnvironment`: a frozen string map limited to STT and vision option keys;
- `runtimeAttachment`: a strict immutable object containing exact `mode: "embedded" | "external"`, `serverUrl`, `directory`, `channelProtocol`, shared-session policy/file, runtime paths, client-auth input and all Channel execution policy that used to be ambient (mirror stdout/Slack target, task timeout/sweep interval, queue rule input, formatter environment, monitor diff threshold and debug flags). Embedded launch data is a closed `serverLaunch` schema containing an absolute executable, structured argv and a package-owned minimal operating-system environment projection; it is not an open environment bag. Only fields applicable to the selected mode may be populated.
- `hostEnvironmentSnapshot`: an ingress-only `{ platform: NodeJS.Platform, environment: Readonly<Record<string, string | undefined>> }` observation captured once by each thin host. It may contain arbitrary parent keys, but the planner's package-owned platform classifier, allowlist and sanitizer are the sole readers: only the planner-produced normalized minimal launch projection enters the frozen plan, operational HMAC or child process. The supplied platform value is itself normalized into `runtimeAttachment`, the operational HMAC and the host attachment receipt; the planner and every managed consumer are forbidden from consulting ambient `process.platform`. The raw environment map is discarded after resolution, is never frozen onto the plan or returned/logged, and cannot supply adapter/capability/config facts (those remain in their typed domains). Thus hosts do not independently choose launch keys and arbitrary parent secrets cannot become child environment through pass-through.
- `sourceConfig`: exactly one raw strict-canonical JSON object plus one raw permission-profile selector. Channel-runtime owns a bounded public `ChannelRuntimeConfigInput` projection for the facts it consumes: a Channel map validated through public `@opencorvus-ai/channel-config` schemas and a JSON-object permission base. It deliberately does **not** claim to be the complete OpenCorvus `Config.Info` schema and therefore creates no reverse package dependency. The planner is the only owner that parses this one object, applies `permissionForProfile` once, and produces both `effectiveBoundedConfig` and, for embedded mode, one frozen `embeddedEffectiveConfig` derived from the same source tree with the same effective permission value. Hosts collect one raw source/profile and must not split, pre-apply, merge or duplicate this parse. Adapters and the embedded server therefore observe the same normalized Channel/permission facts. OpenCorvus's normal `Config.get()` remains its upstream full application validator. For standalone, fields outside the bounded projection remain opaque strict-canonical JSON in that same source tree and are validated by the embedded server during startup; they are never a second config input. A bounded-valid but full-application-invalid embedded config has a typed embedded startup failure, not a falsely promised supervisor-equivalent configuration result. Cross-host normalization/error equality is asserted only for the bounded schema domain owned by this planner.
- `credentialObservation`: the result of the one public canonical saved-credential observer described below;
- `log`: a typed callback receiving structured bootstrap events rather than writing process globals/console inside the reusable owner;
- no public adapter/STT/vision factory override.

Schemas reject any control key in the wrong map and reject duplicate aliases. `adapterEnvironment` cannot contain server/directory/protocol/shared/config/Auth/STT/vision keys; `capabilityEnvironment` cannot contain adapter or runtime-control keys. For every Channel, the planner calls the existing single resolver exactly once as `resolveChannel(id, effectiveBoundedConfig.channel?.[id], adapterEnvironment)`. Config field values are the documented precedence owner; if a configured field and its environment alias are both present with different normalized values, planning returns a typed `channel_source_conflict` rather than silently selecting a host-dependent value. The frozen resolved-channel snapshots — never host-projected `channelEnv()` output — are the only input to configured ordering, adapter factory options, operational identity and public receipt. The supervisor deletes its `channelEnv()` projection, and standalone performs no pre-resolution.

The planner computes two deliberately different identities; neither is a fallback for the other:

- `operationalIdentityDigest` is process-local and is the supervisor's sole **running-owner** reuse/replacement key. A package-owned random 32-byte key is created once per process. The planner applies domain-separated HMAC-SHA-256 to strict canonical bytes covering the entire **declarative** planner input that can affect configuration, including the planner-produced configs, resolved adapter values, selected saved credentials, STT/vision values and declarative runtime options. Thus provider `apiKey`, authorization headers and future schema-valid secret-bearing fields cannot enter an unkeyed digest or be omitted. The log callback is a process capability retained by exact reference on the branded plan and excluded from both digests. This digest is exposed only to the in-process lifecycle owner, never written to logs, public HTTP, standalone machine output or durable storage. It is explicitly invalid to compare it across processes.
- `publicTopologyReceipt` is versioned, stable across processes and contains only an allowlisted non-secret projection shared by both hosts: the constant bounded-config schema ID/version, profile identity, configured Channel IDs, per-field **source/presence classification only**, STT/vision provider/model identifiers, credential slot/source classification and canonical adapter/capability membership. It deliberately excludes embedded/external mode, directory, server identity, runtime paths, launch environment and client authentication. `ChannelFieldType` is not treated as a publicity label: extend the channel catalog field contract with an independent `publicIdentityProjection` metadata enum whose default is `omit`; raw values enter the receipt only when a field explicitly selects a safe projection such as `literal_safe` or a URL `origin_only` sanitizer. The initial delivery defaults all sensitive or personally identifying text fields to `omit`, including Matrix/Mattermost/Signal URL/account/recipient/allowlist data. It never includes arbitrary config key paths, a generic hash of raw config or secret bytes. Its `publicDigest` is SHA-256 over those canonical bytes. It proves that hosts selected the same public topology and secret slots, not that their secret values match.
- `runtimeAttachmentReceipt` is a separate versioned host-local receipt. It contains sanitized embedded/external mode, canonical directory/server origin without credentials/query, path identities, declarative policy/source classifications and client-auth/launch-environment **slot presence only**. Its own public attachment digest proves the non-secret projection of one host attachment but is never compared as equal between an embedded standalone process and an external-server supervisor. Secret values and raw child environment are present only in the process-local operational HMAC input.

Use the repository strict canonical primitive for both byte encodings. An operational digest hit proves exact planned equality only inside the current process; a public digest proves only the documented non-secret cross-process projection. Tests and machine receipts must name the appropriate field and may not relabel the public digest as complete configuration identity.

The planner, starter and every managed runtime call below them never read or write `process.env`, call `process.cwd()` for policy, change the working directory, load `.env`, read Auth, log secrets, or call `process.exit`. Standalone-specific ambient source loading happens once before planning; the in-process supervisor passes its already resolved OpenCorvus facts. `ChannelRuntime`, formatter/queue helpers, runtime-path helpers and the managed SDK client/server path consume only `runtimeAttachment` options. This delivery removes the managed-path ambient reads currently used for mirror output, shared-session mode/file/default cwd, task timeout/sweep, queue limit, tool-status formatting, Slack mirror target, monitor diff threshold, home/temp/screenshot paths, SDK server username/password, server binary, child environment and config content. The SDK gains explicit command/minimal-environment/client-auth/config inputs for this path; unrelated SDK callers may retain their current public defaults outside the supplied managed path. Changing any secret or execution-affecting value anywhere in bounded/embedded config, adapter/STT/vision inputs, selected credential observation or runtime attachment changes `operationalIdentityDigest` and forces the supervisor to stop the previous owner before starting the new plan. The topology/attachment public digests may remain unchanged for a same-slot rotation by design.

The minimal child environment is selected once by the planner from the explicit `{platform, environment}` ingress through a strict platform-specific allowlist. The host supplies the observation unchanged and cannot submit a pre-projected child-environment field; such a field is rejected by the input schema. The planner permits only operating-system launch necessities actually consumed by process creation (Windows `SystemRoot`, `WINDIR`, `ComSpec`, `PATHEXT`, `TEMP`, `TMP`; POSIX locale and temporary-directory keys where required) plus explicit OpenCorvus runtime-root/config facts generated by the planner. The executable is absolute, so `PATH` is omitted unless the package-owned platform contract proves it mandatory and then it is normalized as an explicit launch fact. Adapter, Speech-to-Text, vision, Auth, machine-receipt and arbitrary parent variables are rejected and never inherited by the embedded child. Operational identity covers the explicit platform and precisely the normalized keys passed to the child, not the whole ambient snapshot; changing an unrelated ambient variable therefore does not restart the owner.

`AbortSignal` is not desired-runtime configuration and is not stored in the reusable plan. `startConfiguredChannelRuntime(plan, {signal})` receives one fresh lifecycle-owned signal for that start attempt. A digest may reuse only an existing owner whose state is currently `running`; failed, stopped, cleanup-pending or aborted attempts are never cached as reusable owners. The supervisor creates a new signal for every actual replacement/start, while an identical running owner remains unaffected by a later sync's caller signal. Reusing the declarative plan for a fresh attempt is valid because the one-shot signal and resource ownership live in the start call, not in plan identity.

`ChannelRuntimeOptions` gains the complete required runtime attachment and passes explicit `embeddedEffectiveConfig`, per-start `signal`, absolute binary/structured argv, minimal child environment, paths and client-auth inputs to `createOpenCorvus`/`createOpenCorvusServer`; it never lets the SDK read ambient `OPENCORVUS_CONFIG_CONTENT`, `OPENCORVUS_BIN_PATH`, server credentials or `process.env` on this path. The existing external-server branch uses the exact supplied server URL/client authentication and directory. A real standalone child test proves the spawned embedded server observes this exact config and launch input.

### 2. One canonical factory registry and capability settlement

Move the complete production adapter factory map beside the public planner/starter inside channel-runtime and reuse one internal catalog projection. Hosts do not enumerate adapters. Remove the factory-accepting `registerAdapters` and individual production adapter constructors from the package-root public index; retain them only as package-internal modules for their own relative-import tests. The root export surface contains the planner, starter, owner/receipt/errors and intentional message-format APIs, but no registry replacement ingredient. The explicit package `exports` map makes private subpaths unreachable to consumers. If focused tests need controlled network behavior, use the real default Matrix/Signal adapter constructors and package-private network/transport ports already accepted by those adapters, or a package-private harness that is not exported and cannot replace membership; production and supervisor equivalence tests must exercise the canonical registry.

The bootstrap creates one `ChannelRuntime`, installs configured STT and vision, registers adapters, and starts it. Capability results are typed:

- STT: `disabled | active` with exact provider identity;
- vision: `disabled | active` with model/base URL/source classification;
- adapters: configured names/warnings plus the physical `ChannelRuntime.start()` receipt;
- configuration identities: one process-local secret-sensitive `operationalIdentityDigest` held only by the lifecycle owner, plus the versioned `publicTopologyReceipt/publicDigest` and separate `runtimeAttachmentReceipt/attachmentDigest` described above.

Invalid bounded config/profile/channel source or plan provenance fails with `ChannelRuntimeConfigurationError`, whose stable reason union is `invalid_config | invalid_profile | channel_source_conflict | invalid_plan`. Invalid configured STT/vision fails with a public discriminated `ChannelRuntimeCapabilityError` containing `capability: "stt" | "vision"`, `reason: "invalid_configuration" | "unsupported_provider" | "credential_unavailable" | "provider_unavailable"`, and safe field/message data plus internal cause. “Not configured” is the only disabled state. Empty vision model/base URL or missing selected-provider key is invalid, not an empty working pipeline. There is no catch that converts malformed configuration into successful absence.

The public signature is unambiguous: `startConfiguredChannelRuntime(plan, {signal}): Promise<ConfiguredChannelRuntimeOwner>` returns only the success owner and throws only the typed errors below. It does not return an error union:

- success: immutable owner with `configuration`, `configuredChannels`, `activeChannels`, `failedChannels`, `capabilities`, underlying readiness receipt, `injectPrompt`, and idempotent `stop()`;
- configuration/capability failure before resource creation: the typed error above with no owner;
- startup failure plus successful rollback: `ChannelRuntimeStartError` with safe configured-channel/capability causes and no owner;
- startup failure plus incomplete rollback: `ChannelRuntimeCleanupError` containing the original safe causes and exactly one retryable owner. Ownership transfers atomically to the caller only through this error; repeated `stop()` converges, and successful stop marks/releases it. There is no second bootstrap/supervisor cleanup set over the same resources.

`ChannelRuntime` remains the internal rollback executor and exposes its one cleanup-pending owner only through `ChannelRuntimeCleanupError.owner`; the starter does not run an independent rollback after `runtime.start()`. Supervisor lifecycle state adopts that owner once, then only invokes its idempotent stop before another lifecycle action. Only a returned owner in `running` state is inserted into the operational-digest reuse map; a thrown start/abort/cleanup result never installs a reusable desired owner.

Startup cancellation is fully propagated rather than merely advertised. `ChannelAdapter.start(signal)` becomes the lifecycle contract; every production adapter threads the signal through startup fetch/client/loop operations, removes listeners on settlement and makes `stop()` converge after abort. STT/vision setup/provider construction and any startup network validation receive the same per-attempt signal. The starter checks it before resource creation, and `ChannelRuntime` passes it to `createOpenCorvus` and every adapter/capability startup. Abort returns typed `reason:"aborted"` start/cleanup settlement and the same zero-resource-or-single-cleanup-owner invariant. This is lifecycle plumbing, not an adapter business-protocol redesign, and belongs to this task's affected surface.

### 3. One canonical saved-credential observer

Move the saved credential schema/read error/observer into a neutral public Util module (for example `@opencorvus-ai/util/saved-credentials`) usable by both OpenCorvus Auth and channel-runtime. It receives an explicit absolute auth path; missing file returns `{kind:"missing"}`, valid content returns one strict credential map/observation, and malformed JSON, invalid credential, or non-ENOENT I/O return the same typed reason currently owned by `Auth.ReadError`, without exposing path/token/parser input publicly.

OpenCorvus `Auth.all()` delegates to this observer and preserves its existing public `Auth.ReadError` identity/cause mapping; standalone channel ingress calls the same observer at the runtime path. Delete `channel-runtime/src/dashscope.ts`'s private JSON parser. One pure projection derives DashScope key/coding-plan/base URL/source from the observed credential map. No host implements a credential schema or base-URL heuristic. The plan receives the observation once and fingerprints any selected key.

### 4. Two thin hosts

- Replace mutating `applyBundledEnv()` with `resolveBundledEnvironment(baseEnvironment, now) -> {environment, receipt}`. It copies the explicit base snapshot, applies accepted bundle values only to that copy, and never touches `process.env`. Delete the mutating public path in the same change. (`CS-064` remains responsible for mixed-line validity/TTL semantics.)
- Standalone `main.ts` owns only process ingress: capture ambient `{platform, environment}` once without choosing launch keys, resolve bundled values into the local raw environment observation, collect exactly one raw source config/profile without applying permission or duplicating bounded parsing, observe credentials through the shared public observer, supply the remaining explicit non-environment runtime-attachment facts, call `resolveConfiguredChannelRuntime` once, call `startConfiguredChannelRuntime(plan, {signal})`, render structured machine/log receipt events, optionally invoke owner `injectPrompt`, and install shutdown handling. Only the planner projects the closed runtime attachment and minimal child-launch environment. The host never imports adapters/core/registry/STT/vision directly. Full embedded-server config validation remains a typed embedded startup concern and is not presented as a cross-host bounded-config validation result.
- OpenCorvus `ChannelSupervisor` declares `@opencorvus-ai/channel-runtime` as a workspace dependency and dynamically imports only package-root public exports to keep lazy loading. It builds explicit adapter/capability/runtime/config/credential input, calls the planner before lifecycle comparison, reuses an identical operational identity without starting, and passes that exact plan to the starter only on replacement. It stores the returned owner/receipt and deletes private `startInProcess`, `channelEnv()` projection, host adapter enumeration and local duplicate rollback.

The supervisor's desired signature is `plan.operationalIdentityDigest`, obtained before stop/start, not a separately assembled `JSON.stringify({env,...})`. Configuration comparison and runtime creation therefore share the same frozen plan. Supervisor lifecycle serialization remains its host responsibility because it owns Project replacement; exact runtime cleanup remains the single owner described above.

Supervisor stores the complete owner/receipt in its one `Instance.state`. No test-only or diagnostic public API is added. Focused tests prove stored-receipt consumption through existing production projections: `status().channels`, `channelStatus()` and `handles()` must equal the active subset from the starter receipt. The channel-runtime package owns one non-exported deterministic lifecycle fault port used only by its integration harness; it instruments canonical starter resources after the fixed registry has selected them and may fail/record stop attempts, but cannot replace membership, options or factories. Channel-runtime tests use it to prove canonical rollback creates exactly one cleanup owner. A separate supervisor test supplies that real typed `ChannelRuntimeCleanupError.owner` at the public starter-call dependency boundary used by the lazy import, then proves the supervisor adopts and retries the exact owner once before the next operation; it claims only supervisor adoption, not registry end-to-end behavior. Normal reuse/rotation remains full canonical-registry production-path coverage. No test recomputes a plan to stand in for supervisor state, and HTTP/OpenAPI remains unchanged.
