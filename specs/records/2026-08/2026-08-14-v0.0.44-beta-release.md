## Post-release activation convergence plan

- Recall: after the user reinstalled the RackNerd VPS, authorized direct SSH bootstrap, and asked Codex to complete the website deployment, the new host was rebuilt with official Caddy `v2.11.4`, Bun `1.3.14`, the committed root-owned activation boundary, a dedicated deploy-only SSH identity, and the exact accepted signing public key. - Observable failure: the first credential-repaired rerun of website run `31822968920` passed source resolution, build, archive, signing, upload, signature verification, database import, pointer switch, and `systemctl restart`, then Caddy returned `502` for the activator's immediate loopback `/health/ready` request. The activator rolled back the release, database, service, and enablement as designed.
- Direct trigger and root cause: `service_start` uses `systemctl restart` on a `Type=simple` unit. That command returns after the Bun process is spawned, not after port `4321` is accepting requests. `probe_live_release` then performs one immediate request through Caddy and treats the startup race as a terminal health failure. The application journal had no crash; Caddy recorded `connect: connection refused` while the service was still starting. The previous sudo failure and a VPS reinstall did not repair this timing gap because neither changed the activator's readiness contract.
- Scope search: activation and rollback both use the same `service_start` primitive, while only the new-release path requires the full signed publication probe. The production web service has a `30s` startup ceiling. A bounded retry therefore belongs in the activator's canonical live-release probe, not in Caddy, systemd overrides, GitHub Actions, or the application runtime. Static, database, exact-archive, and rollback validation must remain unchanged and fail closed when readiness never converges.
- Implementation and acceptance: make only the loopback readiness request retry connection/HTTP unavailability within a 30-second wall-clock deadline, with each connection and response attempt bounded to one second, before the existing exact publication checks proceed. Add a positive activation fixture in which readiness is initially unavailable and then returns the exact current publication; retain the existing persistent-failure rollback fixture. Run the real activation harness, production configuration checker, shell syntax checks, and an independent read-only review before committing.
