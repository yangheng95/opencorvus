### Work-conserving queue and rolling settlement incident — 2026-08-28

- **Observable state:** after recovery reached 80/600, the Luna supervisor launched batch 17 and 18 together. Seven physical trials ran because cases 81–83 were reusable candidates, but the catalog, receipts and verified dashboard frontier could not advance until every remaining case in both selected batches settled. The user correctly identified that this still behaves as a nested batch group instead of a rolling long-run queue.
- **Direct trigger:** `run-automationbench-batch.ts` waits for `Promise.all(contexts.map(launchRollingBatch))`, then performs one trial catalog refresh, writes every sibling receipt, and performs one final catalog refresh. `run-luna-mission-base-cases-51-600.sh` groups exactly two pending batches, waits for that coordinator, and—with `set -e`—exits when any selected batch contains an invalid, failed or unsealed case. The Sol Base and Luna Advanced supervisors have the same fail-fast wait behavior for one batch at a time.
- **Data/control-flow root cause:** `rolling_case_slots_v1` only sequences multiple profile waves for the same five case indices. It does not provide a work-conserving queue across case indices, does not publish a receipt when one audit batch becomes ready while sibling work continues, and does not isolate an invalid case from the remaining manifest. The batch receipt, which should only prove five-case audit membership, was incorrectly promoted into scheduling and supervisor-continuation authority.
- **Why the previous path did not root-fix it:** paired batches raised Luna physical concurrency from five to ten and independent receipt status prevented one failed sibling from falsifying the other sibling's receipt. Those changes improved throughput and audit truth, but the enclosing coordinator and shell still imposed a group barrier and returned failure before later batch indices were admitted.
- **Horizontal shared-mechanism audit:** all three production supervisors—Sol Mission/Base, Luna Mission/Base and Luna Mission/Advanced—call the same coordinator and stop at a non-zero coordinator wait. The trial runner already has typed inactivity settlement, append-only terminal evidence, per-case leases, exact batch authorization and reusable-candidate selection. Mission/Task/Session occurrence convergence and Provider streaming happen wholly inside each trial and are independent across projects; no product control-plane change is required. The defect is confined to the benchmark coordinator/supervisor queue above those isolated trials and below batch receipt/catalog publication.
- **Single-mechanism repair:** the coordinator will accept an ascending set of pending audit batches, create immutable plans, and feed only missing slots into one bounded work-conserving queue. A finished, failed, invalid or unstarted trial always settles its physical slot so the next manifest case can start. Batch contexts become settlement-ready independently; one serialized coalescing settlement loop refreshes raw evidence, writes every ready receipt, then lets the next refresh adopt those receipts. Active authorizations are created lazily and removed when that batch settles. A normal case failure is preserved and reported after the entire admitted queue drains; only a coordinator/catalog/authorization framework failure stops new launches.
- **Retry and completion boundary:** a problem case is deferred for the current pass, not erased and not converted into a score. Clean sealed siblings remain reusable. The supervisor completes the rest of its pending manifest before returning an exact unresolved-batch failure; a later authorized continuation plans only missing or invalid slots. This prevents one pathological case from consuming the whole queue while preserving the exact 600/600 final acceptance requirement and avoiding an unbounded automatic retry/spend loop.
- **Acceptance plan:** add positive contract coverage proving bounded work-conserving admission, input-ordered settlement results and forward progress after a case-level invalid result; allow an ascending pending-batch set while rejecting ambiguous identities; update every production supervisor to submit its full pending set with an explicit global concurrency bound; verify shell syntax, focused non-UI tests, benchmark TypeScript, documentation and diff checks; obtain an uninvolved read-only review; commit, merge upstream and push. Do not replace the source under the currently healthy Luna coordinator. Synchronize and resume with this mechanism only after the old process reaches a natural terminal boundary, then confirm that a settled slot admits a later case and that failed cases are the only remaining retry frontier.
