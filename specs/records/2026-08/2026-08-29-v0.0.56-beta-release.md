## Impact and release-chain analysis

- Observable state: the architecture-debt campaign and its exact-source Mission acceptance are pushed on the maintenance branch, but package metadata, public binaries, updater metadata and the website still identify an older release family.
- Direct trigger: freeze the reviewed maintenance history, promote its single version authority to `0.0.56-beta`, validate an index-materialized source tree that excludes both unrelated worktree files, and publish one immutable tag from that exact source.
- Control flow: canonical release commit -> immutable tag -> five-platform graphical application and command-line interface matrices -> staged draft assets, checksums and signed updater manifest -> explicit complete-matrix gate -> GitHub prerelease -> immutable repository dispatch -> signed website candidate -> RackNerd transactional database/release activation -> public readiness and exact-download probes -> fast-forward integration into `main`.
- Website authority: `deploy-opencorvus-com.yml` resolves the dispatch tag and source SHA, rebuilds `downloads/latest.json` from the published GitHub Release, verifies canonical archives and database lifecycle, signs the complete candidate in Continuous Integration, and lets the root activator atomically switch the immutable release. Sites and any parallel deployment path are excluded.
- Risks: accidental inclusion of either dirty parallel path, version drift, a tag/source mismatch, incomplete native matrices, mismatched checksums or updater channels, a failed signed website activation, stale public downloads, release-source divergence from `main`, or a runtime scheduling regression hidden by static checks. Each is verified at its owning Git, build, Release, updater, deployment, public-page or database boundary.
