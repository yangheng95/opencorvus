# ARC-008 Conversation MCP Context-Budget Convergence

## Recall

| Item | Evidence and decision |
| --- | --- |
| User requirement | Continue repairing every finding from the repository architecture-debt audit on `v0.0.55beta`; after the ledger is fully closed, run a real Mission end to end and keep repairing any abnormal scheduling trajectory from the architecture root. |
| Finding | ARC-008 records that a project with no explicit Chat/Work MCP assignment still projects the complete Browser and Computer tool catalogs on every Turn: 53 model-visible tools and about 6,725 estimated tokens in the audited measurement. |
| Observable trigger | `ConversationCapability.assignment()` falls back to `DEFAULT_ASSIGNMENTS`; both Chat and Work use `DEFAULT_INTERACTIVE_MCP_SERVER_REFS`, which contains `browser` and `computer`. `runtimeMcpTools()` then materializes those configured providers for every Session Turn. |
| Data and control-flow root | The default assignment conflates level-0 configured inventory with level-2 harness activation. Configuration proves a provider exists; it does not express that an operator selected it for every conversation. Permission and scoped Session ownership act only after projection and therefore cannot recover the context budget. |
| Why prior paths do not cure it | Browser/Computer permission checks constrain calls, not model-visible schemas. Scoped connection owners constrain runtime lifecycle, not Turn projection. The historical Tool-block plan is not the current runtime. Adding a host keyword gate or hidden on-demand fallback would create a second activation authority and is excluded. |
| Definitions and callers searched | `conversation/default-capability.ts`, `conversation/capability.ts`, `work/harness.ts`, `session/loop.ts`, the Chat/Work capability routes, config schema, SDK route artifacts, Browser/Computer ownership tests, current architecture chapters 04/05/17, the saturation audit, and the staged remediation ledger. |
| Corrective contract | Configured Browser/Computer declarations remain level-0 inventory. Default Chat and Work MCP assignments are exactly empty. The existing project-owned `primary_assistant_capabilities.<chat|work>.mcp_server_refs` setting and PATCH routes are the sole activation authority; an explicit assignment projects the same complete provider tool catalog and retains the existing permission and Session-owner contracts. Work keeps its independent default `work-artifacts` Skill assignment. |
| Acceptance | Positive route evidence must prove exact empty default assignments while Browser/Computer remain configured, then explicitly assign both providers and prove the complete Browser/Computer runtime catalog has a non-zero schema payload. Focused tests, OpenCorvus typecheck, documentation checks, architecture index, formatting, and `git diff --check` must pass. No User Interface automation is added, modified, or run. |
| Delivery and risk | This changes the out-of-box Chat/Work MCP surface: users who want Browser or Computer must explicitly assign the configured server per assistant. It does not change provider declarations, tool identities, permissions, stream behavior, runtime ownership, cleanup, Mission, Task, or Expert-Squad projections. The old shared default module is deleted so there is no fallback or second source. |
| Independent-agent feedback | None before implementation. After first green verification, an uninvolved read-only agent must review the complete scoped diff and evidence. Every valid finding must be repaired and the review repeated until no unresolved P0-P3 finding remains. |

## Implementation record

- `DEFAULT_INTERACTIVE_MCP_SERVER_REFS` and its module are deleted. Chat owns an exact empty MCP default in `ConversationCapability`; Work owns an exact empty MCP default beside its unchanged `work-artifacts` Skill assignment. No fallback, host gate, keyword match, or shadow activation path was added.
- The production Chat/Work capability route proves both assistants report exact empty `assigned_server_refs` while `configured_server_refs` still includes Browser and Computer. Direct runtime materialization for both defaults returns the exact positive receipt `{ toolNames: [], schemaChars: 0 }`.
- The same production PATCH route explicitly assigns Browser and Computer to Work. Runtime materialization then returns exactly 53 tools: 45 from Browser and the complete eight-name `ComputerMCPBuiltin.ImportableToolNames` projection, with a non-zero serialized schema payload. Existing Browser scoped-owner, Computer takeover/disposal, disabled-provider, direct-Work and Expert-Squad contracts continue to pass after their inputs are made explicit where the old test depended on default activation.
- Final focused acceptance is **23 pass / 0 fail / 94 assertions**. Root typecheck is **8 / 8**; OpenCorvus package typecheck passes; docs are **337 operations / 25 groups**; architecture index is **26**; exact Prettier and `git diff --check` pass. No User Interface automation was added, modified, or run.
- Independent read-only review: **PASS with no unresolved P0-P3 finding**. The uninvolved reviewer independently confirmed the inventory/activation separation, exact default zero payload, explicit 45 Browser plus eight Computer projection, unchanged provider/permission/scoped-owner lifecycle, focused tests, package and documentation gates, and exact commit isolation. It found no fallback, dual read, second activation source, omitted production caller, or unsupported evidence claim.
