## Problem analysis

### Observable gap

User Messages are durable in Session/Part tables, but Project memory is written only when an agent explicitly invokes `memory.write`. Consequently a user request can be present in a conversation and absent from Project memory. The existing Session `MEMORY.MD` does not solve this: it is Session-scoped, appears only after compaction, and is a continuation summary rather than an all-user-message ledger.

### Direct trigger and data flow

The canonical Message commit is `Session.persistMessage* -> persistMessageBundleRows`. It writes the Message header and Parts in one SQLite transaction, then publishes visibility effects. External and internal inputs both use `Message.role = "user"`; therefore capture based only on role or author text would incorrectly record runtime wakes and projected prompts. Trusted ingress stamps Message-level provenance because a real user Message may contain only attachments and no Text Part. Capture then occurs beside the committed Message bundle. Direct Task creation uses the same occurrence writer inside its canonical Task transaction. Interaction reply content is propagated through the existing permission/question terminal event and captured in the transaction that writes terminal `engine_interaction_request` state. Shell is migrated from separate header/Part writes to the canonical Message bundle transaction.

### Root cause

The Project semantic-memory subsystem is an optional main-agent-operated knowledge store, not a durable inbox plus a separately owned Project-context document. There is no authenticated mapping from real user input to a pending occurrence, no task/conversation-title resolver, no two-message context snapshot, no fixed Organizer role, and no atomic compare-and-swap from an ordered pending prefix to one bounded context document. Asking the main task model to remember messages conflates work and memory responsibilities; asking the host to group or score entries cannot understand the user's full meaning.

### Why existing paths do not cure it

- Session compaction runs later, may never run, summarizes rather than preserves every user Message, and is not Project-scoped.
- `memory.write` depends on the main model's choice and mixes task execution with memory maintenance; it is neither mandatory nor bound to the Message commit.
- `Memory.captureEpisode` is unused, derives heuristic facts, and does not distinguish authentic user ingress from runtime-authored role=`user` controls.
- Reading Session rows directly on demand would lose audit history when a user deletes or rewinds a Message and would not be an immutable Project-memory record.

### Impact surface

- **Definitions:** Project memory kind/type, capture/projection module, tool and HTTP document schema.
- **Writes:** canonical Session Message bundle commit, direct-user Task persistence, interaction-response persistence, and the narrow explicit ingress sites that establish trusted user-input provenance.
- **Reads:** memory tool, Project-memory HTTP inspection, semantic-memory search defaults.
- **Data:** existing `memory_file` and `memory_chunk`; no physical schema migration. One keyed `user_message` pending item per source occurrence plus one protected `project_context` envelope/chunk containing the entire document and Organizer lifecycle state. Neither protected kind enters generic full-text search (FTS), search, write, update, or delete surfaces.
- **Tests:** focused positive contracts for capture, context ordering, task/conversation naming, idempotency, internal-message classification, read projection, and reopen durability. Existing UI tests are out of scope and will not be run.
- **Documentation:** current memory architecture plus records indexes.
- **Delivery risk:** overlapping dirty files, accidental duplicate capture of direct Task projection, leakage of secrets/inline payloads, Organizer unavailability, stale concurrent Organizer output, over-capacity output, and a notification that is visible only to agents rather than users. Each is addressed below.

## Current contract and exclusions

- Session `MEMORY.MD` remains the compaction checkpoint and is not renamed or mutated.
- Existing semantic fact/note/profile/lesson/episode memory remains agent-managed.
- The all-caps Project `MEMORY.MD` is the single Organizer-owned Project-context document. Main agents and generic memory tools can read it but cannot rewrite it. It lives in existing Project memory tables and is not mirrored into the worktree. The existing Session document is also named `MEMORY.MD`; `scope=project` versus `scope=session` is the semantic discriminator.
- No historical Session backfill is inferred in this change. Capture begins for newly committed explicitly user-authored Messages; fabricating historical authorship from role/author is unsafe. A future explicitly authorized migration may backfill only from provable provenance.
- Binary attachment bytes are not duplicated. Ledger entries retain sanitized filename, media type, and canonical attachment reference.
- Interaction replies and rejections are included even though the interaction subsystem consumes them without creating an ordinary Session Message. Unrelated button clicks and API mutations remain outside the message/input contract.

## Design

### 1. Unified user-input occurrence and trusted provenance

Define one versioned, host-owned `ProjectMemoryUserInput` occurrence contract with a stable occurrence kind/ID, owning Project, optional Session/Task identity, capture timestamp, user content, attachments, and ingress surface. It is constructed only by trusted server/channel/task code; public callers cannot inject it through arbitrary Message metadata.

For ordinary Messages, trusted ingress adds a versioned Message-level provenance marker. This supports text, mixed, and attachment-only Messages. Text Parts continue to use `kind=user_content` and `source=user` for content classification, but the Message-level marker is the authorship authority. Host/runtime context Parts remain `context/system/task_tool/mcp_app` or unstamped. The canonical hook requires role=`user`, valid host provenance, and no compaction marker. It never infers authenticity from a title, author label, Session kind, Part presence, or keyword.

Direct Task creation emits an occurrence only when durable `TaskCreatorMetadata.actor` is exactly `user`. Other Task creator actors retain their already-captured originating Message. Trusted operator interaction routes use separate user contracts without an `autoReply` field. After the Question answer or Permission choice is fully validated, the user-bearing terminal event is committed to the durable Bus outbox (atomically with the Permission decision when applicable). The durable subscriber writes the Engine terminal row and immutable occurrence in one transaction; a crash before delivery is recovered by the outbox. Internal tool/service and automatic terminal events do not carry user provenance. Command and shell ingress preserve the literal user-submitted command in trusted occurrence metadata rather than recording only host-expanded prompt text. `SessionShell` persists its user header and Part via `Session.persistMessage` so the transcript and occurrence are one bundle transaction.

### 2. Durable pending inbox entry

Within the same SQLite transaction as the originating Message, Task, or interaction response, enqueue one `memory_file` with:

- `project_id`: owning Project;
- `kind`: `user_message` (host-owned pending inbox; omitted from agent `memory.write` input kinds);
- `source`: `user`;
- `id`: deterministic cryptographic digest of Project ID, occurrence kind, and stable occurrence ID;
- `key`: stable occurrence identity for diagnostics only, never relied on for uniqueness;
- `title`: capture-time Task title, otherwise Session/conversation title;
- `importance/confidence`: fixed host values, not model estimates;
- one versioned JSON chunk containing source Message/Session/Task identities, event time, sanitized literal input/attachment references, and the two immediately preceding visible same-Session Message snapshots.

Insertion uses the deterministic `memory_file.id` primary key and a deterministic chunk ID with conflict-ignore followed by a full canonical-payload comparison. Byte-identical replay returns the existing item, including under concurrent writers. A different payload for the same occurrence raises a typed invariant error and rolls back the enclosing transaction. Pending rows are not a permanent archive: after one accepted Organizer commit covers an ordered prefix, that prefix is atomically deleted. The Session transcript remains the raw-history authority.

### 3. Task name and two-context snapshot

Resolve the display owner inside the transaction:

1. Follow the durable Session-parent lineage to an `engine_task.session_id` owner.
2. If exactly one Task owns the lineage, record its current title as a capture-time snapshot and its stable Task ID.
3. Otherwise record a capture-time Session/conversation name and stable Session ID. For the first Message, use the same first-message title derivation as Session naming so the snapshot is not the pre-title placeholder.

Context is the two preceding persisted Message bundles returned by the same `Session.messages` / `MessageStore` transcript source used by the public Session transcript, ordered oldest-to-newest. “Visible” means the Message and Parts satisfy `Message.VisibleInfo` / `Message.VisiblePart`; it does not invent a separate role or keyword filter. Therefore a durable internal wake/control Message that appears in the real transcript may supply meaning to the Organizer without being mistaken for a user occurrence. Only visible text and safe attachment metadata are enqueued. Empty/non-text context is represented by participant identity and attachment inventory. A later title edit does not mutate the already-enqueued evidence; the Organizer decides how the complete meaning belongs in current Project context.

### 4. Secret and payload safety

Before inserting the ledger chunk and before rendering the Project document:

- remove inline data URLs and raw base64 payloads through the shared payload redactor;
- redact recognized API-key, Authorization/Bearer, password, token, client-secret, private-key block, and credential assignments with tested boundary rules;
- retain only attachment filename, media type, size when known, and a canonical `AttachmentStore` reference; arbitrary external URLs, query strings, fragments, inline data, and local filesystem paths are replaced by `<external-reference-omitted>`;
- replace unsafe values with explicit `<redacted>` markers;
- preserve Message/Part identity so the operator can return to the authoritative transcript.

The capture contract stores the sanitized representation, not a second secret-bearing copy. This is the only intentional difference from the original Message content.

### 5. Separate Memory Organizer agent

Add one fixed hidden helper identity `memory`. It is neither a main/primary agent nor a host state machine. Its only job is to maintain the Project-context document. Its system prompt receives:

1. the current Project `MEMORY.MD` content and revision;
2. an ordered pending prefix containing each task/conversation name, literal user input, safe attachments, and the preceding two transcript messages;
3. the hard output ceiling of 10,000 estimated tokens;
4. the instruction to translate the evidence into the user's complete intended meaning, merge duplicates, reconcile corrections, retain active decisions/constraints/work state, and autonomously remove or compress stale/low-value context.

The Organizer must not produce a turn-by-turn quotation ledger or invent facts. It streams a complete candidate replacement. The host does not group, rank, summarize, or rewrite its content. The host validates only structural integrity: unchanged base revision, exact ordered-prefix occurrence IDs, sanitized text, nonempty Markdown, and estimated token count at or below the effective configured `document_token_limit` (whose hard maximum is 10,000). One transaction then replaces the protected `project_context` chunk and deletes exactly the covered pending prefix. Newer concurrent arrivals remain pending for the next run. A stale or invalid candidate commits nothing and is retryable.

The Organizer has one serialized/coalescing run owner per Project. New captures request a run after their source transaction commits. Project/runtime initialization also resumes Projects with pending items. Organizer/model unavailability leaves the inbox intact and records an unavailable status; it never routes organization back to the main task agent.

#### 5.1 Persistent envelope and durable run request

Use one deterministic protected `project_context` file ID and one JSON envelope as the only Project-context state source. The versioned envelope contains `revision`, `markdown`, `tokenCount`, `status`, `lastAttempt` (generation, start/end time, model identity, terminal classification), cumulative `droppedPendingCount`, and the last notification occurrence/acknowledgement state. An empty Project is initialized at revision zero. Every accepted Organizer commit increments revision in the same transaction that replaces Markdown and consumes pending rows. Generic memory full-text/search/mutation surfaces exclude both `project_context` and `user_message`.

Every pending insert also publishes one durable `project.memory.organize.requested` outbox occurrence inside the source transaction. A fixed durable subscriber with one stable ID coalesces by Project and owns the serialized Organizer run. `capacity_reached`, `evidence_too_large`, `model_context_incompatible`, and the closed `unavailable` states settle only after their envelope state, participant notice, and any authorized FIFO result are durable. Project/session configuration changes invalidate the persisted availability generation and publish a new durable organize request for retained pending rows; Project initialization also requests organization when pending rows remain. Other provider/transport/output failures reject the durable delivery so the Bus retry ledger retains and retries the original occurrence. Therefore a crash after source commit but before scheduling is recovered from the outbox, and a crash after an Organizer commit but before receipt settlement replays against the same revision/prefix without a second semantic rewrite.

#### 5.2 Bounded Organizer input and streaming submission

Pending selection is a deterministic `(time_created,id)` prefix bounded by an effective Organizer-input estimate. After resolving the selected model, compute `min(configured organizer_input_token_budget, model usable input minus fixed runtime reserve)`, then require it to remain greater than the effective `document_token_limit` plus the fixed Organizer protocol reserve. An incompatible configuration/model records a durable `model_context_incompatible` attention state without making a provider request or entering infinite retry. The budget includes the full current document, prompt/protocol reserve, occurrence metadata, user evidence, and two-context snapshots. It admits complete occurrences only; host code never truncates or summarizes evidence. At least one complete item is admitted when it fits. If the oldest item alone cannot fit, the attempt records `evidence_too_large`, preserves the row, and emits a user-facing action notice; it is not `unavailable` and does not authorize FIFO.

The helper receives only the already-sanitized envelope and pending prefix, no project files, environment context, semantic memory, or tools. It emits one streaming textual response using a strict terminal envelope carrying `baseRevision`, exact ordered `coveredOccurrenceIDs`, `disposition`, and complete Markdown. The host parses only after the stream terminates. Only the fixed helper runner may call the internal commit function; public HTTP and main-agent tools can request a run but cannot submit content. If the candidate contains a detected secret, invalid envelope, wrong prefix, stale revision, empty document, or more than the effective `document_token_limit`, the entire candidate is rejected without sanitizer rewriting or pending consumption.

### 6. Access, capacity notice, and availability FIFO

- `memory.project_read` and the Project-owned HTTP endpoint return only the current organized `MEMORY.MD`, explicit `scope=project`, its revision/token count, pending count, Organizer status, and a capacity notice. Session reads return the same filename with `scope=session`. Main agents never receive the pending inbox through ordinary tools or automatic prompt injection.
- `memory.project_organize` and a Project-owned HTTP action request the dedicated Organizer; they do not let the caller supply organization content. Automatic post-commit scheduling remains the normal path, while this explicit action lets a user retry or ask for organization after a capacity notice.
- Project prompt injection reads the same protected organized document and respects the existing `enabled`/`auto_inject` switches. It is all-or-nothing: if the complete document fits `experimental.memory.token_budget`, inject it unchanged; otherwise omit it and add a short tool pointer/status generated from the envelope. Host code never selects, truncates, searches, scores, or summarizes document sections. The former host-selected semantic-memory auto-injection path is replaced, not retained in parallel. Explicit semantic-memory tools remain available.
- A candidate with `tokenCount <= document_token_limit` may commit. Only `tokenCount > document_token_limit`, or a candidate that cannot incorporate pending evidence within that configured ceiling, produces `capacity_reached` with a direct user-facing message asking the user to run memory organization/review. The product must not silently truncate the organized document or pretend pending evidence was incorporated.
- The existing `experimental.memory` configuration is the single policy surface. Add `document_token_limit`, constrained to a positive value no greater than 10,000 and defaulted to 10,000; `organizer_input_token_budget`; and `pending_availability_limit`. Configuration validation enforces `organizer_input_token_budget > document_token_limit + FIXED_ORGANIZER_PROTOCOL_RESERVE`, with the reserve defined once by the Organizer protocol. No parallel environment variable or hard-coded caller limit is permitted.
- `unavailable` is a closed FIFO classification only for a missing configured `memory`/Project model before a provider request begins. Provider/model lookup failures other than missing configuration, provider authentication, timeout, rate limit, transport failure, context rejection, model/parse/secret validation failure, `evidence_too_large`, and `capacity_reached` are retryable/attention states and never authorize deletion.
- FIFO runs in one transaction only when an unexpired, database-persisted Organizer lease exclusively owns the current Project revision and availability generation, the same missing-model generation was already persisted by the immediately preceding serialized attempt, pending count is above `pending_availability_limit`, and the exact oldest excess prefix is unchanged. A second runtime cannot overwrite an active lease; it may take over only after expiry. Both semantic commit and unavailable/FIFO settlement require the same fencing token, and known failures release their own lease. The first missing-model attempt only records a visible notice. Every Project/session configuration event increments the persisted availability generation, revokes the current lease, and publishes a fresh durable organization request; a stale unavailable or streaming attempt therefore loses write/delete authority. FIFO deletes only the validated pending prefix, updates cumulative dropped state, and emits a durable user notification. FIFO never edits Project `MEMORY.MD`, never runs after a provider request begins, and never masquerades as semantic organization.

#### 6.1 Real user-facing notices

`capacity_reached`, `evidence_too_large`, `model_context_incompatible`, `unavailable`, and FIFO loss persist one notice envelope with Project ID, status, plain-language action, generation, and acknowledgement state. The dedicated Project-memory Server-Sent Events stream exposes `project.memory.notice.changed`, and the Overlay hydrates the canonical read on startup/project switching and renders an actionable banner; the same unacknowledged state is included in `project_read` and HTTP for reconnect recovery. It is not a hidden main-agent prompt and is not synthesized as a user Message. A successful Organizer commit clears the notice and publishes the corresponding hide edge.

## Unknowns and explicit risk decisions

- Existing historical Messages often lack explicit `source=user`; automatically backfilling them would guess authorship and is therefore excluded.
- Cross-resource filesystem atomicity is avoided: the named document is a database-backed read-only document, consistent with the existing virtual Session `MEMORY.MD`. No lagging filesystem mirror is introduced.
- Exact provider tokenization varies by model. The 10,000 ceiling uses the repository's single deterministic persisted-memory estimate; provider prompt budgeting may be stricter but never looser.
- A visible capacity prompt does not authorize the host to delete organized meaning. The user can request another Organizer pass/review; unresolved new evidence remains pending subject only to the documented unavailable-agent FIFO safeguard.

## Benchmark definition

- **Task:** prove the production fixed `memory` helper autonomously maintains the Project `MEMORY.MD` without main-agent or host semantic organization.
- **Input → output:** a clean isolated Project plus an ordered scenario containing initial intent, two-message context, a duplicate, a correction, a superseding constraint, and stale detail → one committed Project `MEMORY.MD` at or below 10,000 estimated tokens, with current complete meaning, no turn ledger, no unsupported fact, and the covered pending prefix consumed.
- **Environment:** load the repository's ordinary configured model/provider through `resolveAgentModel("memory")`; never copy credentials into output, logs, fixture, spec, or command arguments. A missing configured model/auth is a reported blocked real-eval prerequisite, not a fixture pass.
- **Timeout:** use the repository inactivity runner with 120 seconds of no streamed activity; do not use a wall-clock timeout from process start.
- **Acceptance:** deterministic protocol tests cover provenance, CAS, token ceiling, prefix selection, durable gaps, notices, and unavailable-only FIFO. The real-provider eval must observe production streaming, exact committed revision/prefix, semantic retention/correction/deduplication/stale-detail compression, and zero unsupported assertions. If it finds a product defect, repair the root cause and run a new clean scenario after the finding closes.
