## Root cause and complete impact

The defect is not merely a missing hook call. The four sources disagree about what a Tool call is:

| Source | Arguments and permission | `after` observation | Materialization and persistence |
| --- | --- | --- | --- |
| Registry | ToolPart and permission identity use normalized pre-hook input; `before` receives a replaceable `{args}` object, but physical execution continues with the old local variable | materialized and Part-stamped result | registry wrapper materializes twice; processor later completes the ToolPart |
| MCP | ToolPart and permission use pre-hook input; App input and physical call use the old argument variable | raw MCP `CallToolResult`, before MCP normalization/truncation/attachment storage | App completes on raw result; MCP wrapper materializes later; processor persists |
| Projected/stage extra | permission-bearing extras use pre-hook input; internal stage Tools return from the wrapper before the central boundary | no Plugin hooks | wrapper duplicates registry materialization/stamping; processor persists |
| Batch child | manual child ToolPart and permission use validated pre-hook input | initialized registry result before the batch wrapper's final materialization/stamping | batch writes child completion/error directly; parent registry call has its own independent pair |

Because `Plugin.trigger` permits hooks to replace `output.args`, registry and MCP currently advertise transformation semantics that they do not reliably honor. A naive repair that starts executing the replacement would be worse: the permission request fingerprint and ToolPart input would still describe the old arguments. Moving `before` ahead of permission without a durable preparation fact would also emit it again after an Ask-me process restart. Moving only `after` behind a shared materializer would leave three ToolPart writers and divergent durable permission results.

The affected facts are the provider-normalized request, Plugin-prepared execution arguments, immutable provider binding, permission fingerprint/request, call/ToolPart identity, physical result and provider-private protocol payload, host post-processing result, MCP App lifecycle, canonical materialized result, durable Tool occurrence outcome, Permission outcome reference, ToolPart terminal state, display/source Parts, `CS-005` turn-control disposition, recovery continuation, and batch aggregation. Public Plugin types, current security/extension architecture, focused tests/checker, and spec indexes are delivery surfaces. The host-only occurrence receipt does not extend the existing terminal ToolPart public contract and no new route endpoint is needed. The public interactive-Artifact terminal lifecycle does gain `abandoned`, so Engine/public lifecycle schemas, OpenAPI, generated JavaScript Software Development Kit types, and bilingual API documentation must change together.

## Target protocol and authority boundary

### 1. One typed source adapter, one envelope

Create one runtime-neutral `ToolExecutionEnvelope` in the Tool subsystem. A source adapter supplies only:

- immutable provider kind/ID/digest and Tool name;
- the source's canonical argument validator;
- its physical executor;
- raw-result-to-canonical-draft normalization;
- an optional provider lifecycle adapter and a strict adapter-owned schema that converts any opaque provider response into canonical JSON receipt bytes before it reaches the occurrence authority;
- the `CS-005` `ordinary | turn_control_exclusive` execution mode already bound by the trusted Tool definition.

The envelope owns the ordered protocol exactly once:

1. enter the assistant-occurrence `CS-005` execution coordinator, then adopt or create the exact open ToolPart and stable `{projectID, sessionID, messageID, toolCallID, toolPartID, toolName}` identity;
2. validate the provider-normalized requested arguments and durably prepare Plugin arguments as described below;
3. derive permission identity from the prepared arguments and cross `withTaskToolInvocation`;
4. deliver the prepared arguments to the provider lifecycle and physical executor;
5. before entering the physical executor, atomically advance the durable occurrence to `physical_preparing`. On return or throw, publish the versioned physical outcome and provider receipt before any host post-processing. A crash, abort, or receipt-write failure while `physical_preparing` is `physical_outcome_unknown`; it is never rerun unless the adapter implements an explicit provider-task reconciliation contract that proves the same occurrence's terminal receipt. A physical success is never rewritten as `execution_failed` because a later hook, attachment, display, or persistence operation failed;
6. deterministically normalize, truncate, and materialize the physical result into a canonical draft; commit `after_preparing` before invoking `tool.execute.after`; then validate the hook output, verify the `CS-005` host-owned control is byte-for-byte preserved, materialize the final result, and commit `after_prepared` with its canonical bytes. `after_preparing` on restart becomes typed `tool-after-hook-outcome-unknown`; arbitrary Plugin code is never rerun after an unknown cut;
7. publish the one strict terminal occurrence outcome described below through `ToolExecutionOccurrenceTable`. Descriptor-backed Permission and descriptorless builtin/internal/batch calls use that same row and exact insert-or-advance contract. Permission events reference the occurrence/result identity; they do not store a competing result payload. Equality compares the full canonical encoding and hashes, not JavaScript object identity or prose;
8. atomically settle the ToolPart, attachment/display/source Parts, and `CS-005` typed disposition from that returned or durably replayed result through the single persistence port;
9. reconcile the provider lifecycle terminal receipt from the occurrence outcome and settlement identity. This includes MCP App terminal state and cannot run before the occurrence outcome commits;
10. let the SDK terminal event verify/project the already committed settlement and disposition; it never becomes a second terminal writer.

Errors before permission admission never execute the physical adapter. Permission pause leaves the occurrence open. A proved physical failure is the only source of physical `execution_failed`; deterministic validation/hook/canonicalization contract failures have their own outcome kinds. Transactional persistence failure is never an outcome: the phase remains unchanged and the exact transition is retried. An unknown hook/physical cut is terminalized as its corresponding unknown outcome without rerunning arbitrary code. The envelope has no catch-all mapping from host exceptions to physical failure.

Registry, MCP, extra, and batch delete their local hook/permission/materialization/stamping/settlement protocols and construct adapters only. Internal stage Tools also cross this envelope. Their existing immutable dispatch-adapter binding maps to the existing `internal` effect class through the trusted adapter resolver, so they do not prompt, but they no longer bypass identity, hooks, result normalization, or settlement. Callers cannot supply an arbitrary `internal` override. The envelope preserves the already reviewed `CS-005` execution mode, reserved result-control field, assistant-occurrence coordinator, permission replay semantics and typed disposition; it does not create parallel inference from Tool IDs or outputs.

`StructuredOutput` remains the single response-encoding callback: it validates/captures the requested structured assistant response and does not cross permission or Plugin execution hooks. This exclusion is explicit in code/type names and architecture; it is not a fallback executable path.

### 2. Freeze `before` once before authorization

The final prepared arguments, not the provider's pre-hook arguments, are the single execution fact and live only in the occurrence row. The envelope passes one mutable `{args}` object through the Plugin chain, reads back the final `args`, validates it with the source adapter, and only then commits `before_prepared`. Permission fingerprinting, the execution context, `after.input.args`, physical execution, doom-loop comparison, recovery and terminal ToolPart input all use this exact prepared value.

One startup/continuation recovery owner runs before Permission interrupted-attempt reconciliation and before generic interrupted-assistant repair. It exhaustively handles the occurrence phases from the single table below: `requested` retries only admission; `before_preparing` maps to `before_hook_outcome_unknown`; `before_prepared` resumes authorization without rerunning `before`; `physical_preparing` invokes only an adapter's explicit same-occurrence reconciliation and otherwise maps to `physical_outcome_unknown`; `physical_settled` reruns only deterministic normalization and advances to `after_preparing`; `after_preparing` maps to `after_hook_outcome_unknown`; `after_prepared` publishes the exact terminal outcome without rerunning `after`; `outcome_committed` performs only atomic Tool settlement; `tool_settled` performs only lifecycle reconciliation; `settled` verifies convergence. The generic assistant and Permission recovery paths delegate these owned phases instead of inventing an outcome first. This creates at-most-once arbitrary hook and physical execution without pretending an in-process callback is transactional. The reserved receipt fields never live in mutable public Tool metadata.

### 2.1 One chosen durable occurrence schema and outcome union

Add one versioned `ToolExecutionOccurrenceTable`; no running-metadata alternative, side manifest, or descriptorless fallback is permitted. Its identity records the exact `{project_id, session_id, assistant_message_id, tool_call_id, tool_part_id}` tuple and enforces both physical aliases impossible: unique `(project_id, session_id, assistant_message_id, tool_call_id)` and unique `(project_id, session_id, tool_part_id)`. Adoption verifies the complete tuple and maps either uniqueness collision to typed occurrence drift rather than allocating another occurrence or executing twice. It stores the immutable provider/source binding, execution mode, requested/prepared canonical argument bytes and hashes, current phase, physical provider receipt/digest, strict outcome bytes/hash, exact batch-parent/child identity where applicable, settlement identity, lifecycle reconciliation identity, and timestamps. Every transition is compare-and-set from the one expected predecessor phase inside a database immediate transaction; same bytes replay is idempotent, different bytes produce one typed occurrence-drift error.

The only phase enum and transition table is:

| Current phase | Sole writer and exact next phase | Restart action |
| --- | --- | --- |
| `requested` | input validator CAS to `outcome_committed(input_rejected)`, or envelope CAS to `before_preparing` with valid requested bytes/provider binding | retry validation/admission against frozen bytes |
| `before_preparing` | hook owner CAS to `before_prepared` after adapter revalidation, `outcome_committed(input_rejected)` when a normally returned replacement fails that schema, `outcome_committed(before_hook_failed)` for an observed synchronous throw/returned or awaited rejection, or `outcome_committed(before_hook_outcome_unknown)` when the process disappears without an observed return | never rerun an ambiguous hook; only an in-process captured rejection is proved failed |
| `before_prepared` | Permission owner may remain here while pending; CAS to `outcome_committed(permission_denied\|permission_expired\|permission_cancelled\|permission_stale)` for its exact terminal receipt; approved/descriptorless envelope CAS to `physical_preparing` | resume exact Permission occurrence or enter physical |
| `physical_preparing` | adapter/reconciler CAS to `physical_settled`, or `outcome_committed(physical_outcome_unknown)` | reconcile exact provider task if supported; otherwise unknown |
| `physical_settled` | normalizer CAS to `after_preparing`, or `outcome_committed` for proved failure/cancel/host contract result | rerun deterministic normalization only |
| `after_preparing` | hook owner CAS to `after_prepared`, `outcome_committed(host_contract_failed)` for an observed after-hook validation/materialization rejection, or `outcome_committed(after_hook_outcome_unknown)` when no observed return exists | never rerun an ambiguous hook; only captured deterministic rejection is host-contract failure |
| `after_prepared` | result owner CAS to `outcome_committed` | publish exact frozen bytes only |
| `outcome_committed` | settlement transaction CAS to `tool_settled` while writing ToolPart/related Parts/assistant finish and Permission outcome reference | replay settlement only |
| `tool_settled` | lifecycle transaction CAS to `settled` while CASing MCP Artifact and writing receipt/outbox; non-MCP CAS directly | replay lifecycle reconcile/outbox only |
| `settled` | none | verify identical terminal identities |

Permission pause is not a phase: its request references an occurrence held at `before_prepared`. Permission denial/expiry/cancellation atomically commits the corresponding terminal outcome. Database write failure never advances a phase. Every named phase appears once in implementation and tests; older `begin/preparing/prepared/result_committed` vocabulary is deleted.

The shared canonical encoder is versioned and runtime-independent: object keys sort by code unit, arrays preserve order, and undefined, sparse arrays, non-finite numbers, functions, symbols, bigint, cycles, accessors and non-plain objects fail with a typed encoding-contract error. It is used for arguments, outcome and provider-receipt hashes. There is no `JSON.stringify` fallback.

The terminal outcome is exactly one discriminated union:

- `canonical_succeeded`: physical success plus exact canonical result/provider receipt and hashes;
- `input_rejected`: requested or prepared input schema validation proved invalid before physical execution;
- `before_hook_failed`: the hook returned/threw a proved failure before physical execution, distinct from an ambiguous process cut;
- `permission_denied`, `permission_expired`, `permission_cancelled`, or `permission_stale`: the exact Permission occurrence terminalized before physical execution;
- `physical_failed`: the provider/executor returned a proved failure;
- `physical_cancelled`: the provider/executor returned a proved cancellation;
- `host_contract_failed`: deterministic normalization, after-hook validation, canonical encoding or materialization proved invalid after a physical outcome. Transaction/database settlement failures are excluded and leave the preceding phase open;
- `before_hook_outcome_unknown`, `after_hook_outcome_unknown`, or `physical_outcome_unknown`: the process crossed the corresponding preparing boundary but no terminal receipt proves what happened.

Each member defines the only downstream mapping. `canonical_succeeded` completes the ToolPart and may complete MCP App. Permission outcomes emit their exact Permission terminal event and settle the ToolPart with the stable denial/expiry/cancel/stale diagnostic. `physical_failed`/`physical_cancelled` fail/cancel the ToolPart, emit matching Permission events, and may reconcile MCP failure/cancel. Input/hook/host-contract/unknown outcomes settle the visible ToolPart with stable typed diagnostics but never emit physical `execution_failed`, never claim MCP terminal success/failure/cancel, and never rerun uncertain code. If no MCP App Artifact was started, lifecycle receipt is `not_applicable`. Because streaming `start` may precede execution admission, any already-started Artifact whose occurrence ends as `input_rejected`, `before_hook_failed`, any Permission terminal outcome, `host_contract_failed`, or any unknown outcome receives the typed terminal `abandoned` state with that exact outcome identity. `abandoned` means provider terminal state is unavailable, not failed. It is a durable public projection and is added to canonical interactive-Artifact event/model schemas, OpenAPI, generated JavaScript Software Development Kit (SDK) types, and API documentation. The assistant receives a normal terminal Tool message unless canonical turn control requires its atomic finish. All mappings consume this row; no old wrapper catch writes a Part.

`PermissionAuthority` creates/reuses the same occurrence before emitting `execution_started`. Its callback API returns an occurrence transition rather than an arbitrary result/throw. Only proved physical failure/cancellation maps to permission `execution_failed`/`execution_cancelled`; host-stage and unknown outcomes have distinct typed terminal events referencing the occurrence. The existing `PermissionExecutionResultTable` is narrowed to the exact reference `{attempt_id, occurrence_id, outcome_sha256}` and stores no raw result, canonical result, provider receipt, diagnostic, or competing terminal payload. All replay, `toModelOutput`, lifecycle, and reconciliation readers resolve that reference to the occurrence row and validate the hash. `reconcileInterruptedAttempts` is removed from eager state initialization. The sole startup order is occurrence integrity/phase recovery, then Permission attempt reconciliation from occurrence outcomes, then approved continuation, then generic assistant interruption. A descriptorless builtin/internal/batch call also creates this row before execution, so no executable source bypasses the authority.

The exact-continuation comparison proves the request fingerprint derived from prepared arguments. A changed provider binding, prepared input, Tool identity, execution mode or permission classification remains stale through the existing authority. A preparation or result receipt with the same occurrence identity but different canonical bytes raises one typed occurrence-drift error; it never chooses a winner by last write. No second permission reader, hook receipt table, or fallback to raw arguments is added.

### 3. One canonical hook/result contract

Define one canonical Tool result used by all four sources and by the public `tool.execute.after` output:

- required `title`, `output`, and `metadata`;
- optional materialized/stamped `attachments`, `display`, and typed `sources`;
- no raw MCP `content`, transport object, or provider-private lifecycle state.

Update the Plugin ABI so these optional canonical fields are typed rather than passed accidentally through structural typing. The hook may mutate/replace canonical fields except the `CS-005` host-owned control, whose exact preservation is checked after the hook. The envelope validates the result and runs the same materialization/stamping pass after the hook, so a Plugin-added data URL becomes a canonical attachment reference and a Plugin-added display/attachment gets the exact Session/Message identity. Provider-private raw payload first passes the adapter-owned strict schema and canonical encoder, then is retained only as `provider_receipt` bytes/hash in the versioned occurrence row, never in the hook object or Permission result reference. The occurrence row is the single restart-safe source for MCP `toModelOutput`, protocol-task recovery and MCP App reconciliation; no process-local raw result or regenerated payload is accepted after replay.

MCP App streaming `start`/partial input remains a provider-stream observation owned by the processor, because it occurs before execution. Final canonical input and physical invocation move through the envelope lifecycle adapter. Terminal `complete | fail | cancel | abandoned` is a post-authority compare-and-set reconcile keyed by `{occurrence_id, outcome_kind, canonical_result_sha256, provider_receipt_sha256}`. `interactive-artifact/persist.ts` atomically changes only the expected nonterminal Artifact to that terminal tuple and writes a `lifecycle_reconciled` occurrence receipt plus durable Bus outbox in the same transaction. An identical tuple replay is a no-op, a conflicting tuple is typed drift, and terminal state never regresses. Bus publishes only the committed outbox and is deduplicated by occurrence. Success comes only from `canonical_succeeded`; fail/cancel only from their proved physical outcomes; `abandoned` comes from every committed outcome that lacks a proved provider terminal receipt: `input_rejected`, `before_hook_failed`, all four Permission terminal outcomes, `host_contract_failed`, and the three unknown outcomes. An occurrence with no MCP Artifact records `not_applicable` while advancing `tool_settled -> settled`. A crash on either side of the Artifact CAS converges through this same reconciler, so no active Artifact is left behind by a settled occurrence.

For batch, the parent `batch` call remains one ordinary occurrence with its own hook pair. Before any child preparation or hook starts, the parent occurrence atomically publishes an immutable ordered batch manifest containing every child occurrence ID, requested Tool/provider binding, requested-argument hash and target Part ID. Prepared arguments and their hashes belong only to each child occurrence after that child's own `before_preparing -> before_prepared` transition; they are not predicted or copied into the parent manifest. Recovery after a pre-manifest cut creates the manifest once from the still-frozen parent request. Recovery after publication advances only those exact children through their own durable occurrence phases and rebuilds the parent aggregate from their outcomes; it never reallocates IDs, reruns an ambiguous child hook, or restarts a settled/unknown child. The parent aggregate and parent hook pair commit once after all manifested children settle. Thus a cut after child one of two performs each physical effect once and retains the same child IDs.

### 4. One atomic Tool settlement decision

The envelope is the only owner of the exact phase enum and compare-and-set transitions in section 2.1. `SessionProcessor` remains the low-level, call-locked persistence port because it owns the assistant Message, but it no longer independently decides terminal state from SDK `tool-result`/`tool-error` events.

- Provider `tool-call` events may create the initial open Part and stream input/provider metadata.
- The envelope adopts that exact Part (or creates a child/recovery Part through the same port), records preparation, and asks one database transaction to write the ToolPart terminal state, all attachment/display/source Parts, and—when the strict canonical result contains `opencorvusToolResultControl`—the assistant's durable finish/time. No observer can see a terminal ToolPart without its related Parts or a control-bearing result without the matching assistant settlement.
- There is no persisted disposition row. `ToolResultDisposition` is only an in-process projection of the control stored in the canonical ToolPart metadata. The later SDK result/error event rereads the committed Part, verifies the canonical hash, and sets only this Turn's in-memory park/handoff state; it cannot write a second terminal value or consult a parallel decision fact.
- Permission continuation calls the ordinary rebuilt Tool adapter. It deletes `completeRecoveredToolPart`/`failRecoveredToolPart`; the envelope either advances the occurrence or resolves the Permission result reference back to the exact occurrence outcome and settles through the same port.
- Batch deletes direct `Session.updatePart` child settlement and uses the same port. Live metadata updates are serialized by that port and preserve the execution receipt. Batch target eligibility and top-level sibling coordination continue to use the exact `CS-005` `executionMode`; `turn_control_exclusive` Tools remain excluded from batch and cannot race ordinary siblings through the envelope.

This keeps one decision owner without moving raw database writes into every adapter. A committed effect result with a later persistence failure stays recoverable instead of becoming a false Tool error. The required transaction is implemented directly against the existing Message/Part tables plus the occurrence row; no optional settlement manifest or alternate path is allowed.
