## Cut 1 — B1 Task-root decision repair Host gate

### Analysis

- **Observable behavior:** after one Task-root Provider step ends without a committed decision receipt, Session loop sets `toolChoice: "required"`; after the next gap it also removes every Tool without a decision declaration. The model no longer sees the same inspection and decision surface it was originally asked to reason over.
- **Direct trigger:** `taskRootDecisionRepairRung`, `taskRootDecisionRepairToolSurface`, the conditional replacement of `tools`, and `processor.process(... toolChoice)` in `session/loop.ts`. The dedicated test asserts the forced/narrowed ladder rather than a domain result.
- **Control-flow root:** the Host converts a semantic model-output gap into workflow-routing authority. The real finite convergence owner is already the Task-root semantic Turn budget and reducer; changing Provider tool-choice and hiding current facts is a second policy mechanism, not a data-integrity check.
- **Why the old path does not cure it:** forcing an arbitrary Tool can produce another inspection call, while hiding inspection Tools can force a lifecycle decision without current evidence. Both alter the model's choice instead of improving prompt/context/Tool definitions. The bounded exhausted/operator-visible settlement already handles repeated non-decisions.
- **Affected surface:** Session loop Provider request options, Task-root prompt projection, decision-repair test, Dynamic frontier decision declaration and documentation. No persisted schema, API, Message visibility, retry budget or Provider streaming mode changes.

### Single-source repair

Keep the bounded semantic-gap count and its visible repair guidance inside the same streamed assistant Turn. Remove the rung type, forced `toolChoice`, decision-only Tool filtering and related logging. Every retry sees the exact originally projected Tool surface and ordinary Provider `auto` choice; the Host continues to validate only whether a committed decision receipt exists and lets the existing finite budget reach its durable operator surface. Delete the obsolete gate-focused test because no replacement Host policy exists; positive Task-root decision/recovery and Dynamic real-provider contracts remain the behavior evidence.

Run the focused Task-root reducer/decision/terminal contracts, Dynamic deterministic/frontier contracts, OpenCorvus typecheck, exact module topology and diff checks. Then obtain an uninvolved read-only review of code, removed test, this record and regression evidence before commit/push.

## Cut 2 — A2 exact dispatch delivery owner

### Analysis

- **Observable behavior:** a current dispatch lineage may omit its delivery owner. A backend that cannot see another backend's process-local pipeline then treats the lineage as live only until `time_created + 90s`; after that it may terminalize a worker which is still running remotely.
- **Direct trigger:** `recordDispatchLineage` catches failure to derive a runtime occurrence and writes no `owner_process_occurrence_id`; its public input also accepts `null`. `dispatchDeliveryOwnerIsLive` interprets the absent field through commit-time grace. The Base dispatch and coordination redispatch production paths both use this writer without an explicit owner authority.
- **Control-flow root:** the immutable lineage commit is admitted independently of the runtime-process control lease that owes its delivery. Process liveness already has one process-wide fenced owner and Task-control activation already requires it, but the lineage transaction does not assert that fence. Recovery consequently has no durable identity to query and substitutes elapsed time for ownership evidence.
- **Why the old path does not cure it:** process-local pipeline and prompt registries are valid fast paths only for this backend; they cannot prove peer death. A grace period only delays the same unsupported inference and can both kill slow live work and postpone genuine crash recovery. Silently omitting owner identity also lets a dispatch report accepted although its required recovery authority was never committed.
- **Production entry coverage:** the only production lineage writes are the initial `dispatch_agent` commit and coordination redispatch binding in `orchestrator/tools.ts`; both run inside a Task-control-owned streamed Orchestrator activation. Direct test writers are fixtures, not additional product admissions. Terminal lifecycle replay, existing dispatch settlement replay, abandoned interruption, restart scans, sibling dispatches, workflows and multi-Project shared-process ownership all converge through the same lineage reader and Task-control scan.
- **Definitions and persisted data:** the current strict JSON payload still makes `owner_process_occurrence_id` optional, and the SQL insert trigger protects only `adapter_input`. Existing databases may therefore contain three historical ownerless classes: an existing dispatch settlement, an exact terminal `agent.execution.lifecycle`, or neither. Current repository data does not prove which classes occur in every deployed database, so migration must handle all three without selecting a latest Message or inventing a successful outcome.
- **Tests and documentation:** the cross-process suite currently enshrines one-lease grace and directly injects arbitrary owners. Positive replacement evidence must prove a live peer lease is preserved, an expired exact peer lease is recovered, admission without the current process fence returns a typed error, and every historical class migrates to one explicit owner disposition. `task-control-plane.md` must remove the grace exception after the migration and writer land.
- **Delivery and risks:** rewriting an immutable payload is allowed only inside the one startup migration before current trigger reconciliation and integrity checks. Every rewritten Artifact must retain its ID/catalog revision and recompute the canonical payload/catalog metadata in the same transaction. Ownerless history with a settlement or terminal lifecycle binds that exact source; history with neither receives deterministic infrastructure-error and dispatch-settlement Artifacts, never a synthetic terminal success. A failed migration rolls back both trigger removal and data writes.

### Single-source repair plan

Replace the optional scalar with one required `delivery_owner` discriminated fact. Current writes may create only `{ kind: "runtime_process", process_occurrence_id }` and must assert that process's current liveness fence inside the same SQLite writer transaction as the lineage. Historical migration may create only `{ kind: "historical_reconciliation", source }`, where source is the exact existing dispatch settlement, exact terminal lifecycle event, or the deterministic infrastructure settlement created in the migration. Recovery reads this one required fact: runtime owners use local fast paths plus exact lease liveness; reconciled history is already classified and is immediately replayable. Delete the optional writer input, exception swallowing, time-created lookup and grace branch; no compatibility reader remains after migration.

### Required verification

Add focused positive migration and process-owner contracts, then run cross-process dispatch recovery, abandonment, production Orchestrator dispatch, storage integrity/migration contracts, OpenCorvus typecheck, docs, architecture index, candidate module topology and cached-diff checks. Freeze the complete input for uninvolved read-only review before committing and pushing this cut.
