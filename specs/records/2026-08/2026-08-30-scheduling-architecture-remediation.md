### Consolidated current-source analysis

1. **Task wait has four competing current-state authorities.** Creation writes an Automation delay; due execution creates an Automation run and Task ingress atomically; early activity is guessed from process-local Bus Message/Part notifications and separately claims, dispatches and tombstones waits; prompt rendering directly scans definition revisions without tombstones. The same business intent can therefore be active, consumed and described as future at once.
2. **The ownership transfer is split around the real business input.** Operator root Messages already accept a Task ingress but are deliberately skipped by the Bus subscriber, so the old wait remains due. Other activity dispatches a synthetic `task_wait_activity` ingress before tombstoning each wait. A crash between those operations produces two semantic Turns. Generic durable Bus delivery cannot repair this because it owns callback delivery, not the relation between an accepted Task ingress and the wait it supersedes.
3. **Wait identity omits Task execution epoch.** A delay created in epoch E1 is validated only against whatever epoch is current when its Automation run later persists ingress. Terminal/reopen therefore turns an E1 intent into valid E2 work. A deterministic job/fire ID prevents physical duplicates but cannot correct the wrong lifecycle binding.
4. **Operator surface treats attempted persistence as acknowledgement.** The helper catches its own write error and returns `void`; the exhausted branch then permanently memoizes the ingress. The deterministic Artifact identity makes retry idempotent but does not prove the first write succeeded.
5. **Scheduled Tool effects lose their request occurrence at the domain boundary.** Wait, Automation definition revisions/tombstones/manual run and Event revisions/tombstones use random or time-derived domain identities without the persisted Tool Part/call and canonical input. A process can commit the real effect, die before Tool outcome persistence, and recover the visible Part as an error; reissuing the intent creates another effect. Permission evidence fences authorization but cannot reconstruct the business result and must not become a second scheduler state.
6. **Automation retry creates a new logical fire.** Projection assigns a failed run's `retry_at` to definition `next_run`; the next execution hashes that changed timestamp into another fire. Project fan-out then reserves all targets again, including targets that already succeeded. Permanent target absence and terminal/stale lifecycle mismatches are stored as transient retries with no absorbing disposition or finite policy.
7. **Bounded slots reuse the poll snapshot as physical claim time.** A worker that waits behind a long target still validates and acquires its lease with the old poll timestamp. It may begin with a lease already expired in real time, lose its terminal write fence and make no progress. The queue bound is necessary; only the reused clock is wrong.

The direct triggers are ordinary operator input, Session input near a due delay, process death between a domain commit and Tool outcome, partial Project fan-out failure, permanent target disappearance, and a queue wait longer than one lease. None depends on model wording or nondeterministic selection. Earlier fixes strengthened due-path transactions, Bus delivery and Mission reservations but left the split authorities intact, so they could not eliminate these cuts.

### Single-source design

#### 1. Native epoch-bound Task wait

Add one immutable Task-control registration and one immutable settlement relation:

```text
task_wait_registration(
  wait_id, task_id, execution_epoch, due_at, reason,
  exact Tool request occurrence, canonical input digest, created_at
)
task_wait_settlement(
  wait_id, disposition = due_ingress_accepted | superseded,
  exact Task ingress id, settled_at
)
```

The current reducer joins registration, settlement and Task lifecycle facts. `scheduled` exists only while the exact epoch remains active and no settlement exists; terminal same-epoch or any later epoch projects `terminal_inapplicable` from the lifecycle fact without inventing another status row. The earliest current due registration joins the existing Task-control driver's wake calculation. Its deterministic due ingress and `due_ingress_accepted` settlement commit in one immediate transaction. Every other qualifying accepted Task ingress settles all still-current registrations for that Task/epoch as `superseded` in the same transaction. The due ingress is the only excluded supersede source because it names its exact wait directly.

Delete the Automation `task_id` delay branch, Task activity Bus subscribers, `task_wait_activity` synthetic Turn, prompt-specific Automation scan and Task-wait Automation helpers. Existing Session delay remains an Automation one-shot, but real Session user Message admission must consume its exact pending delay in the Message transaction rather than a post-commit Bus callback. No current reader consults legacy Task-delay Automation rows after migration.

The Session boundary is the transaction that changes the exact persisted user Message from pending delivery to an assistant's accepted input. Its synchronous scheduler hook receives `(db, sessionID, acceptedInputMessageIDs, assistantMessageID, now)`, may only compare/acquire the one-shot definition lease and append its tombstone/consumption fact, and performs no I/O. If the due owner already owns the live lease, acceptance records that exact due occurrence as winner and does not create a second reminder activation; otherwise the accepted assistant consumes the current delay. The hook extends the upstream occurrence-bound `beginAssistantReplyWithCommit` transaction rather than adding a second Message writer. An ancestry audit (`git log -S beginAssistantReplyWithCommit` plus blame of the exact writer) proved that callback is the reviewed `139fff2f9` authority; the local reverse hunk is a stale pre-merge blob, not newer product semantics. Cut 5 may therefore restore/extend only that exact callback hunk while leaving every unrelated formatting change unstaged.

#### 2. Exact scheduled Tool occurrence

Use the persisted Tool request Part as request authority. Tool-created Task wait registrations, Session-delay/recurring Automation revisions and tombstones, Event revisions and tombstones, and manual Automation fires carry the exact `session_id`, `message_id`, `tool_part_id`, `tool_call_id` and canonical input digest. A unique Tool-causation constraint makes replay read the existing domain fact and validates identical input; drift returns one typed occurrence-conflict error. The domain fact remains the only business state — there is no generic scheduled-effect shadow queue.

Session dead-owner recovery examines pending schedule/wait Tool Parts before generic interruption settlement. If the exact domain fact exists, it reconstructs and persists the normal Tool outcome on that same Part. If no fact exists, normal interruption remains truthful. A manual run is write-ahead: the Tool occurrence fixes the fire identity before any Message/Session/Provider effect, so replay can resume/read the same run rather than create another. Non-Tool HTTP/API callers use their existing explicit request boundary and never fabricate Tool causation.

#### 3. One immutable Automation fire

Each immutable `automation_fire` stores the exact scheduled due boundary and definition revision; manual Tool occurrence fixes its fire identity. Every physical owner appends one fire attempt in the same immediate transaction as Fire creation/replay and lease acquisition. A pre-reservation failure settles only the attempt. Once target runs are reserved, target receipts append under the same runs/fire and never rewrite the definition's next logical due. Projection reads Fire directly, so an owner crash before any run remains visible. Claim resumes the incomplete fire; target runs already terminal as `succeeded`, `failed` or typed `disposition` are not executed again.

Transient attempts are finite under one frozen policy. Exhaustion appends a terminal failed receipt visible in history. Current permanent target outcomes are `target_deleted`, `mission_closed` and Session-delay `superseded`; they are absorbing. The recurrence advances only after the current fire is terminal; no poison occurrence can create an unbounded family of fire IDs.

### Consolidated current-source analysis

1. **Pure `closing` has no restart owner and cannot replay its own effect.** The event persists before physical cancellation, but startup does not enumerate latest pure `closing`. Its strict payload holds only Mission/request identity, while the actual cancellation surface/reason and algorithm live in a route-local callback. A later abort/archive/delete therefore resumes the old operation with a new request's effect input, then records the old source/request in `closed`.
2. **A peer backend can commit `closed` while the real Mission Prompt still runs.** The close callback cancels only process-local `SessionPromptState`; absence of a local controller is treated as settled without reading the durable `SessionPromptOwner`. The terminal transaction asserts only the lifecycle lease, so a remote streamed Provider/Tool Turn may continue after `closed` or deletion.
3. **The Mission closure cut does not cover wake admission.** Operator, Scheduler Message, Automation and Event paths read `opened` before the real Message bundle transaction. Another backend can commit `closing`, settle the then-visible wakes, and still have the first backend commit a new Message and acquire a Prompt owner afterwards. The same request also lacks deterministic Message identity/fingerprint, so replay can duplicate a wake or execute an old request after `closed`.
4. **The closure cut does not cover Mission-owned Task creation.** `panel.create_task` may cross the close snapshot: close enumerates existing children, the Tool then commits a new active Task, and `closed` follows without cancelling it. Task creation must compare-and-set the exact current `opened` occurrence in its own commit transaction.
5. **Process recovery does not prove physical owner death.** Startup selects every trailing incomplete Mission assistant and immediately terminalizes its Tool Parts, Provider activity and Message. It never reads the durable Prompt owner whose `exact_live`, `unknown_live` or `dead_or_reused` observation is the only cross-process liveness authority. A new backend can therefore corrupt a peer backend's live streamed Turn.
6. **`mission_process_recovery` is a second mutable queue without a fenced first claim.** The marker copies interrupted assistants, attempt and three wake identities, is amended on retry, and is cleared by a process-local completion callback even though the real wake Message/control/reply already persist those facts. Two backends may both observe no marker, create different random requests, and only discover the contradiction after both inserts.
7. **Recovery is neither well-founded nor continuously driven.** Attempt increments and wake identity rotation are unbounded and are not bound to the immutable Mission execution operation. A failed recovery reply leaves a marker but no same-process driver; the next attempt usually waits for another process restart. There is no durable exhausted/operator-visible disposition.
8. **B4 close ownership is an unbounded busy join with an ineffective abort.** A loser polls every 10–100 ms indefinitely; an owner renews forever without an occurrence deadline. Lease loss aborts a controller, but the production callback ignores its signal and neither child Task waiting nor Mission Prompt settlement observes the outer fence.

These are not eight unrelated patches. They arise because `opened/closing/closed`, route callbacks, process-local locks, the mutable recovery marker, real wake Messages, Prompt ownership and Task creation each claim part of the same Mission occurrence. The old P0 wake settlement closes only already-materialized Scheduler Messages and cannot exclude a writer that has read `opened` but has not committed its Message or Task yet.

### Single-source design

The one reducer is:

```text
Mission execution occurrence
  opened(operation)
    exact operator/non-operator activation -> real Message + reply
    exact dead Prompt-owner recovery       -> same real recovery Message + reply
    Mission Task creation                  -> Task creation fact
  closing(operation, durable cancellation provenance)
    Mission Prompt owner settled or proved dead
    stable child Task set converged by each Task's own cancellation request
    materialized scheduler wakes settled
  closed(operation)
```

Protocol events and real Message/Task/Prompt-owner facts are business truth. A generic control lease gives one physical reconciler a fence; it never becomes a second status. The implementation proceeds through the following inseparable boundaries:

1. **Replayable close request.** `closing` stores strict normalized cancellation provenance that the Protocol envelope does not already own. Current writes use request provenance; a one-time migration rewrites historical closure events to an explicit `historical_reconciliation` provenance without pretending to know the lost user surface/reason. Delete the opaque close callback. First execution, HTTP retry and startup all invoke one Mission-domain reconciler whose effects are derived only from the winning `closing`.
2. **Finite fenced close owner.** Acquire the existing Mission lifecycle lease once. A live contender receives the typed current `closing` projection instead of busy polling. The owner has an explicit deadline; lease loss and deadline share one `AbortSignal`. The signal stops the current wait/new effect admission, while already-durable child Task cancellation requests continue through their own reconciler. `closed` commits only with the exact lease, exact unchanged `closing`, no live durable Mission Prompt owner, no active Mission child Task and settled closure wakes.
3. **Atomic activation fence.** Every Mission wake Message bundle preflights the exact current `opened` event inside the same immediate transaction. Operator reopen commits its new `opened` event in that bundle. Request-derived Message/TextPart/control identities and a canonical input fingerprint make exact replay one occurrence and drift a typed conflict. Prompt-owner acquisition revalidates the Message-bound `opened` occurrence so a persisted Message cannot start physically after `closing`.
4. **Task creation fence.** A Mission-created Task carries the exact source Mission opened event/operation through its existing creator authority. The Task insert transaction revalidates that occurrence. A close that wins first produces the typed closure conflict; a Task that wins first is in the stable post-fence child set and is cancelled by the same close.
5. **Razor recovery.** Delete `MissionProcessRecoveryMarker`, the `mission_process_recovery` SessionControl kind, payload amendments, random wake rotation and completion callback cleanup. A recovery request is deterministically derived from the exact `opened` event, dead Prompt-owner generation/process occurrence and interrupted assistant set. The request's one real wake Message, consumed `wake_reason` control and reply are its only ingress/outcome facts. Live or unknown peer owners remain running; only a proved-dead exact owner can be terminalized. The same lifecycle owner serializes recovery with close, and the wake bundle rechecks the exact `opened` occurrence before commit.
6. **Finite recovery policy and driver.** One recovery semantic wake is allowed for one dead Prompt-owner occurrence. Physical replay resumes the same Message; it does not mint another semantic request. Its terminal reply is the disposition. A bounded per-Mission-operation recovery policy projects `exhausted` from immutable requests/replies and exposes the final real error reply to the operator. The unified Mission startup/reconciliation candidate includes latest `closing`, dead-owner interrupted work and persisted unanswered recovery wakes; independent Missions within one Project run with bounded concurrency while Scheduler delivery drains concurrently, so one stalled activation cannot serialize its siblings or ready delivery.
7. **Migration, then deletion.** Before current readers run, migrate strict historical closure payloads and validate every legacy process-recovery marker against its real Message/reply/current closure. An unanswered real Message is upgraded to the strict current wake reason; every legacy marker family is then deleted because those real facts are the authority. The migration creates no replacement classification queue. Current code never reads the old kind after migration. Migration is one immediate transaction, idempotent, fail-closed on identity conflict and covered by full schema-drift checks.

The process-local admission/active-operation maps may remain only as non-authoritative latency joins while the cut is implemented; they must be deleted if no longer needed by the final reducer. No compatibility read, optional provenance or fallback recovery route remains.
