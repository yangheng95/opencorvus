### Stage 4 shared root-cause and implementation boundary

The common observable failure is a final directory or file set that is physically present but has no durable proof that the exact producing occurrence completed. The direct triggers are process death between rename/copy/install/populate steps and another process reading or mutating the shared root. The control-flow root is five in-memory protocols whose booleans, locks and catch rollback disappear with their process; the data-flow root is that readers inspect final paths and metadata instead of one immutable completion receipt bound to the produced revision. Atomic rename or atomic JSON replacement prevents torn writes but cannot make several filesystem and metadata authorities one commit.

Stage 4 therefore introduces one host-independent durable-publication protocol in the lower `@opencorvus-ai/util` package. Each occurrence has a UUID, kind, immutable intended targets and identities/digests, durable no-replace phase facts, caller-derived path validation, and exactly one terminal `committed` or `rolled_back` receipt. A subsystem-specific owner may prepare or validate bytes, but it may publish readiness only from that terminal receipt; restart/retry enumerates nonterminal occurrences before catalog/discovery/import projection. The protocol does not infer ownership of unknown residue and never deletes a path whose identity/digest it cannot prove.

The five migrations are bounded as follows:

1. ARC-015 binds the exact Project ID and database `generation`, configured/physical source, destination and scratch paths. Recovery fences the current database row before forward relocation or rollback and runs before any server/ACP project exposure and before retrying promotion.
2. ARC-020 binds the complete multi-Skill target set, before/after directory digests and the global-config revision. Recovery exposes either the complete before catalog or the complete after catalog; per-directory booleans and direct canonical replacement are deleted.
3. ARC-021 installs an exact dependency tree in an isolated generation, verifies the resolved manifest/lock/package entrypoints, and publishes a completeness receipt/current generation under a cross-process owner. Both shared registry packages and per-config dependencies use it; module existence and requested-version metadata cease to be readiness.
4. ARC-022 records created, populated and ready phase facts bound to primary worktree identity, branch/base and Task/Session owner. `reuseIfValid` and recorded recovery require the ready receipt in addition to Git linkage; an incomplete occurrence resumes population or converges removal before a sandbox/Ready event is exposed.
5. ARC-034 keeps every generated SDK/OpenAPI artifact in one verified generation and publishes one durable current-generation receipt/pointer. The six public paths are materialized only from that one generation and recovery finishes or rolls back a journal before removing staging/backup evidence; mixed generations are rejected by the manifest.

Impact includes public Project promotion results, Skill inventory/policy, Plugin and Provider imports, Build Worktree Ready events, generated OpenAPI/SDK/docs and packaging. No route shape needs to change for ARC-015/020/021/022; ARC-034 may add a generated manifest but not a compatibility reader. Focused tests must cut each durable boundary and prove recovery to one complete old/new outcome, including a real child-process/cross-process case for shared roots. Current architecture documentation is updated with the single publication fact owner before Stage 4 closes.

### ARC-015 implementation — generation-fenced Project promotion publication

The pre-existing draft mutable `project-promotions.json` map was not retained. It could not bind an immutable occurrence, did not fence a deleted/recreated Project generation, selected forward recovery from destination existence alone, and ran only after the server listener was exposed. ARC-015 now owns the first consumer of the shared durable-publication fact store: one immutable intent records operation ID, exact Project ID/generation and all source/quarantine/staging/destination paths; append-only `prepared` and `published` facts record the digest of the completed staging tree and publication boundary; one non-replaceable `committed` or `rolled_back` receipt settles the occurrence.

The first implementation review proved that immutable filenames alone were insufficient: a process could die after creating a final JSON file but before completing its bytes, two backends could race `listOpen -> create`, and recovery still lacked path/content ownership and an exact database before-snapshot. The repair publishes each fact from a fully written and file-synchronized same-directory temporary through an atomic no-replace link and parent-directory sync. An occurrence intent is completed inside a staging directory and the complete directory is atomically published. One cross-process subject lock serializes create/phase/terminal and the whole Project operation; phase rechecks terminal after acquiring the lock, so no phase can appear after settlement.

Promotion now binds the exact source-tree digest, a complete Project/Session relocation snapshot, and scratch paths deterministically derived from the operation ID. Every recovery validates absolute paths, exact parent/name derivation and non-overlap before removal. A source/quarantine double-presence preserves both and blocks. A destination-mapped database with no destination uses generation/worktree-fenced Project restoration and an exact Session-set/projection check in one SQLite transaction; any concurrent mutation leaves the occurrence open. Forward relocation is likewise a conditional `id + generation + expected worktree` update and Session relocation occurs only after it succeeds.

The repeat review found three further shared-boundary defects. First, acquiring the database fence before publishing the intent left a kill window with an orphan fence and no recoverable occurrence. The final admission order is therefore: read the complete Project/Session before-snapshot, digest the source, durably publish the intent, then in one immediate SQLite transaction re-read and deep-compare that complete snapshot and acquire the exact Project-generation/operation fence; the first filesystem rename happens only after both facts exist. A death after intent publication but before fence acquisition is now an ordinary open occurrence that startup fences and rolls back. Second, direct Project and Session writers could bypass an application-only fence check. SQLite triggers now reject every external Project update/delete and Session insert/update/delete while the persistent fence kind is `promotion`, using one deterministic `project_promotion_fenced` error contract. The promotion transaction temporarily changes its exact owned fence to `promotion_commit`, performs the conditional Project and Session relocation or restoration, then restores `promotion`; uncommitted transaction state is not visible to other database connections. Third, a terminal receipt could be observed before public projection was safe. Project `get/list` exclude rows carrying the persistent promotion fence, historical terminal occurrences are replayed only when that exact generation/operation still owns the fence, and terminal settlement is followed by fence release before the Project event and HTTP success.

The committed terminal is the sole durable Ready decision; the exact fence is the projection barrier that keeps that decision and the relocated database state invisible until startup or the live owner releases it. The destination digest is checked against the prepared fact immediately before database relocation, while it is still unpublished staging content. After the exact Project/Session relocation commits, destination is a live worktree and recovery relies on the generation-fenced database projection rather than rejecting legitimate content changes. Quarantine cleanup must still succeed before terminal settlement, and only after settlement plus fence release may the Project update event and HTTP success be emitted. `cleanupPending` remains in the public response schema but every successful result is `false`; cleanup failure is an error with an open recoverable occurrence, never a second success state.

`prepareServerRuntimeForListener` runs promotion recovery before process/workspace cleanup and before `Server.listenPrepared`; the duplicate post-bind call is deleted. Focused verification includes seven real killed-child fact-publication cutpoints, a real child killed exactly after durable occurrence publication and before fence acquisition, a real child killed after terminal publication and before fence release, one real two-backend race over one persisted Project generation, forward and backward crash recovery, source/quarantine ambiguity preservation, destination-mapped database rollback, the Project/Session trigger contract, malicious path rejection, ordinary completion, lost-terminal recovery, foreign-generation preservation and listener ordering. The combined focused run is **25 pass, 0 fail, 64 assertions**: durable store **2 tests**, Project journal **12 tests**, and startup recovery **11 tests**. Both package typechecks, the documentation checker and `git diff --check` pass. The dependency install attempt encountered registry `ConnectionClosed`; the already-installed exact `proper-lockfile@4.1.2` and type package remained usable and the workspace lock manifest was updated from its existing locked entries. The final uninvolved repeat review independently reran the same checks and returned **PASS with no unresolved P0–P2**.

## Stage 1 — Renderer privilege containment (ARC-030)

### Analysis

- Observable behavior: any renderer script or DevTools expression in a release build reads `window.settingsStore.password` in plaintext and calls `window.applyDirectory`, `window.loadTasks`, `window.selectTask`, `window.loadBoard` and `window.persistOverlaySettings`, which are live production mutators, not observers.
- Direct trigger: `installGlobalBridges()` runs unconditionally at renderer start, and `window.openWorkspaceDiff` is assigned unconditionally at module scope.
- Control/data-flow root cause: diagnostic observation was implemented by publishing production containers and functions on the global object. `packages/overlay/src/services/workspace.ts` then consumed `window.persistOverlaySettings` for real persistence, so the bridge became a production control-flow edge instead of an isolated hook.
- Why the existing path does not cure it: host transport capability checks constrain host calls, not same-renderer global reads. Nothing in the renderer gates the bridge by build mode.
- Definitions, callers, contracts: the repository search above proves the entire consumer set is inside `packages/overlay/src`, and that `workspace.ts` already imports `saveSettings` from `../store/settings`, so the global indirection is redundant rather than load-bearing.
- Data, tests, documentation, delivery: no durable data changes. No test consumes the bridge. No document declares it as a contract. Delivery is the Overlay renderer bundle only.
- Excluded as not applicable: server, engine, database, permission and scheduler surfaces are untouched by this stage.

### ARC-037 — Permission effect leases were abandoned, not released (new finding, implemented)

- How it surfaced: with ARC-036 cleared, the same checker advanced to MCP task recovery and failed with `Permission execution per_… did not settle before Session deletion`.
- Trigger and impact: an execution attempt interrupted while its durable MCP task is still open keeps its 120-second `effect` control lease. Recovery in the next process calls `acquireEffectLease`, cannot take the abandoned lease, and `awaitExecutionSettlement` polls for only ten seconds before failing. Every recovery inside the lease window fails deterministically.
- Root and failed cure: `executeUnderEffectLease` in `permission/authority.ts` only cleared its renewal interval in `finally`; `completeExecution` and `appendEffectOutcome` fenced the lease but never ended it, and the two "durable task is still open, rethrow" branches returned without releasing ownership. This is exactly ARC-036's defect on the Permission authority's own lease target, which the audit's ARC-036 boundary scoped only to Automations.
- Change: `completeExecution` and `appendEffectOutcome` release the attempt's lease inside the transaction that writes its terminal receipt, and a new `abandonEffectLease` releases ownership on both paths that deliberately leave the attempt open for recovery.
- Evidence after the change: the checker passes MCP task recovery and the SSE, CLI and ACP transport hydration steps that follow it.

### ARC-038 — Attached public clients have no terminal signal on a non-Task Session (new finding, open)

- Trigger and impact: `opencorvus run --attach <server> --session <id>` converges only on `agent.execution.lifecycle` with a terminal status for its session (`cli/cmd/run.ts:556-564`). When the Session settles through the restart-safe settled path, that event is published on no transport the CLI can see, so the CLI does not exit when the session is aborted — it waits out its stall timeout instead.
- It is nondeterministic, which is why it must not be downgraded. Before the second review's repairs, two consecutive `check:permission-modes` runs on the same source disagreed: the first reported `{"status":"passed"}` with `transports.cli` bound to the exact permission request; the second failed with `Attached CLI did not exit after the transport session was aborted`.
- Current observation, stated as observation and not as a fix: after the second review's repairs — in particular `session/control.ts`'s early-return release and `session/loop.ts`'s settlement-conflict releases, which stop a dead compaction owner from holding a `session_control` lease while the prompt tries to settle — the checker passed three consecutive full runs. ## ARC-009 — Shared data root versus process-local mutation locks

### First half: no shared fact is replaced from a snapshot the writer did not read under the lock

- Root cause as recorded by the audit: `withKeyedLock` is a process-local `Map`, while the current data architecture explicitly supports several backends over one data root. Two processes read the same snapshot, update different keys, and the later atomic replacement discards the earlier update. Atomic replacement prevents torn bytes, not lost updates.
- The repository already had the correct pattern in exactly one place: `provider/models.ts` wraps its keyed lock in `withProcessLock` and re-reads inside it. This change generalizes that pattern rather than inventing a mechanism: `withSharedJsonFactLock` in `util/process-lock.ts` provisions the fact file with the empty representation its readers already synthesize, takes the process-local writer queue, then takes the cross-process lock, and runs the read-modify-write inside it.
- Applied to every mutable shared JSON fact the audit named: `config/config.ts` (`writeConfigFile`, both project and global), `auth/index.ts` (`set`/`remove`), `mcp/auth.ts` (`updateStore`/`removeMany`) and `expert-squad/configuration.ts`, which had only a module-level promise chain.
- Contention policy converged: `CROSS_PROCESS_LOCK_RETRY` is now declared once in `util/process-lock.ts` and consumed by the JSON fact lock, by `expert-squad/install-lock.ts` (which had declared its own copy) and by `provider/models.ts` (which had none, so a contended catalog write failed instead of waiting).
- Focused positive test: `test/shared-json-fact-lock.test.ts` spawns a second OS process that holds the critical section while this process performs its own read-modify-write, and asserts both updates survive. Without the cross-process lock the peer's write lands last and drops this process's key entirely.

### Second half: the revision is a durable fact, not a process-local counter

- `mcp/auth.ts` kept its compare-and-swap value in a process-local `Map`. A revoke performed by another backend on the same data root was invisible, so a stale holder's write succeeded and resurrected a credential that had been revoked.
- The value now lives in the store as `Entry.revision` — a revocation generation, random, minted only by `invalidate`, preserved by ordinary writes, compared inside the same cross-process lock as the read-modify-write. The first cut of this (a bump-per-mutation counter) broke MCP OAuth and was repaired in the fifth review round, recorded below.
- `revision()` is async now, because the answer comes from the file. Its six call sites await it.
- Focused positive tests in `test/mcp/auth-durable-revision.test.ts`: one captured generation survives a five-write flow; a revoke refuses the old holder and admits the new one; a peer's revoke through the shared file is visible; a pre-removal generation never matches a post-recreation one.

### Still open in ARC-009

Peer caches are still invalidated only in the writing process — `Config`'s `state.reset()`/`global.reset()` and the `config.changed` Bus event do not cross a process boundary. A second backend keeps serving its cached configuration until something in that process resets it. The durable facts are now correct; their propagation is not.

## ARC-017 — a provider OAuth authorization is a durable flow occurrence

- Root cause as audited: a provider OAuth authorization lived only in a process-local per-provider slot, so a second authorize silently replaced the first, a callback could complete against a different flow than the one that produced its code, and nothing durable recorded that a flow ever existed.
- The repair: `ProviderOAuthFlowStore` (`provider-oauth-flows.json`) records each authorization as a durable occurrence `{id, providerID, scope, method, inputsDigest, state: pending | superseded | consumed | failed}`. Opening a flow supersedes the previous pending occurrence for the provider and scope atomically (in-process keyed queue plus the shared cross-process lock), as an explicit durable fact rather than a silent replacement. The live executor — the plugin's closure holding PKCE material a restart cannot resurrect — is held under the occurrence's own ID and claimed exactly once by the callback. `ProviderAuthAuthorization` gains a required `flowID`; both callback routes accept it to settle the exact occurrence; mismatch, already-settled and not-executable each fail with a named error.
- The consume-before-write trade, stated: the callback consumes the occurrence BEFORE `Auth.set`. The reversed order would let a flow superseded mid-callback durably clobber the newer flow's credential; consume-first instead converts a crash or credential-write failure inside that window into a re-authorization of a flow marked consumed. A lost consume-settle reports the flow's real durable state (for a claimed executor that can only be a supersession, so no credential was written).
- Not settling a flow on `NotExecutable` is deliberate: settling would break a concurrent legitimate finisher, and in a multi-backend deployment would make a callback routed to the wrong process unrecoverable — as is, retrying against the opener process still succeeds. A dead-executor flow stays pending, bounded to one per provider and scope by supersession.
- Recorded boundaries: a `Flow` carries no project identity, so two projects authorizing the same provider supersede each other — consistent with the credential store being per data root, and stated here rather than implied. `inputsDigest` is a forensic fact only; nothing reads it yet.
- Ledger note against the one-implementation rule: `cli/cmd/auth.ts` drives the plugin closure directly and performs its own `Auth.set` — a pre-existing second OAuth-finish implementation that bypasses the occurrence store, so CLI logins record no flow. Open.
- Focused positive tests in `test/provider-oauth-flow.test.ts` (5); SDK/OpenAPI/docs regenerated and parity-gated.

### Round-17 correction — ARC-018 authority lifetime and rejected callback terminality

Commit `823b4aba2` re-landed the durable OAuth callback design and closed the earlier duplicate-code redemption window by spending `oauthState` under the credential lease before exchange. It also replaced the single global authority slot with project-keyed authorities and clears a timed-out waiter's state. The mandatory independent review nevertheless rejected the commit with two P1 production reproductions.

First, authority registration had no Instance lifecycle receipt: only process-wide callback-server shutdown cleared the project map. A disposed project's authority therefore remained first in iteration order; its failed Instance re-entry returned HTTP 500 before a later live project could claim its valid state. The correction makes registration return an exact generation receipt, stores only the current receipt in the owning MCP Instance state, and unregisters it during that state's disposal. A receipt can test whether it is still the listener map's current generation; an older concurrent registration therefore cannot replace or remove a newer registration, and repeated authentication does not retain a linear set of obsolete authority closures. Resolution isolates per-authority failures, accepts a later exact owner, and reports the collected failure only when no registered authority can answer.

Second, an unattended `error` or missing-code callback resolved the durable owner but only settled an in-process waiter, which did not exist. The same state could then return with a code and be exchanged. The correction gives the callback authority one `abandon` operation that enters the owning project and consumes the state through the same compare-and-clear admission used by successful finish. Provider rejection and missing code therefore terminalize the exact durable flow before returning their typed HTTP error; there is no listener-local shadow terminal state.

The review then extended that same crash boundary to callbacks that still have a local waiter: listener response must not precede durable abandonment, because the process can die before `authenticate` observes the rejected waiter and performs cleanup. Error and missing-code requests therefore resolve and abandon their durable owner even when a local waiter exists, then settle the in-process promise. Abandonment atomically clears both `oauthState` and its PKCE verifier. Beginning a new credential lease likewise clears the previous flow's transient state/verifier while minting the new generation, so a crash after writing the next state but before its verifier cannot manufacture a recoverable flow from the new state and old verifier.

Acceptance must use the production listener boundary: a retired throwing authority followed by a live project authority completes the live callback; unregistering an old generation leaves a newer same-project registration authoritative; unattended and local-waiter provider rejection/missing-code callbacks durably abandon before response and a later code for the spent state receives the invalid-state response; reject flow A followed by a new lease/state B without verifier B is refused by durable finish rather than using verifier A; a sole failing authority still maps to the caught HTTP 500 contract. The OAuth security, durable-finish, concurrent single-use and real callback tests, package typecheck, documentation and route checks must all pass before repeat review.

#### Fourth review of the creation journal — NOT PASS, corrected implementation

The renewed uninvolved review found two P1 and two P2 defects, and the main-agent audit independently reproduced the first control-flow contradiction before the review returned. First, both convergence and create-failure compensation read the Project table and recursively delete later without sharing admission with `Project.fromDirectory`; a peer can commit the same directory between those operations and be left with a durable Project whose worktree was deleted. Second, the compensation branch says an undecidable database read or failed `fs.rm` retains the open occurrence, but then unconditionally calls `rollback`, which settles and removes the only future recovery owner. The same unconditional rollback reports an already committed Project row as rolled back and then throws the tail error even though the durable business result succeeded. The preceding **92/0/189** is therefore only the pre-review baseline and does not prove these boundaries.

The correction uses one current `ProjectDirectoryAdmission` primitive shared by Project registration and creation reclamation. It deliberately uses one global Project-directory admission fact under the data root, outside every directory it can remove, rather than a family of path-string keys: aliases, case variants and symlinks must not create two locks for one physical directory. `Project.fromDirectory` preserves the existing lock-free Git discovery entry timing, then acquires the cross-process admission, rechecks directory integrity and commits its Project row while still holding it. Reclamation acquires the same admission, re-reads the Project table inside the critical section, and deletes only when the row is still absent; therefore a registering peer either commits first and is retained, or observes the post-reclamation missing directory and cannot commit stale discovery data. Compensation follows the same primitive and publishes `rolled_back` only after physical deletion succeeds; an undecidable read or deletion failure leaves the occurrence open. A row already committed publishes `committed` and returns the canonical Project result instead of converting durable success into caller failure.

The positive creation-journal suite now has **17 pass / 0 fail / 43 assertions**. Two isolated backend processes are held at explicit admission boundaries and prove both legal winners: registration-first retains the committed Project and settles the journal, while reclamation-first removes the abandoned directory and the waiting registrar receives the typed `ProjectDirectoryIntegrityError` after its lock-internal recheck. Three additional cases prove that a failed registry lookup and a failed physical removal both retain an open recovery occurrence, and that a Project row committed before an initialization-tail error is returned as canonical business success. #### Fifth-review correction implemented — durable directory ownership

- **SQLite is the destructive authority for every overlapping path.** `project_directory_admission` records the canonical physical key, exact operation, generation, operation kind and runtime process occurrence for `registration`, `reclamation`, `promotion_restore`, `promotion_publish` and `promotion_workspace`. Conflict is path-hierarchical in both directions rather than exact-string-only. The proper-lockfile file remains a queue, not safety authority: registration and reclamation survive a real renewal compromise because each writer checks or settles its own SQLite generation atomically with the Project mutation. A completed callback is not changed into failure solely because its queue lock was reported compromised at release; the exact compromise branch is observed by a test hook and logged. Dead registration rows are removable because registration has no external effect before its registry transaction, while reclamation or promotion takeover is restricted to the same exact operation after process-occurrence proof.
- **Registration is one covering ownership transition.** `fromDirectory`, `addSandbox` and `registerExecutionDirectory` all record the physical directory occurrence before waiting, acquire registration authority, revalidate the occurrence and physical registration projection, and release their exact tokens in the transaction that writes ownership. Overlapping candidates from one discovery are reduced to the smallest ancestor-covering token set, so a registered nested execution directory resolves to its canonical Project/worktree without self-conflicting parent and child tokens. `registerExecutionDirectory` checks raw Project existence so a promotion-fenced durable row is not misreported as absent; its actual write remains closed by the promotion fence and workspace admission inside the transaction.
- **Physical ownership is revalidated, not inferred from a stale row snapshot.** Recovery captures the complete raw Project table, including promotion-hidden rows, plus canonical physical keys for the target, every worktree and every sandbox. After any destructive token is acquired and before its filesystem effect, it re-resolves all those keys. A junction retargeted to the anonymous directory while reclamation is held therefore releases the exact reclamation generation, preserves the directory and leaves the journal open. The target and registered-path snapshot also protects promotion destination, staging and quarantine effects. Physical ownership ambiguity fails closed.

The old raw-string `projectOwningDirectory` helper and unused one-shot writer assertion were removed so this physical capture is the only ownership fact source.

Backward recovery additionally owns `promotion_restore` across quarantine-to-source rename and the Project/Session database restoration. A killed promotion owner can be taken over only for the exact occurrence, and partial acquisition failure releases only the tokens already acquired. Registered destination conflict continues to surface the public `ProjectRegisteredDirectoryConflictError` contract.

The context carries a random lease generation that must still match the process-global active lease; the generation is invalidated before the physical lock releases. The lease key uses the canonical physical `.locks` root plus the subject key, while the physical lock filename is root-local `hash(kind, subject)`.
