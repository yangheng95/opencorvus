## Analysis and execution design

### Observable path and evidence

Each case is copied from its immutable seed under `specs/artifacts/2026-08-09-backend-algorithm-test-loop/fixtures/` into a separate temporary Git project. The request uses `POST /task` with the exact temporary directory, explicit `model: openai/gpt-5.6-luna`, `productPillar: code`, and host-authored `node --test` checker. The harness records:

1. exact request body and response headers/body;
2. the complete Server-Sent Events stream;
3. periodic Task, status, progress, and board projections through terminal state;
4. dev-server logs and request identifiers;
5. final Git diff, test/checker output, and downloadable Task project archive;
6. a classification of every abnormal observation as algorithm defect, test-design defect, toolchain/environment failure, or known issue.

The two Task requests may be submitted as one batch, but the harness never submits another case until both are terminal. There is no queue or launcher path capable of starting a third case.

### Impact boundary before modification

The initial run is observational and does not authorize OpenCorvus product edits unless evidence proves a new defect. A new product defect must be traced from observable event/status evidence through the route, Task creation, model/session/orchestrator control flow, persistence, checker, and terminal projection. Definitions, all call sites, same-semantics implementations, public schemas, data rows, tests, docs, delivery behavior, and regression risk are searched before editing. Model failure or poor task output alone is not assumed to be a backend algorithm defect.

## Conditional defect loop

For a suspected new algorithm defect, append its preserved identifiers and evidence here, delegate one uninvolved read-only agent for deep causal and impact analysis, verify the report against code/data and a whole-repository search, then implement only the proven root-cause repair. Add a focused positive product test, run it through the real checker, rerun both Batch 01 cases and every relevant historical failure case, and record the results. After first-pass verification, delegate a different uninvolved read-only reviewer over the complete diff, tests, evidence, documentation, and regression risk. Resolve every valid finding and repeat review until clear.

## Stop rule

Stop only when both Batch 01 missions are valid, new, different, terminal-successful through the real backend and checker; no new reproducible algorithm defect emerged; every earlier finding and toolchain fault is closed; evidence is complete; and the final independent review has no unresolved finding. If either mission reveals a new defect, complete its analysis/repair/verification/review loop and then run a new two-mission batch with new coverage before applying this stop rule.
