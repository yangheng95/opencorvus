## Observable failure and common cause

`local-meta-before.json` records requests path/vcs at `http://backend-a.invalid`, current server B, directoryEpoch0 and the same owned-dummy project directory, followed by committed result-from-a/branch-from-a. loadMeta's owner checks request counter, directoryEpoch and activeProjectDirectory, so those comparisons still succeed after an endpoint-only change. This is sufficient evidence of a shared response ownership gap; endpoint validation alone cannot repair it.

Connection Save now correctly serializes persistence and onConfirmed publication, but that callback only publishes URL/username/password. It does not obtain requestWorkspaceSelection admission or advance selection/workspace/directory owners. API configure holds one mutable URL/credential/directory set and notifies auth changes; it has no applied authority revision. An already constructed fetch retains A's URL/headers, yet its completion can publish after B becomes current. Checking URL equality alone misses credentials and ABA.

Two symmetric partial fixes are incorrect. Clearing views without fencing asynchronous owners permits late A success/error/finally to recreate or alter B. Fencing responses without a single admitted departure retains actionable A rows, file targets, cursors and pending compound operations; a later request can dispatch against B. Both parts must use the existing owners, without replacing backend execution facts or inventing a new persisted server-selection profile.

## Identity and transition policy

Public global.health returns healthy/version/paths and optional databaseUnavailable; it does not expose dataScope or a stable public logical database ID. The route uses Database.Path/unavailable and deliberately does not open SQLite. Database.Identity is a private persistent authority singleton that opens Client and writes/reads its row; its presence in source or a legacy UUID does not make it a public health contract. Do not add that call to health or use path/URL hashes as namespace equality. Clones and files shared outside SQLite would remain separate identity questions even if an API were later designed.

Proposed explicit navigation policy under the current public contract:

- An operator saves a different endpoint string: treat it as deliberate workspace departure through admission, even if the strings happen to be aliases. This is a declared user-action policy, not proof of different physical databases.
- Credentials change with unchanged endpoint: transport reauthentication invalidates old response/stream authority while preserving the workspace/draft. Current backend Basic Auth selects one process configuration, not a per-user namespace. Reverse-proxy credential-selected tenancy is not established; do not claim this policy proves equivalence for such deployments.
- Native managed port/PID rotation: existing native manager authority identifies the same owned backend-root purpose, so preserve workspace/drafts while advancing transport authority and rehydrating under that owner. This is not a guarantee against external database replacement. A failed current source lookup after restart follows its existing typed recovery contract.
- Same endpoint/credentials saved again: ordinary preference persistence, no new namespace departure. Directory changes continue using existing directory/workspace admission; they do not independently create an API connection revision.

No new mode flag, URL-derived backend identity, per-server workspace history, auto-discovery or fallback is introduced. If root requires alias/tenant identity preservation beyond this explicit policy, a separate public authority contract is needed before claiming that behavior.

## Single reservation across persistence

The present file close boundary is synchronous and cannot simply be called before an asynchronous settings save. Calling it first can discard a dirty editor even if persistence fails. Saving B first and then asking permission can leave durable B with an operator who cancelled departure. A check after await cannot undo the persisted fact.

Extend the existing workspace admission/file navigation owner with a prepare/reserve/commit-or-release handle:

1. An explicit connection-departure intent receives its token from the current workspace admission sequence and selection/file owner, not a new queue. A later navigation before write admission can supersede it normally. When it reaches the existing settings save tail, verify that intent still owns the captured source/resource before asking or persisting; do not let an old queued Save implicitly approve a newer workspace.
2. The registered FileEditorPane owner captures its exact target, draftRevision and baseline plus the current API authority. Existing Save/Discard/Cancel interaction remains the decision. A draft/resource change during an unsettled decision invalidates that approval; it cannot silently extend Discard to a new draft. Save uses A's captured authority and requires the real file revision receipt; a save error/cancel retains the editor and releases admission.
3. Once prepared, the same file owner holds a short reservation across persistence. Its existing editor/read-only/save controls and service-level file/workspace entrypoints observe that reservation, including keyboard/save/reload/rename/delete/navigation routes. A disabled Settings button alone is insufficient. Normal cancellation/supersession is allowed before write admission; after the durable write starts, the exact fact's completion must be handled even if the Settings view unmounts.
4. Discard is only an approved future departure: keep its exact draft until persistence confirms. On native persistence rejection, release the reservation, call the existing failure callback with the confirmed document, and retain original source/editor/draft. If the user chose Save and the A file write already succeeded, retain that truthful saved baseline/bytes; do not restore fake dirty state or undo A's legitimate write when preference persistence later fails.
5. On acknowledgement, the existing onConfirmed boundary synchronously commits the reserved file close, advances existing selection/workspace/directory owners once, clears old projection owners and publishes the confirmed connection/directory-free workspace fields in one batch. This must happen before the tail releases and before main's sole reactive API effect can issue B requests. Queued preferences then snapshot confirmed B plus the new empty source/saved-workspace pointers. Health/reload awaits belong after this synchronous boundary.
6. Existing SettingsActivationError remains an honest saved-but-not-applied outcome if synchronous activation fails. Release physical reservations in that path without claiming persistence rollback, retain diagnostic provenance and allow a later explicit correction. The implementation must demonstrate this with a controlled callback error; do not hide it by catching and resetting B to A.

Use current clear/apply primitives as the one implementation, extracting their synchronous portion if needed. Do not invoke applyDirectory's async save recursively while already holding settingsSaveTail. A resource reservation is data integrity for existing authoring, not an LLM tool gate or a new Task execution state machine.

## One API authority revision and captured operation

Add one monotonically advancing revision to api-state's existing applied URL/username/password owner. configure increments it once when any of those applied fields actually changes, then uses the existing auth-change notification. A→B→A and credential A→B→A therefore have distinct revisions even when their final strings match. No second URL/credential store or backend namespace UUID is needed. Directory epochs retain their current role.

An operation captures the current authority once. Capture/check and actual URL/header construction must be one synchronous dispatch step before any await. The transport needs that token for body decoding/error delivery and streams; compound services pass the same operation token to every subsequent request. Before a follow-on GET/PATCH/PUT, require that token still current; do not resolve a fresh B target merely because A's first request completed. Do not bypass routeRequiresProjectDirectory/requestTarget by manufacturing full URLs for each caller.

Fence both success and error before they reach current UI publishers. Otherwise an obsolete named missing-project error can invoke onApiError's current-directory recovery even if success data is ignored. A stale outcome is a typed local authority result, not a fake HTTP400/500 or evidence that the original backend rejected the operation. If an already-dispatched mutation returns an actual A receipt after departure, preserve that original public receipt in its originating operation outcome/diagnostic context, label it obsolete for current projection, and never automatically replay it against B. No durable side receipt/cache is introduced. Exact representation of this stale outcome should be settled in the implementation plan with the existing ApiError/TransportResponse consumer types; silently discarding a known successful mutation as generic failure is unacceptable.

Existing loader generations still govern resource replacement within a connection. They additionally bind the captured API revision. Completion, catch, finally, delayed retry, queued refresh and deduplicated pending joins may settle only their own operation pointer/revision; a prior finally cannot set B loading=false or clear B's request. Transport fencing alone does not make unconditional finally safe. On namespace departure clear old actionable rows/cursors through the existing owners; on preserved reauthentication/native rotation retain the current draft but deliberately refresh/rebind its projection owners. Never store a second server URL in each loader.

## Stream and backend execution settlement

Shared transport auth-change already snapshots active stream closers. Business onClose callbacks may retry immediately, so invalidating only after configure is too late. Stop/revise selected/global/MCP/side/VCS owners before connection publication, then establish current bindings explicitly. Every event, parse failure, onError/onClose and retry captures the same authority/source owner; cursors, cached connected events and normal/terminal A events cannot project onto B, even with equal Session IDs.

Crucial exception to projection-only cleanup: `/panel/message/stream` creates requestAbort; stream.onAbort aborts it. ControlMessage.handleStream tracks the actual prompt owner and invokes terminateOwnedSessionPromptInScope with source `control.message_stream_disconnect`, then joins settlement. Connection departure/credential changes can close this POST stream under the existing transport contract. Preserve and separately qualify the exact control Session prompt terminal outcome, not merely an idle UI label. Do not remove this behavior to make a switch look harmless, synthesize Messages, or fan it out into Task/Mission cancellation.

Ordinary selected/global GET streams are projection subscriptions; aborting those requests does not by itself invoke Task/Mission cancel routes. Task/Mission execution, accepted Message/request identity, retries/restart recovery and durable terminal reducers remain server-owned. An explicit stopChatRequest carries remote cancellation while local abortChatRequest is different. The plan must test normal reply completion, terminal messages, a disconnect during the owned control prompt and independent Task/Mission continuation as separate cases. No real execution proof is claimed from the current metadata fixture.
