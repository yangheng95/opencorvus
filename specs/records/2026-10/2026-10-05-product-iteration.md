## Completed analysis and selected implementation

### Existing Mission draft editing

- Observable: actual manual draft card contains Open, Dispatch and right-click Delete, with a read-only request summary (01). A typo in the saved request cannot be corrected. Opening the Mission composer and sending uses `wakeMission` and executes input rather than saving pending text.
- Source/history search: pendingPrompt lives only in Session `metadata.mission.pendingPrompt.text`; current creation writes it, dispatch's accepted-input SQLite transaction consumes it. Existing title/archive updates do not edit the request. The original Board separates manual creation from execution but never defines drafts as immutable. Four Mission operator ingress routes still converge on the shared accepted wake; only dispatch consumes pending text. boardLane is derived from outcomes/activity and is not draft edit eligibility.
- Contract: add strict `PATCH /mission/:missionID/draft` with `{request, expectedRequest}` and existing MissionRecord response. In one immediate transaction reread exact Session, Project, directory, kind and Mission identity; compare current pending text to expectedRequest and use the existing metadata writer. Changed/missing/archived values return named MissionDraftEditConflictError 409; wrong project/identity returns current NotFound 404. An archived draft is explicitly read-only until restored; this is the new editing contract, not a claim that existing title editing already forbids archive.
- No Message, provider call, requestID, scheduler or accepted-input rewrite occurs on save. Existing dispatch atomic consumption and durable replay remain unchanged. The UI offers Edit request alongside a clearly named Start action, uses the canonical record as the opening value, preserves typed text on failed save, and refreshes the existing shared store on success. Cancellation leaves the persisted request unchanged.
- Same-value retry: after identity/archived/missing checks, if the current pending text already equals the submitted target text, return the current record without another write. Otherwise require exact expectedRequest before mutation. This preserves a lost-response retry using the existing sole text value; no receipt/revision is introduced, and consumed/archived drafts cannot be revived by same-value retry.
- Risks/acceptance: competing editors and dispatch may change/remove pending state. Focused real HTTP/SQLite checks cover success/reopen, changed/missing/archived typed errors, project isolation, both edit/dispatch orderings, and old dispatch replay preserving a later draft. Root manually edits/cancels/saves/reopens a real Board draft, then uses authorized streaming exact Sol to execute the edited request. SDK/OpenAPI and bilingual API docs are generated through the canonical root pipeline.

### Schedule edits lose the persisted calendar

- Real reproduction: a valid future Friday schedule `DTSTART;TZID=Asia/Shanghai:20261225T160037` / `FREQ=WEEKLY;BYDAY=FR`, nextRun `1798185637000`, was created on the owned server. Actual page edit changed only its name. Saved result became October 5 at 16:00, Monday, zero seconds (02–03 and scheduled-before.json). Immediately restore the owned rule and pause it; no scheduled execution is needed or claimed.
- Root/data flow: parse strips date/weekday/seconds, then submit always rebuilds with today's target-zone date and weekday. Prior tests only parse a freshly built schedule in the same moment. The backend already keeps current.recurrence when PATCH omits it.
- Shared audit: production build/parse caller is only this settings form. HTTP POST/PATCH and schedule Tool create/update send full recurrence directly to one AutomationService; all three target scopes use the same normalized immutable definition owner. Normal terminal, retry and startup recovery read durable rules/Fire and the same Recurrence.nextRun, never the frontend converter. Project target resolution isolates actual runs. Task waits and Session delays have separate defined occurrence owners. Evidence proves frontend definition corruption, not a shared execution anomaly; no scheduler/API/schema changes are selected.
- Selected single implementation: basic form/service retains explicit `startDate` and `weekday`; current target-zone date/weekday are creation defaults only. Build requires explicit values and validates true calendar dates, time, zone and weekday. Parse maps only losslessly expressible zero-second rules to basic controls; nonzero seconds or advanced rule components remain intact in the existing custom editor. New basic UI exposes Start date and weekly Day. Changing time zone retains the chosen calendar fields.
- The existing Weekly review suggestion explicitly describes Friday but previously used the same today's-weekday builder. Its suggestion data now owns Friday explicitly, which initializes the same weekly form field; no separate scheduling implementation is added. Calendar controls use the existing form primitives in a compact two-column desktop region with ordinary wrapping.
- A pure update helper compares the original persisted recurrence with effective form fields; unchanged schedule yields undefined and PATCH truly omits recurrence. Daily/weekdays ignore hidden weekly day; custom compares its authored raw rule after trim. Untouched UTC Z rules retain their original representation; an explicit edit may emit equivalent TZID=UTC.
- Risks/acceptance: future anchors, different weekdays, leap days, seconds and custom expansions, unchanged edits and explicit calendar edits. Positive service tests verify exact rules/errors. Root uses actual UI name-only save and GET to compare complete recurrence plus nextRun, then explicitly edits date/day and checks the real normalized backend response. No timed firing, model call or scheduling claim is substituted by this configuration acceptance.

### UTC schedule summary qualification

- Actual final calendar interaction changed only timezone from Asia/Shanghai to UTC. Backend normalized the explicit UTC anchor to `DTSTART:20261219T153000Z`; date, Saturday and 15:30 were retained, with nextRun `1797694200000`. The current summary displays 15:30 without UTC while Next run shows the device-local 23:30. This hides the basis of the two different clocks.
- Direct/root cause: recurrenceSummary extracts timezone only from the TZID spelling and misses the equally authoritative Z anchor. Existing parseAutomationRecurrence already derives UTC from Z and exposes the validated original anchor/time. All summary callers are the same Scheduled form's list, details and search. No scheduler, API, execution or model change applies.
- Plan before mutation: reuse parsed validated anchor/time/zone for summary clock fields, retain existing rule-summary wording and unknown-rule raw output, and add focused positive exact UTC/advanced UTC summary assertions. Avoid a second timezone parser or inferred device zone for unparsed anchors. Rebuild and visually read the actual UTC schedule summary after the original real save; retain the real normalized recurrence/nextRun evidence.
