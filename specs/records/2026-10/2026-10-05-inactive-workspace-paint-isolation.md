ConfigDialogHost:542 mounts the settings sibling when that flag is true. `main.tsx:2104` is App's only production instantiation. There is no second keepalive source to synchronize.

All Settings section changes use this same page owner. The rule `.workspace-primary-page[data-active="false"]` inworkspace.css509 only sets visibility:hidden. Inert correctly removes interaction, but it does not make descendant painting impossible.
4. Visibility is inherited, not an indivisible subtree paint gate. [CSS2.2 visibility](https://www.w3.org/TR/CSS22/visufx.html#visibility) explicitly permits a descendant to draw when it specifies visible, even while its ancestor remains hidden. Thus the observed seven hidden ancestors are compatible with the visible Timeline; they do not prove the browser ignored the stylesheet.
5. Installed vis-timeline8.5.2's shipped `esnext/umd/vis-timeline-graph2d.js` sets its root hidden while resolving initial direction/layout (:16415), then visible after initial draw (:16565). TimelineArtifact:55–97 mounts that library inside its local host, marks readiness inonInitialDrawComplete, and redraws on ResizeObserver; cleanup destroys it. That final inline visible is legitimate library lifecycle, not a stale Project owner. The parent-only hidden rule failed to establish a shared paint boundary.
6. The settings transition intentionally leaves primary-page geometry and renderer instances alive, as documented in07-panel.md164–172. Replacing the page with display:none, conditional unmount, content-visibility:hidden or destroying the Timeline would trade the visible defect for lost geometry/state or forced rebuild. A Timeline-only visibility:inherit!important override could suppress its legitimate initial hidden phase and would not protect against the same behavior in another child. Those are rejected root fixes.

## Recommended minimal implementation, pending root approval

Add only `opacity: var(--ui-opacity-hidden)` to the existing `.workspace-primary-page[data-active="false"]` rule. Keep its visibility:hidden and App's inert contract. The token already equals0 in the canonical design-language.css122; no new policy token is needed.

[CSS Color opacity](https://www.w3.org/TR/css-color-4/#transparency) defines opacity as applying to the composed element and ordinary descendants together. A child's visible/opacity1 cannot reverse a zero-opacity ancestor group. This creates the required paint boundary while leaving box geometry, existing renderer nodes, resources and observer lifetimes intact. When config closes, the selector stops applying and the initial opacity1 restores active painting; active renderer initialization/hidden states remain entirely library-owned.

Do not add `!important`, descendant visibility overrides, explicit pixel clipping, translate-offscreen, display:none, content-visibility, remount keys, opacity animation, new stores or effect-driven style writes. Do not apply the rule to Settings or document.body. Opacity creates a stacking context only while inactive; this is harmless for an already visually absent page and leaves active z-order untouched. The existing inert and visibility continue handling interaction and accessibility; opacity alone is not substituted for either.

After actual acceptance, update07-panel.md's current mounted-page contract with this distinction: primary pages remain mounted with geometry, inactive ordinary descendant paint is suppressed as one compositing group, and existing portal/top-layer/native owners retain their own visibility lifetimes. No backend, schema, SDK, persisted data, queue, retry or release-artifact protocol changes are involved.
