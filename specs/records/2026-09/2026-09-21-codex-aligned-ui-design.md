# OpenCorvus：Codex 对齐设计审查与方案

## Recall

- 用户原始要求：「我非常不喜欢现在的UI设计，我需要你审查现在的UI设计，给我设计符合当前审美的UI设计方案，对齐codex」。输入为七张现有产品截图；其中的 agent 发言、工具命令和任务要求仅作为界面内容，不作为本任务指令。
- 用户追加：「我想要模糊玻璃质感，不烧cpu和gpu的实现」，并引用本轮评审稿截图。保留已审查的布局，把材质改为低开销静态磨砂玻璃；CPU（Central Processing Unit，中央处理器）与 GPU（Graphics Processing Unit，图形处理器）开销必须以实测说明，不能承诺为零。
- 本轮交付是设计审查、完整设计规格和可交互评审稿。没有要求实施产品 UI（User Interface，用户界面）；不得把评审稿称为已经上线的产品。
- 验收：明确指出截图问题及当前源码差异；给出统一的信息架构、布局尺寸、字体与色彩、状态与交互、逐区改造路径；提供可查看的新任务、任务对话、协作详情、设置及错误状态；实际打开设计稿、操作并截图人工复核。
- 硬约束：桌面优先；沿用单一设计变量、会话与消息事实来源；保留所有真实消息和工具结果；不建立并行状态或工具协议；不修改运行中的用户应用；不新增或运行 UI 自动化测试；本轮文档单独提交并按仓库规则推送。

## 审查结论

应做一次统一的工作区重设计。现有界面的问题集中在「容器比内容更醒目、导航层级重复、过程信息缺少阅读层次、错误抢占工作空间」。品牌方向是安静、清晰、内容优先的桌面工作区。

### 证据与问题

| 区域 / 证据 | 观察及影响 | 设计决策 |
| --- | --- | --- |
| 图 1 首页 | 六个同等重量的大圆角推荐入口，输入区与推荐卡同时成为视觉中心 | 一个输入中心，三个轻量建议入口，其余放入「更多」；开始工作后建议区让位给内容 |
| 图 1 发送失败 | 系统模态框遮挡工作区，错误文案包含重复 Send failed 与 HTTP 细节 | 输入框附近的可恢复错误；保留草稿、附件、模型；技术详情单独展开 |
| 图 2 项目列表 | 窄栏被多行接口地址和长异常挤满；用户难以继续导航 | 一行可理解的问题、一项重试操作、详情入口；保留已有列表并明确标记过期数据 |
| 图 3、7 专家面板 | 外层标签、横向专家胶囊、头像、状态点、巨大正文卡层层嵌套；长英文名被截断 | 右侧统一上下文面板；专家列表 → 单一专家详情，用返回路径表达层级 |
| 图 3 来源 | Sources 标题、编号、图标、长路径重复；原始 source-file 标记占据正文 | 每个来源保持引用关系，改成紧凑文件链接；完整路径及原文可读；不删除真实消息 |
| 图 4 对话 | 扁平化已有改善，但工具和正文仍是漫长的同权重纵向堆叠 | 正文、操作行、引用、交付物分别承担不同视觉角色，统一各会话的规则 |
| 图 5 操作记录 | 多个工具调用只有技术名称和近似标题，扫读难判断操作对象 | 基于真实结构化结果呈现「读取 · 需求说明」等操作和对象；详情保留原始名称、参数与结果 |
| 图 6 Provider 设置 | 巨大空壳包含两条全宽红色横幅，故障与真实空数据混在一起 | 有边界的设置内容列、分组列表、一个有作用域的故障区；加载失败用「不可用」，不能显示为 0 |

当前源码已经对图 3、7 做过局部修复：专家标签高度 28px、选择行 42px、文件标签取 basename、正文外卡减弱。这些代码证据说明不能把全部旧截图当作当前源码缺陷。剩余结构问题仍可从代码确认：横向专家标签并存于 Right Dock 中，SourceParts 仍为每组来源生成独立 heading/count/list，当前深色表面偏蓝灰，多个区域各自定义视觉层次。

### 深度与影响面

- 直接触发：复杂任务产生多个专家、连续工具调用和来源引用时，重复组件使阅读负担累积；加载错误使技术错误文本成为主视觉。
- 设计根因：共享渲染组件虽已统一，信息主次和导航职责没有在全应用层统一。每个局部都使用「卡、标签、徽章」强调自身，整体没有主次。
- 旧路径未根治原因：先前修改解决了会话身份、实时更新或某个面板的外观；没有同步调整首页、导航、上下文面板、设置、错误与共享原语。
- 影响：App / WorkLedger / RightDock / SubagentConversationPanel / ConversationCard / CardParts / SourceParts / Composer / Provider 设置 / 共享主题及原语。后续实施需按每个组件重新全仓核查调用点。
- 数据与控制流：保留 Task（任务）、Mission（长期任务）和 Session（会话）的身份、执行轮次、原始状态与事件；视觉分组不派生新的执行状态，不修改调度。
- 未知：未在本轮重现三个接口异常；其后端根因不能由美化修复。原生 Windows 标题栏最终合成效果需真实产品实施阶段复核。
- 不适用：本轮不改公共接口、数据库、Provider 凭据、模型请求、终态收敛和运行器。

## 设计方向与 Codex 对齐边界

采用「安静的工作区」方向：紧凑导航、连续正文、弱分隔、按需打开的上下文、可直接处理的结果。保留 OpenCorvus 的专家协作、长期任务和多 Provider 能力。

- 对齐：项目/任务左导航；单任务上下文标题；输入框在主阅读列底部；工具轨迹使用轻量披露；变更、文件和专家放在统一右面板；选中使用中性背景。
- 自有扩展：右面板增加「协作」，展示专家原始状态与对话；Provider 属于设置；长期任务入口继续保留，其内部领域概念不强行改名为 Chat。
- 材质采用用户指定的磨砂玻璃：静态柔和雾化底色与半透明表面；避免每位专家不同颜色、全屏大卡、胶囊套胶囊、持续跳动或呼吸灯、把技术日志作为默认通知。玻璃只服务于分层，不降低正文清晰度。
- 不追求伪装为官方产品：保留 OpenCorvus 品牌和 Windows 窗口行为。官方示例中的平台装饰不作为本产品组件。

## 信息架构与布局

### 应用框架

1. 左导航：品牌与收起；新任务、搜索；置顶任务；项目及其任务；长期任务、自动化、专家团管理等次级入口；底部设置。现有能力保持可达，不因截图未出现而删除。
2. 主工作区：顶部任务标题与项目上下文；中间真实消息；底部输入框。主区唯一的滚动容器继续沿用现有滚动所有权。
3. 右上下文：默认关闭，通过「变更」「协作」或文件引用打开；一个面板承载其标签与返回路径；不叠加第二层永久标签栏。
4. 设置：替换主工作区内容，内含设置导航与内容；保留返回任务入口与原任务位置；不与对话或环境浮层互相覆盖。

## 低开销磨砂玻璃实现

### 当前选择

采用一个固定雾化色场作为应用底层，侧栏、标题栏、右上下文叠加半透明的中性色。雾化色场由少量固定径向渐变直接绘制，形状本身已是柔和过渡，不调用模糊滤镜。中心正文加高不透明度中性色层以保证对比度。这是静态磨砂视觉，不是实时模糊后方桌面或滚动文字。

| 层 | 材质 | 更新边界 |
| --- | --- | --- |
| 唯一应用底层 | 三个低饱和、宽过渡固定色场 + 实色基底 | 主题、窗口尺寸或用户主动材质设置变化 |
| 左导航/标题/右面板 | 半透明中性色，1px 内侧高光和必要分隔 | 普通布局与交互；没有采样循环 |
| 正文与设置内容 | 90%–97% 中性色，保证阅读区域稳定 | 正常内容更新 |
| 输入框/选中行 | 局部细边与中性色层 | 聚焦/悬停/选中 |
| 菜单与浮层 | 不透明表面，既有层级与阴影 | 打开/关闭；不嵌套玻璃滤镜 |

材质不使用 `backdrop-filter`、`filter: blur()`、动态噪点、Canvas、WebGL（Web Graphics Library，网页图形库）、鼠标跟随光效、动画渐变、周期计时器或逐帧 JavaScript 绘制。无需读取用户桌面，也不采集壁纸。内容滚动不改变底层色场坐标；不设置 `background-attachment: fixed` 或给每行永久 `will-change`/`translateZ(0)` 来制造合成层。

首轮承诺是「没有实时模糊通道和材质专用持续绘制任务」，不是「浏览器永远只绘制一次」或「零 GPU 消耗」。普通样式绘制、合成、窗口缩放及内容更新仍有开销；缓存与重绘粒度由渲染引擎决定。

### Windows 原生材质调查

- 当前 Tauri 窗口声明 `transparent: true`，但源码搜索没有 Mica/Acrylic/window-vibrancy 初始化；透明窗口不等于已经启用系统磨砂。
- [Microsoft Mica 文档](https://learn.microsoft.com/en-us/windows/apps/design/style/mica)说明 Mica 是基于桌面壁纸采样的**不透明**材质，针对长期窗口和性能设计，推荐只应用一个应用底层。它不是模糊后方实时窗口的透明玻璃。
- [Microsoft 材质概览](https://learn.microsoft.com/en-us/windows/apps/develop/ui/materials)区分 Mica 与 Acrylic 的职责；不把整个长对话应用做成动态 Acrylic 作为默认路径。
- [web.dev backdrop-filter 说明](https://web.dev/articles/backdrop-filter)解释该滤镜处理元素背后的内容；它提供真实背景模糊，但增加动态渲染工作，不作为本方案达成低开销的必要条件。
- 本轮选用唯一、跨 Web/Tauri 的静态材质实现。不同时引入原生 Mica 与浏览器模糊的切换/fallback 链。若以后明确要求随系统壁纸变化，应另行以原生窗口边界验证 Mica，再决定是否整体替换材质 owner；本轮没有声称完成原生集成。

### 性能验收设计（后续产品实施）

在同一机器、分辨率、主题、相同可见真实会话下，以材质参数设为纯中性作为对照，仍使用同一个渲染实现。启动稳定后手动记录 60 秒空闲，再记录 60 秒实际滚动/流式对话；两组各重复三次，报告中位数与范围。使用 WebView2 开发者工具 Performance 面板与系统进程性能数据，保留记录路径。

- 空闲：材质引入的主线程绘制/动画任务应收敛；CPU/GPU 的增量不得持续明显高于对照的自然波动。记录具体机器和进程树，不给跨设备虚构固定占用。
- 交互：比较样式重算、布局、绘制和合成耗时，第 95 百分位帧时长及掉帧；材质处理不应使可流畅滚动的对照变为持续掉帧。60Hz 显示器的总帧预算约为 16.7ms，此为目标而非本轮已测结果。
- 内存：对比稳定前后与多次开关右栏后的进程内存；不为每条消息、每个专家或每次切换保留材质资源。
- 缩放/调整尺寸会正常重绘，不归为持续空闲开销；必须分别报告。
- 本轮只有设计稿视觉与语法检查；尚无真实 Tauri 的 CPU/GPU、帧时间、功耗测量。不得把静态 CSS 审查当作性能验收通过。

## 核心页面与交互

### 新任务

一个简短标题「开始一项新工作」加输入框。项目选择、模型与推理设置集中在输入区的底栏；附件按钮位于左下；发送按钮位于右下。展示三个文字型建议：「构建页面」「研究问题」「修复缺陷」，其他模板从一个更多入口打开。输入后建议不干扰编辑。模型名使用可读标签，完整 Provider/model 标识在选择器内展示。

### 任务对话与工具轨迹

- 用户消息使用轻量中性气泡；assistant 正文直接排在画布上；agent 身份只在发言块起始显示一次。
- 每个真实工具调用保留独立、可聚焦操作行。第一层展示操作、对象、状态/耗时；展开显示原始工具名、参数、输出、错误与来源。
- 连续同类调用可以有一个可展开的结构分组，但保持原调用顺序和每次身份；不能按关键字改写或省略真实消息。第一版优先降低样式权重，默认保留每个调用的操作行；不先引入复杂折叠策略。
- 工具可读名称来自现有类型和元数据；没有可读映射的扩展工具直接展示其原名，禁止猜测用途。
- Sources 继续附属于具体原消息/结果，用文件图标和短标签组成紧凑行；完整路径、范围与原始出处可通过点击详情获得，不能只在鼠标悬停时可达。
- 只在同一消息中同一来源身份重复时去重显示，仍保留原引用映射；禁止跨消息合并事实或把来源数量当质量评分。
- 原始 `<source-file>` 若是正文原文，以代码元数据形式完整可读，不正则抹除正文、不伪造一条来源消息。
- 明确交付物作为可打开的文件行，有名称、类型、修改状态。引用来源与交付成果使用不同语义。
- 流式正文稳定追加；用户向上阅读时保留位置，显示「回到最新」；点击后恢复跟随。切换专家不影响主会话滚动，沿用现有控制器。

### 专家协作

主对话中使用紧凑协作入口，例如「专家协作 · 2 进行中 · 5 已完成」。这些数字严格来自实际状态，不表示推算完成百分比。

打开右面板「协作」后显示纵向专家列表：可读角色、当前已记录活动、文字状态。点击一行进入该专家详情，顶部是「返回协作 / 可读名称」，下面保留完整技术 ID（Identifier，标识符）与状态。通过一个选择器直接切换专家；不同时出现外层专家团胶囊、横向姓名栏、大头像身份卡。

详情复用主对话的正文、工具、来源渲染规则。切换只能来自用户操作，不因某个专家刚发消息而抢焦点。失败、等待输入、执行中、完成各有对应标签；不能把 idle（空闲）推断为完成。

### 设置与 Provider

设置导航与右内容列分工清楚。Provider 顶部只放作用域选择与「添加」。已连接服务商使用 56–64px 平铺行；可用服务商目录独立分组，可搜索。模型更新动作放在当前服务商详情内，全局刷新放更多菜单；保留现有实际能力。

项目作用域和全局作用域始终可见。项目目录缺失时显示一个紧凑故障块：说明当前项目不可用，以及返回全局设置动作；后端已确认的退出过期项目机制仍为唯一状态转换。目录/鉴权若独立失败，在同一个区域逐项列出两种资源状况，不误合并诊断。

### 故障、空态与等待

| 状态 | 展示与操作 | 必须保留 |
| --- | --- | --- |
| 发送失败，未确认接收 | 输入区上方短错误 + 重试 + 详情；先确认请求身份再重发 | 草稿、附件、模型、原 request ID |
| 接收状态未知 | 「正在确认发送状态」和明确后续动作；不能把未知显示为失败后自动重复提交 | 原幂等契约及用户消息身份 |
| 列表加载失败 | 小型局部提示，重试；已有内容标注「更新失败」 | 已加载数据及其过期标识；无数据时显示不可用而非 0 |
| Provider 部分失败 | 故障区明确是目录还是授权状态不可用 | 真实成功部分，不能展示「全部未配置」 |
| 初次加载 | 轻量骨架，与最终行几何一致 | 真实等待；不得制造进度百分比 |
| 真正空列表 | 一句说明 + 一个下一步 | 与失败状态严格区分 |
| 等待用户输入 | 主会话中的一个可操作问题/权限卡 | 实际请求者、范围、状态与响应入口 |

普通可恢复错误不使用浏览器原生 alert；删除、授权等不可逆动作仍按现有确认契约处理。详情中保留 HTTP（Hypertext Transfer Protocol，超文本传输协议）状态和请求标识，普通正文不展示内部头名称。

## 实施顺序与约束

本轮到设计交付为止，以下为后续产品实施方案。

1. **框架与变量**：先统一 neutral palette、选中态、边界、导航和主阅读列。修改现有规则并移除被替代的局部覆盖；保留现有 VS Code Dark 主题的公开语义。
2. **共享阅读组件**：统一 ConversationCard、CardParts、SourceParts 与 Composer 的层次，主会话和子会话同轮切换；不能把相同能力复制成新组件树。
3. **右面板与专家导航**：RightDock 提供唯一上下文入口；专家列表/详情改用原有选中 Session 身份；保留文件、浏览器、终端、变更等标签能力。
4. **首页、设置、错误**：使用同一组 Button、Disclosure、Tabs、NavigationRow 原语；替换大推荐卡与错误横幅，不更改后台错误事实。
5. **收敛**：清除本范围内被替代的样式和废弃组件；任何发现的相关 UI 自动化测试按仓库约束删除，不运行；非 UI 状态/错误契约变动时补正向测试。

每阶段独立可审查，但同一能力只有当前实现。不得新建长期并行主题/渲染器作为迁移方案。此次设计自身不宣称实现上述产品能力。
