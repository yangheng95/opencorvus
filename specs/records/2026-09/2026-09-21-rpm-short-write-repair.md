## Analysis and plan before implementation

The prior split only moved RPM into independent jobs; every job still executes the defective producer. The npm CLI contains precompiled Rust, so changing the application's Cargo graph cannot repair it, and the current npm patch release has the same dependency. Use the existing CLI version's upstream source and one small Cargo dependency patch. This is the sole RPM producer; other formats retain their current CLI, and there is no fallback to the broken RPM command. Preserve gzip level 6 and all package metadata/content behavior. The patch belongs to the packaging tool, not the application or a format-conversion bypass.

1. Add one Linux preparation owner that resolves the installed CLI version, obtains exact upstream source and checksum-verified locked rpm crate, applies the minimal short-write correction, checks that only this dependency's source changes in the lock, and builds the original CLI. Cache only the resulting tool/identity receipt, keyed by CLI version, native architecture and preparation/patch identity; ordinary product version bumps must not invalidate the tool cache. Source/patch/tool digests identify immutable tooling inputs, not functional acceptance.
2. Call that owner from the existing RPM bundle phase. Reuse it in the existing Linux format workflow with a narrow tool cache. Add a real package checker for system rpm verification, explicit uncompressed payload digest and isolated package installation/file comparison against the exact compiled input. Preserve complete-row assembly and publication ownership.
3. Exercise positive preparation/error contracts locally; run both native Linux architectures through the existing debug workflow and original asset checker. Measure cold tool setup separately from bundling; target RPM bundling under five minutes for this ~210 MB input, correct ALT/file digests and real isolated install. A fixture or source check is not native acceptance. Use activity-based observation and timed result checks for long runs.
4. Independently review implementation, evidence and docs; address findings; commit/push scoped changes with normal hooks. Preserve current release identity. Once a concrete corrected candidate is ready, resolve any approval required to replace the unpublished frozen 0.1.10 identity, then finish native/website delivery and verify public downloads.
