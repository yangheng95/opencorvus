## 1. 定位与中心问题

建议定位为软件工程与智能体系统交叉的系统研究论文。暂定标题：

**OpenCorvus: A Runtime for Durable Execution and Evidence-Traceable Delivery in Long-Horizon Agent Work**

中文工作题名：**OpenCorvus：面向长时程智能体工作的持久执行与可追溯交付运行时**。

标题是研究主题；其中能力边界必须在正文明确，不隐含已验证的普遍有效性。

中心问题：当智能体任务跨越多个执行轮次、参与者、工具副作用和进程中断时，如何表示并维护业务状态、物理执行所有权与交付证据之间的一致性，同时保留模型的规划与判断能力？

先定义“长时程”的研究单位：多阶段依赖、多次工具交互、上下文更新与可能的执行中断；不能把墙钟运行时长、token 数量或 agent 数量直接等同于复杂性或可靠性。论文可以使用具有这些属性的任务分层，但具体阈值须由数据与实验协议确定。

平台功能数量、模型目录规模、界面、专家团市场和支持渠道属于实现背景。专家团组合与反馈修订只在服务中心问题时进入主文；跨任务自我改进若无独立迁移评估，应放到讨论或未来工作。

## 4. 方法分析的严格要求

- 以当前控制面定义为起点，研究状态投影 `P_t = Reduce(F_≤t, policy, valid leases, t)`；随后从源码核验每个符号和更新边界。队列提示、持久化事实和实际执行所有权必须分开描述。
- 列出数据库事务/持久性、进程故障模型、时钟及租约语义、网络与 Provider 可用性、调度公平性等假设。单进程、跨进程和跨项目适用范围分别说明。
- 安全性关注有效所有权、精确 occurrence 的结果归属、交付引用的版本一致性；活性关注在资源恢复和公平调度等前提下，未解决工作是否继续处理。不能从有租约推导所有操作必定完成。
- 对外部工具副作用单独分析：数据库内幂等结算不等于外部世界端到端“恰好一次”。明确可重放操作、幂等键、未知结果和需要人工决定的边界；没有实现证据的保证不能写入论文。
- 若使用定理，给出明确抽象模型、前提、证明及到实现的映射限制。测试通过不能代替证明，抽象模型的证明也不能自动证明整个生产实现。
- 图表使用统一记号：整体架构、故障与恢复时序、证据来源/版本图。算法是对已有实现的精确抽象，不为论文临时发明未实现路径。

## 5. 预先设计实验，但本轮不运行

| 研究问题 | 实验思路 | 主要观察 |
| --- | --- | --- |
| RQ1：一致性与恢复机制是否有效？ | 在独立实验环境的真实持久化、进程与工具边界注入明确定义的故障；覆盖正常与终态、重启和跨项目并发 | 正确恢复与终态比例、恢复耗时、错误契约、重复执行/副作用及未决结果 |
| RQ2：是否改善长任务的最终交付？ | 选用公开、可核对结果的长任务并按依赖/交互复杂度分层；相同模型与预算做配对比较 | 独立验收的完成率、需求覆盖、交付缺陷、失败类型与证据完整性 |
| RQ3：哪些机制有贡献，代价是什么？ | 在隔离研究配置或固定快照中进行单机制消融；不向生产系统加入兼容/后备实现 | 质量变化、token/调用数、延迟、实际可观测费用、人工介入次数与时间 |

基线从论文与当前实现审计中选择，候选包括最小单智能体工具循环以及支持相同模型/工具边界的公开运行时。相关工作不自动成为可比基线；论文版本和现行 SDK（Software Development Kit，软件开发工具包）必须区分。

按用户约束，主实验首先使用 `openai/gpt-5.6-luna`，冻结 Provider 标识、实际请求 model/API（Application Programming Interface，应用程序接口）ID、模型目录或非秘密配置 revision、源码 commit、专家团 package digest、接口日期、工具权限、上下文和预算。只保留非秘密配置与身份摘要，不复制凭据。若只验证一个模型，结论仅覆盖该条件；不宣称跨模型普适性。不擅自增加模型、购买额度或开始实验。

SWE-EVO 等长任务基准可作为候选，须核读任务、许可、输入污染与验收定义后决定。单一 issue 修复基准不能独立支撑运行时恢复和多阶段交接主张。现有 Actual 案例是选定后公开讨论过、经过维护者反馈的演示，只能作动机/定性例子，不计作随机样本、独立用户研究或总体成功率。

实验前冻结任务纳入/排除规则、主要指标、重试和超时处理、模型预算、干预条件及分析方法。以任务为分析单位，考虑同一任务重复运行的聚类，报告效应量、不确定性区间和全部失败；样本量由先导方差/功效或精度分析决定，不凭经验先填一个漂亮数字。禁止把选择后的成功案例补充为独立样本。

协议必须形成可执行字段：每个故障点及持久化/进程/Provider 边界、触发时序、预期事实集合、正确终态和副作用判定器；明确重复执行、重复结算、未知外部结果分别如何计数。恢复正确性要求精确 occurrence 的预期事实和结果契约满足，不能以进程重启成功或最终 status 字符串代替。基线/消融冻结各自 revision 及能力、预算和人工干预差异。预先指定 primary endpoint（主要终点）、estimand（待估计量，例如固定预算下配对任务的验收成功概率差）、超时/缺失/部分结果处理、任务内重复的统计模型及多重比较处理。上述字段先完成并冻结，再运行任何对照实验。

既有 AutomationBench 数字只有网页展示与算术一致性证据，不进入结果表或效应量计算。七角色历史材料同时记录交付和越序：必须保留其过程缺陷，不能只抽取最终成功。历史记录不证明当前版本仍有相同缺陷，也不证明已修复；这些判断须单独追踪版本与来源。

可程序化的验收使用真实后端、文件和命令输出；涉及 UI（User Interface，用户界面）仍按仓库约束进行真实页面交互、截图和人工复核，不新增 UI 自动化测试。盲评规则、评审者一致性及冲突裁定提前规定；LLM（Large Language Model，大语言模型）评委不能单独决定正确性。人工介入和维护者调试与无人运行分别记账。

## 7. 执行顺序、交付物与验收

0. **既有证据包接管与映射**：从 foundation manifest 核对输入、边界、验收记录与来源版本；保留 evidence、cases、experiments、figures 事实输入及 integration 原件，逐项纳入已知缺陷和不可引用范围。历史材料只支持其当时观察，不能替代当前实现审计。
1. **论证与证据锁定**：固定论文源码版本，建立文献矩阵及正文到原有机器主张/原始来源的引用映射；输出中心问题、候选贡献及反例/限制清单。验收标准是每个核心主张均有证据路径，未知项显式列出。
2. **方法先行**：完成问题定义、系统设计、条件性质、实现章节及三张方法图；每个算法和系统保证回查源码。先由方法决定叙事，避免先写宣传式引言再寻找理由。
3. **补齐学术正文**：完成 Introduction、Related Work、已知限制、复现附录；编写结果占位明确的摘要与结论骨架。引用和记号全篇一致。
