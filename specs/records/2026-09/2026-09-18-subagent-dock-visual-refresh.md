# Sub-agent dock visual refresh

## Recall

- User reports that the child-agent Side Dock looks dated. Their screenshot shows a wide dark dock with pill-shaped agent tabs, a large rounded transcript card, oversized monotone tool rows, repeated prominent Sources badges, long paths and raw source markup competing with the agent's prose. This is a visual and information-hierarchy request, not a request to alter or suppress the underlying messages.
- Acceptance: the selected agent remains obvious; long sessions read as a clear conversation with distinct prose, tool activity and sources; file sources have a short visible label and full path remains accessible; switching, source opening, and tool disclosures still work. Review the actual dark desktop-sized page and a narrower dock with screenshots, correct visual defects, and keep the running OpenCorvus process uninterrupted.
- Hard constraints: no UI automation tests, DOM assertion tests, snapshots or screenshot baselines; UI validation is real page interaction plus manual screenshot review. Do not restart, close or interrupt the user's OpenCorvus. Preserve every real participant message and tool/result; no hidden or synthetic messages. Use existing design tokens and one canonical transcript/source implementation.
- Sources read: the user screenshot, `specs/current/architecture/07-panel.md`, the prior sub-agent dock repair records, `SubagentConversationPanel`, `SourceParts`, `CardParts`, `ChatBubble`, `TextPart`, and the related inspector, message and chat-bubble styles. Whole-repository search located the single selected-child transcript component and shared source renderer; its source-chip CSS is shared with the main conversation. Independent agent feedback: none yet.
- Observed visual/control flow: one exact child Session is rendered through `SubagentConversationScroll` and `ConversationCard` with `collapsible={false}`. A single card projects all message parts; tools are already real disclosures and Sources are separate source parts. The current panel CSS uses bordered pill tabs and full-width card treatment, while shared SourceParts renders the relative path as each file chip's label. These choices produce the screenshot's repeated high-weight chrome and long truncated labels. User-provided screenshot is the baseline; current browser state and exact dark theme will be checked before implementation.
- Direct trigger: selecting an active child session with many reads and source references fills the dock with same-weight content. Root visual cause is the dock's reuse of main-conversation card, tool and citation styling without a dock-specific reading hierarchy; it is not missing backend data. The previous session-switching fixes addressed data identity and live projection, not presentation.
- Impact: Side Dock child transcripts only for scoped styling; changing the shared file-source visible label would also improve citations in the main conversation while retaining full path in tooltip and accessible name. No backend, persistence, scheduling, or message-content change is planned.

## Plan

1. Give the child-session dock a restrained navigation and reading layout using current theme tokens: flatter selected tab, clear current-agent identity, a centered readable transcript column, and less heavy outer card chrome.
2. Reduce visual weight and improve scanability of tool and source rows in this dock. Show a concise file-source chip label while preserving the full path in tooltip and accessible name. Present standalone literal `<source-file ... />` text as scrollable machine metadata, with its exact text still readable, rather than letting a long path fill many lines of prose.
3. Use a separate frontend page connected to the running backend for real task interaction because the running desktop UI cannot be refreshed. Inspect dark-theme screenshots at wide and narrow dock sizes and iterate. Run Overlay typecheck/build, CSS-token check and docs check; do not run UI automation tests.
4. Obtain independent read-only review, fix any valid findings, commit and push the task changes. The current desktop process remains on its loaded UI until a later user-authorized update.

## Status

The dock now uses flatter selected tabs, a continuous readable transcript column, a sticky agent identity row, restrained tool disclosures and compact source rows. File-source chips show the filename while their accessible label and tooltip retain the exact relative path. Standalone literal `<source-file ... />` text is rendered in a horizontally scrollable metadata line; its bytes remain in the message text.

- Actual page acceptance used an isolated Vite development page at `http://127.0.0.1:5174/` with the current task's live backend, because the user forbids interrupting the running desktop UI. The page theme was set to Dark through its own browser settings, not the native client's settings. At narrow dock width and after expanding the dock with its real separator keyboard control, screenshots were personally reviewed; the large rounded card and pill-heavy references were replaced by a continuous hierarchy. The first iteration still showed long file titles, so `SourceParts` now prefers a basename for path-like file titles; a second visual check confirmed concise labels. The raw source-file marker still dominated one screenshot, so it was styled as scrollable machine metadata and rechecked visually.
- Actual clicks switched from `implementation-engineer` to `source-investigator` and back; the selected tab and transcript identity matched. A file source opened its editor tab, the sub-agent tab reopened, and a tool disclosure expanded. The isolated browser console had no errors.
- Overlay typecheck, CSS-token check, `docs:check`, `git diff --check`, and production Vite build passed. No UI automation test, DOM assertion test, browser fixture, snapshot or screenshot baseline was added or run. The running OpenCorvus process was not restarted or interrupted.

Independent read-only review found no actionable issue. It traced the source-chip label, tooltip, accessible name and file-open path, confirmed the standalone source markup classifier against rendered Markdown, and checked the scoped CSS and Kobalte tab behavior. It correctly limited the visual acceptance claim to the manually reviewed Dark narrow and wide layouts; Light uses the same theme tokens but was not separately screenshot-reviewed in the final iteration.
