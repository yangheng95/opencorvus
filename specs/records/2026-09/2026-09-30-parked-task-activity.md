# Parked Task activity projection

## Recall

- User: 子任务向 Mission 发消息后仍转圈；用户指出“状态更新不正确，因为似乎实际上是暂停执行了”。Investigate actual execution and correct the shared projection rather than treating a status field as proof of work.
- Acceptance: a live Task scheduler or descendant execution shows running; a parked Task waiting for a Mission reply is inactive while its durable lifecycle remains active. Wake/retry restores running, and idle/terminal settles it on the mounted page. Task status, Mission counts and global Work Ledger agree, including standalone Tasks and separate projects.
- Constraints: one agent; preserve all concurrent release, participant-message, context-disclosure and Harbor changes (initial diff saved outside repo); no credentials, new model calls, live runtime mutation/restart, UI automated tests, scheduler gates or shadow state. Focused backend positive tests plus isolated real `/ui` interaction; scoped commit and normal upstream merge/push.
- Read/search: AGENTS; architecture 03-control, task-control-plane and 07-panel; task status snapshot, Mission and Work Ledger projection; Session lifecycle/status/tree and Task session lineage; global ledger stream and Overlay consumer; prior follow-up convergence and execution-redesign records; all callers of activityFromTaskLifecycle. No delegation.

## Evidence and root cause

- Read-only production SQLite and HTTP inspection: Task `tsk_g00VWfE9RS00BUoFJ1dv`, scheduler `ses_-zUTKlXTzzzHa4yICSwm`. At 09:48:53 and 09:56:19 China time, real no_action outcomes requested immediate_park, assistant messages completed, and agent.execution.lifecycle published idle. These are actual pause boundaries. At 10:07:38 a Mission request caused a new execution; subsequent real Tool outcomes continued until the operator stopped execution at 10:24:48. Cancellation settled by 10:24:52. At the later inspection there are zero pending Provider requests and zero Session prompt owners. Do not conflate the resumed interval with earlier paused intervals.
- `activityFromTaskLifecycle` maps every durable active Task to running. Its three callers drive Task status, Mission task counts and Work Ledger rows. An unfinished Task can legitimately have no current physical execution, so this projection contradicts the documented binary activity contract.
- Shared update defect: Task list invalidations cover lifecycle/goal/interaction events but omit agent.execution.lifecycle. The global status path only refreshes Mission/direct Chat Session rows, excluding Task schedulers/workers. Correcting a getter alone would still leave mounted rows stale after park/wake.
- Existing current-process SessionStatus is the liveness authority: it is generation/input-message scoped and defaults idle after restart. Durable execution events are historical facts, not proof of a live owner. Reuse listTaskSessionIDs and the current SessionStatus for the whole owned tree. Keep Task lifecycle as its independent diagnostic field.
- Scope/audit: Task create, operator follow-up, Mission requests/replies, scheduled wait/recovery and worker completion all converge on the same Session publication and Task protocol bridge. Mission/direct Chat already use physical Session status. Include descendant-only execution, serial new input generations, parallel Tasks/projects, terminal lifecycle and history-only/restart observations in focused checks. No queue, retry, wait, lease, cancellation or acceptance writer needs replacement. Long-running tool/permission ownership remains governed by the existing physical Session status, not inferred from missing text.
- Risks: a parked scheduler can still have an active worker; an unrelated Task must not keep it running; a previous occurrence cannot override a new one; historical streaming cannot resurrect liveness after process loss; an idle event must refresh both sidebar and Mission aggregates. Existing test asserting running for an unstarted active Task is obsolete and must be corrected.

## Plan

1. Replace lifecycle-derived activity with one shared current-execution resolver, using existing Task session lineage and SessionStatus. Update all three consumers; retain the public running/inactive shape and raw lifecycle.
2. Include real Task execution lifecycle publications in the existing Task/global ledger invalidation route. No UI timer, polling workaround, new event channel or duplicated state.
3. Add positive backend tests through real projections, public routes and the global event stream; run existing Session occurrence/no_action checks. Use an isolated server with explicitly labelled local presentation inputs to inspect running → idle → running updates on the same mounted desktop page.
4. Record evidence and limits, review only this task's diffs, commit, fetch/merge and push. Do not restart the user's installed app to apply source changes.
