## Credential handoff defect: analysis before repair

The earlier host copied the complete OAuth credential store and let the production plugin refresh its copied OpenAI entry. The original source still has that old generation; successful isolated refresh outputs were removed on shutdown. The present copied generation returned exchange_uncertain. Do not claim a proven remote error code.

Scope search found the shared `RealProviderAudit`, its six script consumers, native audit plugin, OpenAI `resolveOpenAICodexOAuthCredential`, `Auth` atomic generation updates and shared `ProviderOAuthFlowStore` refresh ownership. Same-data-root production refreshes already serialize and persist generations. This experiment introduced a separate data root with a copied authority, so production Task/Mission scheduling is not the observed failure and will not be changed. Other audit callers retain their existing behavior.

Repair the current Inspect host's copied authority: validate the copied OAuth access expiry before copying/starting; use the shared audit to enforce the expiry for every external request, so an expired copy cannot start its own refresh exchange. Copy only the authorized Provider entry plus the full matching model catalog. The original Provider remains the refresh owner. Preserve a typed `CopiedOAuthCredentialExpiredError`, zero-request audit and cleanup receipt on startup failure. Move credential provisioning inside cleanup protection and ensure cleanup runs even if server disposal fails. This is an access-expiry integrity boundary, not a model tool/workflow gate. Focused positive tests cover valid streamed evidence, exact expiry error and local control access; the real expired-source startup must reproduce the typed error without a benchmark result.

The protocol decision was checked against [RFC 9700 section 4.14.2](https://www.rfc-editor.org/rfc/rfc9700.html#section-4.14.2): rotating refresh responses replace the previous refresh token, and replay can invalidate active authorization. This supports keeping renewal in one authority; it does not establish the remote cause of this particular uncertain exchange.

### 1. Confirmed evidence-consumption defects in the authoring loop

The third author read the complete thirty-row score index but opened only five detailed case records, all from .4. It read no .2/.3 case detail or reference definition. That is a coverage limitation, not evidence that those cases were absent from its directory. Actual `tool_part_request` / `tool_part_outcome` records also show incomplete pages:

The second author similarly read four detailed records out of twenty and only 592/686 lines of its baseline capacity comparison. Its attempted reference-incumbent directory read failed at an incorrect nested path and was not followed by a successful reference-definition read. These are actual read receipts, not an inference from final summaries. They do not establish that every unobserved field was necessary, but they invalidate a claim of complete successful-behavior review.

There is a second, independent loss mechanism: the evidence JSON retains original Tool outputs as escaped single-line strings. `src/tool/text-file.ts` limits each displayed line to 2,000 characters and each page to 50 KiB; `src/tool/read.ts` uses this renderer. Reading more lines does not recover the clipped suffix of an individual line. For example, .4 capacity event 9, `GET https://desk.zoho.com/api/v1/tickets`, has an 8,177-character original output, but the third author's read clips that JSON line. The budget file contains six overlong output lines (up to 16,932 characters), despite its page metadata saying all 413 lines were returned. The exact discovery-evidence file has five clipped output lines too. Original files and logs retain their full content; the loss occurs in what the author receives. This is an author evidence-presentation defect, not proof that the benchmark world lost records or that the generic reader violated its documented bounds.

Why the earlier changes did not cure this: additional instructions to read evidence and preserve successes neither repair the author-facing representation nor establish which pages/fields the author actually consumed. A high requested line limit is not a completeness receipt. The next algorithm improvement should use existing immutable evidence references to provide lossless bounded author-facing views, with original event identity and explicit coverage, then require the author to resolve missing decisive evidence before making a causal claim. This must leave original Tool outputs and benchmark inputs untouched. Verification should demonstrate actual model-visible access to a decisive field beyond character 2,000 and beyond the first page, with exact reconstruction of the cited original field, not merely a file-present assertion. No reader/runtime change is authorized by this audit.

The eight revision tests exercise version derivation, target identity, publication/installation/undo/history, capability integrity, append claims and path errors. They do not measure whether a model reads its evidence completely, preserves operational prerequisites, chooses the correct item or computes the correct amount. Passing those tests validates the transport and mutation contract only. The real official runs provide the behavioral results, including regressions and the unavailable sample.
