## Depth and impact analysis

1. Reported output completes but process waits. `SessionLoop.finalizePrompt` publishes exact-input `idle` through `settleAcceptedExecutionOccurrence`; run only breaks on `terminal`. Bus still forwards lifecycle through GlobalBus to `/event` (the canonical Session stream separately persists it). Thus merely switching streams would not correct the idle/terminal mismatch. Current CLI also starts prompt before lazy event subscription is connected. Terminal matching checks only Session, not input occurrence.
2. Explicit attached chat calls `PrimaryAssistantRegistry.get`, whose cache loads Instance-bound Config in the client process. The server owns configured availability. Client should validate the primary ID without materializing local agent definitions; actual prompt endpoint remains configuration authority.
3. SDK returns HTTP errors in `error` by default; run ignores response errors and assumes catch is sufficient. Input failures directly exit with human stderr; global error handler also emits only human text. JSON branch continues after session.error whereas human branch breaks. Probe default parses empty string as zero, disabling intended inactivity detection; heartbeats renew its timestamp. Stream cancellation currently happens only after iterator return, whose reader merely releases its lock, leaving the server-side stream alive during local disposal.
4. Shared-mechanism audit scope: normal standalone Session completes idle; error/abort can complete terminal; retry remains active. Task/Mission use their own durable ingress/epoch reducers and must not be changed to make a CLI exit. Existing-session and concurrent projects require exact submitted Message ID plus Session identity. CLI bootstrap owns local runtime settlement; attached clients own only their connection. Recovery reuses persisted identities in public Session routes; CLI mints a fresh input identity for each run. Code audit is not runtime proof of every shared path; targeted real checker and persistence evidence pending.
5. No database/schema/Task/Mission lifecycle changes or Prism adapter work. Public contract changes are error JSONL coverage and correct process exit; keep existing event names and stable Session ID where allocated. Risk: output truncation, request/stream races, error duplication, cleanup hangs, attached server cancellation, timeout during long tools.

## Implementation plan

1. Centralize run failure serialization (existing named errors preserved, generic errors explicit), make argument/preflight failures reach it, keep exit 1.
2. Validate agent ID statically and let server resolve configuration; enable checked SDK HTTP results and attached environment auth.
3. Subscribe and observe connection before submitting; settle exact submitted input on idle/terminal, cancel stream before iterator returns, join request and stream and always clear owned timers. Account for stream failure and current occurrence outcome without treating heartbeat as useful progress.
4. Add focused positive contract tests and a real process checker using isolated local streamed provider, local/attached runs, continuation, errors and persistence. Check type/document contracts, then independent review, fix findings, rerun and commit/push main.

### Shared Config lock root cause and repair plan

Phase-instrumented reproduction `opencorvus-test-run-4a4jf7/runner-27256-ivcmS6` again failed both concurrent projects. Its server stderr proves second-project validation completed model/profile checks and stalled inside `ConversationCapability.assertConfig`. That method reads installed Skills. `SkillManager.withCatalogProjection` holds the global durable catalog owner while `installedAtPublication` reads `Config.getGlobal`. In parallel, `writeProjectPatch` already owns global Config generation write, then validates Skills and waits for that catalog owner: catalog-owner -> Config-read versus Config-write -> catalog-owner. All projects stop on the same generation writer, explaining both timeouts and cleanup starvation. This is a shared config/Skill ownership issue, not an isolated chat/model error.

Whole-repository callers: project and global Config writers are the two generation-write entries; Skill mutations and Instance capability preflight take reference locks before Config reads; ConversationCapability.settings takes Skill reference read before Config.get. Current project/global writers also invert that reference-read order. Canonical mutation order will be Skill reference mutation -> conversation reference mutation -> durable catalog owner -> Config generation write -> config-file lock. Use one common owner function for the two writers, retaining reentrant-mutation rejection, candidate validation, exact commit, peer convergence and runtime settlement. No alternate config path or persisted status is introduced. Existing Skill-owned global writes reuse their already-held owners.

Acceptance extension: positive concurrent catalog/read versus project/global Config mutation tests; existing Config peer convergence; original real concurrent-project CLI matrix, including graceful server shutdown. Remove temporary phase instrumentation after diagnosis. Bootstrap model-catalog and Memory-reply harness corrections are separate fidelity fixes, not the deadlock repair.

Independent review identified the remaining recovery inversion before acceptance: a catalog projection may recover an already-published replacement and write Config, so catalog ownership itself must precede reference locks. Canonical order is therefore durable catalog owner -> Skill reference owner -> conversation reference owner -> Config generation -> file. `withSkillCatalogMutation` and `withSkillCatalogReferenceRead` will both enter the existing recovery-capable catalog owner before their process-local reference lock; recursive calls reuse that same owner. This makes ordinary Config writes and recovery-triggered writes share one order, rather than adding a reader/writer bypass. Instance preflight, settings and Skill mutations already enter these reference primitives. Extend recovery tests, then rerun original acceptance; the intermediate four lock cases alone do not prove journal recovery.
