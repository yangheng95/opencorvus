## Analysis before implementation

### Observed behavior and trigger

Real MCP inventory read returned 45 Browser and 8 Computer tools, without server instructions. The builtin Skill payload has no generic browser-use or computer-use entry. Tool descriptions are copied to model definitions. Browser guard failures advise force:true. Computer input consumes the latest observation before one backend action; the description does not explain that consumption. Its amount is actually lines, while Browser scrolling uses pixels.

### Root cause and why existing paths do not cure it

Capability publication and instruction delivery are separate. The existing Skill loader only loads its exact active/granted Skill family; tool availability does not imply a corresponding guide. Adding standalone Skills or only MCP server instructions would not guarantee that all native/projected consumers receive them. The Computer public API further encodes an atomic input as an entire observation transaction, so a model cannot submit a useful ordered group even when it can generate one.

Host runtime currently records active requests but does not serialize physical desktop operations. Authorization is checked before awaiting request-body parsing. An overlapping observation or a queued request surviving takeover can contradict the intended single-owner input contract. This is a shared mechanism concern, not a model/prompt fault.

### Horizontal ownership audit

- Entry points: Chat, Work, Mission and projected Task worker/orchestrator use the same host authority and exact runtime scope identities.
- Occurrences: normal reuse retains logical sessions; a returned human takeover creates a fresh authorization and requires attachment/observation. Restart has no persisted native observation and cannot replay input.
- Terminal paths: session_destroy, Session disposal, owner close and takeover must settle admitted operations and cancel queued/unstarted input. Batch failure must publish the completed prefix and the exact failing action/outcome.
- Concurrency: serialize a complete group and its final capture at the physical host boundary, including different logical/project owners in the same process; revalidate the exact authorization after waits. Input within a group executes sequentially. Observations must not race their own controller mutation.
- Isolation: identities and observations stay per runtime owner. Serialization does not share IDs, credentials, grants or observation caches. Separate application processes and human interference remain outside the in-process lock; guidance requires current visual evidence and explicit target selection.
- Recovery: no retry/replay of effects. Unknown transport or native outcome requires observation and a new decision. A failing action ends the group; human takeover revokes subsequent actions before publication of human ownership.

### Impact and exclusions

- Replace the five model-facing Computer atomic input tools with one typed `act` group tool; one-element arrays cover individual actions. Update catalog, host transport, driver adapter, controller, permission identity and focused tests together. Historical transcripts remain history; no runtime alias or config migration is introduced.
- Keep Browser execution API and connection modes. Repair guidance and force-recovery text without adding an agent workflow state machine.
- Bundle compact Skills in the existing builtin payload. Both `skill` loading and provider initialization/help read the same artifacts. Provider `help` is read-only documentation, not an authorization gate; `session_create` returns instructions naturally so partial projected harnesses already carrying initialization receive them too. Full catalog and future projections include help. No global Skill-mount or Mission-family bypass is needed.
- UI, provider credentials, releases and packaging/restarts are outside implementation scope. No UI automated test is added or run. Actual model behavioral frequency is unknown until exercised; protocol and manual runtime evidence will be reported separately.

## Implementation plan

1. Add concise browser-use/computer-use Skills and a small pure builtin-guidance reader. Expose help and initialization guidance from their canonical providers; update generated payload and tool catalogs.
2. Define one shared Computer action-group schema and receipt contract. Atomically consume one observation for the group, validate all known bounds before dispatch, execute sequentially, return a completed prefix, a typed failure/uncertain index when applicable, and a fresh screenshot binding when capture succeeds.
3. Serialize host desktop operations with the existing lock primitive; validate authorization after parsing/acquiring, propagate revocation into action boundaries, settle cleanup deterministically. Serialize controller operations to protect returned observation ordering.
4. Correct Browser grounding/recovery/evaluate descriptions and coordinate-guard feedback. Explain profile/session ownership, selector evidence/ambiguity, focused keyboard input, short predictable groups and re-observation at uncertain state boundaries.
5. Update architecture and focused positive tests. Run actual MCP inventory/help/initialization and shared host transport checks, package typecheck, docs and architecture checks. Run actual Browser provider in its Node sidecar against an isolated project dev `/ui` page and inspect screenshots. Exercise native Computer against a task-owned application, inspecting before/after screenshots; use no credential or automated UI assertion.
6. Review the complete diff, record exact evidence and unresolved limits, commit only task files, fetch/merge upstream, audit every outgoing commit, complete hooks, and push current main.

## Verification / progress

### Actual Windows finding and plan amendment (before DPI implementation)

- Focused protocol suite: 26 passed, 0 failed. Actual Node Browser sidecar creates an isolated Chrome tab, returns the Skill, navigates the isolated development `/ui`, clicks Settings and returns inspected screenshots.
- User explicitly authorized a short native foreground acceptance interval. Native session/create and capture succeeded. A real two-action click/type group returned two successful dispatch receipts, but the inspected screen still showed an empty draft and the cursor was displaced. This is a failed functional acceptance, not success inferred from a receipt.
- Read-only native diagnostics report primary desktop/screenshot 1921x1201 with scale_factor 1.0. The embedded SDK does not establish Windows DPI awareness before creating its native executor. Upstream [issue 3449](https://github.com/trycua/cua/issues/3449) and [unmerged repair 3450](https://github.com/trycua/cua/pull/3450) document this exact embedded-host class of failure. A coordinate multiplier would retain the cropped capture and cannot repair the root cause.
- Amend implementation: before constructing the application-owned native driver, establish and verify Per-Monitor V2 process DPI awareness in the headless server host using a portable Node-API foreign-function library (Koffi), not Bun FFI. The server owns its process and has no application windows; its driver workers must inherit the correct default before creation. An already-correct host is accepted; a refused/incompatible host gets a typed backend error. No runtime switch, daemon, image resize, guessed scale or user display-setting change is introduced. Packaged Windows runtime must carry the same dependency. Microsoft requires this setup before DPI-dependent calls/windows; validate with a fresh host process and actual input/capture, not only a setter return.
- Browser Settings initially reported a skills inventory timeout during cold startup. A subsequent real `/skill` request completed in 473 ms and returned all six builtin Skills including both new guides. This is tracked as cold-start evidence; do not mislabel it as a failed Skill definition or provider credential issue.
