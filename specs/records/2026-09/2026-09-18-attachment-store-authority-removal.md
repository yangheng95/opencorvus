# Attachment-store authority marker removal

## Recall

- User requires deleting the attachment-store database lock and forbids recreating it. The concrete failure is `Attachment store .../.authority.json belongs to another database authority` after a database reset.
- Acceptance: no production path writes `.authority.json`; a fresh database can initialize and use a project whose attachment runtime previously belonged to another database without an authority-marker conflict; attachment publication, verified reads, garbage collection and Project identity convergence retain one current implementation; the installed-data repair leaves no authority marker and preserves Provider configuration.
- Hard constraints: old task data does not need to be retained; preserve repository source and `auth.json`/`models.json`; do not introduce a fallback, compatibility reader, automatic migration or second attachment location; do not weaken content-addressed pair validation or per-blob cross-process publication locks.
- Observed facts: the first reset was run from the application directory, so it removed SQLite DB/WAL/SHM but not the actual Project `.opencorvus/.r`. Starting installed `0.0.64-beta` recreated `.authority.json`. The failing project and three other old projects carried the same marker. All known markers were removed with the canonical project-scoped reset while the client was stopped. The installed client remains stopped because its current code would write the marker again.
- Direct trigger: `AttachmentStore.write` and `AttachmentStore.sweep` call `claimAuthority`, which creates or validates `<project>/.opencorvus/.r/project/attachments/.authority.json` against `Database.Identity()`.
- Root cause: database reset and Project runtime cleanup are separate operator targets, while the attachment store persists a second database identity in the Project filesystem. A reset that reaches SQLite but misses a Project runtime creates contradictory current database and filesystem authorities. Startup then warns during sweep, and the first attachment write fails closed.
- Impact search: `attachment-store.ts` owns marker parsing, locking, claiming and two call sites; Project open catches its typed authority error; Project identity convergence reads the marker as an additional conflict source; current data architecture documents it; one focused convergence test writes it. Content-addressed pair locking and integrity checks are independent and remain required.
- Plan: remove the marker type, parser, lock and claim implementation; remove both claim call sites and the now-dead Project-open catch; make Project identity convergence rely on its canonical database and embedded-reference checks; delete the obsolete marker-only test; update current architecture. Namespace physical attachment bytes by a digest of the canonical SQLite path so independent databases never share a sweep set, while same-path rebuild and transfer restore keep resolving the same bytes without a marker file. Add a positive current contract that publishes and reads attachments across a rebuilt database/project lifecycle. Run focused storage, Project convergence/open, transfer and reset checks, typecheck, documentation/diff checks, native build/first-run, then independent read-only review.
- Independent agent feedback: the initial marker deletion was complete, but sharing one unnamespaced directory would let one Database sweep another Database's blobs, and the first architecture wording overstated metadata-pair validation during sweep. Database-instance namespacing then exposed a transfer regression because `Database.rebuildSqlite` intentionally rotates the instance ID while attachment URLs remain stable. The final design uses a canonical database-path digest and exact GC wording. The reviewer rechecked the final implementation and reported no remaining findings: no producer for `.authority.json` remains, independent database paths have disjoint sweep roots, and same-path rebuild/import retains attachment resolution.

## Status

The authority marker, its parser/claim lock, both production claim call sites, the Project-open authority error path and the marker-only convergence test are removed. Attachment bytes now live under a deterministic canonical-database-path digest while per-blob publication locks and content verification remain intact. All known installed-data markers were removed while the old client was stopped; Provider configuration was preserved. The installed `0.0.64-beta` client remains stopped because that old binary still contains the removed writer.
