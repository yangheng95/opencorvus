## 总判断

现有系统已有执行、证据读取与同任务续行能力。主要问题是相邻环节对“义务、事实、审查对象、审查通过、最终接受”的含义不一致，导致每个角色完成自己的局部动作，整体仍可接受错误解释。继续增加角色、字段或试验次数，不能自行消除这种不一致。

统一链条是：**原始义务 → 有界派单 → 实际产物与源证据 → 对指定内容的独立判断 → 同执行者修正 → 当前交付验收 → 有可比证据才作进化选择**。

| 环节 | 唯一责任人 | 输入/事实来源 | 输出与责任边界 |
| --- | --- | --- | --- |
| 总体义务 | Mission；直接 Task 则由 Task Orchestrator 承担 | 真实用户要求、授权、原附件 | 任务划分与最终接受；规划者不能重定义用户义务 |
| 任务内分工 | 当前 Task Orchestrator | 原请求、包能力/依赖、已有成果 | 有界工作和明确被审对象；不把执行者总结当成果本身 |
| 业务生产 | 对应原 worker | 原始材料、可追溯前驱、明确派单 | 实际产物；计算、解释、假设和未知均可受质疑 |
| 独立审查 | 现有被派定 reviewer | 指定版本的实际产物、原义务与源材料 | 具体支持/反证、影响和未审范围；不代替 Task 完成决定 |
| 返工 | 原执行者，由 Orchestrator 路由 | 具体缺口、源反证、须保留的正确工作 | 同 Task 新交付及其真实验证；不换任务逃避失败 |
| 接受 | Task Orchestrator；Mission 再判总体义务 | 当前交付、适用审查、真实执行证据 | 显式接受判断；局部 clean 不自动继承为整体正确 |
| 进化选择 | 既有 Evolution Lab 比较/推荐链 | 冻结、可比较的测量和独立评审 | 有证据的选择；单次正常交付或人工修复不叫进化收益 |

## 一次性问题清单

### M1：上游解释被提升为事实或约束

**已证问题。** 包方法要求区分源字段、派生指标、观察与假设，但多个生产者又要求保留上游 explicit unknowns。G65 中“后来是否关闭未知”从 charter/dossier 延续到分析与终稿，而原 `closed_month` 已能回答行政关闭月份。保留原证据被混同为保留上游结论。

**统一处置。** 用户要求决定义务，原数据决定可观察事实，团队产物提供可质疑的解释。未知同样是需要依据的判断；下游应保留可追溯原件，允许反驳解释。集中在包方法及真正冲突的生产者指令收敛，不在每层继续复制同义警告，不让 Host 按字段或关键词判业务真值。

证据：[包方法](../../../expert-squads/builtin/data-analysis/skills/method/SKILL.md)、[synthesizer](../../../expert-squads/builtin/data-analysis/agents/data-analysis-insight-synthesizer/system.md)、[feedback-01](../../artifacts/2026-09-27-team-feedback/assessment.md)、[G65](../../artifacts/2026-09-27-review-evidence/assessment.md)。现有 `.3` reviewer 已改变证据标准，仍漏判，故不能只重复同一改法。

### M2：身份锚点、实际审查对象和条目范围混在一起

**已证问题。** adapter 开头要求检查 exact assistant message，并突出生产者的简短总结；Core 与包则允许/要求检查实际 Artifact。生产者又被要求把 final message 写成 narration。消息身份正确并不能说明审查了消息指向的全部产物。注册片段只要求生产者暴露自认未核验的声明，且排除读过文件和观察过的 Tool 结果；它不能作为独立审查的完整范围。

**统一处置。** 保留 Session/Message/hash 身份定位和真实 Artifact provenance，但把“谁交付的哪次结果”和“这次需要审什么”明确分开。实际被审内容由真实派单义务和选定产物决定；生产者注册条目只是风险提示，不能缩小该范围。统一 adapter 投影、Core 职责、注册片段的含义和选定包的职责；不新增角色、目标数据库或另一份产物运输。

证据：[输入投影](../../../packages/opencorvus/src/fact-check/index.ts)、[Core](../../../packages/opencorvus/src/prompt/core/fact-check-core.txt)、[注册片段](../../../packages/opencorvus/src/prompt/fragments/fact-check-registration.ts)、[包 reviewer](../../../expert-squads/builtin/data-analysis/agents/data-analysis-fact-checker/system.md)。G65 原 user input 同时要求审简报；完整 `artifact_read` 确实返回了错误声明，原材料也读到了。因此不存在本例读权限或运输硬阻断；上述职责冲突成立，但不能独占解释全部漏判。

### M3：局部判断的有效范围在接受时被放大

**已证问题。** FactCheckReview 的条目与数量由 reviewer 自报，Host 检查结构和一致性；clean 表示该声明集合的结论，不是用户义务覆盖证明。包 audit 审 brief，后来 report 可能新增或改变解释。feedback-01 的最终报告被完整读取后仍接受，不能归咎于“没读到”或 Task/Mission 没有接受职责。

**统一处置。** 将业务事实判断、请求覆盖、当前版本适用性区分清楚，由已有责任人合并决策。审查输出明确具体被审内容、结论与遗漏/限制；接受者按原请求检查当前交付，不能以条目数、出版状态或 clean 标签作替代。涉及实质新声明/修正时，复用已有 reviewer continuation 对新交付作适用审查，保留 brief audit 的原范围。不得每个产物机械增加多层审查，也不得让 Host 新建“覆盖业务答案”的 gate。

**保留现有正确合同。** `orchestrator-core` 已要求原义务与证据对应、反证解决、最新审查匹配最新交付；`complete_task` 的 summary 已属于 Orchestrator 接受判断。不能再声称系统没有这些要求，或再加一段同义“必须仔细检查”作为修复。需收敛的是 M2 与本环节交接的具体对象/范围，消除局部 verdict 被扩大解释的接口语义。

证据：[审查 schema](../../../packages/opencorvus/src/fact-check/schema.ts)、[审查持久化调用](../../../packages/opencorvus/src/orchestrator/fact-check-tool.ts)、[完成输入](../../../packages/opencorvus/src/orchestrator/task-lifecycle-input.ts)、[Orchestrator](../../../packages/opencorvus/src/prompt/core/orchestrator-core.txt)、[Mission](../../../packages/opencorvus/src/prompt/core/mission-core.txt)。

### M4：有反馈原语，不等于有有效的业务反馈

**事实与缺口。** 原生 coordination/continuation、完整 `turn.input` 改目标、同 worker 第二次 merge/publish 都已存在且有真实使用证据。guidance 只补指导，不自动改变继承的结构化审查目标。feedback-01 证明小舍入自纠可续行；G65 在给出参数错误后仍未纠正调用；尚无“独立发现实质反证→原执行者修正→复核通过”的完整业务证据。

**统一处置。** 反馈由既有 Orchestrator 负责，把原义务、具体反证、当前对象、要修的差异与须保留内容一次送到原执行者；复核指向实际新结果。统一这些派单语义与 M2/M3，不另造调度器/角色/Task，也不以失败次数自行引入新轮次或费用上限。G66 已修实际发布层级障碍，不重做或推广为业务纠错成功。

证据：[continuation 投影](../../../packages/opencorvus/src/orchestrator/dispatch-turn-projection.ts)、[包 scheduler](../../../expert-squads/builtin/data-analysis/agents/orchestrator/system.md)、[G66 主记录](2026-09-25-supervision-causal-iteration.md)。

### M5：协作接口与上下文中存在多余负担，不能用底座重写替代梳理

**已证局部问题。** 来源搜索子集未命中曾被解读为全局缺失；G61 已运输作用范围，但 discovery 指令仍将 empty result 概括为 missing-evidence fact。多角色反复构造复杂发布参数导致自然失败，G66 已将选定包收敛为单一结构。两分析分支本应并行，实际却先后派单，第二派单还加入第一分支结果。

**统一处置。** 整理现有交接：查询结论必须保留查询范围和完整性；已知、授权的精确证据复用当前结构化引用；角色只携带完成当前工作需要的材料；真正独立分支由已支持的并行派单表达。基础身份、完整读取、权限、不可变来源与实际持久化保护保留。

**不得升级为已证结论。** 尚未复现“已请求并行但 Host 串行”，也未证明固定七节点本身必然错误、每个包都需要更换发布器或减少审查。不能凭耗时/角色数改图、造新工具发现层或扩大到所有包。上下文/接口整理与 M1–M4一起评审，不独立扩成性能重构。

证据：[discovery](../../../packages/opencorvus/src/fact-check/discovery-instruction.ts)、[原调度观察](../../artifacts/2026-09-27-team-feedback/assessment.md)、[当前发布器](../../../expert-squads/builtin/data-analysis/tools/publish-data-analysis-artifact.ts)。Codex/ZCode 的参考价值是主协调者保留目标、有限上下文、反馈回原执行者；它们有状态机与恢复，不能反向歪曲为“成熟系统不需要状态”。

**统一处置。** 先完成下面的整体机制方案，再为必要效果验证固定研究问题及结束后的下一决定。协议正确、业务交付正确、纠错发生、优化/进化收益分开记。一次正确交付无错误触发就记未触发；不能重抽直到找到错误或成功。没有可比基线/候选测量就不选择“已获收益”的候选。

## 统筹实施顺序：一套方案，分清责任层

1. **先统一 M1–M3 的语义合同。** 确定每个角色的原义务、输入证据层级、实际被审对象、审查有效范围与接受责任。共享 Fact Check 的 Message 身份锚点与产物审查语义同时收敛，选定 data-analysis 方法/scheduler/reviewer 的相邻职责同步；不是只改一句 reviewer 提示。既有注册能力作为风险提示保留，不能同时留一套“注册之外不审”和一套“完整产物审查”的冲突解释。
2. **再沿同一责任链整理 M4–M5 的交接。** 复用 exact Artifact 引用、真实读取、完整更新的 adapter input 和原 worker continuation；查询范围、版本适用性和具体异议必须随本次交接明确。没有必要证据，不改 Host API、数据库、队列、恢复算法、其他包或角色数量。已完成的 G61/G62/G63/G66只作为前提。
3. **最后验证这套改动，而非继续找下一处小问题。** 本地真实 checker 检查身份/内容运输、正确审查对象、原任务续行、最新版本引用及错误合同；这不代替模型判断。只有机制方案与实现稳定后，才决定一个必要的、完整预登记的业务观察。旧运行不恢复，不向模型给已知答案，不默认恢复 review-unit 草案。

统筹者为恢复后的原 Opus 主管；Codex负责按原件独立复核，不并行改它持有的源码。22:45后的原会话交回安排不变。本文件作为新的方案入口；历史 G 号仅供证据定位，不再按旧待办逐个扩展。

## 验收与停止扩展的边界

- 文档/代码自洽：同一审查不再一处指总结消息、一处指完整产物；局部事实判断不被解释为完整请求接受；每个具体异议和接受决定有明确责任人。以真实输入/输出和源码审查确认，不用提示字符串存在或自报条目数量冒充。
- 运输与反馈：原源材料及具体被审对象可达，实际新交付与其适用审查对应；反证回同 Task 原负责人。沿已有原语验证，不另建影子状态或自动业务路由。
- 业务效果：只有自然错误被独立识别、原负责人实际修正、修正后复核且正确工作保留，才记一次完整纠错观察。没有触发、不识别、不执行、未复核分别如实保留。
- 进化收益：另需预先冻结的可比测量和独立评审；本次机制梳理、接口修复和一次业务观察均不能单独声称达成。
- 任一新发现先归到 M1–M6及具体影响面；不影响主链的事项记未知/后续，不即刻派生新工单。用户未授权的模型、账号、预算、窗口、分支或 UI 自动化不引入。
