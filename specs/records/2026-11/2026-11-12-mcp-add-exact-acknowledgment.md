## 根因与影响

1. `39899/ui/` 基线提交 `ack-review`。正式 `0c826c9f-6f31-47f9-b20e-dfb9058d2712` 实际保存并返回 HTTP（Hypertext Transfer Protocol，超文本传输协议）200 与目标 `connected`。隔离代理给浏览器送达完整 200 和只有 `other-receipt` 的状态映射，符合公开静态结构，但没有本次目标。页面无提示、关闭表单，重开时两个字段均为空，原项目列表随后显示独立读回的真实状态。中文第二次提交 `invalid-review` 的正式 `45f2fb42-0c97-483f-9770-37eb0e1147e7` 也完成连接，浏览器收到完整 200 和同名 `failed` 条目但缺少必填 `error`，页面同样清空。原两笔真实协议初始化成功，另一项目为空。[基线截图与实际回执](../../artifacts/2026-11-12-mcp-add-exact-acknowledgment/README.md)
2. `apiJson` 能解析完整正文，并对非 2xx 提供 `ApiError`，新增服务函数仅等待传输，丢弃 2xx 内容。连接面板把该 Promise 成功结算当作新增回执，在独立读回之前执行清空。先前覆盖了网络截断、草稿所有权和连接操作的布尔确认；合法 JSON 的目标与状态语义未在写入回执处核对，原前端服务测试用空对象作为成功新增回执也会通过。
3. 服务端的新增回执是有效配置的状态映射，确切目标名来自已规范化的提交；目标的 `failed`、`needs_auth`、正常连接和执行所有权都是有效保存结果。新增应核对所提交的自有键及其状态，独立读回继续验证整张当前项目映射。不能用其他键、派生值或 HTTP 状态替代这个凭据，也不能把已保存但连接失败当作保存失败。项目隔离、配置、服务端、旧数据、API（Application Programming Interface，应用程序编程接口）、任务执行和调度契约沿用现状。删除的配置快照回执与控制的布尔回执具有各自结构，本批处理新增目标。

## 实施与验收

- 将已有单条 MCP 状态判断复用于项目读回和新增回执。新增要求本次确切名称是回执映射的自有键，且其值符合已生成的状态结构。区分目标缺失与目标状态无效的本地具名错误，送入已有的不确定回执分支，保留草稿、展示实际读回、维持一次明确核对。合法目标回执按既有完整确认清空所提交的匹配草稿。
- 核心前端合同核对确切目标的成功与明确失败状态、错名和缺失错误详情的具名错误。真实桌面在另一隔离项目重跑两种完整错误回执及有效完整回执，复核双语、草稿、诊断和真实连接状态。检查后台实际请求次数、协议响应、两项目持久定义和零模型活动，再关停隔离资源。
