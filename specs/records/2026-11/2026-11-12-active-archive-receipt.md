# 主动归档回执中断后的状态确认

## Recall

- 用户要求持续分批调查、先落盘再实施、真实桌面交互及截图人工复核、聚焦正向测试、同步上游并推送，由当前操作者独立完成。此批验收主动归档一笔请求、原项目精确读回、原内容与归档时间保留，以及传输和明确错误下的界面反馈。隔离项目使用独立开发服务和有头浏览器，无凭据或模型请求。
- 已读 `AGENTS.md`、`03-control.md`、`07-panel.md` 的归档段落、[归档恢复回执](2026-11-12-archive-restore-receipt.md)、[草稿编辑回执](2026-11-12-mission-draft-edit-receipt.md)及[工作台事件范围](2026-11-12-work-ledger-selection-invalidation.md)。全仓追踪 `setConversationSessionArchived`、`setTaskArchived`、`setMissionArchived`、`restoreMission`、`settleArchiveRestore`、`verifyWorkLedgerRestore`、原身份读取、连接与过期条件、导航/标题归档、两条交接归档、设置和阅读页恢复、服务端一般 Session 与三个产品归档入口、终态和事件测试。相关 Overlay 服务测试没有界面自动化。

## 根因与影响

1. 隔离开发服务 `39794` 通过真实 WebSocket 连接的代理 `39795` 提供当前桌面。标题菜单归档所选 Chat 时，服务端返回 HTTP（Hypertext Transfer Protocol，超文本传输协议）200，代理保留前 12 字节后断开。精确读取显示同一会话已经归档，标题下出现归档时间和只读内容，弹窗同时显示 “Couldn't confirm the action” 并建议重试，诊断为 `TypeError: Failed to fetch`。原写回执 `980f6d42-037b-4eca-9b20-595b17016d2f`，正式精确读取 `af839d4c-7187-4d0b-8537-845df78556b1` 与回执归档时间一致。另一同名项目读取原身份得到 404 `934cab78-ddda-43d4-90f1-212d3fffedf7`。
2. 由侧栏主动归档原多步任务草稿，写回执 `8a125fb4-899e-49d9-a161-9c64ab7baf7c` 同样截断。真实事件使活动行退场，该行的错误弹窗也失去所属界面。服务精确读取 `e68a135c-cddf-4270-881c-34109e36569f` 返回同一会话、草稿、目录、归档时间、原请求和零子任务。后台事件可以刷新列表或选中读取，发起动作的 Promise 仍从响应解析异常退出，未走归档后协调。这个竞争可以令同一故障表现为消失的行或互相矛盾的反馈，取决于发起处仍否存在。[桌面和正式接口证据](../../artifacts/2026-11-12-active-archive-receipt/README.md)
3. 当前 Task、Mission、Chat/Work 主动归档都只用写回执触发协调。Task 对任何解析完的 JSON 都继续协调，Mission 缺少正向身份验证，Chat/Work 直接接受写返回对象。已有精确读确认只用于恢复方向，前一批共用的连接权威和不确定回执判定覆盖不了这些入口，服务端结算请求选项仅改变客户端等候期限。Task/Chat 的成功返回恒为 `true`，现有 Overlay 调用端的 `false` 分支没有生产结果；采用已确认时完成、未确认时抛出实际错误的同一个约定，并删除对应未用文字。Mission 的两个方向合为同一入口，原始目录、Mission ID（Identifier，标识符）和 Session ID 必须齐备。
4. 横向审计把回执与执行轮次分开核查。Task 路由使用当前项目权威，活动轮次先完成取消、根会话输入结算和 Goal（持续目标）暂停，再提交归档时间，已终结轮次走同一保留操作。Mission 首次归档随关闭轮次事务写保留标志，已关闭轮次和恢复经原关闭事件约束，失败或重启仍由既有关闭/恢复 owner 收敛。右栏 Chat/Work 按目录、类型和 experience 校验，结算原 Prompt（提示请求）后才写会话归档；恢复不重新开轮次。一般 Session 路由是公共独立入口，按公共权威约束处理，没有本范围 Overlay 调用。项目删除、直接停止和删除走各自不可逆契约。侧栏、标题菜单及两类交接对已执行服务不增加重新启动或写入。真实读与回执表明本次故障发生在提交完成后；现有并行/冷启动和终态测试进一步检验取消、闭合和保留。真实模型下的活动轮次时序本轮未验证。
5. 公共协议、数据结构、取消 provenance（操作来源）、调度、并发结算和已提交事件保持现有归属。设置归档和阅读页恢复依旧用当前投影与原焦点守卫。计划只调整 Overlay 对归档回执的结算、已确认后的现有协调及两种语言的未确认提示，不需数据库迁移或版本发布。

## 实施与验收

- 用一个归档状态结算函数复用现有 `settleMutationReceipt`，将归档和恢复的检查共同用于三个产品 owner。Task 写回执要求真实 `true`；Mission 要求确切草稿/会话/目录和归档时间方向；Chat/Work 要求原会话/目录/experience/界面归属和归档时间方向。写回执中断或无效时，在同一连接精确读一次原 Session 或 Task；仅当前身份和请求方向相符才进入既有成功协调。明确拒绝保留原错误，未确认保留写、读两个真实诊断。不会自动再发归档或恢复。
- 标题和活动行反馈采用当前语言；归档结果仍未确认时引导在设置归档查询该项目的条目，显示原有诊断。归档结果确认后走原有列表/选中协调。恢复仍显示现有恢复专用提示。
- 用真实开发服务及 WebSocket 的前置代理截断归档回执，人工验收同一桌面英文所选 Chat、中文归档入口和设置归档精确打开。检查完整回执、截断后精确确认、确认读取中断后的界面和诊断；对同末段项目隔离、一次写、原身份/请求/归档时间用线上契约验收。争取验证真实 Task 与 Mission 归档/恢复；准备 Task 前态的方式单独记录，禁止以测试夹具代替真实页面。
- 聚焦服务测试覆盖精确归档、恢复、明确拒绝与未确认错误。运行已有三个 owner 的真实路由生命周期测试和独立结算测试、Overlay 类型与本地化、构建、公开面及文档检查。确切尚未满足项随候选结论记录。
