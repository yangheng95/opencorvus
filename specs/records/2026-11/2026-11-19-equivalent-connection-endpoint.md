## 基线与根因、影响

1. 首次观察在上批 `40208`。本批再从新项目 `40210/ui/` 实际录入未发送草稿 `B334 draft stays with this project`。保存前 Network 的 Proxy 显示该项目。只在现服务地址末尾添加 `/` 后回车，页面退出项目作用域。回到工作区，文本仍存在，但从有项目标题的草稿变为全局输入框中的草稿。并非文本丢失，也没有发送消息。保存前后服务地址的实际请求均以同一回环服务为目标。
2. `saveConnectionSettings` 先以 `requested.serverUrl !== settingsStore.serverUrl` 决定离开。`createWorkspaceDepartureIntent` 捕获原文件和选择归属。确认后清空目录、工作条目及模型指针，`prepareComposerDraftDeparture` 把纯文字移到全局并退役服务器归属引用。这些是真正换端点所需的操作。尾斜杠两端均通过校验，网络请求已经由 `joinServerBaseUrl` 生成相同根和目标。旧实现以地址拼写近似表达操作员离开意图，在这一步误把同一目标当成不同端点。
3. `configure` 也以原始地址变化推进 API（Application Programming Interface，应用程序接口）归属。`SideChatPanel` 与历史显示偏好中有原地址键。只跳过工作区清空、仍发表另一拼写会更改历史键和活动归属。普通项目输入偏好已有自身范围合同，不批量改写历史拼写。沿用已经应用的有效地址拼写解决本次关系，保存回执和页面显示同一事实。无新索引、别名映射、双读写或存储迁移。
4. 同一有效目标判定直接使用既有 `joinServerBaseUrl(value, "")`。标准解析覆盖尾斜杠、默认端口及主机大小写，对不同协议、主机、端口和服务前缀仍判为不同。不能推断 `localhost` 与数字地址必指同一服务。格式错误不作为等价，从原保存路径获得具名校验；历史无效输入可由真实有效地址纠正。
5. 手动保存同一地址但凭据变化继续刷新当前归属并保留工作区。真正离开仍使用已存在的 reservation（预留）和持久回执。托管进程轮换、服务连接协议、数据库及 Task/Mission/Session occurrence（执行轮次）策略不改。两次 HTTP（Hypertext Transfer Protocol，超文本传输协议）连接均正常在线，没有调度或终态异常证据。
6. 主要风险是误吞校验错误、误判代理前缀相同、丢失新地址或让显示与发表值不一致。只吸收比较时的既有具名 URL（Uniform Resource Locator，统一资源定位符）错误，由实际保存处理输入。真实切换只用一对隔离回环服务。以正在保存的唯一表单和长度有限的反馈所有者更新实际回执地址。
