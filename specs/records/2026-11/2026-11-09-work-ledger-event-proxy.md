## 实施前证据与影响

早期第 105 批的真实页面截图里，主页已有项目但左侧 Projects 仍说「No work yet.」。该轮服务实际先完成列表（10:27:35.629Z），后完成默认项目路径（10:27:36.314Z），其后重复创建 SSE 请求却没有同页列表重读。该现象也可能来自项目实际读取与注册先后顺序，不能单凭文本推断产品根因。第 107 批对照 39156/39158 的正常首读在路径准备之后，列表有项目（图 01）。

代码查明 HTTP（超文本传输协议）只读测试代理只有 `request` 事件，未转发 WebSocket 升级；服务端可以准备真正的 SSE，而浏览器未能通过对应 WebSocket 接收它。直连与代理上的原 SSE 均实际给出 `work-ledger.connected`，这只证明底层流可读，不证明桌面接到它。项目落盘后原 `Project.Event.Updated` 经过共享事件边界，正常产品路径不依赖同一个 `/path` 响应。原测试代理的目录成功与失败行为仍由真实请求和界面证明；代理不能作为会话、任务终态、唤醒、重试恢复、重启、串并行或多项目事件的端到端证据。影响是诊断范围，未发现共享产品调度异常。

对照决定：记录一个仅监听隔离本地端口、保留原 HTTP 数据和 WebSocket 双向字节的诊断代理，明示它在此批的选定慢路径实验配置与用途。比较同一次真实登记动作在只转发 HTTP 与完整代理下的桌面行为。没有产品补丁；不因为旧基线假象改动现有 SSE、项目注册、列表缓存或计时器。证据适用项目元数据与此启动顺序，不能推出所有启动时序均已覆盖。
