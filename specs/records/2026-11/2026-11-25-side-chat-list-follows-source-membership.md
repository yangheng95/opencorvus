## 实施前证据、根因和影响

- 实际 `41804/ui/` 使用 `main-9eEzcgq5.js`。正式 Chat 创建端点在两个隔离项目各创建一个来源，其中主源是 `ses_hMAuuk19aX4W2AsCeJj8`。同源两个实际标签页打开 Side chat 1。观察页在该旁聊中输入了未发送草稿。同源另一页点击 New side chat，实际切到 Side chat 2 `ses_-zUO43KkLzzDSAnfEnv2`。观察页此后打开选择器仍只有 Side chat 1，要关闭再打开整个面板才读到 2，且重挂载把视图切到最新项。公开列表读取 `f34966c7-44df-4ec8-86a0-e564269ac44d` 已接受两条同源原会话，另一项目源保持空列表。两条旁聊均没有消息，也未运行模型。[基线实图和读取回执](../../artifacts/2026-11-25-side-chat-list-follows-source-membership/README.md)
- 服务在旁聊原事务提交后发布真实 Session 创建事件，其中 `metadata.sideChat.sourceSessionID` 指向源会话。现工作记录通道把旁聊作为独立辅助会话排除在普通 Chat／任务的刷新外，这符合主侧栏范围，但没有为旁聊列表投影成员变化。`SideChatPanel.loadSessions` 只从源／会话连接权限变化或初始失败重试调用；本页创建只合并自己的响应。整页连接在线、重新打开选择器也不会重新列出，重新挂载面板才会读。仅重新打开选择器时刷新也存在空集合的问题：现有选择器在零选项时不触发打开回调。
- 影响同一来源下合法新建、归档、恢复及删除的旁聊目录，包括断线期间的成员变化。普通消息、会话状态、模型选择和标题更新不改变成员，不能引发旁聊列表刷新。主任务、独立执行轮次、所选旁聊的消息流、输入归属、持久数据和权限继续由原机制负责。实页只有两个完成提交的空旁聊，没有任务执行、调度、队列、唤醒、恢复或终态异常。最初为观察准备的裸 Session 根节点不是 Chat 工作台来源，真实链接被明确拒绝，已改用产品的 Chat 创建入口并核实精确目录。这是夹具准备错误。

## 实施方案与验收

- 沿现有工作记录统一事件流，从真实 Session 创建、归档状态改变和删除事件投影专用旁聊成员事件。只带原项目、目录、源与成员会话身份。事件只通知一次已提交的事实，名单继续由原旁聊列表接口读取。现普通工作记录、通知和任务读取各自保持原有事件筛选。统一连接重新建立时复查当前源名单，弥补断线期间的变化。同步公开事件声明、生成的接口投影和当前架构。
- 复查仅影响当前接口权限和准确来源／目录。使用同一个现有列表读取逻辑，首次读取建立状态，成员变化在现有名单上复查。在途期间合并一次待复查，并在当前本地创建结清后收敛。接受时保留仍存在的当前旁聊、打开的消息流、草稿和作者焦点。成员确实离开时改为同一原列表中最新项；空列表保持可见且可新建。读取失败继续显示已接受的名单，并呈现原诊断与可重试操作。源变化、面板关闭和连接权限退休会取消未完成读取。
- 使用相同隔离生产式开发服务和真实桌面页面重复两标签操作，确认不重开面板即可在选择器看到新增旁聊，同时原选择及草稿稳定。再检查另一项目与该来源隔离，做一次保留数据的归档／恢复及真实重连，核对原名单和事件身份。运行正式接口及事件正向检查、类型、双语、构建和文档检查。发送消息及模型不属于此名单行为验收。
