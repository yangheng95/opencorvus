## 根因与影响（实施前）

实际基线 `40616/ui/` 加载 `main-Dy2mKUlK.js`。用正式项目对话和 Shell 请求保存四条用户命令及其退出记录。静默成功命令原生输出为空，退出码为 0，正式回执只有附加结构。桌面展开后，「Output」却显示整段退出字段，标题和输入区已经显示退出码。退出 7 的命令有实际输出 `Observed validation note`，其后也重复附加字段。另一条命令确实打印三个包含同名标记的正文行，正式输出尾部随之出现独立的应用记录，两段文字在默认界面上无区分。本人查看三张截图，并从正式导出逐项核对静默、普通、有内容非零退出和字面标记四个精确工具回执。[基线截图](../../artifacts/2026-11-23-shell-output-readable-receipt/README.md)

直接原因是已完成 Shell 输出沿通用纯文本路径，把正式持久回执整体当作可读正文。当前 Raw（原始内容）切换只对结构化 JSON（JavaScript Object Notation，结构化文本格式）开启，Shell 结果是文本，界面无法在一份原回执上切换显示。已有处置保留退出码于正式回执和结构状态，确保截断、模型和原始导出准确，但未给详细界面可读投影。影响限带确认退出码且只包含普通尾部退出记录的完成 Bash 结果阅读。相同完整文本继续用于保存、重放、导出、原始查看与复制；真实输出中的同名字面文字需保留。附有超时、背景进程提示等额外记录的原详情完整保留。路由、持久数据、工具授权、运行状态、调度、队列和模型不变。

## 方案与验收

把现有 Shell 回执文本写法移到生产者和界面都已依赖的纯工具库中，以同一写法按正式状态的确切退出码匹配最后的简单退出记录。静默命令可读视图明确显示本地化「命令没有输出」。有输出时显示实际文本，打印同名标记仍能阅读。带额外记录或非正式格式的现有结果继续作为完整正文显示。沿用已有 `ToolPayload` 存储的原始内容切换、展开和阅读位置；可读输出仅为同一字符串的展示，复制按钮明确标为复制完整回执，实际字节仍取当前原始回执属性。保留原处理中的终端文本显示和所有其它工具行为。风险包括误把真实命令文字当作信封、截断语义、丢背景说明、静默时无法获取完整回执和本地化或标题焦点不一致。

候选 `40618/ui/` 从相同的实际四个 Shell 请求验证正式回执完全一致。人工复核中英文静默「无输出」、普通两行、非零退出旁的真实一行、字面同名标记，确认切换到原始时可读完整真实记录，切回可读视图恢复展示，原命令、数字、焦点和复制反馈准确。共享格式聚焦正向测试覆盖确切输出切取、空输出、字面标记和后台/额外说明原文，原后端验证确切正文、非零退出数据与尾部截断。类型、双语、正式构建、文档及架构检查。核对两个隔离服务的准确项目和数据，正常关闭、提交、合并上游并推送。
