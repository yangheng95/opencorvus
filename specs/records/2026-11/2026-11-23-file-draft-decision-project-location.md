## 修改前证据与影响

真实基线 `40412/ui/` 使用 `main-BVXNIiKP.js`。两套独立 `site-notes` 项目都有 `notes/receiving.txt`，正式读分别得到 `Warehouse: north` 和 `Warehouse: south`。实际在北区添加未保存行后点南区，英文确认只显示 `Save changes to notes/receiving.txt before leaving?`。选择继续编辑保留原文和新增行，焦点返回南区项目按钮。再次实际放弃本人测试草稿，进入南区。在其同相对路径文件添加未保存行后点北区，英文确认正文完全相同。保留南区草稿并切换到简体中文，使用实际编辑器的「从磁盘重新加载」，确认同样只显示相对路径。执行放弃并重载后，应用显示南区原文及没有未保存的更改。两个正式读取均为 200，磁盘内容与起始原件一致。 [基线桌面截图和确切读取](../../artifacts/2026-11-23-file-draft-decision-project-location/README.md)

旧的草稿确认修复已经把原因和原文件 `path` 在决定开始时成对保存，成功防止退场动画跟随目标刷新。`path()` 仍是项目相对键，而 `directory` 只存在于作为保存所有者的真实 `FileEditorTarget`。提示因此虽稳定，两个不同项目可以出现完全相同的身份文字。离开与重载共用同一个对话框和已接受草稿决定。普通比较已使用准确项目路径，该显示只属于自己的比较快照。影响是操作者在 Save（保存）、Discard（放弃）或 Reload（重新加载）前无法从确认本身辨认源项目。实际取消、丢弃和重新加载均按现有文件与流程结算，未发现写错文件或 Task（任务）、Mission（多步任务）、Session（会话）调度、队列、唤醒、重启恢复、并发或终态异常。公开接口、存储和权限不参与这项呈现变化。

## 方案

将文件比较已有的完整服务路径拼接复用于同组件两个对话框。离开决定发起时，从该次原 `FileEditorTarget` 取完整路径，继续和原因存入唯一提示快照。正文将完整路径单列为可换行的双向隔离文本，继续使用现有两种原因的双语短句解释操作。共享当前两个对话框的位置样式，保持路径原字符及空格。继续编辑、保存、放弃、重载、焦点、错误、动画期间的原目标和写入修订仍沿现有准入。更新架构合同。
