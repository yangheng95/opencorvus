## 修改前证据与影响

基线 `40408/ui/` 提供 `main-PwFUbjDs.js`。北区和南区各是真实、身份不同的 `site-notes` 项目，均有 `notes/receiving.txt`。在资源管理器实际打开文件并输入各自的临时草稿。两个英文比较框同为 `Compare versions · receiving.txt`，正文位置同为 `notes/receiving.txt`。磁盘与草稿内容各自正确。只改南区实际文件的数量为 29，在比较框「Read disk again」后显示 `29` 对未保存草稿中的 `12`，并启用采用磁盘基线。该框仍只显示共同相对路径。简体中文复查也复现。正式读取北区保持 12、南区为 29，均返回 200 且与真实磁盘一致。 [基线截图和源数据](../../artifacts/2026-11-23-file-comparison-project-location/README.md)

同一 `FileComparison` 请求从当前 `FileEditorTarget` 捕获 `directory`、`path` 和连接身份，既有文件接口以目录和相对路径读取确切快照。对话框标题只使用文件名，位置只取 `target.path`，丢掉了该次读取绑定的项目根目录。工作台普通标题此前只调整相对位置换行，比较读取和基线采用修复只约束操作归属。两者都未解决两个项目的相对路径完全相同时如何在对话框里独立确认位置。可稳定重现的影响为比较窗口中的目标辨认，遵循原规则的文件内容、版本和草稿均正确。无界面写入发生，也未发现 Task（任务）、Mission（多步任务）、Session（会话）调度、排队、唤醒、重启恢复、并发或终态异常。只读绝对来源无需进入这个可写比较入口。根本变更与接口、存储、权限和执行无关。

## 方案

比较框位置用 `read.target` 的项目目录与项目内规范路径合成一个完整服务路径，复用 `isWindowsPath` 和 `normalizeServerPath`。路径采用已有文件界面的正斜线显示语法，保留文件名与目录内部空格，支持按容器宽度折行。双向隔离保护路径字符排列。显示路径是本次已知逻辑目标，可随当前比较对象更新。路径不参与读取、比较、采用基线或保存。标题保留简短文件名。补充架构中的比较呈现，现有比较按钮、样式区和状态继续承载操作。
