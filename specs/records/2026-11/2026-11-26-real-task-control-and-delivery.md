## 首轮失败：检查器缺少当前创建合同

- 现象与触发：`seed-ingress` 的首个 `POST /task` 被正式服务的目录准备前校验拒绝，明确字段错误是 `promptProfile` 期望字符串但收到 undefined。预检凭据、目录投影及实际模型均正常，不能归因为 Provider 或任务调度。
- 数据流根因：当前 `CreateTaskInput` 要求显式专家团身份；检查器 `createTask` 仍以未校验的 JSON 手写旧请求，只包含支柱、来源、标题、需求、模型。该脚本排除在核心 tsconfig 的检查范围，既有局部控制测试没有经过这个真实创建请求，无法发现接口合同演进后的遗漏。
- 全仓影响：已核对 canonical `engine/model.ts`、服务目录准备校验、正式路由、`EngineService`、SDK（软件开发工具包）及界面创建调用；当前其他被检索到的真实 Task 检查器已显式指定专家团。缺陷是本检查器的两个 Task 创建共用入口，产品拒绝错误请求的公开合同正确。本轮尚未观察到调度/并发/恢复异常，不能以输入拒绝为由重构它们。
- 修复方案：在原项目模型投影预检的同一 Instance 中，使用 `Config.get` 和唯一 `PromptProfile.activeID` 读取当前已物化的专家团；两个创建请求明确提交这个身份，并通过 canonical `CreateTaskInput.parse` 构造请求。保持配置单源、原角色与工作流，不引入硬编码专家团、语义路由或兼容默认。公开接口、持久数据及产品执行不改。
- 验证与风险：先核对两个 Task 共享当前请求构造，再以真实检查器重跑，必须观察正式创建接受以及原后续执行路径；补充脚本范围类型检查，复用相关正向创建与控制合同检查。所有重跑共用剩余 30 次请求。风险是当前配置专家团的实际角色行为不同于历史基线，保留具体接受身份和派发事实，不由宿主补造模型决策。
