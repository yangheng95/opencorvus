## 实页发现：真实交接消息与控制唤醒同名

- 本人从编程用途、多步任务真实输入创建 Mission `ses_-zUNt8zYJzzVZK3isz0S`，由当前产品正常创建 Task `tsk_g00Vc6rEH000wydhL06W`。没有通过后端直接制造该 Task 或消息。Task 实页首次连续显示两个相同的“调度上下文”，展开后第一条是 Mission 原交付要求，第二条是 Orchestrator（编排器）的控制唤醒。截图 `run1-request-and-wake-same-label.png` 和公开 Session 消息给出直接证据。
- 原始事实：第一条 `msg_g0Vc6rFSW00ZTsW6xSV8` 的 author=mission、role=user，正文 TextPart 没有 control 类型；第二条 `msg_task-root-control_art_hHH2jR7ip6HCtyfRnygx_art_hHH2jR7ip6HCtyfRnygx` 的 author=orchestrator、role=user，其正文 TextPart 明确 kind=control、source=system。两条真实参与者消息及正文完整保留，不能通过匹配标题或正文关键字猜测区别。
- 根因是共享 `DelegatedContextDisclosure` 只收 id/children，两个调用点全部使用唯一固定 `transcript.delegated_context` 标签；`CardParts` 虽仍持有原 Part 类型，却没有把它用于当前披露语义。另一个调用点 SubagentProgressGrid（成员进展）只有原输入预览，并不等于控制消息。原分类 `isDelegatedContextMessage` 正确将非 human（人类）非 main（主通道）的委托输入归入接收者消息段，本次不改变该唯一分类、作者、归属和折叠状态。
- 旧路径原因：9 月方案已修复自然高度、换行、滚动阅读和不隐藏正文，但范围没有区分交接消息、typed control（已声明控制类型）及进展输入预览的标签。当前 live/hydrate（实时/回读）和成员完整会话最终共用 CardParts；进展预览共用同一个披露组件。不存在必须新增消息、补写正文或迁移旧数据的需求。
- 限定方案：共享组件接收必填的当前展示种类 message/control/input（消息/控制/输入），由两个现有调用者按真实事实给出；CardParts 对该消息段原 TextPart.kind=control 显示“调度上下文”，其余委托消息显示“交接消息”，成员进展原输入预览显示“输入消息”。共享组件以同一当前语言文案生成可见标签和无障碍名称；英文同步。不得解析自然语言、推断创建/授权语义、改变模型请求或消息内容，也不新增作者影子状态、配置或第二套类型分类器。
- 影响和排除：仅影响真实主卡、完整成员会话及紧凑进展的披露名称，不改 Task/Mission/Session 执行准入、工具、路由、数据库、业务数据格式、调度/重试或终态。已有 disclosure key（展开键）、键盘/焦点、原文渲染及自动跟随释放保持同一实现。风险为完整/预览命名漂移、误按正文判种类、中英无障碍名称不一致及展开后阅读位置变化；通过上述原真实消息、实际点击/键盘、成员预览和中英页面截图人工复核。纯 UI 改动不添加或运行界面自动化测试；原真实功能任务继续执行，产物完整验收仍待完成。
