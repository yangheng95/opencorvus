## 实施前证据、根因与影响

旧版 `39326`，浏览器经 39327 实际加载 `main-CzKUCAnP.js`。分别点击项目目录按钮和在全局目录按 Enter，截图 01–02 都报复制失败。透传代理在两次真实 `POST /mission-skill/directory` 捕获合法 JSON（JavaScript Object Notation，结构化文本）分别为 `source=project`/`global`；请求线上 `Content-Type` 的实际值均是 `application/json, application/json`。真实服务分别返回 400（`9d5ddc03-164c-4591-b2eb-d9d4069dc2ef` 和 `e1931c17-5ec5-418c-8b17-267c9e590071`）。前批同一真实运行的直接对照用合并值复现相同 `source` 验证错误，单独 `application/json` 返回 200 及准确目录，说明不是技能名称、根目录或源码数据不合规。两次旧版截图已本人查看，基线隔离页面、服务和代理均已关停。

`apiJson` 识别调用方小写 `content-type`，将字符串解析成结构化 `RequestBody` 并保留原请求头。共享 `applyBody` 对 JSON、文本和带类型的二进制分别用普通对象加入 `Content-Type` 默认项，再展开请求头；大小写不同的属性在 JavaScript 对象仍是两个键，Fetch 正常化为同一个逗号合并值。服务解析 JSON 之前检查媒体类型，所以合法字段变成未读取，表面错误才指向 `source`。原服务测试只在边界直接读已解析请求，不覆盖线上媒体类型；改这一调用的大小写只能躲开触发点。依据 [RFC 9110 第 5.1、8.3 节](https://www.rfc-editor.org/rfc/rfc9110.html#section-5.1) 与 [Fetch 的 Headers](https://fetch.spec.whatwg.org/#headers-class)，字段名大小写等价，Content-Type 为单值。影响面是共享宿主普通请求所有三种自动写媒体类型的分支；本次实证是目录写动作，不是任务调度、队列、执行轮次、唤醒或恢复异常。

保留明确调用方媒体类型及参数、现 `Accept` 和授权头、目录/请求时限/响应解析所有权。未给类型的二进制和无体请求保持原语义；FormData（表单数据）由 Fetch 生成实际 boundary（边界标识），不引入手工媒体类型。现有发布、数据库、接口与模型无关。风险是改变调用方显式媒体类型、丢失 multipart（多段表单）边界或二进制内容，需用真正线上输出回归。范围只收敛“适配器默认项与既有字段”的合并，不为调用方手写非法重复值另建解析规则。

## 方案与验收

请求体设置共用一个私有入口，只有存在建议默认类型时构造平台 `Headers`，按字段名大小写等价检查，缺失才写默认；JSON、文本、二进制均使用它，FormData 和无体不改变。没有每个消费者修补、不放松服务 schema（结构）。正向网络测试通过两个真实宿主适配入口与环回服务器，验证现实际 API 小写 JSON 请求、默认 JSON、显式文本/二进制类型及准确正文、真实表单 boundary 和解析值；初次用旧传输复现失败后再改产品。复用现聚焦权威/错误/上传检查，不跑全量。
