## 现象、直接触发点与根因

隔离服务 `39777` 和代理 `39779` 正常返回 `/global/transport/stream` 的 101。两个项目具有相同末段目录，选中第一个项目的未执行多步任务。正式接口修改另一项目 Chat 的标题，响应 `4609444f-116b-451d-a5c6-1b1bc83356a3`，真实 `work-ledger.changed/session.updated` 携带的是另一 Session 的 ID。侧栏及时显示新 Chat 标题。网页同时发出对原多步任务的精确 GET（读取），该请求不是本次改名所需的数据。仅在代理截断此真实 200 响应 `762f1d3c-b979-40a0-b76d-ff4556bbc6e1` 的前 12 字节时，选中草稿标题、原请求从阅读页消失，输入区不可用。直接 GET `24d80bf7-6751-4106-baa3-601792aed7d0` 返回原草稿原样。页面显式重试 `552cda3e-452e-4f3c-b3e3-ed9e10de8db9` 后恢复原请求。

全局事件处理器无条件提升 `missionSharedRefreshToken`，该信号同时驱动侧栏列表与精确选中资源。后者以当前连接、选择代次、完整目录和身份读取，但触发时已丢失事件归属。资源正确将真正失败的读取呈现为未知并禁用输入，错误来自无关的 Session 更新将精确读取置入这条路径。已有读取超时、取消和重试解决故障结算，未隔离触发范围。上一批恢复完成后已经直接刷新一次精确读取，再借共享信号更新列表时重复触发同一读取。真实事件连接下，归档恢复待回执时收到本 Session 通知、回执中断后再次精确确认，随后原显式读取及共享信号的另一读取各返回 200。

原 HTTP-only（仅超文本传输协议）代理缺少升级转发，早期侧栏不刷新的观察只反映验收工具。复用历史升级处理后重跑，101 和真实页面列表更新同时成立。上一批阅读页 Mission 和设置归档 Chat 的中断恢复在完整连接下都重新通过，分别由原身份确认读 `82d6b66b-50dc-433f-8bd4-001e69362fc7` 与 `befcc81f-5398-44b1-8c70-f5cc50e668a9` 证明。

## 共享审计与影响

- 全局生产入口由 `startWorkLedgerSSE` 在健康启动、重连和重新认证恢复。服务端工作台通道投影 Session 创建、更新、删除和活动状态时携带精确 Session ID。当前生产者只投影 Mission 及右侧 Chat/Work 会话。Task 的持久事件和 `TaskUpdated` 走独立的 Task ID 投影，可能不携带目录或 Mission 根 Session，不能根据不同的 Task ID 排除 Mission 子项变化。
- Task 的精确行来自 `findTask`、项目/绑定与原 Task 的活动状态。Mission 来自精确 Session、该 Mission 的子 Task、结果和交互计数。Chat/Work 来自精确 Session 和本会话活动。另一确切 Session 的生命周期通知不修改上述被选中的对象。项目元数据、无完整身份的通知、Task 子项事件、连接恢复和 handoff 保留原刷新语义。全局列表仍接受所有工作台事件，邮件通知和任务事件的已有消费者继续按原契约处理。
- 这里只收紧界面选中读取的通知所有权。请求取消、归属代次、传输超时、读取失败和重试、归档留存、Task/Mission/Session 执行轮次、正常与终态处理、队列、持久恢复、接口、迁移和语言文案均沿现契约。基线包含两个同名项目、无关与本 Session 事件、可逆归档和恢复、实际中断和原位重试。真实桌面使用未执行草稿与空闲 Chat。活跃模型执行和重启后的运行轮次未纳入本轮实机验收。
- 风险在于把全局通道的通知误分类，导致 Mission 的子 Task 变化或连接恢复无法触发读取。只限制含确切 Session ID、无 Task ID 的 `work-ledger.changed` 通知。已明确目标的本地操作沿原刷新策略。已完成显式刷新后的归档动作只通知列表。使用两个不同读取所有者的现有失效信号用途，持久数据仍来自原读路由。

## 方案与验收

1. 用共享工作台通知的确切 Session 身份区分列表与选中读取的刷新范围。列表仍响应全局事件。选中读取跟随同一 Session 与保守的未限定通知，不让外部 Session 的更新触发精确请求。
2. 将列表失效和选中失效分别连接到两个现有读取。保留已有本地刷新、连接、请求队列和焦点流程。归档恢复在直接刷新选中读取后只刷新列表。
3. 添加聚焦服务契约，验证同 Session、不同 Session、Task/连接恢复和项目通知的明确刷新范围。运行现有通知流、真实 WebSocket 及 Task 通知契约，运行 Overlay 类型检查和构建、文档和架构检查。
4. 使用完整真实事件连接，先用另一项目真实 Chat 改名重跑基线的故障条件，再修改当前 Session 核对其确切读取、正文及输入语义。保留实际 101、服务端变更事件、页面前后截图和正式接口读回。候选检查原草稿、原 Chat 身份和零模型活动。证据见[验收产物](../../artifacts/2026-11-12-work-ledger-selection-invalidation/README.md)。
