- `41952/ui/`、`main-CvYJx5Hd.js` 两个真实桌面标签页进入同一个隔离 Git 项目的空白聊天。两页环境栏初始显示 `main`。第二页实际选择 `review`，正式 `POST /vcs/branch` `03bcb343-83ba-48e0-a773-94710b09788a` 于 `15:27:32.481Z` 返回 200，发起页的后读 `7b1f5798-0228-44e8-acbb-703ab8f94f93` 返回 200。实际 Git 与发起页均为 `review`。旁观页仍显示 `main`，点击原「刷新项目元数据」后才由 `ba033089-eb56-4a08-970e-941873bb0325` 读取并显示 `review`。
- 从 `review` 切回 `main`，真实请求 `7b2feea2-7061-4dd1-b644-fbb6e00cfe1e` 于 `15:29:08.706Z` 返回 200，公共工作记录流确收同一精确目录的 `vcs.branch.updated`。旁观页保持打开的分支菜单，依然把 `review` 标为当前，实际 `git branch --show-current` 和磁盘样本为 `main`。[桌面截图](../../artifacts/2026-11-24-project-git-branch-peer-refresh/README.md)
- 根因在界面事件订阅。既有分支变更通知传播准确，`handleWorkLedgerStreamEvent` 只把它送到文件工作台，未触发现有项目元数据读。发起方写入完成的 `refreshMetaAfterAcceptedMutation`、人工刷新和重新展开面板可以读到当前 Git，却覆盖不到旁观页持续打开的面板。工作记录通知连接恢复同样没有重验这一投影。菜单使用一次 `GET /vcs/branches` 的选择状态，公开菜单快照保存到关闭，后续 Git 元数据的确认也不会退役它。
- 影响是活动目录的当前分支、相关 Git 状态和已经打开的分支选择菜单。现状可能让用户根据旧分支标签操作真实当前目录。保留当前项目路径、Git 独立错误、连接与选择所有权，保留分支选择现有确切目录和写入条件。其他项目同名目录、受管工作树和无项目会话各有自己的作用域。公共接口、分支变更来源、工作树数据、持久化、提交/推送操作和发起方已接受回执均不改。未发现执行轮次的调度、队列、唤醒、重试或终态异常。单独观察到的真实通知未丢失；基线未断流，恢复用例在候选验收中单独验证。

## 实施前方案与验收

- 同一分支通知仍交给文件工作台，同时按现有目录键核对活动项目并沿原 `loadMeta` 刷新。仍由原真实读取负责路径和 Git 状态、最新请求及选中项目隔离，通知本身不灌入分支文本。工作记录连接重新建立时，对已有活动项目元数据走同一读取，弥补断流期间的分支变化。原会话初始化和发起方写入后回读均使用现有服务。
- 已确认的 Git 分支身份更新时，由原分支菜单所有者退休在途读取及已打开的选择快照，结束时沿共享菜单的原焦点策略。环境信息面板保持打开。再次开启菜单按原入口真实读取并勾选当前分支。作用域已退休或读取失败使用现有错误和取回机制。
- 用实际菜单切换正反两个方向，旁观页环境栏更新且键盘重开菜单获得新勾选，另一个项目保留自己的事实。经本地转发隔离工作记录通知连接并跨断开切换，复连后核对当前分支。逐项核对 Git、实际请求、截图和任务/模型空闲。运行目录作用域及元数据正向检查、实际分支通知/读取检查、构建、类型、文档与架构。此批无需真实模型。
