## 基线现象与根因

真实隔离开发服务 `40118` 收到普通提示、注册命令和网页对话中的 `resource.blob: ""` 及 `resource.text: ""`，均返回 `end_turn`，但公共历史只保留非空任务文字，零字节附件和明确空文本都丢失。本人通过 Computer Use 查看真实 `/ui`：用户卡片只有任务文字。非空一字节二进制对照保持原字节并正常结束。

同一服务通过已修复的公开 `attachment.create` 上传零字节 `.bin`、`.txt`，公共提示保存两个规范附件引用，实际下载均为零字节；因此不是附件存储或 HTTP（Hypertext Transfer Protocol，超文本传输协议）空请求体故障。但对这条真实历史执行 `session/load` 和 `session/fork`，两者均报告 `-32603`，细节为 `ACP replay file URL empty packet.bin: expected non-empty base64 payload`。正常退出并重启同一数据库后，两项失败完全重现。`session/resume` 和后续提示均正常完成。

有两个明确的数据流原因：

1. ACP 输入用内容真假值判断资源，空字符串根本没有进入公共提示。只把判断改成字符串还不够：blob 随后被装成 `data:...;base64,`，而通用数据网址解码器按明确合同拒绝空载荷。前一批只修可选媒体类型，非空用例无法覆盖这个边界。
2. 历史回放把规范原件读出后再次编码为数据网址，再交给要求非空的输入解码器。已经验证并保存的合法空文件因此变成无效输入。公共原件本身完整，报错来自不必要的编码/解码转换。文本回放也用真假值，纵使入口保留空文本仍会丢失回放。

## 实施方案、影响与风险

- 对嵌入资源按字符串类型接收明确空内容。blob 使用现有 MCP 资源专用解码器，它明确允许零字节，非空内容仍采用严格 base64 解码；复用现有公开 SDK 原始上传，将其规范引用送入当前公共提示/命令。普通图片、音频、通用数据网址和 Task/Mission 内联媒体的严格解码器不变。不增加第二套上传或空文件备用路径。
- load/fork 的同一回放实现接收已经确定的目录，在该目录的真实项目上下文内调用 `readVerifiedReference`，直接使用已验证原件字节；规范文件与真实 data URL 各按其自身合同取得字节，然后共用唯一的 ACP 内容投影。删除规范文件“编码为数据网址再解码”的旧步骤。原有有效远端和本地资源链接继续按链接表达；非空图片和二进制回归通过原检查证明。
- 空文本消息按字符串判断回放，继续使用原用户身份，不补写隐藏消息或伪消息。更新当前扩展架构的资源输入合同；历史记录保留原交付事实。
- 影响限于 ACP 资源物化及 load/fork 的文件与文字投影、对应正向协议检查和当前架构。公开上传、Session、Task/Mission API、数据库及持久格式不改，无迁移、版本更新或发布。
- 上传发生在公共提示前，沿既有原始上传合同保存原件，随后公共提示再次核对项目及媒体。若后续提示被拒绝，上传本身仍是已接受的原件；本批不引入 GC（Garbage Collection，垃圾回收）或伪造跨接口原子事务。验证目录和媒体，防止从 URL 自称的项目推断权限。通用二进制仍受模型媒体能力限制，不以脚本回复宣称模型理解文件。零字节图像不是有效图片，本批不放宽媒体有效性合同。
