### 临时目录错误的实际来源

临时追踪定位到 `bus/index.ts:1220` 的真实持久发布重试，经 `runWithInitializedIndependentProject` 重新发现旧项目。失败模型的冷停止保留了未结清的发布，符合可靠发布合同。`memoryProject` 仅执行 `Instance.disposeAll` 就删物理目录，`resetMemoryDatabase` 也未结清进程拥有的 Bus（事件总线）重试；下一用例可能在清理时遇到旧目录发现。临时追踪还证明即使三个用例显示通过，后台仍出现旧目录重入，因此通过一次不能排除问题。

已核对 Task、Mission、Session 的生产发布、取消和恢复、目录变更与项目退休、进程关停和回滚；生产 Server 在总线及执行结清门内停止重试、请求物理取消、等待原始发布结清，再提交进程交接。正常 Instance 释放故意保留可恢复的总线发布，不能改成吞掉发布或拒绝业务恢复。修复限定测试宿主的实际资源销毁：公共 memory 夹具在销毁实例/目录或重置数据库前使用现有 RuntimeExecutionSettlement 和 Bus.acquireProcessSettlementGate，等待物理发布归属结清并释放物理重试，原数据库 outbox（发件箱）事实保留到显式重置。正常业务算法、重试和持久格式不变。新增正向真库验证：失败的原发布在夹具退出后仍有原始出箱与项目事实，后续另一项目能独立发布并收到自己的值。复核总线持久、租约、事务、进程关停及原 13 文件，再取三平台证据。调查追踪从生产源码删除后才提交。
