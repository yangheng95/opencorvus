## 实施前根因及影响

真实独立基线 `main-AWoNT5go.js`。在 Alpha 项目主页输入 `Alpha project draft for the inventory handoff.`，切另一个真实项目输入 `Beta project draft for the customer handoff.`。通过公开的工作目录选择，把同一实际目录路径最后一段从 `branch-review` 改用 `BRANCH-REVIEW` 打开。项目首页切到该拼写，但输入区确认为空。服务器的工作目录检查接受两种拼写，项目真实 ID 都是 `prj_hxZyJ5gqoIF0sOchiqwM`，工作树一致；独立 Beta 有不同 ID。再在大小写变体输入 `Alpha alias draft with a separate follow-up.`。点原项目行读到第一段，按目录选择返回读到第二段，Beta 项目草稿和 Alpha 的一个独立会话草稿也各自可读。[桌面和实际项目身份](../../artifacts/2026-11-25-project-launcher-draft-canonical-path/README.md)。

`workspaceComposerDraftKey` 对无会话的项目主页直接编码活动目录的原字符串。目录选择经服务器按合法目录验证，保留 Windows 路径名称的输入拼写；项目列表与项目偏好使用规范等价身份。当原地址从不同入口传入大小写或斜杠拼写时，当前同一个项目实际从浏览器数据库读写两个不同的草稿键。已交付的草稿事务防止标签页互相覆盖，但不改变项目作用域键，因此每个别名各自可靠保存仍会导致用户在同一项目找不到原稿。Task（任务）、Mission（多步任务）与已建 Session（会话）草稿按原 ID 或既有精确作用域写入，浏览器主页键的改动不参与执行、队列、重试、终态、重启或模型运行。浏览器存储与 UI（User Interface，用户界面）选择在独立项目/标签、已建会话、全局主页和打开不同拼写时有可审计的边界。

影响限有明确项目目录的 Windows 首页草稿存储和其现有消费者，涉及草稿输入、读取、切换、引用、当前请求修订和数据库升级。POSIX 路径大小写、其它项目及投递后的确切会话身份沿用既有格式。需要在升级后覆盖真实的旧草稿，避免只换当前键导致已写入文本失联。两条曾用同一项目不同键提交的正文若确有区别，风险是任选一条造成丢失、合并后复用原请求身份、或旧已确认回执消耗新稿。公开服务器接口、项目身份与路径展示、Git 和模型无需修改。

## 实施方案

已声明 Windows 项目目录经现有 `projectDirectoryKey` 产生唯一的首页草稿键。已建任务／会话和无项目首页继续使用既有键；以宿主目录语法区分 Windows，POSIX 的原样名称及作用域保留。用现有浏览器记录承载增加版本化升级入口。Composer 数据库提升到版本 2，在 IndexedDB（浏览器索引数据库）升级事务内，把已有记录的 Windows 项目首页键一次性改为当前规范键。首次建库仍完成旧 localStorage（浏览器本地键值存储）导入，并经同一升级变换后提交。设置库继续使用当前版本，不重写版本 1 已接受的设置迁移。升级后的草稿读写全部用当前键。已打开的旧版验证页在升级前关闭；旧版本与候选的实时混用不在本批实页验收中。

同一身份仅一个旧记录时保留完整的原草稿、结构化引用、精确重试身份和时间。等价旧草稿重复时保留最新完整记录。不同内容的旧别名草稿按时间顺序保留到同一可编辑正文，用现有引用序列化保留引用文本，去除相同的显示段落；合并稿未来按自身序列化内容分配新的发送身份，用户仍可审阅。并列更新时间继续保持输入记录的遍历顺序。其它作用域原对象沿原键保留。升级失败按真实事务中止；用户存储仍由同一个当前浏览器索引库拥有。

候选用实际基线的浏览器地址、两个项目、原真实 v1 草稿库做正常升级。实际检查先前只在两种拼写各自可见的两段合并，再往其中一种拼写编辑、重新打开另一种拼写，核对正文、另项目和已保存会话草稿仍各归原处。新增聚焦变换测试覆盖单条旧数据、实际碰撞、重要元数据和非 Windows 键，再跑原草稿和共享设置合同、类型、双语、构建与文档。用实际隔离运行路径和截图完成确认。
