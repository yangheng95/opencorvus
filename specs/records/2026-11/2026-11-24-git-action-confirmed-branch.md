## 实施前证据、根因和影响

- 用 `41956/ui/`、`main-BTSp3JBu.js` 两页打开无远端的 `branch-review`。`main` 和 `review` 有不同指针，`notes/local.txt` 的草稿可随正式 Git 切换保留。第一页面在 `main` 打开原提交弹窗，手写 `Review fixture change originally prepared on main`。第二页从原分支菜单切到 `review`，`5ce21d8f-220a-4e29-b8a7-36ffbc980a2e` 于 `15:38:33.300Z` 返回 200。第一页面标题随既有通知切到 `review`，原草稿不变，提交按钮仍可用。按 `Ctrl+Enter`，实际 `75466aa3-c15d-4c68-8588-50c941e0ef03` 于 `15:38:58.161Z` 返回 200。截图停留在提交等待阶段，最终结果由回执和 Git 对象核实。`refs/heads/main` 仍为原 `d7df079…`，`refs/heads/review` 成为 `cbfe58f…`，包含上述精确主题和实际 `notes/local.txt` 改动。[桌面证据](../../artifacts/2026-11-24-git-action-confirmed-branch/README.md)
- 对话框标题、资格和提交都是活动 Git 投影，草稿和生成说明却只被项目、连接及会话选择代次控制。分支变化同目录同会话并不退休提交上下文。键盘和鼠标同一路径以最新投影的资格提交原文本，传输只含目录和消息。服务端 `Vcs.commit` 阶段性读取实际目录并提交当前分支；`push` 同样按调用时的当前分支执行。原目录保护、通知、完成后的读回或 Git 拒绝覆盖都无法表达作者确认的分支。合并操作中提交接受与随后推送是两个独立回执，可能在它们之间换分支。
- 影响覆盖打开的弹窗、重新打开时同范围留下的手写说明、在途生成说明、鼠标和快捷键、独立提交、提交后推送及独立推送。现有公共错误、目录所有权、模型流式生成、工作区内容、正常 Git 配置和已接受回执的含义须保留。条件校验是数据目标校验。此处是 Git 写入的目标选择问题，未观察到 Task（任务）、Mission（多步任务）、Session（会话）执行轮次的调度、队列、唤醒或终态异常。B591 保护已确认的分支身份，同分支下文件或提交变化继续使用原有当前工作树语义；未命名提交位置按现 Git 信息的无分支值处理。外部 Git 命令在检查之后与我们的写入并行属于独立进程竞态，本批共享锁只覆盖 OpenCorvus 管理的参与者。

## 实施前方案与验收

- 现有弹窗保留起草时确认的分支。确认的实际分支变动后，清楚展示准备目标和当前目标，保留可改的说明，停止旧分支的流式生成，以既有按钮规则暂停写入。用户在同一弹窗显式确认采用当前分支，可继续编辑或提交。关闭后原文字仍与原分支绑定，重新打开保持相同保护。所有写入和键盘入口复用同一作用域判定。
- 双路径的正式请求都携带同一已确认分支 `expectedBranch`（明确的空值代表当前 Git 投影没有命名分支）。服务端复用项目 Git 租约，按原当前物理分支规则在写入前验证分支。分支切换同样进入已有租约，先后请求无法在 OpenCorvus 的检查与写入之间改换分支。不同分支给出具名 412 合同和可恢复的当前元数据，先检查后写入。提交后推送复用起初确认的目标，保留提交已成功而推送失败的原回执。复用本地 Git 的现有上游，更新全部调用、生成的软件开发工具包及文档。已接受的现有工作树状态和错误继续沿原路径结算。
- 再用两真实页面：在 `main` 手写，另一页切 `review`，观察草稿、状态和两个明确分支，随后主动确认 `review` 后创建实际提交并核对它准确落到 `review`。验证读取过时的正式条件请求给出 412，以及正常独立提交和本机远端推送的确切分支。聚焦真实路由、另项目、非 Git、无头状态、受管工作树、界面类型、双语与文档，逐项核对截图、请求、持久事实和独立数据库。完成提交和正常推送，未授权模型不使用。
