## 现象、根因及影响

真实基线服务 `40112` 中，将 `Blob` 放入公开 `attachment.create` 的常规 `body` 参数并提供明确媒体类型，31 字节二进制文件、零字节文本和 100 字节 PNG 全部得到 HTTP 400，错误为 `Attachment upload requires Content-Type`。同一服务的实际原始 HTTP 对照全部得到 200，分别保存 31、0、100 字节。不是服务器拒绝空文件或附件存储故障。[基线请求及对照](../../artifacts/2026-11-19-attachment-upload-sdk-body/README.md)

根因是 `POST /attachment` 的运行处理器接收原始请求字节，但其 OpenAPI（开放接口描述规范）没有请求体声明。SDK 因而生成 `AttachmentCreateData.body?: never`，方法只绑定目录与文件名，忽略调用者给出的 `body`。共享客户端看到真实请求体为 `undefined`，按现有正确规则去掉媒体头，所以服务最终报告缺少 `Content-Type`。最后的错误是字段遗漏的结果，不是应修改请求头清理器的理由。现有网页通过自己的原始字节 HTTP primitive 上传，因此之前的网页验收没有覆盖这个公开 SDK 缺口。

影响是 OpenAPI 的单一操作定义、公开 SDK 的请求体类型、方法绑定和媒体序列化，以及使用该 SDK 的外部调用者。修复以同一路由的声明为事实来源，官方生成过程同步产物。服务器处理器、现有界面上传、原件路由、权限、项目隔离、附件持久格式及数据库结构均不改变，无需迁移。零字节文件仍用明确的空 `Blob` 表达，不能把缺失参数当作有效输入；具体 MIME（Multipurpose Internet Mail Extensions，互联网媒体类型）仍由当前媒体头给出，SDK 默认使用通用二进制类型，显式类型可通过现有请求选项提供。风险是生成器对原始二进制的序列化、空文件媒体头被错误剔除，以及默认 JSON 序列化损坏真实非文本字节。无调度、并发、恢复或终态异常。此前 ACP（Agent Client Protocol，编辑器客户端协议）的零字节嵌入资源问题仍是另一输入合同，本批不宣称已经解决。

## 首次候选揭示的共享参数根因

补齐路由声明并经正式 SDK 生成后，公开方法已正确生成必填 `body`、原始字节绑定和 `bodySerializer: null`；SDK 和后端类型检查通过，但三个真实上传仍返回 400，三个新正向检查均失败，原件下载四项继续通过。失败保留在 [首次候选请求](../../artifacts/2026-11-19-attachment-upload-sdk-body/first-candidate-uploads.json)，不能以类型或生成代码存在宣称完成。路由检查首次误用了不存在的脚本名称，随后按当前 `package.json` 的 `api:routes-check` 重跑，并发现下述检查器缺陷。

继续追查生成客户端的 `buildClientParams`：它已经将明确 `body` 映射为真实 `Blob`，随后 `stripEmptySlots` 用「对象没有可枚举属性」判断空占位槽，因而删除具有真实字节的 `Blob`、`File`，也会删除明确提交的空 JSON 对象。这和最初 OpenAPI 漏声明是两个必须共同修复的原因。媒体头在更下层再次因缺少真实请求体被正常移除。不能通过绕过参数绑定、去掉媒体头清理或要求调用者覆盖内部参数修复。

全仓审查得到 11 个整块 `body` 绑定方法：附件创建、项目/全局配置更新、工作区创建、专家团演进变更、网关控制操作、全局流准备、Task 与 Mission 归档、技能挂载覆盖、浏览器目标选择。非空结构化对象、数组和标量保留其原合同；本次修复应保留调用者明确提供的整个对象或原始媒体值，只有函数自己创建且仍为空的请求体占位对象可以被清理。头、路径和查询槽仍使用既有清理与无原型对象。未进入 Task/Mission 运行入口或观察到调度异常。

实施仍由现有事务生成流程拥有：沿用当前针对已安装模板的规范化步骤，在参数清理前记录初始请求体对象身份，使生成的唯一参数绑定器只清理自身空占位体，不清理调用者替换的明确请求体。保留当前已固定的依赖、参数分组、安全对象初始化及原流式清理修正，不直接手改产物或引入备用上传器。生成模板变化必须显式复核。新增纯参数输出正向检查，覆盖有内容和零字节的 Blob/File、明确空 JSON、正常分组字段，连同真实上传和 SDK 空配置请求验证共享合同，再重跑原验收。

正式路由检查将已存在的 `POST /attachment` 误报为缺少 SDK：其共享 `extractSdkRoutesFromText` 正则要求请求对象第一个属性必须是 `url`，而官方原始字节方法在 `url` 前自然生成 `bodySerializer: null`。已搜索该 helper 的定义和唯一检查器调用，所有方法共用此提取器。以仓库已使用的 TypeScript 语法解析器替换该单一正则实现，读取 HTTP 调用第一个对象参数的真实 `url` 属性，支持普通及流式调用，不受属性顺序或嵌套对象影响。不删除路由验收，不对附件路由设置豁免。增加普通、流式及原始字节形状的正向路由输出检查，最后重跑完整真实路由库存检查。

参数绑定修复后，六项纯参数输出和九项真实上传/下载及路由提取检查已通过。随后保留完整公开类型的消费检查揭示类型命名冲突：`AttachmentCreateData.body` 中未限定的 `File` 被绑定到同文件已有的仓库文件统计类型（`added/path/removed/status`），与方法接收的 Web File 不是同一类型，出现 TS2322。不能删去这项公开类型检查或加类型逃逸。

已核官方已安装的字符串格式 resolver（类型解析器）接口和实现，并再次完成隔离生成试验。在现有 TypeScript 插件中只对 `format: binary` 使用官方 `~resolvers.string`，生成 `globalThis.Blob | globalThis.File`。由同一生成器同时保证请求与响应的二进制类型真实指向 Web 标准，保留原有领域 `File` 名称和公共合同。影响包括本请求及既有九个声明为二进制的响应类型：渠道附件、文件下载、日志导出、Task/Mission 项目归档、对话产物、浏览器证据产物与捕获、Build 观察内容。它们共用同一个二进制格式解析器，运行处理器不变；本批验证类型和代表性真实附件运行路径，不宣称逐一执行过这些领域操作。继续使用不带类型逃逸的原公开类型消费检查证明修复。
