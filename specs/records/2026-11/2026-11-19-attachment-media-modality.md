## 真实基线

隔离开发服务 `40160`；公开接口上传五份原件：相同 4983 字节 PNG（Portable Network Graphics，便携式网络图形）分别声明 `image/png`、`IMAGE/PNG`、`image/png; profile=srgb`，相同 343 字节 SVG 分别声明 `image/svg+xml`、`Image/SVG+XML; charset=utf-8`。相同字节使用不同存储扩展名，遵守已发布原件的媒体身份冻结合同；没有改写或绕过回执。五次原件 GET 均与输入逐字节相同。

分别创建五个真实单文件 Chat 会话和一个合并会话。模型明确声明支持 image 输入。六次输入都完成 stop，但实际流式请求只有普通 PNG 和带参数的小写 PNG 各获得一张图像，大写 PNG 的输入图像为零；两种 SVG 都变成 `[Attached ...]` 文本引用。合并会话 `ses_hg9XYjioexmXG6mAM1RU` 的模型请求只有两张图像。不是据模型自述推断：本机模型服务记录了真实请求的消息、图像 MIME、字节数和原始用户标记。

官方 ACP load 回放五个原件：普通 PNG、参数 PNG、小写 SVG 为 image，大写 PNG 为 blob 资源，大写 SVG 为 text 资源。本人真实 Windows 桌面看到五张缩略图均正确，打开大写 PNG 的全图也准确、100% 显示。故“页面能看到”不能证明“模型或编辑器收到正确模态”。[原件、请求、协议与人工截图](../../artifacts/2026-11-19-attachment-media-modality/README.md)。

## 根因与影响分析

1. `SessionPrompt` 正常物化和规范回执保留完整声明；网页分类先取基础类型并识别图像，因此原件和页面正常。`Message.toModelMessages` 的图像判断却直接对原字符串做小写前缀比较，PDF（Portable Document Format，便携式文档格式）用完整相等判断。合法大小写或 PDF 参数会改变能力判断，出现文件已保存、界面可见却没有对应模型字节的投影。
2. 同一函数先调用 `isDecodableText` 再判断二进制模态；共享文本函数按既有合同把 SVG 视为可读 XML，其正向测试明确验证 true。这是“文本可读性”而非“模型输入模态”的定义。用户 SVG 和工具 SVG 在图像准备前被选入文本路径。修复调用优先级，不把 SVG 从文本分类器删除，也不为通过旧测试保留两种模型投影。
3. `modelBoundFilePart` 已获得图像准备器返回的实际 MIME，但只向上返回 data URL（Uniform Resource Locator，统一资源定位符）和 note；上层仍把原 `part.mime` 当作模型 file.mediaType。该路径需传回真实准备后媒体类型。现有准备器已能标准化格式、裁边和限制像素，不能再写一条 SVG 转图或格式兼容路径。
4. `ProviderTransform.mimeToModality` 私有函数重复原字符串判断，影响能力过滤和工具结果适配器选择；文件准备的 image 判断也使用原媒体字符串。低层 agent runner 有另一份四模态判断，虽然转为小写，但 PDF 参数仍会绕过实际能力分类。这些共同边界需要同一媒体基础类型与模态实现。既有已验证适配器集合、模型能力目录、音视频输入政策保持，不扩大任何适配器支持。
5. ACP 用户回放直接判断原字符串；工具图像先以同样前缀筛选，再用只接受 `data:<base>;base64,...` 的正则。规范附件数据 URL 保留参数，所以参数图像在工具投影阶段会被错误拒绝。当前代码可确定触发点，真实 MCP（Model Context Protocol，模型上下文协议）图像工具回放尚待验收。回放内联数据 URL 分支也丢弃参数，应保留通过现有严格 Base64（二进制文本编码）校验的完整头。规范原件继续以回执 MIME 为事实来源。
6. 本地 file URI 明确图像声明进入 `SessionPrompt.parts` 后，`Filesystem.isTextLikeMime` 又把 `+xml` 改为 text/plain；这个局部文件上下文选择必须先识别客户端明确图像，SVG 声明才会走真实字节物化。通用文件读取、技能文本、webfetch 的 SVG 源码读取各有原合同，保持它们的文本行为。当前全仓还发现 GitHub 拉取、设计/研究资源清单、浏览器原生截图事实及 Copilot 序列化等判断：前者属于各自输入/展示子系统，后者消费已经准备的模型消息；本批不宣称覆盖这些独立功能验收，保留后续调查范围。
7. 影响生产入口包括公开 Chat/Coding/Work、ACP 普通提示和命令附带文件、MCP 工具结果、持久历史和派生，以及复用 Message/Provider 的 Task/Mission 模型上下文。身份、角色权限、组织流程和调度未变；本次六个实际输入均正常完成，没有队列、恢复所有权或终态异常证据。若后续真实工具过程出现此类异常，须按仓库规定立即扩大共享机制横审，不能以分类问题掩盖。
8. 不修改已发布 MIME 或原件字节，不更改数据库 schema（数据结构）、公开 HTTP/SDK（Software Development Kit，软件开发工具包）结构、凭据或配置面，无需数据迁移。旧历史从完整原件重新准备模型数据；只改归一后的传输，不猜格式或伪造消息。图像 URI 的一般资源身份语义仍是另一项调查，不在本批顺手改写。
9. 风险：不可因归一而给原件重写元数据；不可把二进制格式凭后缀猜成图像；不可让音视频、已不支持图像的模型或未验证适配器获得新的传输能力。需要实际准备后 MIME、字节和解码尺寸的正向验证；请求 stop、页面正确或模型自述均不足以证明模态。当前图像准备测试中源码 buffer 摘要与独立完整字节断言重复，触及测试时删除冗余摘要，保留真实输入字节与准备输出的直接核对。

1. 在 util（通用包）提供唯一媒体基础类型与 image/audio/video/pdf 模态分类，复用成熟解析器；文本可读分类仍保持其原合同。同步上述模型投影、图像准备、Provider、runner 和 ACP 调用，删除旧私有模态函数和重复实现。原件 MIME 和模型实际传输 MIME 分别表达真实对象，不建立影子身份。
2. 用户和工具结果先识别图像，再按可读文本处理其他类型；用户模型 file.mediaType 使用同一次准备的实际 MIME。明确本地图像链接保留字节物化；未知/未支持媒体仍按原公开合同处理。ACP 图像内容保留原件及完整声明，参数不使规范图像投影失败。
