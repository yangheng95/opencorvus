## 实施前证据、根因和影响

真实开发服务 `39294` 经 `39296/ui/`。两个自有项目由领域 `ProjectMemory.setStatusInTransaction` 创建不同通知：A `owned-review-before-a`（容量）、B `owned-review-before-b`（条目超限）。两项目及原正文 revision 0、pending 0 和未确认通知均通过实际接口运行时 schema；没有用伪响应替代任何通知。真实在 A 以键盘执行 Dismiss（01），立即从工作区列表切 B（02）。服务对 A 实际返回 HTTP 200 `35aff873-3d6f-4a1d-a307-a0f1cbb1ca3d`、`acknowledged:true`；仅延后页面收到原响应 16 秒，超出实际客户端请求期限。B 加载后 `Bravo review` 仍是自己的通知，但两按钮禁用并显示 `Dismissing…`（03）。A 页面请求超时后，B 显示 `Action failed: signal timed out. Try again.`（04）。切简体中文后动作和标题翻译，原组件保存的英文错误仍在（05）。直接回读 A 为已确认、B 未确认，后端没有把写入串到 B。

直接原因：固定在 App 根的提示条实例把 `busy`、`busyAction` 与已翻译 `failure` 存为无归属信号。通知对象被替换时只重新创建展示节点，异步完成仍能更新同一实例的全局信号。共享服务已用连接、项目目录与目录代次保护持久结果投影，但它发布的投影本身不带这组身份，提示条没有办法验证其当前来源或按代次管理控件。确认旧通知的服务契约以 generation（通知代次）判定，不会确认另一通知；这次实际失败是已提交后网页等回执超时，错误既不属于 B，也不表示 A 未提交。存翻译文本使语言切换后无法重新本地化。

影响面限提示条状态、局部错误、原始诊断和按钮；共享读取及组织结果的单一当前投影增加实际归属，设置文档与传输/API（应用程序接口）、后端确认 bool、项目文件、数据库格式和发布不变。已核对主启动、切项目、连接变更、事件后的刷新、同通知对象刷新和新代次、普通确认与组织调用；同一通知期间只能触发一次动作，其他项目不应等待旧动作。组织流程、队列、Task/Mission/Session 执行、唤醒和终态未发生异常；旧 POST 已从真实服务正确结算，本批只修前端回执归属。对当前 `acknowledged:false` 依旧使用同一服务刷新当前通知，不新增服务分支或重发。

## 方案与验收

用现共享服务接收的单一记忆投影携带项目目录、连接代次和目录代次；提示条仅消费当前投影且只处理当前未确认通知的实际 generation。把动作与错误合并为同一有归属的状态：同一作用域当前操作在途才禁用相同通知动作，晚结果不能覆盖其他项目/代次/操作；当前失败保存原原因，按当前语言显示准确动作摘要和可展开的原诊断。现按钮在忙时保持键盘可聚焦，由同一 handler 防重复，成功后原有通知清除机制仍由真实数据负责。不改变原服务写入、刷新、重试策略或模型工具。

独立候选 `39295` 经 `39297/ui/` 重现 A 真正提交后页面超时，切 B 期间 B 自身动作可用、晚结果不污染 B，直接读回仅 A 已确认。再在 B 真实桌面操作时让连接在到达服务前中断，验证此失败归于 B，原始诊断可展开并随界面语言重译摘要；恢复传输后明确重试 B，验证实际成功及通知清除。用实际公开 schema、真实持久值和四个原 Git 文件比对；现连接归属测试更新为正向投影检查，加项目选择晚响应的正向服务测试。类型、双语、样式、构建、文档与架构索引作辅助；截图本人复核、关闭自有服务、范围提交并正常推送。
