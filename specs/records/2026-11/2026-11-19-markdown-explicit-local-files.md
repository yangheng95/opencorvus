## 修改前的现象和影响

1. 开发版 `127.0.0.1:40244/ui/` 中，文件树打开 `release bundle.zip` 得到只读文件和中央下载入口，打开 `LICENSE` 得到实际纯文本。在同一个指南预览中点击 `../release%20bundle.zip` 与 `../LICENSE`，浏览器分别请求服务的 `/release%20bundle.zip` 和 `/LICENSE`，显示 HTTP（Hypertext Transfer Protocol，超文本传输协议）400 `DirectoryRequiredError`。浏览器返回后重新打开指南，其中 `./reference.md` 能在 `/ui/` 内打开预览。真实项目的 `file.read` 对这三个对象都返回 200。`file.download` 返回 200 和编码的正确文件名，174 字节逐字节匹配实际归档，内含 `review.txt`。[基线截图](../../artifacts/2026-11-19-markdown-explicit-local-files/README.md)
2. 触发点在共享 Markdown renderer（渲染器）的 `markdownProjectFileReference`。路径分离并正确解码后，扩展名表既充当模糊代码引用的证据，又被当作显式 Markdown 链接进入工作台的必要条件。`.zip`、任意自定义扩展和无扩展名文件即使拥有 `./` 或 `../`，仍被输出为浏览器相对地址。此时文件点击委派没有路径属性，丢失 Markdown 文档的目录归属。文件树已持有规范路径，绕过此分类，故服务与下载均正常。此前的下载改进处理已打开二进制的行为，原样百分号解决解码，跨文档标题解决已识别 Markdown 内的章节，这些修复均未改变路径分类。
3. 分类由共享 Markdown 渲染器使用，覆盖工作台文档、会话和顶层委派可达的其他产品 Markdown。工作台预览相对源文档解析；会话等现有全局委派以当前目录解析。后者在带 `open-path` 能力的本地宿主会把普通已知类型交给操作系统。新承认的任意类型须明确留在工作台，避免把新的文件类型交给系统关联打开。规范化、草稿离开确认、项目读权限及物理路径限制由现有工作台与文件服务处理。真正的文件或目录类型由服务器读取结果决定，仅凭链接语法无法判断未以斜杠结尾的目录。可能的兼容影响是旧文档里带点段且形似文件的相对网页路径会按项目文件处理；网络地址应使用现有完整地址。
4. 影响限显式链接解释、工作台归属及相关数据合同，没有公开接口、存储数据格式、上传、文件下载授权或迁移变化。原 Markdown 文本不重写，已有记录按当前规则重新解释。首读错误和本地化标签均继续使用公共工作台。没有提交任务、启动会话、调度或终态异常的证据。主要风险是相对站点地址和目录误分类、编码只应解释一次、桌面把扩展到的类型交系统打开、改变已有标题/行范围的定位，以及替换有草稿的编辑器目标。

## 实施和验收方案

- 在现有 `markdownProjectFileReference` 中保留扩展名作为模糊路径证据。作者写明 `./` 或 `../` 且解码后有文件末段时即承认文件身份。末段不采用空值、`.` 或 `..`，范围采用链接语法中的正斜杠。地址的协议、查询、附件、普通片段、Markdown 标题、源码定位和单次解码继续沿已有合同。未写明相对前缀的任意类型由原规则解释。
- 仅首次由明确相对路径承认的类型携带 `workbenchOnly` 文件引用属性，经现有序列化、点击委派及 `openProjectFile` 使用同一个工作台打开方法。已识别扩展名、明确的代码引用以及原系统打开合同继续沿当前路径。保持 Chrome 与本地宿主共用当前文件路由及草稿准入。
- 聚焦文件引用与路径数据测试明确验证压缩包、无扩展名、自定义类型、编码字符、带行范围以及旧的普通标题引用。使用真实服务候选 `40246/ui/`，从同一内容的指南点击三个目的地。亲自查看中文与英文页面、获取真实下载回执、核对原件和下载包内容。实际渲染和打开的桌面证据以隔离 Chrome 为准。本地宿主的系统打开分支以源码与编译证据核验。以项目当前构建和文档检查验收，停止本人创建的服务并检查工作区后提交与推送。
