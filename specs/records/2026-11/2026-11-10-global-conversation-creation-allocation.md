## 证据、根因与影响

前批 39342 实际 /global/chat 串行两次、/global/work 并行两次，各由同样的正文返回两个 201、两个匿名 Project 和两条 Session，桌面显示四个不同项目（前批图 01）。以前一批对真实浏览器 pre-header 透明重发的证据为触发链；本批不把受控的两次 HTTP 送达冒称为浏览器自动重发。根因是目录未选中的客户端创建没有明确作者请求身份，路由每次调用原 GlobalConversationService，未提供 creationAllocation 时先由 ImplicitProject 生成独立匿名项目，再写不同 Session。仅让 Session 行幂等不足：匿名项目及目录的分配先发生。响应追踪 ID 由服务器每个 HTTP 到达单独生成，不是作者身份；现有 Global Chat Start 已有原子全局分配及目标，但旧的纯创建路径没有进入该机制。用户会见到重复项目与空会话，自动重发与明确新建必须区分。

同一隔离档 39346 在实服生成普通 Chat/Work 和已接受的旧 Global Chat Start Session，再通过真实分配服务生成一条仍未物化的旧 Automation 分配；不执行它们。已实读版本 10、数据库完整性 ok、3 条 Session、2 条分配（1 接受、1 仅预留）、0 消息/Task/模型使用；原行号、完整列和项目行暂保存在本人私有验收目录，提交只保留身份、状态和核对结论。截图 01–02 真实打开、点击旧 Work；02 是切换过程。版本 10 服务已关闭，后续用同一隔离配置目录启动真实升级，备份和目标都按精确行事实检查。

影响：两个 /global 创建入口、全局创建 HTTP（超文本传输协议）/SDK 合同、工作台侧栏、现有共享分配表的 CHECK 与两条接受触发器、数据库迁移及备份、创建并发、重启和删除后重发。已有 Global Task、Global Chat Start、Automation Run 走同一表，现 SQL 仅允许三种，追加新合同必须保留它们所有既有状态、约束和数据；现有真模型、权限、调度、Task/Mission/Session 执行不改变。此前共享请求横向证据仍见项目内记录；不以修复两个入口宣称所有公开写入、真实执行轮次及恢复已经完成审计。

## 实施及验收

- 两个无项目创建入口接受同样可选 requestID，客户端总是为本次动作生成，实际草稿沿同一项目内已建立的作者提交入口保留重试身份，成功后照常转移草稿。未提供标识的调用每次代表独立意图，仍走同一事实来源。Chat 和 Work 各自的全局创建 kind 隔离同一字符串；不可变合同记录体验与显式模型。完整接受之前预检并冻结必要的初始配置 overlay，不把其他全局配置、模型凭据或请求代理数据另存。
- 复用现有全局分配：查持久请求先于读取可变模型，原子预留唯一携带 Project 和目录，Session 插入与接受记录在同一写事务完成，精确重发查已接受 Session，冲突复用明确 409，删除后复用 410。正常并发只加入同一持久分配，不补一次匿名 Project；取消旧的纯创建未分配路径，保留 Global Chat Start 原配置/执行行为。应用无新界面文本。
- 版本 11 将新的冻结 DDL 片段追加到版本 10 的冻结定义（不改已经发布的旧迁移）。完整快照仅改变分配表与两条接受触发器；冻结定义中三个无关对象的行尾空格触发差异检查，直接去除会改变当前检查器读取的对象文本。因此以现有版本 4 的组合方式声明目标：在隔离目标库替换分配表及其所属索引和触发器，实际数据仍由同一迁移器保留，迁移检查必须证明完整目标对象与当前定义一致。业务 schema 和接受触发器同步扩展项目、请求、Session/体验和初始 overlay 约束，旧三种验证继续；现版本化迁移重建表时保留所有值/rowid，正常启动应产出版本 10 到 11 的备份/回执，不要求清库。更新当前数据和控制架构、OpenAPI、SDK 及双语文档。
- 聚焦测试实际接口串行/并行、体验隔离、明确新建、输入冲突及删除终态；隔离服务真实升级后验证历史行和备份（含完整列及 rowid），真实新请求及重启复用、版本 11 空库启动；至少用真实桌面查看/切换旧和新会话并人工截图。若从首次发送消息 UI 触发需要模型，此批明确记录用公开 API 触发和真实侧栏复核的边界，不启动模型。记录时间、状态、数据和进程收尾；范围提交后正常合并推送并继续。

类型复核补充：全仓再次按函数引用搜索发现 `Server.initializeGlobalAutomation` 将同一创建器作为函数值注入 Automation。调度入口的全局目标从已预留或新物化分配构造，Run 在唤醒前已经接受其 Project 分配；它按确定 Session ID 创建并唤醒，目标 Session 并不是该分配的接受类型。共享创建器只要求调用方持有分配和 Session ID，并用互斥类型区分既有模型预检与新纯创建的冻结 overlay；Automation 继续用既有模型预检和 Run 的所有权，不将新会话提交回执用于 Run。类型、旧带消息 Chat Start、当前调度测试的全局火次及现有迁移检查重新验证。该发现是编译期调用面问题，尚未观察到实际调度异常。
