## Confirmed current behavior

Actual pure-module probe `server-url-protocol-probe.ts/json` imports the current transport protocol guard, persisted settings parser, bootstrap settings and API URL primitive. It constructs native Request objects only; it never fetches. It restores the process-local API URL afterward. This is TypeScript protocol/URL qualification, not actual Browser/Tauri persistence or UI/network behavior.

| Supplied serverUrl | Guard/parser | Actual apiUrl(global/health) |
| --- | --- | --- |
| empty or spaces | rejects with TypeError persisted overlay settings payload is invalid | not projected |
| not a url | accepts unchanged | TypeError cannot parse not a url/global/health |
| http://[::1 | accepts unchanged | TypeError on malformed IPv6 authority |
| //example.invalid | accepts unchanged | TypeError because no absolute base |
| http:// | accepts unchanged | http://global/health, with hostname global |
| localhost:7878 | accepts unchanged | localhost:7878/global/health, protocol localhost:, empty hostname |
| https://example.invalid/prefix/ | accepts unchanged | https://example.invalid/prefix/global/health |
| https://example.invalid/prefix?mode=DUMMY | accepts unchanged | pathname /prefix, query ?mode=DUMMY/global/health |
| https://example.invalid/prefix#DUMMY | accepts unchanged | pathname /prefix, fragment #DUMMY/global/health |
| leading/trailing spaces around http://example.invalid/prefix | accepts unchanged | direct API configuration makes trailing spaces part of pathname as %20%20; normal UI/applySettings trims first |

ftp/file/data/javascript and dummy user-info inputs were recorded as parseable URL/Request values in Bun. This does NOT establish that fetch supports them or that the product ought to accept/reject them. No scheme ban is proposed on the strength of syntax alone. The probe result includes the complete actual matrix.

The http:// outcome is important: api-state removes all terminal slashes BEFORE appending the route. The incomplete authority becomes http:, then http:/global/health, which URL parses with global as host. Thus invalid inputs can fail before transport or change the projected target, not merely show an unfriendly error. No actual request was sent to that host. Transport applies the configured Basic Auth headers to its generated URL when a password is set; whether a particular wrong target would receive any request/authorization depends on host/fetch/CORS behavior and was not exercised. Do not call this proven credential exfiltration.

## Current single data/control flow

- `transport-protocol/src/index.ts`: OverlayPersistedSettings declares serverUrl:string. isOverlayPersistedSettings validates it with isNonBlankString; projectComposerIntents[*].serverUrl has the same check. isNativeCommand(settings.save) delegates to that guard. It validates complete documents/known keys and other preference enums/ranges, but has no server-base URL parser.
- `overlay/services/persisted-overlay-settings.ts` returns the validated object unchanged or a generic TypeError. `bootstrapOverlaySettings` builds the complete current document and invokes this parser. It does not check URL syntax or normalize serverUrl. `applySettings` trims nonempty serverUrl and uses the default only for missing/blank values; it does not validate syntax.
- `overlay-settings-storage.ts`: Browser save parses, JSON-stringifies and writes the one localStorage key oc_settings. Browser load JSON-parses and validates the same document. Source therefore demonstrates these malformed nonblank strings pass Browser persistence admission. This investigation deliberately did not write browser storage.
- `src-tauri/src/main.rs`: OverlaySettings has server_url:String and deny_unknown_fields. parse_overlay_settings_text performs JSON5 parsing then validate_overlay_settings. That validator only trim-checks server_url for nonemptiness. overlay_settings_save validates then atomically writes overlay.jsonc using a same-directory temporary file/sync/persist; load repeats the same validation. URL behavior is source-qualified, not a newly compiled/native runtime result.
- `store/settings.ts` current saveSettings serializes writers, takes the full snapshot when its turn starts, calls bootstrap, waits for native persistence acknowledgement, updates confirmedPersistedSettings, publishes explicit onConfirmed, then releases the next writer. This transaction correctly preserves authority/order; admitting malformed serverUrl is a semantic validation hole, not evidence that the new queue mechanism failed.
- `ServerConnectionSettingsGroup.tsx` saves the draft snapshot with an onConfirmed callback that publishes the connection fields. It then probes connection and reloads scope. The field uses type=url, but its save control is an explicit type=button onClick in SettingsGroup/SettingsRow containers, not a submitted form. No checkValidity/reportValidity call or equivalent check exists in this inspected caller/control chain. This is source evidence that HTML URL validity does not supply a save admission contract; no browser behavior test was run.
- `main.tsx` reactive settings effect and `services/init.ts` syncApiConfig push the applied serverUrl to api-state.configure. configure accepts any truthy string and updates auth listeners. apiUrl then concatenates base/route and only afterward constructs URL. RequestTarget separately handles route/directory query authority; it does not validate the configured base.
- Browser and Tauri both use the same createTauriTransport HTTP implementation. request, authenticated fetch streams and EventSource streams all call buildUrl -> apiUrl. Thus the shared failure affects API reads/mutations, board/config projections and live streams, not a single Network operation. It occurs in the client before a canonical server execution has been addressed; no Task/Mission/Session scheduler/terminal anomaly was observed.
- resolveResourceUrl separately prefixes configured serverUrl onto host-relative resource paths as text. It leaves absolute data/blob/http(s)/file resource URLs alone. API resource fetching through HostTransport uses apiUrl; displayed raw host-relative resource URLs share the base-string risk. An eventual URL contract must audit both without changing external resource semantics.

## Other URL producers and isolation

- currentDefaultServer reads actual browser origin + path before /ui to preserve reverse-proxy prefixes, otherwise uses the canonical server-defaults.json loopback address. No startup injection supplies another URL authority. Saved explicit remote/cross-origin choice overrides the default and is intentional.
- Native server_info_with_pid_and_log builds http://LOCAL_SERVER_HOST:port from the actual managed port; it does not consume user server_url to launch the sidecar. connection.syncLocalServerUrl/restartLocalServer read that info, trim trailing slashes, save/apply it through current settings. Their loopback classification uses URL parsing and protocol.startsWith(http) for managed ownership, not general admission. A malformed saved URL generally fails that classification, so autoServer alone does not prove recovery will overwrite it.
- Direct settings load and a native command consumer can reach the same persistence document without the Network editor. Unrelated preference saves serialize the applied serverUrl too; projectComposerIntent scope keys use the trimmed/trailing-slash-reduced server string and canonical directory. Changing normalization can merge/split preference scopes and must not silently discard or migrate those facts.
- SDK createServer consumes its validated occurrence startup URL rather than Overlay preferences; plugin input carries a URL object. ChannelRuntime has its own explicit attach baseUrl/environment surface; package update server_url and Multica import server_url use distinct feature schemas. They are analogous URL consumers found in the full search, not extra Overlay persistence owners. Multica's HTTP(S)/no-userinfo/query/fragment restriction and externalUrl browser-opener rules must not be copied as if already the Overlay base contract.

## TS/Rust contract discrepancy, separate from URL

The current TypeScript guard explicitly permits username:"" (typeof string). `transport-protocol/test/contract.test.ts` has a positive test titled accepts an explicit empty username for a server without Basic Auth. Rust validate_overlay_settings still includes username in its nonblank field loop, so it returns an explicit error for that same document. This contradicts the current architecture claim that both load/save schemas are equivalent. It is exact source/test-contract evidence, not new native execution. Do not fix it silently inside an unrelated URL change; root has been informed.

## Errors, recovery and historical constraints

- checkConnection catches actual request errors, marks offline and returns false. Saving invalid syntax has already committed/published before this later probe; a failed connectivity probe is not persistence rollback. Some later scope refresh may also reject. Current startup loadSettings -> onSettingsLoaded -> syncApiConfig loads nonblank malformed URLs and can enter the ordinary offline workflow.
- Tightening the persisted LOAD guard has a separate consequence: loadSettings throws before onSettingsLoaded, main's settingsHydrated remains false, and its reactive API/theme effects stay gated. Main catches and reports the init error. A naive stricter parser may strand previously accepted documents before their intended Network recovery path. The exact user repair experience under such a new error is unknown until designed and manually qualified. Do not silently reset the complete document or add a fallback address/parallel store.
- The current connection-recovery-entry record expressly preserves saved remote/proxy addresses, original prefix semantics and one canonical Network editor; it rejects hard same-origin replacement/discovery/fallback ports. Connection-save-authority and05-config require persistence confirmation before publication, and explicit SettingsActivationError for a saved fact whose callback fails. Admission must preserve that transaction boundary and cannot substitute an online probe gate: an offline but syntactically valid configured server remains a legitimate saved intent.
- Ordinary API response errors have server requestIDs; local URL construction TypeErrors have no response or real requestID. They must not be presented as server-rejected400 or masked with a fabricated correlation ID. Debug-info currently includes the raw server.url line; user-info/query-bearing addresses can therefore also appear in copied diagnostics. This was not exercised with credentials and is not a universal-redaction proposal.
