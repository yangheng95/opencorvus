# Task coordination: tank-game case and public materials

This is the evidence entry for the September 2026 README and homepage improvements.
The implementation plan and verification record are [here](../../records/2026-09/2026-09-19-outcome-first-marketing.md).

## What the case establishes

A user asked for a browser tank-battle game recreating the original experience.
The task decomposed this into 19 acceptance requirements and involved intent analysis,
requirements, source research, architecture, workload review, interface design,
implementation, testing, interface-integrity review and system-integrity review.
A single squad owned the delivery; this is not a demonstration of multiple squads running concurrently.

The retained Mission notes record two correction rounds:

1. Repair scoring across stages and results presentation, then recheck.
2. Following an operator decision, replace 35 maps and enemy rosters with public, non-ROM source data and record provenance.

[Selected source excerpts](source-excerpts.json) include verbatim requirement and repair passages,
observed role names, the retained test summary, and SHA-256 fingerprints of the inspected files.
These are excerpts from local records, not a complete public transcript or a newly rerun acceptance.
Original local paths, session identities and unrelated payloads are deliberately omitted.
A hash identifies the inspected bytes; it does not make unavailable originals independently accessible.

## Evidence limits

- The closing narrative reports 242 passing tests; the retained report records 241 passed and one failed.
  The report's exact revision relative to the final delivery has not been reconciled. Neither homepage
  nor README claims all tests passed.
- The data is traced to a public remake. Equivalence to the original game's read-only memory (ROM) data
  was not independently established. Partial terrain cells, individual enemy order and second-loop
  rosters have documented simplifications or derivations.
- Some live-play evidence, including the high-score screen and actual shovel pickup, remained incomplete.
- The operator intervened on the source-data requirement. This was not an entirely unattended run.
- The diagrams communicate responsibilities and correction flow, not exact chronology, simultaneous
  execution, agent count, runtime improvement, cost savings or general success rate.

### Historical product-led revision (superseded)

The user rejected the first pain-led layout and explicitly required a graph, not a stage list.
The replacement uses a shared SVG renderer with individual role nodes and directed edges:
three initial roles join at architecture; design and workload review branch; implementation
branches into testing and interface review; reviews join at delivery. Two dashed edges return
to implementation. These summarize review-led corrections; they do not identify an exclusive
initiator for each repair or purport to replay every event.

The solid-edge abstraction follows the Advanced `greenfield-interface-delivery` dependency
contract in `packages/opencorvus/src/expert-squad/builtin/advanced/expert-squad.jsonc`;
the observed role inventory and two correction topics come from `source-excerpts.json`.
The delivery node represents the orchestrator's collection of independent outputs.
