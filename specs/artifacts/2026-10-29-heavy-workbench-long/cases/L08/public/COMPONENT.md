# Release manifest acceptance

Read source/release-clock.json and release-lines.csv. The as_of is canonical UTC. Exclude future release rows. Empty tenant or item is an identity error (record source_id/code identity); for valid identities group by joint (tenant,item), select highest published revision. Compare normalized status and whole quantity among that revision's rows. Equal payload repeats retain every source_id but count once. Different top payloads give conflict and units=null. Lower revision disagreements cannot override a higher unique revision. Published UTC metadata is eligibility information, not an extra conflict payload.

Units are nonnegative ordinary decimal text with an exact whole value (12.0 equals12); nonwhole/negative/malformed quantities give invalid_units/null. Active valid rows give ready/integer units. Withdrawn valid rows give withdrawn/0. Conflicted/invalid/withdrawn entries contribute0 to totals. Future-only keys have no state. Output manifest.json has states [{tenant,item,revision,status,units,source_ids}], invalid_rows [{source_id,code}], excluded_future [source_id] and totals_by_tenant {tenant:integer}. Counts/booleans/null must keep their types; row and identity-list order is immaterial. No huge-number formatting puzzle is involved.

The legacy source is a historical defective artifact, not a current fallback. Its native0/self_status does not certify data correctness. Evaluation independently executes your declared repaired component against the actual raw CSV. A correct manifest can explicitly quarantine unresolved source errors and pass this limited acceptance. It does not mean all data are resolved, every security feature is tested or a real client signed off. Only actual acceptance can authorize the conditional cash receipt; schedule R01/R02 as genuine new work and do not rewrite historical H04 delivery or invoice.
