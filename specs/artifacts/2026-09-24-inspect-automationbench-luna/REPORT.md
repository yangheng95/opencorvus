**后续审计更正：** 适配器 0.3.2 遗漏了官方场景的业务时间，模型可能按宿主日期计算相对日期。在[十例自进化实验](../../records/2026-09/2026-09-24-automationbench-self-evolution.md)中，真实销售操作已证实该影响。下列原始分数仍可复算，但涉及时间的结果混入了输入环境缺陷，不能作为修复后自进化的受控基线；旧日志与分数全部保留。

2026-09-24。模型为 **openai/gpt-5.6-luna**，专家团版本为 **2026.09.24.2**，Inspect 适配器为 0.3.2，AutomationBench 固定为官方提交 `4a8e106`。本轮完成了提示词校准和真实模型抽样；**严格通过率仍只有 2/6，专家团尚不适合据其完成声明直接认定业务成功**。

## 结果与实验中断

最初用三个固定案例诊断旧版 2026.09.22.2：严格通过 **0/3**，平均部分分 **31.48%**。随后冻结新版，在六个业务领域各抽一例，种子 20260924，排除三个诊断案例。两个集合不同，分数差异不能解释为配对实验中的性能提升。

首轮宿主的 600 次请求预算设置不足。累计 581 次请求时，三例已经计分；我通过正常 Task 取消接口取消另外三例，让 Inspect 保留取消和未计分状态，随后关闭自建宿主并清理凭据副本。首轮真实覆盖是 **3/6 已计分、1 例严格通过、3/6 未计分**。

修正宿主预算后，只对三个取消/未计分成员进行一次补测，使用相同模型、相同专家团版本和相同原始输入。三个已计分结果全部保留，包含失败结果。以下是**补测后的六例汇总，不是一次无中断首轮成功率估计**。

## 校准内容

只修改三个角色的提示词，通过现有生成器更新包版本与内置载荷。工具权限、业务 API、世界数据、官方评分规则、Task 调度和终态协议均未改变。

1. 工具发现明确使用专用 MCP 工具类型；缩小 API 文档查询并复用已发现契约。
2. 交接保留原始 SYSTEM/USER 约束；空的完整名称查询需改用较短来源锚点或有界集合读取，核验者独立复查“来源不存在”的结论。
3. 政策与 SOP 通过业务文档/邮件读取，区分 API 文档与实际业务规则；明确最新政策前提。
4. 通知验收对应真实收件人、正文和发送回执，内部报告不能代替客户收到的内容。

真实诊断支持这些调整：旧版销售精确查询因为名称标点差异返回空，较短查询可以找到候选；旧版营销把没有 SOP 接口误当作没有政策，而官方邮件查询能找到政策；旧版财务核验把内部金额报告当作通知证据，官方仅给 50%。这些诊断答案、实体名和官方断言均未加入提示词或补测输入。

## 剩余问题

- **通知完整性与范围仍不可靠。** 预算邮件遗漏评分器要求的部门级金额；销售邮件包含原始约束要求省略的未处理实体。部分原文交接仍被模型摘要化。
- **政策和最新往来核验仍可能发生得太晚。** 运营任务额外创建了不应处理的请求；人力流程已把需撤回候选人及过时可用性发给客户，并遗漏内部通知/台账更新。后续纠正邮件无法消除已经发生的错误发送。
- **核验成本与完成判断仍有长尾。** 首轮销售超过 100 次工具调用，依次补查规则和风险证据；两个官方未达标案例仍被判 completed。基于当前六例无法宣称专家团已经可靠或性能改善具有统计意义。

这些是可见请求、真实 Tool 输入输出、业务状态和官方断言之间的差异。没有用宿主关键字过滤、强制工作流状态机或改评分规则来制造通过。角色提示词遵循率仍是模型层面的待改进项。
