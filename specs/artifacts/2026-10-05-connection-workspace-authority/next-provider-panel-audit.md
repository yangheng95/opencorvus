## Findings with concrete paths

### 1. Interactive Provider authentication can retarget collected input after an await

Priority: highest of this audit because the request body may contain credentials. Source proves a reachable continuation, not an actual disclosure. ProvidersPanel.handleAuth331 is the sole production authenticateSelectedProvider caller and passes only its captured directory. llm.ts24–26 ProviderRequestOptions contains only directory. The helper stack is authenticateSelectedProvider737 → runProviderAuthMethod696 → providerAuthInputs498 / authorizeProvider574 / executeProviderAuth553. Every API call captures the then-current authority independently.

Exact API-key trigger: method and optional provider prompts are selected from A; runProviderAuthMethod awaits nativePrompt710 for the API key. While that dialog is unresolved a confirmed native replacement or another allowed connection publication advances API authority. The continuation726 calls executeProviderAuth with A's method index/inputs/key and the old directory;559 dispatches under newly captured B. The source directory string remains A, so it does not repair backend identity. The preceding providerAuthInputs loop has the same problem: POST auth/prompts508 → await nativeSelect524 or nativePrompt533 → append input → next POST. authenticateSelectedProvider's own method-selection await752 also precedes a fresh helper entry without a shared token.

OAuth (Open Authorization) has the same chain: authorize608 returns exact A flowID; code prompt653 waits; callback669 or cancel634/665 uses that A flowID/method under current B. The browser-open failure path641–649 also calls cancel after an await. The auto/device callback680 and instruction callback belong to the same logical flow. A private/native renewal can occur while a modal is open; this finding does not assume the operator can open Settings behind an application dialog. Whether any real dialog/network schedule triggered it is untested.

The existing API primitive guards each individual request and preserves retired original outcomes. It cannot reconstruct a token omitted by the next helper after a dialog. Backend exact flowID, method/scope, Auth generation and executor checks correctly refuse mismatched OAuth state, but receive the input before doing so; API credential execution may persist on the wrong target if its public method is valid there. This is not evidence that backend guards failed. Provider Test is a single immediate POST with no same-helper continuation; it shares options/public scope but its separate problem is stale panel feedback (below).

All production helper callers were searched: these six auth functions call each other only; ProvidersPanel is the sole top-level UI caller. testProviderConnection is also called only by that panel. No CLI or backend implementation imports this Overlay helper. Both explicit project routes and directory-free global routes use the same helper stack, so a fix must cover both without changing their selected route or inventing a new credential store.

### 2. Provider panel compound writes and local feedback lose the originating owner

Directory A/B/A invalidates Test and form-discovery generations through their existing effects, so those exact paths are not claimed unguarded against ordinary observed A/B/A. ### 3. Network proxy and Channels own form generations but omit connection renewal
