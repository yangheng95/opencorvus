长对话中的流式正文、来源切回与交互稳定性
1. 研究范围与证据层级

文档事实：本次实际通过 webfetch 读取了指定的三篇页面：MDN 的 ResizeObserver、pointer-events，以及 W3C 的 Understanding Focus Order。前两篇解释浏览器接口与 CSS 属性；第三篇是 WCAG 2.2 成功准则 2.4.3 的解释性文档，页面明确说明 Understanding 文档属于信息性解释，不是额外的符合性要求。

设计建议：应把问题分成尺寸观测、指针命中、键盘导航与阅读连续性四个层面。三篇文档分别提供部分依据，但不构成完整的聊天界面规范。下文关于自动跟随、阅读锚点、恢复位置与用户意图的方案，均是针对长对话的设计建议，不是这些页面直接规定的行为；本次没有检查实际产品，也不据此宣称任何实现已经合规。

2. 流式正文不等于每次都发生尺寸变化

文档事实：ResizeObserver 页面开头定义，其报告元素内容盒或边框盒尺寸的变化，也可报告 SVG 元素包围盒尺寸变化。文档示例通过改变容器宽度调整文字大小，说明这种观测不局限于视口改变。它观察的是目标的几何尺寸，而不是正文的语义、网络流片段或用户是否已经读过内容。依据：ResizeObserver

设计建议：流式文本追加与尺寸变化应作为两种事件处理。追加几个字可能还没有换行，正文尺寸不变；来源栏展开可能没有新增正文，却让正文变窄并增加行数。因此，不宜把观测回调次数当成生成进度，也不宜把没有回调解释为没有新内容。内容更新用于维护消息状态，尺寸通知用于重新评估布局，两条路径可以协作，但不能互相替代。

3. 内容盒、边框盒与观测目标

文档事实：MDN 说明，内容盒是可以放置内容的区域；边框盒则包括内容、内边距和边框。页面列出 observe()、unobserve() 和 disconnect()，分别用于开始观测目标、结束单个目标的观测以及结束该观察器的全部观测。它们描述了观测生命周期，却没有指定聊天产品必须观测哪一层容器。依据：ResizeObserver

设计建议：选目标时先问“哪一种尺寸变化需要影响阅读”。固定高度的滚动容器即使内部正文增长，自身盒子也可能不变，因而不能单靠观测外壳发现全部内容增长。可考虑观测内部正文及会改变可用空间的来源区域，但不要不加区分地观测每个字符节点。目标过多会增加管理复杂度；目标过少则可能遗漏布局变化，应通过具体场景验证取舍。

4. 布局变化不能直接证明用户意图

文档事实：ResizeObserver 的接口描述与示例都围绕尺寸，未提供“正在阅读历史”“希望继续跟随”或“刚从来源切回”的状态。pointer-events 页面讨论事件目标，Focus Order 页面讨论顺序导航，也都没有定义通过滚动距离判断阅读意图的算法。依据：ResizeObserver、Focus Order

设计建议：尺寸变化只能说明布局条件变化，不能自动授予界面移动用户视图的理由。建议单独维护“跟随最新”“阅读历史”“阅读来源”等交互状态，并让明确操作具有较高优先级。例如，用户点击“回到最新”可明确恢复跟随；正文变高则不应自行清除阅读历史状态。状态名称和切换规则属于产品策略，必须承认其推断性质，而不是包装成浏览器提供的事实。

5. 用户上翻时，保留阅读上下文

文档事实：三篇页面没有规定用户向上滚动后必须暂停多久，也没有给出距底部多少像素算作“正在跟随”。Focus Order 要求顺序导航在影响意义或操作时保持二者，但这不是自动滚动阈值的规定。尺寸观测能力与焦点顺序要求，都不足以直接推出某个聊天滚动策略。依据：Focus Order

设计建议：用户主动上翻后，可以暂停自动追随，让后台流式正文继续增长，同时显示不抢位置的“有新内容”入口。需要避免把所有位置变化都归因于用户：程序定位、窗口变化或布局调整也可能改变滚动位置。判断机制应区分明确输入与系统调整，并为误判提供恢复入口。尤其不要在用户刚找到历史引用时，因为新一行出现就把视图拉回底部。

6. 底部跟随应是可撤销的模式

文档事实：ResizeObserver 能通知尺寸变化，但页面没有要求回调执行滚动操作。它也没有保证一次通知就意味着流式正文已完成、所有图片已布局或页面不再变化。接口能力是“观察到某种变化”，而不是“整个对话已经稳定”。依据：ResizeObserver

设计建议：底部跟随适合用户明确选择持续观看最新正文时，但应允许随时退出。决定是否跟随的状态最好在新内容导致布局变化之前就已确定，否则可能把内容增长造成的底部距离变化误认为用户退出。恢复跟随后也无需把键盘焦点一起移走：视图位置、焦点位置和生成状态是三个不同对象。将它们绑在同一个更新回调中，容易制造难以解释的跳动。

7. 来源阅读是任务切换，不只是面板开关

文档事实：Focus Order 页面举例说明非模态对话框：触发按钮激活后，对话框中的交互元素插入到按钮之后的焦点顺序，关闭后按钮后续的导航恢复。模态示例则将焦点移入对话框，打开期间外部内容不可获得焦点，关闭后返回触发按钮或其后元素。这两种示例体现了不同交互模型。依据：Focus Order

设计建议：来源面板应先确定是并行阅读区域还是要求暂时独占操作的模态区域，再设计导航。不能只因它浮在正文上方，就自动认定为模态；也不能视觉上阻断正文，键盘却仍无提示地进入后方操作区。打开来源时可保存触发项与正文阅读位置，让来源任务有清楚的起点和返回路径。具体采用哪种模型，是产品选择而非文档唯一答案。

8. 来源切回要分别恢复位置与焦点

文档事实：Focus Order 的模态示例允许关闭后返回按钮或按钮后面的元素，并未要求所有关闭动作都采用同一目标。页面关注恢复后的导航是否逻辑清楚、能保持操作；它没有指定正文滚动偏移如何保存，也没有规定必须回到打开来源时的像素位置。依据：Focus Order

设计建议：切回时应分开回答两个问题：用户接下来从哪个控件继续操作，以及用户接下来阅读哪段正文。来源触发项仍存在时，返回该项通常便于延续上下文；正文已经重排时，可按消息或段落身份恢复附近位置，而不是盲用旧偏移。若触发项已经删除，则需要合理后备目标。恢复过程不宜默认跳到最新消息，除非用户明确选择了这一动作。

9. 尺寸观测回调存在循环风险

文档事实：MDN 的 Observation Errors 部分说明，遵循规范的实现会在绘制前处理尺寸通知；样式和布局重新计算又可能触发更多通知。部分通知会延后，并产生 ResizeObserver loop completed with undelivered notifications. 错误。文档强调，这种机制避免浏览器锁死，却不消除无限循环本身，还可能让布局跨多帧调整并出现闪动。依据：ResizeObserver

设计建议：不要在每次观测到正文变化后，无条件再次改变其宽度、字号或其他会影响尺寸的属性。来源栏与正文如果相互决定大小，更应检查反馈链。页面提到使用 requestAnimationFrame 延后调整，也介绍预期尺寸检查；但延后无限增长仍是无限增长。正确目标是使计算收敛，并在尺寸已经满足条件时停止写入，而不是只让错误不那么显眼。

10. 代码示例一：观测尺寸，不代替滚动决策

文档事实：ResizeObserver 页面示例读取 contentBoxSize，并在其不可用时使用 contentRect。同时，页面提供停止观测的方法。下面是依据这些能力构造的简短示意，不是原文代码，也没有执行；它只保存最近收到的尺寸，不修改被观测元素。依据：ResizeObserver

JS
function watchBody(body, state) {
  const observer = new ResizeObserver(([entry]) => {
    state.lastSize = entry.contentRect;
    state.layoutDirty = true; // 不在这里自动滚动或移动焦点
  });
  observer.observe(body);
  return () => observer.disconnect();
}

设计建议：示例刻意把“尺寸变化”与“应该跟随”拆开。后续控制逻辑可在检查阅读模式后决定是否定位，也可仅更新布局记录。它不是完整聊天实现：没有覆盖多目标、阅读锚点、嵌套滚动区或组件生命周期的全部细节。停止观测函数应在对应界面退出时调用；这些集成要求需要真实实现验证，不能因示例短小就宣称已经解决流式跳动。

11. pointer-events 控制的是指针目标

文档事实：MDN 定义 pointer-events 用于决定元素在什么条件下成为指针事件目标。none 会让事件穿过该元素，命中其下方目标；auto 恢复默认行为。页面还区分了多个 SVG 专用值，部分值在 HTML 中属于实验性支持，因此不能把全部枚举值当作普通网页上的等价通用选项。依据：pointer-events

设计建议：长对话中纯装饰性的渐变层、流式光标背景或高亮覆盖层，可以考虑避免阻挡下方链接的指针命中；真正的来源面板、菜单与按钮则需要正常响应操作。应根据层的职责选择，而不是把整个流式消息设成不可命中以规避误点。该属性也不是防止正文变化、保证文本选择或维持滚动位置的机制，不能承担这些互不相同的职责。

12. 事件穿透并不等于父级监听器失效

文档事实：pointer-events 页面明确指出，父元素设置 none 后，如果子元素显式允许成为目标，针对子元素的事件仍可沿父级路径传播，在捕获或冒泡阶段触发父级监听器。页面还解释，进入或离开可命中子元素时，父元素仍可能触发 pointerenter、pointerleave。该属性具有继承性。依据：pointer-events

设计建议：若来源浮层采用“外壳穿透、按钮可点击”，父级处理器应检查真实事件目标和操作类别，而不要假设外壳设为 none 就永远收不到事件。否则，点击关闭来源可能意外触发容器上的“回到最新”操作。继承性也意味着恢复子控件命中通常需要显式设置。排查时应把目标选择与传播路径分别看待，不能把所有异常笼统称为“穿透失效”。

13. 代码示例二：让装饰层穿透、操作入口保留命中

文档事实：下面示意使用 none 与子元素的 auto，对应 MDN 对穿透和子元素可命中的说明。但文档同时明确：pointer-events: none 不会阻止本来可以顺序聚焦的元素通过 Tab 获得焦点。它不会自动把普通元素变成可聚焦元素，也不是键盘禁用开关。依据：pointer-events

HTML
<style>
  .stream-overlay { pointer-events: none; }
  .stream-overlay button { pointer-events: auto; }
</style>
<div class="stream-overlay">
  <span>新正文仍在生成</span>
  <button type="button">回到最新</button>
</div>

设计建议：示例只演示命中职责分离，没有实现浮层定位、按钮动作或完整无障碍行为。如果目的是禁用真实操作，应另外处理控件状态与键盘行为，而不是仅改 CSS。如果目的是模态来源阅读，更不能用“后方 pointer-events: none”冒充完整模态隔离。鼠标点不到但 Tab 仍能进入的背景，会产生视觉与键盘模型不一致的问题。

14. 焦点顺序要求保留意义与可操作性

文档事实：Focus Order 页面引用的成功准则带有条件：网页能够顺序导航，且导航顺序影响意义或操作时，可聚焦组件应以保持意义和可操作性的顺序接收焦点。页面说明，可能存在多个合理顺序，不要求焦点顺序必然等于视觉排列，也不要求必然等于程序化阅读顺序。依据：Focus Order

设计建议：对话可采用“消息相关操作就近成组，来源操作与其触发项有清楚关联”的顺序。双栏布局不必机械地左栏先、右栏后，但不应让用户在正文复制、另一条消息来源、当前来源关闭之间无规律跳转。应同时考虑看得见布局的键盘用户与依赖程序化阅读顺序的用户，让两者都能理解当前操作属于哪条消息、哪个阅读任务。

15. 流式更新不应随意扩大焦点负担

文档事实：W3C 页面说明，普通 HTML 在没有脚本和 tabindex 干预时，顺序导航按内容流顺序发生；动态内容和脚本可以改变导航序列。页面并未禁止静态文本获得焦点，但将避免无操作用途的可聚焦元素列为最佳实践，并指出嵌套可聚焦元素造成重复、混乱的停靠可能违反焦点顺序要求。依据：Focus Order

设计建议：不要为每个流式片段增加 Tab 停靠点，也不要每收到一批文字就把焦点移到最新段落。若用户正在操作历史消息的来源按钮，应尽可能维持该控件及其关联关系稳定。需要定位某段正文时，可以设计有目的的入口；“静态内容允许聚焦”不能解释成“所有段落都应该聚焦”。长对话的导航成本本来就高，额外停靠点需要明确价值。

16. 三篇文档的职责比较

文档事实：三个页面回答的核心问题分别是“尺寸何时变化”“指针命中谁”“顺序导航是否合理”。这些证据不能互相替代：看到尺寸回调，不能证明用户想滚动；鼠标能点来源，不能证明键盘导航合理；焦点顺序合理，也不能证明阅读位置不会跳动。依据：ResizeObserver、pointer-events、Focus Order

17. 建议的验证场景与判定边界

文档事实：Focus Order 的失败示例展示了在不同表单分组间交错跳转造成的混乱，模态和非模态示例展示了动态打开区域与触发项的导航关系。ResizeObserver 则给出循环错误和跨帧布局闪动风险。它们提供了值得检查的行为，但没有提供聊天产品的完整测试矩阵。依据：Focus Order、ResizeObserver

设计建议：可分别验证底部跟随、上翻后持续生成、打开来源导致正文变窄、来源关闭后内容已增长、触发项消失，以及键盘焦点位于历史消息时的新内容插入。每项记录操作前后的阅读段落、焦点目标、下一次 Tab 去向及实际点击目标。若出现尺寸循环，应检查反馈原因，而非只屏蔽错误。本次仅完成文档研究，未执行这些交互测试，因此它们是后续建议，不是已通过的核验记录。

18. 综合结论与实际读取记录

文档事实与结论：实际读取的正文支持一个明确边界：尺寸通知、指针目标和焦点顺序属于不同机制。ResizeObserver 能帮助发现重排，但不识别阅读意图；pointer-events 能改变命中，却不等于键盘禁用；Focus Order 要求相关导航保留意义与操作，却不规定聊天自动滚动。MDN 的 pointer-events 返回内容包含完整的属性正文、说明与示例，之后较长的站点导航被工具截断；本文未使用被省略内容。

设计建议与限制：来源切回宜保留阅读上下文，分别处理焦点和位置；流式增长宜服从明确的阅读模式，不应自行覆盖用户上翻选择。这些是基于文档边界提出的方案，不能宣称为原文要求，也没有经过实际界面验证。本次只调用 webfetch 读取下列三条指定 URL，未搜索扩展资料、跟随链接、读取本地文件或凭据、创建或修改文件、调用其他成员或发布额外产物。
