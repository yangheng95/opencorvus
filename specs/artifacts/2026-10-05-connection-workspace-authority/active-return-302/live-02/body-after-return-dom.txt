        - paragraph:
          - strong: 文档事实
          - text: ：本次实际通过
          - code: webfetch
          - text: 读取了指定的三篇页面：MDN 的

            - /url: https://developer.mozilla.org/en-US/docs/Web/API/ResizeObserver
          - text: 、
          - link "pointer-events":
            - /url: https://developer.mozilla.org/en-US/docs/Web/CSS/pointer-events

            - /url: https://www.w3.org/WAI/WCAG22/Understanding/focus-order.html
          - text: 。前两篇解释浏览器接口与 CSS 属性；第三篇是 WCAG 2.2 成功准则 2.4.3 的解释性文档，页面明确说明 Understanding 文档属于信息性解释，不是额外的符合性要求。
        - paragraph:
          - strong: 设计建议
          - text: ：应把问题分成尺寸观测、指针命中、键盘导航与阅读连续性四个层面。三篇文档分别提供部分依据，但不构成完整的聊天界面规范。下文关于自动跟随、阅读锚点、恢复位置与用户意图的方案，均是针对长对话的设计建议，不是这些页面直接规定的行为；本次没有检查实际产品，也不据此宣称任何实现已经合规。
        - heading "2. 流式正文不等于每次都发生尺寸变化" [level=2]
        - paragraph:
          - strong: 文档事实
          - text: ：ResizeObserver 页面开头定义，其报告元素内容盒或边框盒尺寸的变化，也可报告 SVG 元素包围盒尺寸变化。文档示例通过改变容器宽度调整文字大小，说明这种观测不局限于视口改变。它观察的是目标的几何尺寸，而不是正文的语义、网络流片段或用户是否已经读过内容。
          - link "依据：ResizeObserver":
            - /url: https://developer.mozilla.org/en-US/docs/Web/API/ResizeObserver
        - paragraph:
          - strong: 设计建议
          - text: ：流式文本追加与尺寸变化应作为两种事件处理。追加几个字可能还没有换行，正文尺寸不变；来源栏展开可能没有新增正文，却让正文变窄并增加行数。因此，不宜把观测回调次数当成生成进度，也不宜把没有回调解释为没有新内容。内容更新用于维护消息状态，尺寸通知用于重新评估布局，两条路径可以协作，但不能互相替代。
        - heading "3. 内容盒、边框盒与观测目标" [level=2]
        - paragraph:
          - strong: 文档事实
          - text: ：MDN 说明，内容盒是可以放置内容的区域；边框盒则包括内容、内边距和边框。页面列出
          - code: observe()
          - text: 、
          - code: unobserve()
          - text: 和
          - code: disconnect()
          - text: ，分别用于开始观测目标、结束单个目标的观测以及结束该观察器的全部观测。它们描述了观测生命周期，却没有指定聊天产品必须观测哪一层容器。
          - link "依据：ResizeObserver":
            - /url: https://developer.mozilla.org/en-US/docs/Web/API/ResizeObserver
        - paragraph:
          - strong: 设计建议
          - text: ：选目标时先问“哪一种尺寸变化需要影响阅读”。固定高度的滚动容器即使内部正文增长，自身盒子也可能不变，因而不能单靠观测外壳发现全部内容增长。可考虑观测内部正文及会改变可用空间的来源区域，但不要不加区分地观测每个字符节点。目标过多会增加管理复杂度；目标过少则可能遗漏布局变化，应通过具体场景验证取舍。
        - heading "4. 布局变化不能直接证明用户意图" [level=2]
        - paragraph:
          - strong: 文档事实
          - text: ：ResizeObserver 的接口描述与示例都围绕尺寸，未提供“正在阅读历史”“希望继续跟随”或“刚从来源切回”的状态。pointer-events 页面讨论事件目标，Focus Order 页面讨论顺序导航，也都没有定义通过滚动距离判断阅读意图的算法。
          - link "依据：ResizeObserver":
            - /url: https://developer.mozilla.org/en-US/docs/Web/API/ResizeObserver
          - text: 、
          - link "Focus Order":
            - /url: https://www.w3.org/WAI/WCAG22/Understanding/focus-order.html
        - paragraph:
          - strong: 设计建议
          - text: ：尺寸变化只能说明布局条件变化，不能自动授予界面移动用户视图的理由。建议单独维护“跟随最新”“阅读历史”“阅读来源”等交互状态，并让明确操作具有较高优先级。例如，用户点击“回到最新”可明确恢复跟随；正文变高则不应自行清除阅读历史状态。状态名称和切换规则属于产品策略，必须承认其推断性质，而不是包装成浏览器提供的事实。
        - heading "5. 用户上翻时，保留阅读上下文" [level=2]
        - paragraph:
          - strong: 文档事实
          - text: ：三篇页面没有规定用户向上滚动后必须暂停多久，也没有给出距底部多少像素算作“正在跟随”。Focus Order 要求顺序导航在影响意义或操作时保持二者，但这不是自动滚动阈值的规定。尺寸观测能力与焦点顺序要求，都不足以直接推出某个聊天滚动策略。
          - link "依据：Focus Order":
            - /url: https://www.w3.org/WAI/WCAG22/Understanding/focus-order.html
        - paragraph:
          - strong: 设计建议
          - text: ：用户主动上翻后，可以暂停自动追随，让后台流式正文继续增长，同时显示不抢位置的“有新内容”入口。需要避免把所有位置变化都归因于用户：程序定位、窗口变化或布局调整也可能改变滚动位置。判断机制应区分明确输入与系统调整，并为误判提供恢复入口。尤其不要在用户刚找到历史引用时，因为新一行出现就把视图拉回底部。
        - heading "6. 底部跟随应是可撤销的模式" [level=2]
        - paragraph:
          - strong: 文档事实
          - text: ：ResizeObserver 能通知尺寸变化，但页面没有要求回调执行滚动操作。它也没有保证一次通知就意味着流式正文已完成、所有图片已布局或页面不再变化。接口能力是“观察到某种变化”，而不是“整个对话已经稳定”。
          - link "依据：ResizeObserver":
            - /url: https://developer.mozilla.org/en-US/docs/Web/API/ResizeObserver
        - paragraph:
          - strong: 设计建议
          - text: ：底部跟随适合用户明确选择持续观看最新正文时，但应允许随时退出。决定是否跟随的状态最好在新内容导致布局变化之前就已确定，否则可能把内容增长造成的底部距离变化误认为用户退出。恢复跟随后也无需把键盘焦点一起移走：视图位置、焦点位置和生成状态是三个不同对象。将它们绑在同一个更新回调中，容易制造难以解释的跳动。
        - heading "7. 来源阅读是任务切换，不只是面板开关" [level=2]
        - paragraph:
          - strong: 文档事实
          - text: ：Focus Order 页面举例说明非模态对话框：触发按钮激活后，对话框中的交互元素插入到按钮之后的焦点顺序，关闭后按钮后续的导航恢复。模态示例则将焦点移入对话框，打开期间外部内容不可获得焦点，关闭后返回触发按钮或其后元素。这两种示例体现了不同交互模型。
          - link "依据：Focus Order":
            - /url: https://www.w3.org/WAI/WCAG22/Understanding/focus-order.html
        - paragraph:
          - strong: 设计建议
          - text: ：来源面板应先确定是并行阅读区域还是要求暂时独占操作的模态区域，再设计导航。不能只因它浮在正文上方，就自动认定为模态；也不能视觉上阻断正文，键盘却仍无提示地进入后方操作区。打开来源时可保存触发项与正文阅读位置，让来源任务有清楚的起点和返回路径。具体采用哪种模型，是产品选择而非文档唯一答案。
        - heading "8. 来源切回要分别恢复位置与焦点" [level=2]
        - paragraph:
          - strong: 文档事实
          - text: ：Focus Order 的模态示例允许关闭后返回按钮或按钮后面的元素，并未要求所有关闭动作都采用同一目标。页面关注恢复后的导航是否逻辑清楚、能保持操作；它没有指定正文滚动偏移如何保存，也没有规定必须回到打开来源时的像素位置。
          - link "依据：Focus Order":
            - /url: https://www.w3.org/WAI/WCAG22/Understanding/focus-order.html
        - paragraph:
          - strong: 设计建议
          - text: ：切回时应分开回答两个问题：用户接下来从哪个控件继续操作，以及用户接下来阅读哪段正文。来源触发项仍存在时，返回该项通常便于延续上下文；正文已经重排时，可按消息或段落身份恢复附近位置，而不是盲用旧偏移。若触发项已经删除，则需要合理后备目标。恢复过程不宜默认跳到最新消息，除非用户明确选择了这一动作。
        - heading "9. 尺寸观测回调存在循环风险" [level=2]
        - paragraph:
          - strong: 文档事实
          - text: ：MDN 的 Observation Errors 部分说明，遵循规范的实现会在绘制前处理尺寸通知；样式和布局重新计算又可能触发更多通知。部分通知会延后，并产生
          - code: ResizeObserver loop completed with undelivered notifications.
          - text: 错误。文档强调，这种机制避免浏览器锁死，却
