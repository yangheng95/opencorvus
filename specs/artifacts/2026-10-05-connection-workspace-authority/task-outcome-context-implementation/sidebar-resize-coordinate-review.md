## Source-qualified defect

`services/pane.ts:54–63` defines the sole Panel config: body panelBody, left separator leftPaneResizer, fixed-left `workspaceNavigation`, sidebar CSS variable `--ui-sidebar-width`. `readPaneGeometrySnapshot` measures body viewport rectangle, handle width and the actual visible fixed controls; `paneSidebarMax` subtracts leftFixed when bounding remaining content. This establishes that sidebar width excludes the fixed rail. Canonical architecture `07-panel.md:208–212` likewise specifies a fixed rail plus independently resizable project list, reserving measured rail width.

However `resizePane` **line315** computes `round(clamp(clientX - bounds.bodyRect.left,min,max))`. `paneResizeBounds` exposes bodyRect/min/max/now/handleWidth, but discards measured leftFixed. The subtraction handles a translated host/body origin; it does **not** handle the fixed rail inside that body. App places navigation then left activity shell then the separator; `styles/surfaces/activity.css:12–17,51–55` assigns sidebar width to the shell and separate navigation width. Thus body-relative separator X is rail+sidebar (and grab/handle offset), while the function saves it as sidebar alone. This is a current production coordinate-domain mismatch, proven independently of Root's numeric trace.

`startPaneResize:356+` stores no initial pointer or rendered width and immediately calls `onPaneResizeMove(event)` on pointerdown. Consequently pressing an unchanged separator queues a recomputation from its body-relative position; rail width can be added even before a deliberate delta. On each subsequent drag start the already changed sidebar moves the separator, and that absolute formula can add the rail again. RAF coalesces moves; stop cancels/flushed pending move and persists the actual CSS width. That machinery makes the wrong coordinate persist rather than explaining it away as just an aria label.
