## 1. Existing authorities and precise epoch semantics

`api-state` has the sole monotonic connection authority. URL/credential publication and confirmed same-URL renewal change it; directory-only configure does not. Thus API A→B→A is already retired by authority even when the endpoint string returns to A. The candidate in this document keeps that authority unchanged and changes the selected project/source.

`boardStore.selectEpoch` is initialized once in store/board.ts. `beginWorkspaceSelection()` in workspace.ts increments it, and `ownsWorkspaceSelection(epoch)` compares it. `admitWorkspaceSelection` first advances the separate existing admission-intent sequence; an already-ready target returns unchanged **without advancing selectEpoch**. An approved close boundary advances selectEpoch once; Cancel/failed admission preserves it. The intent sequence is not a substitute for this public selection lifetime, and this plan does not expose it or create another counter.

Other actual advancement paths: workspace confirmed manual connection departure/directory-free entry; `supersedePendingWorkspaceSelection` when opening Mission Board (even a stable selected project may remain); explicit Task creation/restoration/deselection in main, chat, init, task and dom-utils; selected conversation Session deletion/archive increments it after the actual accepted mutation. `selectTask` copies the caller's already-admitted epoch into the store; it does not independently increment on every call. The board-store comment saying every selectTask call increments is an imprecise historical description, not the implementation contract. Conversation/Work/Mission selection hydrates use the admitted selection epoch; Mission remains a canonical Session. Selecting another Task or Session within the same project is a real new selection lifetime; clicking the already-ready same source is not.

`settingsStore.directoryEpoch` is also existing authority, advanced by actual applyDirectory, directory-free entry and the explicit settings epoch primitive. It is used by config-load, meta and project-memory. It is not enough alone for this candidate: Task and Session selection set `selectedSource` synchronously before async health/claim/applyDirectory. A rapid A→B→A can expose B through `activeProjectDirectory()` then return to A while `settingsStore.directory` never left A and directoryEpoch never advanced. `setProjectDirectoryContext` is limited to startup ensureDirectory; this plan does not change its semantics or create a project identity.

**Selected policy:** UI-side continuations born in a selected workspace capture its existing selectEpoch in addition to API authority, explicit directory and their existing request/action generation. After a real selection departure, an old UI callback remains retired even if directory text returns to A. This does not cancel server-owned work, reinterpret an accepted response as failure, or invalidate the global UI locale choice. Stable current-project actions and already-ready reselection retain their current outputs. Existing narrower request identities still distinguish two requests within the same epoch.

## 4. Permission write queue: missing logical-entry API capture

### Existing production sequence and public contract

ComposerPermissionControl.pickMode is the production caller of setPermissionMode. The service captures `directory` and increments permissionWriteGeneration, then appends work to its **one permissionWriteTail**. Its ownsResponse predicate compares latest permission generation and current directory only. Within the later tail callback it calls project patchConfig or global patchGlobalConfig **without supplying API authority**, so those calls default-capture whatever connection is current at dispatch time. setPermissionMode returns void; error reporting is owned by the tail, and newer mode picks already retire earlier presentation.

Concrete source sequence: request1 occupies the tail; request2 is chosen in backend A/project X and waits; the user applies backend B; request1 settles; request2 invokes patchConfig against B with retained A directory X, or invokes B global config for an originally directory-free A action. This is a connection-ownership gap even without returning to A. It is not established by the file screenshots and is not a demonstrated real permission write.

### Minimal selected repair

Capture the existing API authority and selection epoch at setPermissionMode's logical entry; keep the one tail and permission generation. At the queued callback, check the original API token before any HTTP and pass it into every project/global helper. The caller's original generation/directory/epoch predicate governs appStore and diagnostics. A superseded selection may retire an as-yet-undispatched UI intent under the existing latest-choice semantics; this must be explicit and must not affect an already dispatched A request. A completed original A PATCH retains its result and committed-error fact, without applying it to B/new A or dispatching another action there. Catch/finally may settle the original tail but cannot overwrite another operation's state. No new tail, queue cancellation controller, public backend protocol or test accessor.

## 5. Locale write queue: global preference and project prompt leg

### Existing production sequence and public contract

applyLocalePreference is called by AppearancePanel, CommandPalette and two TitlebarMenubar actions. It captures localePreferenceGeneration and the current directory, sets the requested local setting, waits for the existing localePreferenceTail, then loads/applies the locale. If that original directory is still current it synchronizes the project's agent prompt locale, then saves the actual overlay settings. It returns true for the current completed global choice, false only when a newer locale selection supersedes it, and throws current failures after restoring the confirmed durable locale. The tail is always released in finally.

`projectOptions` currently has no authority. After await previous and await setLocale, a backend switch with the same directory string can cause syncAgentPromptLocale to default-capture B. The rollback branch also constructs fresh options and can repeat this wrong-target leg. An ordinary project departure already skips the scoped prompt sync while allowing the global locale preference to complete; the fix must preserve that established distinction.

### Minimal selected repair

Capture one API token and selectEpoch at the logical applyLocalePreference entry and pass them through the existing projectOptions predicate/helper. After each await, project prompt sync is eligible only for that original project lifetime and API authority. Keep localePreferenceGeneration/tail as the sole owner of the **global** locale/render/settings choice; do not redefine global locale ownership as API ownership. When a project leg is retired before dispatch, skip that obsolete leg and finish the current legitimate local/global preference. If an already dispatched prompt sync throws the existing typed API-retirement outcome, preserve the actual A response classification and retire that leg; do not replay against B or roll back a valid global selection merely because its old backend disappeared. Unknown transport failure is not proof of A commit. Ordinary current-backend failures retain the existing rollback/error contract, and any rollback project sync must carry the same original token and owner. The local settings writer remains the current canonical saveSettings transaction, not another preference store.

This distinction needs root review before source work. In particular, a true local settings persistence failure after an A project PATCH is still a real failure requiring the existing local rollback; it must not be confused with backend-leg retirement. No blanket catch, fabricated committed success, default-locale fallback or swallowed current error is proposed.
