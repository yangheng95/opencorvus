## Busy and timing distinction

Composer primary action is stop exactly when busy=true and no draft; otherwise send. Busy comes from messageStore.chatRequest, actual task interruptibility or active Session ledger interruptibility. In stop mode, sendDisabled reads only stopping and sendTitle reports Stop before considering enabled. Hence the reported disabled **Send** help cannot be asserted to occur throughout active streaming: during a correctly projected empty-draft active request this code should show Stop help. It may be an admission/request transition, an existing draft, a request/busy publication window or another actual owner combination. Without the intermediate persisted image/signal timings that exact condition is unknown. The confirmed placeholder mapping is independent: textarea always uses enabled to choose static configuration text, even when Stop is valid.

Session selection intentionally clears composer model projection, then projects effective Session config under API/selection/generation ownership. An intermediate empty model is a loading transition, not evidence that configured Sol is missing. canComposeChat may stay true during that projection; modelAvailable then gives model-specific Send guidance. A late/retired model response is already constrained by existing generation/authority contracts. Nothing in this evidence establishes that model loading caused the reported disabled_unavailable string, since that string's direct predicate is parent enabled=false, not modelAvailable=false.

The source distinction is therefore: real unavailable connection/workspace mode; intentional launcher/submission busy; model projection pending/actual missing selection; empty draft; upload progress; active-work Stop/stopping. Current textarea help ignores those distinctions. Saved ready/final PNGs establish no persistent missing setup and must not be reported as failing intermediate screenshots.
