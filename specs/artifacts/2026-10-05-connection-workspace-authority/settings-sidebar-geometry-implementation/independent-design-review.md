## Direct cause and finite design boundary

Current initial aria current may compute before configSidebar joins document and chooses140; DOM geometry is not reactive so mounting alone cannot renew it. resizeBounds is a memo with no reactive dependency: currentUIScale reads computed CSS, not a Solid signal. Adding zoom as a dependency while synchronously reading CSS is insufficient because main's applyZoom effect ordering is not guaranteed. ChatComposer's synchronous zoom/update pattern is existing code, not proof that it is safe for this width/scale contract.

One local rendered-geometry projection should replace the old pre-mount lookup/minimum output. It is read-only {actualWidth,scale} measured from current mounted sidebar and current computed CSS in one callback. ActualWidth is not another requested width/cache/config; never write CSS default measurement into dialogStore. Bounds are derived reactively from this measured scale; configured request is clamped using those current bounds for its existing width/min-width style. Preserve current CSS clamp when requested width remains null.

## Smallest lifecycle proposal

Use the existing sidebar element via callback ref, with one component-local reactive ref/geometry projection and the existing createAnimationFrameScheduler. Because ConfigDialogHost survives while Show children close/reopen, component onMount alone does not cover each new sidebar. An open+current-ref effect owns each observed node lifetime. On new open node: clear stale geometry, create native ResizeObserver, observe current sidebar border-box, schedule initial measurement. On effect cleanup/close: disconnect observer, remove any relevant window listener, cancel queued frame, clear projection; measurement also checks open, node.isConnected and current ref identity. A queued old callback cannot publish a retired node's geometry on reopen. Component cleanup calls the same existing lifecycle cleanup, without a parallel observer/owner abstraction.

Native RO callback schedules measurement; do not directly use contentRect or borderBoxSize as actualWidth. Use sidebar.getBoundingClientRect().width in the scheduled callback, identical to existing pointer start CSS-pixel domain; use currentUIScale in that same callback. Observing {box:'border-box'} tracks padding/border size changes as well as content. RO borderBoxSize is untransformed layout inline-size, whereas getBoundingClientRect is physical axis/transform-aware rendered border box. Current CSS uses horizontal layout/universal border-box and ui-scale custom-property dimensions, not a Settings transform scale. Thus current domain is aligned, but transforms/writing-mode changes are not qualified; do not introduce another conversion or assume general equivalence.

A zero/disconnected measurement should leave geometry unset, not publish minimum140 as actual. Initial ARIA can omit current until mounted measurement exists; do not advertise a fake pixel value. Min/max likewise use measured current scale, or derive from an explicit current measurement at the event boundary. Root should admit exact brief pre-measure semantics before implementation; do not gate the whole dialog. Stable screenshot must show current actual width and consistent measured bounds.

## CSS scale ordering without a second zoom authority

A zoom dependency can schedule the existing frame, not read CSS immediately. The frame reads CSS after synchronous main/theme applyZoom effects and style/layout resolution. Include initial/open schedule, RO changes and window resize; use settingsStore.zoom only as an invalidation request for schedule. It is not the scale value authority. This scheduled invalidation is needed because an explicit requested width can leave sidebar border-box unchanged while ui-scale changes min/max/keyboard step. RO alone is not guaranteed to notify in that case. No MutationObserver/global CSS-scale store is required for the admitted normal application zoom entry. theme.ts applyZoom writes --ui-scale synchronously; main applies it in its existing hydrated settings effect, and normal zoom controls call it. Arbitrary external CSS edits and browser transform zoom remain unknown/unadmitted.

After measured scale changes, existing configured request clamp/style may change actual box and schedule another measurement. This is projection convergence, not persisted width mutation. Avoid observer loops by updating geometry only when measured width/scale differ; no layout writes inside measurement. Keep the sole setter's currentUIScale policy; it already reads actual CSS at action time. If a source proof finds an externally changed scale without normal zoom invalidation, investigate that entry before expanding observer scope.

## Keyboard repeat and pointer semantics

Do not drive rapid Arrow repeats only from last asynchronously measured width: multiple keys before the next frame would all add16 to the same old sample. Keyboard event should use latest explicit configured/request width clamped against current event-time CSS scale if request exists; otherwise read mounted actual sidebar width synchronously. Then use the existing nextConfigSidebarKeyboardWidth and setter. This is reading the sole requested fact for cumulative actions, not a second width store. Home/End use those same current bounds. ARIA can reflect the measured rendered projection; it may briefly lag the commanded target until the frame, which is actual rendering semantics, not reason to persist the projection. Root should confirm stable label and rapid repeated keys manually.

Pointer retains captured actual rect plus native clientX delta, existing RAF/final flush/listeners. Existing onStart captures bounds and actual width; do not replace origin with asynchronous geometry or rebase during drag. Current code sets resizing markers before reading rect; Root can assess exact effect only if actual evidence shows those markers alter Settings width transitions. This source did not prove that change necessary. Close must still clear existing resize session/pending final move via its current owner; observer cleanup must not leave body resizing or bypass that final flush. Whether current close during active drag receives subtree lifecycle cleanup is a separate existing useResizable lifecycle question, not silently repaired through the geometry observer.

Settings has no dedicated collapse; close/open is its lifecycle. Explicit width remains current dialog presentation state across reopen; default remains responsive CSS. No main-sidebar persistence/reset, dock behavior or form/Provider logic changes.
