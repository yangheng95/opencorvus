## Source cause and chosen SQL bridge

The actual Sol04 native query returns Session `ses_-zUSmY0NLzz5W92TdJ0R`; forward query returns empty. Middleware resolves selectedDirectory (`server/server.ts:890–918`) while routes/session passes raw query.directory (`:786–787`) into raw SQL equality (`session/index.ts:1060,1101`). Mission condition `mission/session.ts:369` and global Task `engine/store.ts:1309` repeat this lexical mismatch class. Existing Instance cache/project ownership normalization never rewrites those later filter inputs.

Project.samePath (`project/project.ts:283–289`) is a JavaScript comparison, **not directly callable inside SQLite**. Embedding that function in a Drizzle SQL expression is not supported. SQL lower(replace(...)) would duplicate and only approximate the existing primitive, especially trailing roots/namespace/OS behavior. Applying a JavaScript predicate after SQL limit/cursor would lose matching rows and break pagination. Removing the directory predicate would violate exact sibling isolation.

Use one small **SQL predicate adapter over the actual Session directory column**: in the caller's existing synchronous database operation, select distinct saved SessionTable.directory values (project_id constrained when the caller has an actual Project scope), filter those values with Project.samePath against Filesystem.resolve(requestedDirectory), and return `inArray(SessionTable.directory, matchingActualStoredValues)`. It binds the actual persisted values, so native/case variants admitted by the existing comparator match without changing data. Zero matching values yields the installed inArray empty-array false predicate. The final real query retains its original other conditions/order/cursor/limit and applies the directory predicate **before** pagination. No rows or endpoint bodies are normalized or cached.

Installed Drizzle SQLite declarations expose selectDistinct (`sqlite-core/db.d.ts:161–171`) and groupBy (`query-builders/select.d.ts:369–393`); installed conditions.js:157–159 implements empty inArray as SQL false. Prefer selectDistinct for this exact column catalogue. Session already imports inArray and Project. This is a repository-installed source/API feasibility check, not execution evidence.

## One filter contract and minimal production scope

Add one narrowly named adapter in the existing Session/data subsystem, for example `session/directory-filter.ts`, exporting a SQL condition function with `(db: Database.TxOrDb, requestedDirectory?: string, projectID?: string): SQL | undefined`. It imports SessionTable, existing Filesystem.resolve, Project.samePath and current SQL primitives. It has no persistent state and captures no current frontend selector. projectID is supplied only from the caller's genuine Instance Project; absence means current global contract. That optional scope changes catalogue breadth, not directory equivalence.

Preserve the existing falsy optional filter behavior: omitted or empty string means no extra condition/all in the existing scope. Do not trim a nonempty path into a different physical name. For supported nonblank filters, Filesystem.resolve validates/resolves OS-native syntax once; cross-platform-invalid input yields existing Filesystem.InvalidDirectoryError. Do not stat directories or reinterpret a valid unmatched lexical path as a required missing-directory error: an unmatched filter yields the precise empty list in global/direct reads. Scoped REST middleware retains its current directory admission/errors before the filter runs. Blank/header-selection edge behavior is not permission to alter server/directory precedence or global route contracts.

Consumers:

* Session.list and listGlobal retain their distinct Project/global scope, title/roots/time/archive/cursor/deletion semantics. Build the condition inside the real DB callback, conjoin it with their current conditions and keep pagination in SQL.
* listMissionSessions/listGlobalMissionSessions retain kind, actual mission metadata, Project/global distinctions and cursor/search/archive semantics. Remove only the duplicated raw directory condition from missionSessionConditions, then conjoin the same shared adapter inside the DB callback. Exact Mission create/get/ownership equalities are not modified.
* listGlobalTasks joins the authoritative root Session directory. Add the same SQL condition to the existing joined query and remove its raw JavaScript equality filter. Keep Task lifecycle/archive/deletion/root projection, title/status/time cursor ordering intact. Project Task list/search stays unchanged because it filters actual project_id, not raw directory.

Catalogue and final query must observe one consistent database read snapshot. Reuse the existing synchronous Database.transaction primitive (`storage/db.ts:1794` onward), which reuses active transactions/savepoints; no immediate writer reservation or asynchronous callback is needed for a read. If existing caller already owns a transaction, reuse that db. Do not perform the catalogue through a separate global Database.use outside the final query's operation and race directory changes. Review exact transaction interactions of Task projections before implementing; a helper must not trigger Project/Instance creation or filesystem admission.

Expected production changes are the single adapter plus Session index, Mission session and engine store filter call sites. Current route validators/DTOs/frontend helpers/SDK and persisted schema need no change. Module topology must be checked before final admission: Session/Mission already import Project and db; the new engine→adapter→Project edge requires the existing topology checker to confirm it adds no prohibited cycle. Do not solve a cycle by copying samePath or leaving two comparison implementations. No schema migration, stored-row rewrite or index/cache is included.

## Lexical equivalence versus physical aliases

The chosen contract treats Windows slash/native separators, conventional case variants and trailing separators according to current Project.samePath. Resolving the request once covers absolute/relative/native mounted syntax according to existing Filesystem rules. Exact sibling paths stay different even within one Project; filtering does not mean all sandboxes/worktree paths belonging to that Project.

ProjectDirectoryAdmission.key additionally resolves physical aliases/nearest-existing ancestors and owns physical occurrence admission; Project.sameFilesystemLocation observes actual device/inode. Those physical primitives are **not** chosen for this read filter: they require filesystem observations, can fail or change with relocation, and could broaden a lexical directory selection to a separate alias. Symlink/junction equivalence, hard links, per-directory Windows case-sensitive flags and arbitrary legacy corrupted paths therefore remain outside this contract. Preserve existing UNC/extended namespace validation through Filesystem.resolve, but accept alias equivalence only when existing lexical comparator actually establishes it. Do not claim a physical-directory identity repair from a filtered list passing.

Catalogue selection has a cost proportional to distinct saved directory strings in the actual Project/global scope, and the generated bound-value list is proportional to matching lexical variants. Their real production sizes and SQLite variable-limit headroom are unknown here. Typical same-directory spelling sets should be small, but that is an assumption, not a qualification. Implementation must inspect generated SQL/bind behavior with a meaningful owned fixture; if pathological variant count needs batching, do not introduce a fallback branch. Reassess the one contract instead. This proposal adds no index and claims no observed query plan or directory-index benefit; final performance qualification remains required.
