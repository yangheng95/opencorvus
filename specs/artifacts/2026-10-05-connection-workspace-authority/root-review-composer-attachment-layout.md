## Trigger and cause

The count and indexing status are rendered inside ComposerAttachmentLoaders, immediately before the plus button. That loader is a nonshrinking flex item (`flex:0 0 auto`) within .chat-compose-meta-left. The footer explicitly does not wrap, its send/stop item also does not shrink, and .composer-toolbar-options gets the remaining flexible width. Reference/model controls already use max-width and ellipsis. Thus extra status text consumes the same finite width as executable controls and causes the actual visible truncation.

The existing ResizeObserver selects full/icons/overflow from the entire toolbar width divided by UI scale (680/400 thresholds). Adding status text does not change the outer width, so it does not select a smaller presentation merely because available control space shrank. This is why the earlier viewport/min-width work correctly made controls reachable but did not resolve this content-dependent density issue. It is not proof of a broken count, incorrect upload owner, lost attachment or inaccessible click target. The image demonstrates label compression at this exact desktop configuration; other widths/locales still need actual review.

## Minimal implementation recommendation

Move the **one existing** indexing/count status branch out of ComposerAttachmentLoaders to the attachment area above the input shell, immediately beside/below the existing chips. A short separate status row is the simplest geometry: it can wrap at the existing composer width and never competes with footer controls. Keep the plus button and file input/menu in the footer, as required by the current directly-accessible attachment action contract.

Render the status directly from existing `uploadingCount()` and `attachmentCounts()` in ChatComposer: indexing wins while count is positive; otherwise use the unchanged count translation with the existing limits. Remove the three count-only props (`fileCount`, `folderCount`, `uploadingCount`) and their spans from the private loader rather than retaining duplicate markup or a mirror store. The parent already owns the sole messageStore attachment memo and live upload collection. No new state, count computation, polling, owner, timer, transport or revision is warranted.

Preserve the status's current visibility semantics independently from the existing `canAcceptComposerAttachment()` chip guard. In particular, a pending first upload has no chip yet but must still display indexing; disabling input must not accidentally hide the pending status. Preserve one role=status/aria-live=polite region, the existing indexing precedence and all file/folder limits. Keep count zero/no upload visually absent. Reuse the existing count typography token class in its new position, allowing normal wrapping instead of ellipsis as needed; keep .chat-attachments chip wrapping and filename truncation intact. No breakpoint, toolbar threshold, font-size reduction, forced full labels or global CSS override is proposed.

Expected production footprint: only ChatComposer.tsx and its composer.css status placement rules, plus root's architectural wording if needed. No locale text changes are needed. `attachmentCounts`, `uploads.count`, submit disabling, clipboard/filepicker/drop/paste/folder capture, batch parallelism, source/authority retirement and preview metadata remain unchanged. Already accepted server bytes are not altered by this layout change. Runtime plus-menu parallelism/unattended controls retain their current private component owner.
