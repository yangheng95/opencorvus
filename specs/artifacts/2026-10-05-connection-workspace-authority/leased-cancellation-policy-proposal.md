## Proven facts and depth

The two recipient catches currently re-read current delivery, preserve terminal/successor-owned facts, then classify most still-leased exceptions as failure. Mission closure is typed; Task active-root mismatch uses a message regex, while epoch mismatch is partly typed. A fixes helper diagnostics only, not these persisted outcomes. Source control flow proves unresolved exact owner cancellation can consume retry/deadletter policy; saved ordinary standby shutdown does not reproduce this leased boundary.

`projectProtocolDeliveryInTransaction` reads immutable lease acquisitions and sets public `attempt = leases.length`. Renewal grants and in-place expiry on release do not create acquisitions. `retry_wait` receipts contain error/visibleAt and are immutable. Terminal task_ingress/session_wake/mission_closed/dead_letter receipts dominate projection. Both catch budgets currently use acquisition attempt >=5 and delay derived from that value. Cancellation-only acquisition therefore consumes the same budget as a fault. Removing a lease or resetting attempt would falsify history.

Control lease release requires target, targetID, exact leaseID, ownerOccurrenceID and now. Existing claim internally receives acquired.lease but returns only projected delivery; owner text alone is expressly insufficient in the control-lease contract. A new cancellation handback must carry the original acquired lease identity through the existing claim path, not reread a replacement and treat it as the old identity.

Mission commitBundle persists session_wake with actual Message before completion. Task transaction persists Message, exact ingress and task_ingress together, then dispatches afterwards. A postcommit execution/dispatch abort or fault must preserve that delivered fact. Failed subsequent reply recovery belongs to Session/Task execution, not a replacement protocol delivery receipt. Task materializer currently has no signal parameter; it can complete an already admitted bundle after abort. That is valid accepted work if committed, but precommit cancellation must have a checkpoint if the policy promises prompt handback before commit.

Event Fire has another receipt schema/claim owner and current-owner defer policy. Its broad lifecycle-aborted branch can hide a simultaneous fault, but Message retry policy cannot be copied into it. Session cancellation also has actual reservation/activation/completion authority. They share cancellation identity/acknowledgement principles, not a universal shared retry state machine.

## Selected policy proposal

Public acquisition attempt remains unchanged. Genuine Message failure budget derives exclusively from existing delivery receipts: next failure ordinal = count(retry_wait receipts for this inbox) + 1. The fifth genuine recorded failure becomes dead_letter; earlier genuine failures append retry_wait with delay min(30000, 500 * 2^(ordinal-1)). A terminal dead_letter ends the inbox and is not evaluated for another ordinal. There is no persisted failure counter, migration or new cancellation receipt.

This is a deliberate semantic change from acquisition exhaustion to recorded-failure exhaustion and needs Root admission. Existing historical retry_wait facts continue to count even if their error text resembles cancellation; origin was not recorded and cannot be inferred. Existing dead_letter remains terminal. A crash before recording a failure counts as an acquisition but not a proven business failure; this is the honest limit of the chosen fact source. Do not claim a complete historical genuine-failure count.

Pure cancellation of an unresolved current claim releases its exact original lease early, appends no business receipt, and returns/rethrows the original reason after physical unwind. Projection then gives pending; its visibleAt remains the latest real retry_wait time or original enqueue time. Preserve previous last_error and backoff as historical facts; cancellation does not erase them or make a delayed retry immediately due. Subsequent poll/restart acquires a new lease for the same immutable inbox/envelope and occurrence bindings. No automatic in-same-drain re-entry after owner abort.

A current claim's rejection is pure cancellation only if its actual admitted scheduler signal is aborted and rejection === signal.reason. A same-text error, same error class distinct object, independently thrown DB/cleanup fault, or mixed AggregateError is genuine failure even during shutdown. Joiner wait cancellation is classified in the joiner's existing awaitWithAbort scope and must never hand back the original drain's claim. Cancellation cannot be inferred from global disposing status, typed error name or keywords.

Settlement precedence, in one existing delivery-owner transaction:

1. Read immutable terminal receipt/current delivery. Return its actual committed disposition first; exact duplicate acknowledgement remains idempotent. Any accepted Message/ingress/wake retains its deterministic identities.
2. Validate the original claim's exact lease fence. Expired, released or retaken claims yield the canonical ownership/recovery result; they must not write a business result or release a successor. Genuine failure still requires diagnostic preservation even when it cannot own settlement.
3. For real occurrence closure/staleness, apply the existing permanent disposition against current durable occurrence facts: Mission closed uses the envelope's opened/closure event; Task stale root/epoch becomes typed stale dead_letter. This wins over a simultaneous cancellation when the durable occurrence itself permanently rejects this envelope. Do not carry the old envelope into a reopened Mission or replacement Task root.
4. For a still-valid occurrence and exact owner cancellation, return exact lease handback plus same-envelope pending projection.
5. For independent failure, use receipt-derived ordinal and existing retry/deadletter writer semantics. A handback or settlement DB fault remains its real fault, not a successful cancellation. Keep existing owner until physical callback settlement; if handback cannot commit, expiry remains the actual recovery route and must be reported honestly.

An exact abort reason alone does not prove permanent occurrence closure. Conversely a typed closure object alone cannot be accepted without validating its durable envelope/occurrence. Policy classification belongs in the existing durable delivery owner; do not add a Scheduler gate or orchestration flow teaching models what to do.

## Horizontal coverage and limits

Production Message entrances converge: durable enqueue effect/signal drain; explicit current-Project drain; independently initialized Project drain/global periodic poll; startup bootstrapping and persisted unanswered-wake reconciliation; manual due-now. Same-Project joins one physical owner; caller cancellation of a joiner changes only its wait. Different Projects retain their own Instance/database scope and lease identity while the global queue joins all admitted siblings. Serial/parallel capacity changes admission order, not classification.

Task occurrence = target Task execution epoch plus exact root Session; Mission occurrence = envelope-bound opened event plus durable closure event; Session wake = deterministic Message/Part/control and actual activation/completion reservation. Closed/reopened occurrences retain original disposition. Restart reads persisted unresolved FIFO head, retained retry receipt and current/expired lease; no scanner memory or live signal is reconstructible. Prior delivered wake may recover actual reply execution without re-materializing Message. Source-body drift remains actual immutable-source failure, not cancellation. Real protocol source digest checks identify immutable source content and are not mutable-source build checks.

Event Fire similarly preserves accepted wake and exact definition/target/lease occurrence; source presently defers on broad lifecycle/runtime abort and may suppress independent faults. Automation reserved targets/Fire Run settlement also have their own receipt policy. Shared principle requires exact cancellation versus real fault and acknowledgement-first; this proposal does not prove or authorize those writers' implementation. Existing multi-Project/revision/reopen tests are local evidence only. Future Event slice should audit its actual signal composition, leaseFence, recovered wake and receipts before adopting any failure budget. Generic catch text or one passing standby shutdown cannot exclude that shared risk.

## Focused positive qualification and actual acceptance

Then successful reacquisition commits the exact Message and ingress/wake receipt.

* Database reopen/restart uses same pending head and backoff, acquires actual new lease and materializes once. Retained historical retry_wait/deadletter facts remain facts, not text-classified migrations. Existing delivered-wake errored-reply recovery remains valid and separate.
