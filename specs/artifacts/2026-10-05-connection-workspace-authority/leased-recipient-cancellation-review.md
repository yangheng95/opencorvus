### 2. Background catch masks genuine failures racing cancellation

runInstanceBackgroundWork owns one controller per physical Project cache entry and merges the optional existing owner signal with AbortSignal.any. It admits work under its own serving lease, cancels on teardown/refresh/disposal, and removes the controller only in finally after work physically settles. This ownership is correct and must not be replaced.

The catch currently says if(signal.aborted) return, otherwise warn. It always returns fulfilled Promise<void>, whose meaning is physical completion, not successful business work. If an unrelated source/DB/cleanup fault is rejected after the signal aborts, its diagnostic is suppressed even when error!==signal.reason. This is a confirmed control-flow/observability gap, not evidence of an actual Task failed state. The previous queue repair carefully preserves mixed real causes, but this downstream wide filter can still hide them.

Message drain catches callback errors into its existing failure variable and rethrows after helper completion, so it repairs error propagation locally; it still depends on its detached signal-drain reporter for classification. That reporter recognizes typed Instance/DB/runtime closed-admission refusals, not arbitrary exact cancellation reasons from the private background controller. Thus a pure owner cancellation can also appear as signal drain failed in a source-reachable detached entrance, while a genuine captured error remains observable. No such extra error occurs in the actual737-row standby log.

Event discovery uses the same helper, waits its running Fires in finally, and only schedules recovery retries while its lifecycle is live. It lacks the message drain's captured-failure rethrow, so a genuine discovery fault racing abort is suppressed by the helper diagnostic filter. Project Memory organizer similarly releases its organizer lease on failure and deletes its scheduledRuns slot in finally; helper cancellation filtering can hide an independent source/commit/handback failure. It does not by itself change the organizer's durable state to succeeded. No actual Event/Memory cancellation-failure race is qualified here.
