## Accepted POST versus secondary refresh/dialog failure

One try/catch currently includes initialization POST, clear, reload and success dialog. Any later rejection enters the same "Failed to initialize Git" catch and returns false after an optional error dialog. The boolean then incorrectly means failure even when POST already returned created:true or created:false (idempotent existing Git). If the error dialog itself rejects, an accepted operation can reject again.

Qualify the real refresh boundary precisely: current reloadProjectScope uses Promise.allSettled and returns ProjectLoadIssue[] for ordinary child GET/config/extensions/metadata failures, while retaining canonical appStore.projectLoadIssues and resource errors. Thus an ordinary failed GET generally does **not** throw through this helper and must not be misreported in this analysis as inevitably returning false. Initial authority validation, synchronous store/projection failures or other exceptional rejections can throw. The same broad catch still has no accepted-write boundary.

The dialog rejection is concretely reachable without a server failure: showAppDialog rejects when its native-surface occlusion/reveal operation fails (app-dialog.ts101–165, completion rejection204–205). Dialog publication is queued; a predicate checked merely before calling showAppDialog is insufficient if selection changes while occlusion is awaiting. The existing optional openingGuard is evaluated at queue head and again after occlusion. Reuse that exact contract instead of another modal owner.

After known accepted POST, an API retirement during **secondary** reload/dialog must likewise retire presentation and return the accepted true; this is different from original POST retirement. Original POST's ApiAuthorityChangedError must propagate unchanged with its private response/failure outcome. Do not inspect, serialize, replay or replace its receipt. Ordinary current primary POST error should retain the existing false/error feedback contract; retired primary errors retain their original truth while skipping obsolete feedback. A diagnostic for a current secondary failure must say initialization was accepted and identify refresh versus notification, retain original cause/details, and never say disk initialization failed. No synthesized VCS success or duplicate error store is appropriate.
