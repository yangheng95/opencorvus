        - heading "3. ResizeObserver 观察的是尺寸，不是正文内容" [level=2]
        - paragraph:
          - strong: 文档事实
          - text: ：文档 A 的定义是报告元素内容盒或边框盒的尺寸变化，也可以报告 SVG 元素包围盒的变化。内容盒不包含内边距和边框，边框盒则包含这些部分。这一对象边界很重要：观察结果描述的是指定元素的尺寸，而不是文本含义、网络传输阶段或者消息生成状态。
        - paragraph:
          - strong: 设计建议
          - text: ：流式正文不断增加时，可以观察承载正文的内容区域，以获知尺寸变化的结果。但不能将一次观察通知理解为“一段文字已经完整生成”，也不能将没有通知理解为“没有新内容”。如果观察的是固定高度的滚动容器，其内部文字增加未必改变容器自身盒子；因此应先明确观察目标，再决定它能支持什么判断。
        - heading "4. 流式更新与布局通知不是一一对应关系" [level=2]
        - paragraph:
          - strong: 文档事实
          - text: ：文档 A 的示例通过滑块改变容器宽度，再按照观察到的尺寸调整字体。正文特别说明，元素尺寸变化可以与视口变化无关。该示例说明观察器能够响应元素局部变化，但没有承诺每个字符、每个传输片段或每个语义段落都会对应一次独立回调。
        - paragraph:
          - strong: 设计建议
          - text: ：应把“收到正文片段”和“布局出现尺寸变化”作为不同事件处理。文字可能先填满现有行再换行，也可能在同一高度内替换内容；这些场景说明尺寸信号不足以承担内容状态判断。产品可用正文更新记录表达生成进度，用尺寸观察表达布局结果，避免以回调次数估算生成速度或完成程度。
        - heading "5. 用户上翻不能由尺寸变化推断" [level=2]
        - paragraph:
          - strong: 文档事实
          - text: ：文档 A 列出的能力是开始观察指定元素、停止观察某个元素，以及断开全部观察目标。其定义和示例都没有把尺寸通知描述为滚动事件或用户意图事件。因此，ResizeObserver 不是滚动意图检测机制；它也没有说明如何判断用户正在阅读历史消息、拖动滚动条或准备返回底部。
        - paragraph:
          - strong: 设计建议
          - text: ：可将界面分为“追随最新内容”和“阅读历史内容”两种状态，并由独立的用户操作与位置判断决定切换。用户上翻后，正文即使继续变高，也不应仅因观察通知而把视口拉回底部。提供明确的“返回最新”操作，是让用户重新表达追随意愿的方案；具体阈值和恢复规则则需要产品自行定义。
        - heading "6. 保持阅读位置不等于保持一个固定数字" [level=2]
        - paragraph:
          - strong: 文档事实
          - text: ：文档 A 提供尺寸变化信号，但正文没有给出完整的滚动位置保持算法，也没有承诺保存某个滚动偏移量即可保持同一阅读内容。尺寸观察本身不标识用户正看的句子，更不解释变化发生在阅读点之前还是之后。因此，它只能是位置维护的输入之一，而不是完整解决方案。
        - paragraph:
          - strong: 设计建议
          - text: ：对正在上翻核对来源的用户，优先考虑保留“哪条消息、哪个段落及其附近位置”，而不只是记录一个像素数。如果阅读点之前的内容展开，原偏移量可能仍然有效却对应不同文字；如果变化发生在阅读点之后，则可能无需修正。这样的语义锚点方案属于设计推导，本次没有实现或测试其浏览器行为。
        - heading "7. 来源面板也会改变正文布局" [level=2]
        - paragraph:
          - strong: 文档事实
          - text: ：文档 A 的示例明确展示了容器宽度变化对文字表现的影响，并强调变化不必来自视口。因而，尺寸观察并不限于浏览器窗口调整。在长对话的情境中，来源栏打开或关闭所引发的局部尺寸变化，属于该接口可以辅助观察的一类布局结果。
        - paragraph:
          - strong: 设计建议
          - text: ：打开来源面板可能压缩正文宽度，使同一段文字重新换行；设计时应同时考虑正文阅读点与来源控件的焦点位置。不能把这种增高误判为新正文到达，更不能因此强制追随消息末尾。建议区分正文追加、来源展开、容器宽度变化等原因，让位置恢复和追随逻辑依据场景作决定，而不是统一执行滚到底部。
        - heading "8. 回调中的布局写入可能产生反馈循环" [level=2]
        - paragraph:
          - strong: 文档事实
          - text: ：文档 A 的 “Observation Errors” 说明，符合规范的实现会在绘制前调用观察通知，样式和布局重新计算又可能引发进一步通知。浏览器通过处理更深层元素、延后部分通知等方式避免锁死，并可能报告

        - heading "14. WCAG 焦点顺序要求有明确适用条件" [level=2]
        - paragraph:
          - strong: 文档事实
          - text: ：文档 C 引述的 SC 2.4.3 条件是：如果网页可以顺序导航，并且导航次序影响意义或操作，那么可聚焦组件应以保留意义与可操作性的顺序获得焦点。页面将其标为 Level A。这里的判断对象是顺序导航中的焦点次序，而不是笼统要求所有内容都获得焦点，或规定唯一可接受的排列。
        - paragraph:
          - strong: 设计建议
          - text: ：长对话应围绕“用户在操作什么”组织焦点路径。例如，某条回答的来源入口、来源面板中的链接和返回操作具有关系，应避免穿插到不相关消息的控件之间。正文 C 的失败示例中，表单焦点在两个业务区域之间交替跳转，正可用于理解这种混乱风险；但聊天界面的具体结论仍需检查实际导航，而非只作类比。
        - heading "15. 视觉布局顺序不必与焦点顺序完全一致" [level=2]
        - paragraph:
          - strong: 文档事实
          - text: ：文档 C 明确说明，焦点次序不一定必须跟随视觉布局，也不必与程序确定的阅读次序完全一致，只要用户仍能理解并操作页面。它以独立双栏为例：若先后顺序不影响意义或操作，先访问右栏再访问左栏不一定失败。页面同时建议，作为最佳实践，让焦点顺序强化视觉布局暗示的阅读顺序。
        - paragraph:
          - strong: 设计建议
          - text: ：不能仅因来源栏在右边、正文在左边，就断言某一种 Tab 次序必然违法。应检查两栏是否独立，以及视觉表达是否暗示了前后依赖。若来源是当前回答的解释入口，焦点突然进入另一条消息可能破坏关系；若两栏各自完整，则可能存在多种合理顺序。建议先保证逻辑关联，再尽量降低视觉与键盘体验之间的认知负担。
        - heading "16. 来源面板应区分非模态与模态交互" [level=2]
        - paragraph:
          - strong: 文档事实
          - text: ：文档 C 的非模态示例将对话框交互元素放在触发按钮之后的焦点顺序中，再接回原页面后续元素。模态示例则在打开后将焦点设到对话框内部，使外部页面内容不可获得焦点，并在关闭后返回触发按钮或其后元素。这些是解释页面给出的示例，不是对所有来源面板只允许一种实现。
        - paragraph:
          - strong: 设计建议
          - text: ：持续对照正文的来源侧栏通常应保留清楚的往返关系；占据当前操作上下文的模态阅读器则需要设计进入、内部导航和退出后的落点。关闭时返回仍然存在的触发入口，通常有助于用户继续原任务；若入口已消失，应选择有意义的替代位置。ResizeObserver 只能辅助观察面板带来的尺寸结果，
          - code: pointer-events
          - text: 也不能代替这套焦点生命周期。
        - heading "17. 流式正文不应无条件扩张 Tab 路径" [level=2]
        - paragraph:
          - strong: 文档事实
          - text: ：文档 C 说明，SC 2.4.3 并不规定哪些内容必须或不得获得焦点；静态内容可以可聚焦，也允许程序将焦点移到静态内容。但若焦点次序妨碍意义、操作或造成混乱，则可能失败。页面还以可聚焦外层嵌套按钮说明重复聚焦的风险，并将避免不可操作焦点停靠点列为最佳实践。
        - paragraph:
          - strong: 设计建议
          - text: ：不要为了“让新增正文可访问”就给每个流式片段增加一个 Tab 停靠点。长回答包含大量静态段落时，这可能使用户到达来源按钮或输入框前需要经过冗长路径。建议保留真正有操作价值的入口，并避免每次正文增长都移动焦点。动态内容如何被辅助技术获知超出本次三页的完整覆盖范围，不能据此声称已满足全部无障碍要求。
