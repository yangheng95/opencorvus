# Evolution Lab

Evolution Lab is the target-agnostic Expert Squad for explicit incumbent-challenger evolution campaigns. It owns campaign evidence, candidate preparation, evaluation, independent integrity review, and an experiment-scoped recommendation. It never becomes a runtime dependency of the target Squad.

## Optional collaboration guidance

The package declares three stage-specific optional workflow references: opportunity analysis, frozen development campaign plus candidate preparation, and two-arm evaluation plus recommendation. Mission is the only cross-Squad coordinator. It creates a new fixed-profile Task for each Evolution Lab stage and separate fixed-profile target Tasks for baseline and candidate runs, waits for terminal acceptance, and imports exact Artifacts into the next Task. Holdout and certification are new Campaign revisions created only after candidate digest fixation and never dispatch a Candidate Author. No Task changes profile and no package workflow engine is introduced.

## Self-contained closure

The package owns the strict nine-type `evolution-lab/...@1` Artifact ABI, exact run-evidence collector, immutable package materialization/comparison tool, typed Artifact publisher, portable resource rehydration tool, campaign Skill, scorer contract, role prompts, and workflow. Payloads store stable role/path/media/bytes/digest manifests instead of Task-bound snapshot locators. Each Campaign carries exactly one declared Dataset partition and its complete input closure; metric evidence and both complete parent/candidate package trees travel in the Engine Artifact resource closure. After Mission import, `rehydrate-evolution-resources` maps the copied current-Task refs back to their declared roles and rebuilds validated resource sets. Candidate packages cannot reference this package or any other Squad at runtime.

Candidate mutation is limited to the target package's validated prompt, README, selector, Skill, reference, and example text closure, plus the manifest's declared descriptive identity text — top-level name/label/description, selector summary and selection guidance, and every agent, workflow, and workflow-node label and description. Those fields steer selection and dispatch; they grant no capability. Manifest capability grants, references, base roles, prompt paths, agent and workflow keys, and dependency edges stay byte-frozen, so a candidate can evolve what the Squad says it is but never what it is allowed to do. Target tools, libraries, scripts, assets, Model Context Protocol resources, scorers, datasets, evaluator workspace, configuration, and permissions remain frozen. Evolution Lab remains frozen unless it is itself the exact Campaign target: evolving the evolution trust root is allowed through the same validated text closure and the same evidence gates, and its promotion confirmation names it as the trust root so the authorizing operator sees what is changing.

## Authority boundary

Imported Campaigns, Candidates, Runs, Evaluations and Reviews keep their original payloads and references. Their exact Host-owned import chain connects those references to the copies in the current Task; the publisher, review resolver, history and promotion checks share that identity rule. Consumers use the current imported Artifact locators rather than transcribing old values or rerunning measurements to repair references. Multiple transported copies of one exact original retain their identities and may be explicitly superseded together. An independently published Review is a new fact even when its text and values happen to match. Missing predecessors remain explicit evidence errors, and import never grants access to another Task's live state.

Metrics are observations and never dispatch work. Failed measurement is typed unavailable, not zero or a substituted scorer. Required unavailable dimensions make aggregate score null. The Recommendation Owner can publish promote, retain, or inconclusive only for the frozen campaign. Promotion, restoration, retry, and installation require separate explicit user-authorized operations and immutable receipts.

Every metric attempt names its subject: the measured Trial's canonical collector bundle. A shell scorer runs in an isolated copy of that Trial's terminal committed workspace, made from the exact root-repository commit the bundle records and removed when the metric invocation ends; its optional `cwd` is a relative path inside that copy. Neither the Evaluator's directory nor the Trial's live directory stands in for it. A Trial without a terminal Git result, such as an inactive or awaiting-interaction observation, or whose result has nested repositories, symbolic links, gitlinks, or objects absent from the repository, leaves its shell scorers typed `input_unavailable`. Files the commit does not contain, such as ignored build outputs, are not part of the subject. A judge reads the same canonical bundle, including only the Message bodies the Evaluator selected at collection; the Run Artifact wrapper is not scorer input. Selected original Messages and provenance remain intact and may disclose run identity; this does not establish a blind comparison. The evaluating Task still owns every attempt, metric result and receipt.

An Evaluation receipt is a transport of recorded metric results, not authority supplied by an immutable JSON file. The publisher reads each exact attempt through the current scoring Task's native metric result ledger, verifies its original Trial subject and frozen scorer, and requires the receipt to agree. All scorer attempts in one receipt must also share their original immutable Task/Tool producer and metric iteration. The current metric package Tool calls the evaluator once per invocation; a later receipt publication keeps that original origin instead of adopting its own. This check does not identify arbitrary multiple internal SDK evaluations within one Tool call. Both measured and typed unavailable observations use this same projection; an arbitrary copied attempt without a recorded result cannot become a measurement. Imported existing Evaluations remain historical evidence; new publication requires results recorded by the current scoring Task.

After all scorers finish, the execution Tool publishes its original receipt as a catalog Task Artifact. It can be discovered and read in the current Task before an Evaluation refers to it, so continuation can publish the completed measurement from the existing receipt. The native result ledger remains the authority and Evaluation publication still verifies every scorer; receipt visibility alone does not guarantee that a Comparison consumed all executed measurements. Historical receipts retain their original publication kind, and cross-Task recovery still requires explicit evidence transport and the original ownership checks.

A Run Evidence Bundle is the Host projection of one collected Trial into the Campaign slot the Evaluator names. The publisher stamps the Trial's Task, terminal time, outcome, activity duration, workspace and package revision identities from a fresh collection; its recorded token usage, priced cost, and serving model from the Trial's own Provider usage ledger; and the environment from the Campaign the publication sources. The Evaluator restates none of them, so the Campaign's frozen-model check compares the model that actually served the Trial. The ledger records completed upstream steps only, so token usage is recorded usage rather than an invoice, and cost is null — unknown, not free — unless every recorded step was priced. A Trial whose ledger names no model or more than one is not a single-model Campaign run and cannot fill a slot, which leaves that slot required unavailable.

A Run Evidence Bundle with `outcome: unavailable` records an inactive or awaiting-interaction Trial. When a slot has only these observations, its exact case/arm/repetition is a required unavailable dimension even when scorer values and independent reviews exist. The aggregate is null and the recommendation is inconclusive; the measured values and original Run Artifacts remain visible for audit. Once the same Trial has a terminal observation, the slot follows the observation rules below. A failed Trial remains a measured failure governed by the declared failure-rate comparison.

The Comparison Recommendation is the publisher's deterministic projection of the selected Campaign and Candidate and every measured fact bound to them. In one frozen Task catalog enumeration of Runs, Evaluations and Reviews, it consumes every published Evaluation whose own stamped facts bind it to that Campaign and Candidate, the exact Run each measured and every proven publication alias, then includes every Review of those evaluations. The Recommendation Owner submits an empty payload and the Campaign and Candidate, then completely reads the published comparison before rendering it; selected measurements cannot narrow the set and Review locators are not selectable comparison inputs. Catalog provider errors remain explicit errors. The publisher also verifies a stable snapshot of the current Task's native metric results. Exact Trial/collector bytes and frozen scorer identities bind results to the Runs; an original exact Campaign/Run request can add another authorized Run, while baseline facts remain reusable across compatible Campaigns. A related native result without a representing Evaluation is disclosed as required `unpublished_measurement` with its original attempt reference. Partial or failed outer calls retain their recorded results; no synthetic Evaluation or inferred SDK batch fills a gap. The original complete receipt can supply the missing Evaluation without rescoring. Unreported Trials, unbound requests and untransported source-Task native facts remain outside this completeness claim. Promotion commits recheck the same membership and later Reviews, together with the native result ID set in the receipt's synchronous SQLite transaction. Any later native result requires a refreshed comparison; a verified unrelated result can be recorded without creating a required dimension. Engine catalog history bounds do not freeze the native ledger: history preserves the recorded recommendation and explicitly labels native membership differences as a current-Task live check, with no current promotion intent until refreshed. Imported Comparisons never authorize reading the source Task's live native database. Historical Comparisons remain immutable.

The collector JSON uses schema version 2. Its `usage` contains the exact ledger event IDs, recorded tokens, cost and models from the same database snapshot as Task lifecycle and the Session tree. The publisher copies that verified snapshot; it has no separate live-usage read. Later ledger entries require a new collection, and the earlier resource remains unchanged. A Task completion Tool can return before its own request usage is recorded, so terminal time is not a final billing boundary. Earlier version 1 collector resources remain historical bytes and are not accepted as current collection inputs.

The publisher stamps each Evaluation with its scoring owner Task and the original native metric result ID for every scorer. One shared measurement key keeps these IDs, Trial, slot, scorer definitions, values, statuses and attempt evidence; it resolves proven original Campaign/Candidate identities and complete equal Run facts, while treating the receipt as transport. Reordering the scorer set or transporting that same recorded measurement with an equal Run publication alias does not create a new observation. Different native result IDs remain distinct even at equal scores or within one Tool call. A historical Evaluation without recorded measurement identity remains an exact published claim: only its complete equal payload proves a publication alias, with no guessed occurrence or backfill. Run aliases still require complete equal typed payloads. Each observation is counted once, every original source remains visible, and reviews may cite any exact evaluation alias. Different Trial, value, recorded usage or terminal facts remain distinct. Every observation of a slot is consumed and none is chosen by time or value: facts the observations agree on are used, a typed unavailable result records no value, and once a Trial has a terminal observation its own inactive or awaiting observations supply no outcome, resource or scorer value. A second Trial or terminal occurrence, disagreeing terminal outcomes and disagreeing measured scorer values are reported as required conflict dimensions; disagreeing usage leaves that resource delta unavailable. History exposes the aliases of each unique observation and preserves conflict identities.

An initial or independent integrity review omits `revision` and replaces nothing. An auditor may publish a complete corrected review with `revision.supersedes` naming exact prior reviews of the same evaluation and slot, and `revision.reason` stating the correction. The same original evidence can support a logical correction. Ordinary citations, newer timestamps and similar finding text never imply replacement. The publisher requires exact direct sources and the single lineage resolver verifies parents, slot identity and acyclicity. All unresolved branches contribute their typed findings; a later explicit revision can supersede several branches without rewriting them. History retains each actual review as current or superseded and exposes the unique current review only when there is one. No synthesized review or separate ledger exists.

An integrity review's `reviewed` status means its investigation is complete, not that its findings passed. A `blocker` finding with `outcome: unavailable` contributes its exact case/arm/repetition/Review identity/category/index to required unavailable dimensions; the aggregate is null and the recommendation is inconclusive. A `blocker` finding with `outcome: failed` also makes the recommendation inconclusive while preserving measured values and the failed finding in the original review. Passed blockers and nonblocking findings retain their declared meaning; the existing failed reward-hacking rule still applies. A nonblocking `unavailable` finding is still an unobserved dimension: it appears under the same name in `unavailable_dimensions` without entering the required set, so the recommendation never presents it as observed. An `unavailable` review's stated reason is carried into the comparison's `unknowns` alongside every review's unknowns and accepted limitations. The package declares no per-Campaign list of required review categories: which invariants block adoption is the auditor's typed `severity`, so a `reviewed` review with no findings is the auditor's claim that the completed review had nothing to report. The ABI has no not-applicable outcome: a category without a finding asserts nothing further, and an inapplicability the auditor states as an accepted limitation reaches the comparison's `unknowns`. All findings remain attributable to the exact review Artifacts in the comparison source set.

Every target Trial must be created with an explicit expected package digest. A missing creation expectation is preserved as null evidence and cannot become a campaign run. Only a literal `target.scope === "built_in"` candidate yields `product_release_required`. A project-scoped package remains executable in project scope even when `target.namespace === "builtin"`; namespace is provenance, not installation scope. Such a candidate cannot be bound as an unpublished Task revision.

Comparison `calculation_inputs` records the exact Campaign, Candidate and all Run/Evaluation/Review publication identities consumed by the single comparator, including aliases and superseded reviews. The Host stamps it; the model still publishes an empty payload. Turn-wide source provenance remains complete and may include background facts not used in that calculation. Replay, history and promotion resolve the recorded inputs in the current authorized Task, including transported original identities. A historical record without this field has unknown calculation inputs: its result remains visible, with no current promotion intent, and is never reconstructed from broad provenance. This makes the original calculation identifiable; it does not establish completeness of unselected measurements or unreported Trials.

Each case/arm/repetition slot in a comparison represents a distinct Trial Task. Re-publication, later recorded usage, continued work or another metric execution on that same Task does not create another independent slot. A single shared identity check relates Run.task_id and Evaluation.trial_task_id across the actual calculation inputs; a reused Trial reports its exact slots and publication identities. Same-slot aliases and later observations keep their existing rules, and distinct Task identities remain distinct even with equal output bytes. Historical recommendations preserve their values and expose a Trial-slot collision; current promotion needs a consistent matrix. This necessary identity check does not prove statistical independence or completeness of reported Trials.
Each distinct measured fact requires its own current integrity Review; a Review of one proven publication alias covers that measurement, not other executions in the same slot. Missing coverage remains required unavailable until a real Review is published. Native terminal event IDs identify terminal occurrences: Run publication stamps the collector's terminal_event_id, while historical absence stays unrecorded. Several terminal observations without that identity remain unknown; identical clock values do not establish one occurrence.

The monetary ceiling `max_cost` is a nonnegative number or explicit `null`. Use `null` when the user or Mission declared no cost ceiling; never invent a numeric cap or use zero to mean unlimited. Zero remains a literal zero ceiling. A suggested budget is not spending approval. Preserve declared numeric limits and record all actual usage and costs independently of this field.
