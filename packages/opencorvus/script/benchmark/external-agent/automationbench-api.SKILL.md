# AutomationBench API mode

The Task is scored only from the final simulated business state. A narrative answer, repository edit, or report does not complete it.

AutomationBench initializes a seeded simulated business environment for every Task. It does not use or require real Airtable, Google, Salesforce, Slack, or other SaaS credentials. A typed 401/404 from one candidate service means that service or route is unavailable in this Task's simulated world; it is not a Host credential failure and does not prove the requested authority or records are absent from the other simulated services.

Use the project-local client with these exact commands:

```text
python3 automationbench_tool.py search "API-native keywords" --top-k 5
python3 automationbench_tool.py fetch GET "https://full.url/from/search" --params '{"key":"value"}'
python3 automationbench_tool.py fetch POST "https://full.url/from/search" --body '{"key":"value"}'
python3 automationbench_tool.py base64 "text that an endpoint explicitly requires encoded"
```

For independent operations, prefer one structured batch instead of multiple quoted shell commands:

```text
python3 automationbench_tool.py batch <<'JSON'
[
  {"command":"search","query":"service action record","top_k":5},
  {"command":"fetch","method":"GET","url":"https://full.url/from/search","params":{"key":"value"}}
]
JSON
```

`batch` accepts 1 through 20 independent `search`, read-only `fetch GET`, or `base64` operations and returns one ordered `results` array. `transport_status` and `transport_ok` describe only delivery through the local Unix bridge; the unchanged `body` is the official tool result and may contain a typed business/API error even when transport is HTTP 200. Inspect every body rather than treating transport success as operation success. A transport interruption marks the current operation `transport_outcome_unknown` and the untouched suffix `not_executed` without inventing a transport or official status. Never batch POST, PATCH, PUT, DELETE, or another mutation: execute each mutation as its own command so its receipt and outcome remain unambiguous. The bridge still executes and records every official operation separately. Keep dependent operations in later batches after the earlier result supplies their URL, identifier, or parameter.

The client path and invocation are already defined above. Do not run `ls`, `glob`, project `read`, or capability discovery merely to confirm that the client exists. Begin with the exact client command needed for endpoint discovery or execution.

`search` is an endpoint-contract directory: it tells you which URL, method, path parameters, query parameters, body fields, and response shape an API supports. It does not search the seeded business records. A zero-result `search` therefore proves only that the endpoint keywords did not match; it never proves that an email, spreadsheet, message, customer, ticket, or other business record is absent. Business existence and content are established only by calling a discovered list/get/search endpoint with `fetch`. `--top-k` accepts 1 through 20.

Use the original business request and fetched business records to decide what work is needed. Replace URL path placeholders with the exact record identifiers; query parameters belong in `--params` and request fields in `--body`. The client passes their JSON strings to the official tools. Inspect returned values and typed errors before deciding the next action.

Before the first mutation, write a compact working checklist from the original request with three columns: authoritative source, destination or action, and exact values that must survive the transfer (including every URL, identifier, date, audience, exclusion, and precedence rule). Mark each required fact found or still missing. Do not perform an irreversible mutation while a fact required by that mutation is still missing, unless an authoritative record or the original request explicitly establishes that the outcome may omit it. Independent work whose own prerequisites are complete may continue. Use this checklist to close discovery and to verify the final state. Do not replace an exact source value with a paraphrase or an invented value.

For each still-missing source fact, complete this ordered query ladder before switching products or source families. First choose the source family where that fact normally lives. Candidate generation is recall-first: query its discovered business-record list/search endpoint with the contract-required namespace, tenant, repository, mode, projection, and pagination controls plus exactly one minimal discriminative source-owned entity, event, account, or record anchor from the original request or an already fetched record. Do not add an abstract category label, speculative qualifier, or a destination identity that has no source-side role merely because it appears elsewhere in the Task. A name shared by the destination and the authoritative source organization or account remains a valid source anchor when the request, a fetched record, or the source contract establishes that role. Fetch only candidates whose identity or content can apply to the obligation. Add one narrowing business condition only when the minimal-anchor result is non-unique. A compound or full-phrase empty query does not consume the endpoint attempt and cannot justify a source-family switch: replace it with the same endpoint's minimal source anchor. Resolve anchor-producing identity or detail facts before dependent rule, approval, link, or exact-value facts when their dependency is known. Whenever a later authoritative read yields a new source-owned anchor, admit it only when that authority identifies it as the requested entity's ID, alias, or more precise name, or as an explicit material dependency of a still-missing fact; ignore incidental people, events, accounts, and records. A newly admitted anchor makes every earlier result with no applicable match for that unresolved fact provisional until the new anchor is tried on each still-open candidate authority endpoint. It does not reopen a route or service already closed by typed unavailability unless new actionable evidence changes that condition. Only after the minimal anchor and every admitted eligible anchor have completed contract-valid candidate inspection with no applicable match may the worklist advance to the next authority supported by the fact's information shape. A result can be empty or contain candidates excluded by explicit identity, content, recency, or applicability evidence; record the concise exclusion basis instead of treating every non-empty result as authority. Try each fact, endpoint, and eligible anchor combination at most once, and close it at the first authoritative match. A typed response that establishes endpoint- or service-wide unavailability, or that the endpoint cannot express the anchor under its declared contract, closes exactly that route and permits the next contract-valid source. A first client call-shape, argument-validation, or contract `TypeError` proves only that the attempted call failed; make one contract-correct call instead of replaying it. If the corrected contract-valid call returns the same external/interface failure, preserve that exact route blocker and stop the route unless new actionable evidence appears. This finite evidence worklist is bounded by material facts, candidate authority endpoints, and newly observed anchors; it is not permission to enumerate records or products.

Start endpoint discovery with one focused query made only from API-native service, resource, action, and known identity-field nouns; do not put business-record values, audience wording, desired content, or abstract guideline/policy labels in an endpoint-directory query. When the first query asks for multiple independent capabilities, request the allowed top 20 results and execute independent returned reads through one structured batch. Search again only for a capability that the first result omitted and the request or a fetched record actually requires. When the request names the authority, do not probe alternative products merely because they might contain similar information. When the authority is unnamed and a required fact remains missing, search once by the information shape and API operation nouns (for example message search get, event list get, or document search get), then try the relevant returned read endpoints together and stop at the first matching authoritative record. A typed unavailable response closes only the route, resource, or capability whose absence it explicitly proves. Close an entire service only when the response explicitly establishes service-wide unavailability; unavailability does not waive a required business fact.

Route an unnamed source by the kind of record the business fact normally lives in. Recent operational instructions, approvals, links, exclusions, and warnings start with message or email search. Query a communication store first with the smallest source entity or event term that still distinguishes the requested subject; do not add the destination organization, channel, audience, or abstract rule label unless it is independently established as source-owned or contract-required scope. Operational messages often omit destination-only qualifiers. Dates and schedules start with calendar or event records. Formal long-form policies start with document or file records only when the request or an observed record identifies a formal policy/document dependency, or after the communication route has completed the ordered anchor ladder without a match. Destination identity and final state start with the destination service. This is a source-location order, not evidence authority: accept only a record whose identity and content match the request, and stop searching that fact after the first authoritative match.

Once a source-family query returns candidates whose subject, snippet, identity, or metadata matches the concrete Task entity, an original material constraint, an applicable shared policy, or an already discovered dependency, fetch only those matching candidates. Do not enumerate or fetch generic noise records to hunt for a better answer. Make each source query answer one material evidence obligation; do not require a source entity, a destination identity, and an abstract document label to coexist in one record unless the known source contract says they should. An empty over-constrained query, whether it combines conditions or uses a full title or phrase, proves only that exact query and must follow the ordered same-endpoint anchor ladder above while the obligation remains unresolved. Once a discovered list/get endpoint has returned the relevant records, do not search the endpoint directory again for that source family. For an unnamed advisory constraint that has no independent mutation field, record the exact minimal-anchor and later eligible-anchor reads, their typed outcome or candidate count, and the concise applicability result that completed the relevant endpoint before treating its attempted scope as bounded. An abstract constraint-or-policy query may supplement that evidence but cannot replace a missing minimal-anchor read or make a newly admitted anchor disappear. After every information-shape-supported route is unavailable or has completed that ladder without an applicable match, record the constraint as unverifiable and stop probing unrelated products or broad record inventories. This bounded attempt does not prove that the source is absent or waive a material fact; do not claim that the unknown constraint is satisfied.

Judge a record by its applicable content, identity, and recency rather than whether its title repeats an abstract request word such as “guidelines,” “policy,” or “instructions.” An abstract user reference to current guidelines, policy, requirements, or instructions is only a lookup trigger; it is not a fact, source identity, or evidence that a comprehensive named policy or broader unseen rule exists. A current authoritative operational record that gives concrete do/don't rules for the exact action is applicable guidance. Immediately map the original obligation to that record, the concrete rule, every exact value it controls, and the evidence needed to verify it. That mapping closes the coverage actually stated; do not create a residual broader/remaining/complete-guidelines item or open a separate guideline-title search unless the original request names another source/document or observed authority identifies another dependency, uncovered scope, conflict, or precedence question. A later empty or noisy title search cannot erase positive evidence already read. For final-state rules, compare the rule with the final destination; process, approval, and historical rules require corresponding execution evidence. Do not require a separately titled policy document or a destination field that echoes the source policy, and do not treat one record as covering rules it never states. When the original request authorizes reasonable assumptions, a bounded absence of all applicable guidance may be reported as a limitation while the supported business action proceeds; never invent a missing rule or claim evidence that was not observed.

Each shell invocation creates a model round trip. Use the structured `batch` command for independent discovery and reads; do not concatenate multiple client commands with shell newlines. Discover the mutation contract and any same-record final readback contract together before changing state. Compare every returned mutation candidate before writing. Require its published description, authenticated context, exact path/query/body fields, and response/readback evidence to give one mutually consistent actor and destination-owner binding. An authenticated-user action may act for another owner only when the contract explicitly defines that authority and binding. A response containing only an ID or acknowledgement remains valid when authenticated context or request location binds the owner and the contract defines corresponding record evidence. When no candidate proves the binding, make one exact endpoint query from the service, destination resource, mutation action, and the owner identity-field noun learned from the destination read contract. Do not discover endpoint semantics by mutation. If a failed mutation introduces an undocumented actor/owner field or contradicts the published owner semantics, do not retry it with a guessed or error-supplied identity field; use that exact read-only contract query. Perform the smallest mutation set after the authoritative records and owner binding are complete, then call that exact readback with the returned record identity and batch only the necessary preservation reads. After a mutation, prefer the pre-discovered contract and never repeat broad discovery. Search once more only when the mutation response identifies a new read mechanism or the exact same-record read contract was genuinely absent; make that one query specific to the returned identity and missing read operation. If it exposes no correct same-record read, preserve the complete mutation receipt and continue verification from its returned record plus independent source reads instead of inventing another route or collection query. If a successful mutation returns or reads back the wrong owner, do not create again. Make at most one bounded read-only search for a correction or rollback contract tied to that existing record; execute it only when authority and the contract permit it, otherwise preserve the discrepancy and fail that outcome.

For independent verification, derive expectations from the original request and the same authoritative records, then compare those exact fields with the final destination or the Host-recorded full mutation receipt. Independently judging raw receipt fields is verification of operation evidence, not trust in the executor's conclusion. Use only query parameters declared by the discovered endpoint contract. When an exact identity filter is sufficient, start with that filter plus only contract-required observation or projection controls. Add optional search or filtering terms only when the exact read is non-unique and needs narrowing; honor contract-declared mode, field projection, sorting, and pagination semantics rather than inferring a parameter's meaning from whether it is optional. If a combined filtering read is empty and the obligation remains unresolved, remove optional filtering terms and make one minimal exact-filter read before recording a conflict. Never call the combined shape the uniquely required readback merely because it resembles an upstream service convention. Preserve the exact method, URL, and parameter shape of a read that has returned the relevant destination record. A correct authoritative read of the same record, or definite later mutation, operation-outcome, or rollback evidence, may contradict or supersede receipt fields. An empty result from a different collection query or documented non-reflecting projection cannot do so by itself. Verify the changed record and any material preservation constraint. Do not rediscover the whole API catalog, inspect unrelated services, or replay the mutation.

Every mutation attempt remains acceptance evidence. Preserve and hand off each exact receipt, including rejected attempts, intended commits, unintended commits, corrections, rollbacks, and unresolved side effects; a later correct mutation never erases an earlier committed extra effect. A successful mutation response that returns the complete created or updated record is authoritative evidence of that operation's returned result at response time. It proves committed state at that time only when the discovered API contract defines the successful response as a synchronous commit; queued, preview, provisional, or asynchronous responses retain their declared status. Some simulated read endpoints expose seeded or query projections that do not reflect every recorded action. Keep the exact action receipt, the first positive same-record readback contract, and any genuine conflicting readback visible. The Skill does not declare the business goal satisfied: an independent verifier must map the original request and relevant source rules to every raw receipt and any correct same-record read. Never repeat a successful irreversible create. Correct an existing result only through a discovered, authorized correction or compensating operation that the interface defines for that state; never replay the original create as a repair. If no such operation exists, report the resulting discrepancy. An unknown outcome is not permission to repeat an irreversible action.

This Skill specifies the environment, tool transport, and efficient evidence loop. It does not prescribe case-specific answers, a planning graph, report artifacts, or a success verdict. Independent verification remains the selected Squad's responsibility.

The client intentionally exposes no world dump, assertions, expected answer, or scoring endpoint. Do not inspect its config or implementation as a substitute for using the official tools.
