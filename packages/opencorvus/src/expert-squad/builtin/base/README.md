# Base

Base is the built-in default Expert Squad and the convenient compact alternative to Advanced. It owns one complete ordinary repository or external-state Task through one bounded plan, capability-matched execution, optional independent research, and verification of the settled result. The Task may contain many product, data, report, audit, and validation deliverables; these are worker partitions, not Mission phase boundaries or a hidden serial state machine.

## Fact and Turn Contract

Every projected agent extends the platform Agent-fact and Turn protocol. Domain tools and message-owned artifacts record durable evidence without becoming submit/finalizer calls; a normal stream end is only a physical Turn observation; and the visible final assistant message is natural narration of work, limitations, and blockers rather than durable evidence transport. File changes and command results remain Host observations rather than Agent self-reports.

Execution attempts and dispatch lineage are immutable physical evidence identities. Exact Delivery Slice revision IDs are optional work and evidence subjects, never lifecycle or scheduling owners. The Orchestrator judges visible final messages, domain artifacts, tool traces, and Host observations and owns Task lifecycle decisions. Every completion appends one typed `task_completion_decision` artifact that names the exact Orchestrator message/tool part, typed EvidenceLocators, every intentionally delivered Artifact locator, every accepted current Delivery Slice revision ID, and the exact selected workflow ID (`null` only for a direct Task). The selected workflow is inseparably bound to the active package revision: scope, project identity, namespace, manifest ID, version, and package digest. Empty deliverable or accepted-revision lists are truthful only when that Task produced no Artifact deliverables or has no Delivery Slices. Reopen preserves earlier decisions, and the current Task projection joins only the artifact whose timestamp equals the terminal Task timestamp. The artifact does not copy the narrative summary or materialize an acceptance aggregate. This package does not infer an active/current Run or persist workflow step state.

## Contract

Base has exactly four projected Agent identities:

- `base-planner` uses a physically read-only Tool projection to publish one complete `base/implementation-plan`. The plan inventories every Task element, classifies observed obligations, discovery work, reversible assumptions, and proven blockers, decomposes them into stable or discovery-bound `AC-N` criteria, and assigns work only to owners whose projected capabilities can finish it.
- `base-researcher` executes an optional read-oriented evidence partition and publishes `base/research-report`. Its `explore` runtime has repository/web reading but no shell, project Skill, local client, or command execution, so no selected workflow allocates those operations to it.
- `base-developer` owns executable discovery and the plan's product, external-state, and generated-output mutation partition, performs implementation-owned checks and real-page inspection when applicable, and publishes `base/development-report`.
- `base-tester` owns independent readback and the plan's test/checker partition, may edit only its assigned test and checker paths, runs focused checks against the settled state, and publishes `base/test-report`. Its acceptance scope is the original request, canonical plan, and current authoritative sources, never another worker's account of what it acted on.

Base declares two binding workflows. `planner-execution-verification` runs Planner -> Developer -> Tester when source discovery or verification needs a project Skill, command, local client, package Tool, Model Context Protocol capability, or mutating browser. `planner-parallel-delivery` additionally runs `base-researcher` beside `base-developer` only when its complete independent repository/web partition fits the Researcher's actual Tool projection. Both workflows keep the Tester behind the Developer.

That last edge is a declared ordering, not an implementation-report handoff. Verification is the one obligation that is meaningless against a moving target: a Tester that runs beside the mutation owner can only observe a half-finished world, and the report it publishes then reads afterwards as a standing claim about a state that no longer exists. The Tester therefore starts once the implementation node has settled. Its dispatch identifies the canonical plan and requires complete read/select coverage of every `AC-N`, every discovery-bound value, and every material field in current authoritative sources. When a dynamic policy/process/template/backlog/history decides actions for a set of business entities, before reading implementation claims it independently closes the bounded candidate ledger, rebuilds the source-derived entity/rule/effect action matrix, and compares every expected row plus every observed mutation with final state. Ordinary repository/software delivery retains criterion-level verification without manufactured entity rows. Its scope never comes from the Developer's account; it does not consume `base/development-report` as an input to its own scope.

Eligible Research stays parallel because reading does not race the implementation. A local or external client read is still executable work and belongs to Developer or Tester, not Researcher. Workers otherwise do not consume one another's reports and must not invent further serial handoffs.

Settling is not the same as final. When a final check must observe state that changed after the Tester's own occurrence — a same-Task repair, a late generated output, or an external system reached through tools — the Orchestrator continues that exact Tester lineage after the Host has observed the current state rather than creating another logical node or a hidden workflow gate. Every worker report is an observation of the moment it was published, so a report that predates the mutation owner's latest settled occurrence is stale for the mutated surface and cannot carry a terminal decision.

The Orchestrator visibly binds exactly one graph before domain dispatch, and every node in that selected workflow is mandatory. The workflow does not create or consume RequirementSet, ContractGraph, Goal, Delivery Slice, Requirements, Architect, or workload-analysis planning facts. The Task remains the sole lifecycle owner, and the Orchestrator judges completion from visible messages, immutable Artifacts, dispatch lineage, the final diff or external state, command results, the test verdict, and rendered evidence when applicable.

Base's Artifact dependencies are same-Task handoffs. A large request is not decomposed into separate Mission Tasks for research, implementation, datasets, reports, audits, tests, correction, or final packaging. Mission creates a different Task only when a different fixed Expert Squad or a genuinely external terminal-evidence boundary owns another complete closure.

Base is self-contained. It does not inherit Advanced Agents, prompts, skills, tools, or workflows. Advanced remains independently selectable for its full requirements, architecture, specialist investigation, interface, and specialist-review team. Selecting another Expert Squad replaces Base's complete projection through the existing `prompt_profile.active` and `PromptProfileResolver` path.

## Artifact protocol

The model-facing file protocol uses `artifact_snapshot` to publish current-Task project files and return one exact content-addressed `resource_set` locator. `artifact_publish` accepts the complete evidence value only as strict JSON text in `payload_json`; object keys must be unique, and `resource_set` is required (`null` when there are no files, otherwise the exact locator returned by `artifact_snapshot`). The Host verifies and expands the immutable manifest inside its trusted boundary, then publishes the structured value through the same canonical service used by typed and package tools.

Task schedulers and projected workers inherit `artifact_search`, `artifact_read`, and `artifact_select` as platform tools. Schedulers additionally inherit read-only `artifact_snapshot` to freeze exact Task input files before dispatch; projected workers inherit `artifact_snapshot` and `artifact_publish` for their evidence resources and outputs. Schedulers never receive generic `artifact_publish` or typed domain publishers. A delegated worker without a typed domain-output producer uses `artifact_publish` for canonical JSON `expert_output` type `<active-squad-id>/...`; it supplies explicit `source_selection_refs` returned by prior `artifact_select` calls in the same physical Turn, while the Host resolves the complete canonical locators and derives Task, Session, Agent, active-Squad, projection, and complete-read observations. Typed domain-output tools remain their domain's sole publishers and are never duplicated. Every consumer passes catalog `artifact_locator_ref` values to `artifact_read`, completes every byte window, then passes the returned `artifact_read_ref` to `artifact_select` for every Artifact that semantically supports its typed output; complete but unselected reads remain observations and zero selections are valid. Models never reconstruct immutable snapshot IDs, paths, byte counts or digests. Durable evidence does not travel through Agent messages or adapter results. A user-pinned locator cannot be replaced by search. For Cross-Task evidence, Mission references a completed source with `{authority: "completion_decision", source_task_id}` in `artifact_sources`; the Host imports that decision's complete deliverable set without copied locator IDs. Failed/cancelled recovery uses `{authority: "terminal_lifecycle", source_task_id, locator}`. The receiving catalog exposes a target-owned imported Engine Artifact that preserves the source type, schema, payload, copied resources, and original consumption provenance in immutable `import_lineage`; copied request prose and foreign reads are not evidence. Empty search/default fields are valid; missing, foreign, corrupt, stale, unreadable, or path-invalid selected evidence is an explicit error.

Each identity publishes exactly one canonical package Artifact for its owned partition: `base/implementation-plan`, `base/research-report`, `base/development-report`, or `base/test-report`. Every worker enumerates the current Task catalog, completely reads and selects the plan, then acts only inside its allocation. Dispatch messages and final narration never copy Artifact payloads or create parallel handoff sources.
