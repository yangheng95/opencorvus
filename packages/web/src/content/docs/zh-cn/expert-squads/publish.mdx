专家团不是一组提示词。它要说明适用场景、角色责任、协作顺序、所需能力和交付证据，并把这些内容冻结在
同一个可验证版本里。

目标是产出一份别人能够理解、检查和复现的能力包。

## 从任务边界到精确能力包

1. **定义选择边界。**先写清团队适合什么结果、需要哪些输入，以及**什么情况下不该选它**。
   只重复宣传语的 selector 不构成边界。
2. **组织角色与工作流。**为每位专家分配可见责任，声明依赖关系、交付物，以及复核独立于生产的位置。
3. **加入 Skills 与工具。**只绑定团队真正需要的能力。所有引用都必须留在自包含包的验证闭包内——
   伸到闭包外的引用会在验证阶段失败，而不是留到运行时才解析。
4. **严格验证。**用 Registry 和 Manager 检查身份、schema、路径、引用闭包、工作流拓扑和能力投影。
5. **冻结精确版本。**导出规范 ZIP，记录 namespace / id / version / digest，
   然后在真实客户端里检查选择与安装结果。

## 一份可交付能力包要回答什么

| 问题 | 在哪里回答 |
| ---- | ---------- |
| 什么时候选它？ | selector 说明任务边界，包括它不覆盖的情况。 |
| 谁负责什么？ | Agent 角色、输入、输出与复核责任都可检查。 |
| 如何证明完成？ | 工作流与 Skills 定义证据、交付物和验收方法。 |
| 拿到的是哪一版？ | 身份、版本和 digest 共同绑定内容。 |

## 发布边界

**构建能力已开放，自助上架尚未开放。**

公共站点展示仓库中已选定的专家团，并分发由 OpenCorvus 发布密钥签名的完整资源包；它还不是第三方自助
Registry：namespace 注册、发布者身份验证、第三方审核与撤回服务都未开放。作者当前通过源码仓库构建、
验证并提交能力包。

## 下载、安装、激活是三件事

网站只负责说明与分发。客户端下载后重新校验，并要求明确安装范围。安装不等于选择团队——只有用户明确
激活后，运行时行为才会变化。
